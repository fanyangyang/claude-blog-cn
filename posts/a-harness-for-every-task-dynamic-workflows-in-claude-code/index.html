为每个任务配备专属 harness：Claude Code 中的动态工作流

阅读英文原文 →

上周，我们在 Claude Code 中发布了动态工作流。Claude 现在可以针对手头的任务，即时编写出专属的 harness。

Claude Code 默认的 harness 是为编码而生的，但它对许多其他类型的任务同样适用，因为事实证明，很多任务都与编码任务相似。不过，对于某些特定类别的任务，我们不得不在 Claude Code 之上构建定制的 harness 才能达到最佳性能，例如 Research、安全分析、agent teams 或 Code Review。

工作流让你能够动态创建构建在 Claude Code 之上的 harness，使 Claude 以更原生的方式解决上述所有问题。你还可以与他人分享和复用这些工作流。

在本文中，我将分享我最初使用工作流的经验和心得，帮助你充分利用这一能力。请记住，最佳实践仍在形成之中：动态工作流通常会消耗更多 token，最适合复杂、高价值的任务。

示例提示词

在深入技术细节之前，我想先展示几个示例提示词，让你感受一下工作流的想象空间：

"这个测试大约每 50 次运行会失败 1 次。搭建一个工作流来复现它。围绕竞态条件提出多个相互竞争的假设，直到其中一个假设经受住所有证据的考验才许停下。"

"用一个工作流检查我最近的 50 个会话，从中挖掘我反复犯的纠正性错误，并把反复出现的问题提炼成 CLAUDE.md 规则"

“用一个工作流梳理 Slack 中 #incidents 频道过去六个月的记录，找出那些反复出现但一直没人提工单的根本原因。”

"把我的商业计划书交给一个工作流，让不同的 agent 分别从投资人、客户和竞争对手的视角把它批个体无完肤。"

"这里有一个装着 80 份简历的文件夹，用一个工作流为后端岗位对它们排序，并复核前十名。用 AskUserQuestion 工具采访我，制定评分标准。"

"我需要给这个 CLI 工具起个名字。用一个工作流头脑风暴出一批候选，然后举办一场锦标赛选出前 3 名。"

"用一个工作流把我们的 User 模型在所有地方重命名为 Account。"

“用一个工作流通读我的博客草稿，逐条对照代码库验证其中的每个技术论断，我不想发布任何有错的内容。”

动态工作流还包含标准 JavaScript 函数，如 JSON、Math 和 Array，帮助处理数据。

尤其有用的一点是，动态工作流可以决定某个 agent 使用哪些模型，以及 subagent 是否在独立的 worktree 中运行，从而让 Claude 自行选择所需的智能水平和隔离程度。

如果工作流被中断（例如因用户操作或终端退出），恢复会话后工作流可以从中断处继续执行。

为什么需要动态工作流

当你让默认的 Claude Code harness 执行任务时，它需要在同一个上下文窗口中同时完成规划和执行。对于许多编码任务来说这非常高效，但在长时间运行、大规模并行、高度结构化和/或对抗性任务上可能会出问题。

这是因为 Claude 在单个上下文窗口中处理复杂任务的时间越长，就越容易受到几种特定失败模式的影响：

  • Agent 懒惰（agentic laziness）指 Claude 在完成一项特别复杂的多步骤任务之前就停下，并在部分进展后宣告任务完成，例如在安全审查中只处理了 50 项中的 35 项。
  • 自我偏好偏差（self-preferential bias）指 Claude 倾向于偏爱自己的结果或发现，尤其是当被要求按照评分标准验证或评判它们时。
  • 目标漂移（goal drift）指经过多轮对话后，尤其是压缩（compaction）之后，对最初目标的忠实度逐渐丧失。每一步摘要都是有损的，诸如边缘情况要求或"不要做 X"之类的约束细节可能会丢失。

创建工作流有助于对抗这些问题：它通过编排多个拥有独立上下文窗口和聚焦、隔离目标的 Claude subagent 来完成。

动态工作流 vs 静态工作流

你可能此前用 Claude Agent SDK 或 claude -p 创建过静态工作流，把多个 Claude Code 实例协调在一起。

但由于静态工作流必须兼容所有边缘情况，它们通常更通用。而借助 Claude Opus 4.8 和动态工作流，Claude 已经足够智能，可以为你的具体用例编写量身定制的 harness。

使用动态工作流的实用模式

你可以直接让 Claude 创建一个动态工作流来开始使用，也可以使用触发词 “ultracode” 来确保 Claude Code 创建工作流。

但为动态工作流建立一套心智模型，会帮助你理解何时使用它们，以及如何通过提示词引导 Claude。

以下是 Claude 在构建工作流时可能会使用并组合的几种常见模式：

分类后执行（classify-and-act）

用一个分类器 agent 判断任务类型，再根据任务路由到不同的 agent 或行为。也可以在最后用分类器来决定输出。

扇出后综合（fan-out-and-synthesize）

把任务拆分成许多更小的步骤，每一步各跑一个 agent，然后综合这些结果。当存在大量小步骤，或者每一步都能从独立干净的上下文窗口中获益、互不干扰交叉污染时，这种模式特别有用。综合步骤是一道屏障——它会等所有扇出的 agent 完成，再把它们的结构化输出合并为一个结果。

对抗性验证（adversarial verification）

对每个生成的 agent，再单独生成一个 agent，按照评分标准或判定条件对其输出进行对抗性验证。

生成后筛选（generate-and-filter）

围绕一个主题生成一批想法，然后按评分标准或通过验证进行筛选，对重复项去重，只返回质量最高、经过检验的想法。

锦标赛（tournament）

不是分摊工作，而是让 agent 相互竞争。生成 N 个 agent，各自用不同方法尝试同一个任务。然后由提示词或模型借助评判 agent 对结果进行两两比较，直到决出胜者。

循环直到完成（loop until done）

对于工作量未知的任务，循环生成 agent 直到满足停止条件（没有新发现，或日志中不再出现错误），而不是固定跑多少轮。

用例

发挥创造力，想想何时以及如何让 Claude Code 创建动态工作流。我发现工作流在非技术性工作中有时反而更有用。

迁移与重构

Bun 曾借助工作流从 Zig 重写为 Rust。你可以在 Jarred 的 X 帖子中了解更多细节，也可以看看我们如何在百万行级的代码库上运行 AI 代码迁移。

关键在于把任务拆解为一系列需要处理的步骤，例如调用点、失败的测试、模块等。在 worktree 中为每处修复派生一个 subagent 来完成修改，再由另一个 agent 进行对抗性审查，然后合并。可以考虑告诉 agent 不要使用资源消耗大的命令，这样你就能最大程度并行，而不会耗尽机器资源。

深度研究

我们在 Claude Code 中发布了一个使用动态工作流的深度研究技能（/deep-research）。具体来说，它会扇出多个网络搜索、抓取来源、对论断进行对抗性验证，并综合出一份带引用的报告。

但这类研究并不局限于网络搜索。比如，可以让 Claude 从 Slack 中的上下文汇总一份状态报告，或者通过深入探索代码库研究某个功能的工作原理。

深度验证

反过来，如果你手里有一份报告，想逐条核查并溯源它引用的每一个事实性论断，可以生成这样一个工作流：先由一个 agent 找出所有事实性论断，然后为每一条派生一个 subagent 详细核查。还可以再让一个验证 agent 检查提供来源的 subagent，确保其来源质量足够高。

排序

你可能有一列想按某种质性指标排序的项目，而你相信 Claude Code 擅长评估这种指标，例如：按 Bug 严重程度对支持工单排序。但如果试图在一条提示词里对 1000 多行排序，质量会下降，上下文也装不下。正确的做法是跑一场锦标赛——一条由两两比较 agent 组成的流水线（比较式判断比绝对打分更可靠），或者并行分桶排序再合并。每次比较都是一个独立的 agent，由确定性的循环持有对阵表，上下文中只保留当前进行中的比较。

记忆与规则遵循

如果你发现 Claude 总是遗漏或搞砸某些规则，即使写进了 CLAUDE.mds 也没用，那就创建一个工作流，列出必须由验证 agent 逐条检查的规则——每条规则一个验证者。再创建一个"怀疑者"人设的 subagent 来审查这些规则的执行情况，确保它们落到实处，这有助于避免过多误报。

反过来同样可行：挖掘你最近的会话和代码审查评论，找出你反复纠正的错误，用并行 agent 聚类，对每个候选规则做对抗性验证（这条规则本可以避免哪个真实错误吗？），然后把幸存者蒸馏回 CLAUDE.md。

根因调查

调试的最好方式是提出多个独立假设并逐一检验，但如果只用一个上下文窗口，Claude 可能陷入自我偏好偏差。

工作流可以从结构上杜绝这一点：生成多个 agent，从互不重叠的证据出发提出假设。例如，日志、文件、数据各由独立的 agent 负责。每个假设随后要面对一组验证者和反驳者组成的评审团。

这不仅限于代码。工作流还可用于销售（为什么三月份销售额下滑了？）、数据工程（为什么这条流水线失败了？），或任何复盘类工作。

大规模分诊

每个团队都有支持队列、Bug 报告或其他靠人力无法完全消化完的积压工作。

分诊工作流会对每个条目分类、与已跟踪的内容去重，然后采取行动：可能是尝试修复，也可能是升级转给人类处理。

分诊工作流的一个实用模式是隔离（quarantine）：禁止读取不可信公开内容的 agent 执行高权限操作，这些操作交给负责根据信息采取行动的 agent 来完成。

把分诊工作流与 /loop 搭配，可以让 Claude 持续自动执行。

探索与品味

在探索不同解决方案时，工作流会很有用，尤其是当评判标准基于品味时，比如设计或命名，此时制定一套评分标准会大有裨益。

可以试着让 Claude 探索一批方案，并给审查 agent 一份"好方案长什么样"的评分标准。当审查 agent 认为已满足标准时，任务才算完成。方案也可以依据评分标准，通过锦标赛来排序或选出。

评估（Evals）

你可以运行轻量级评估：在 worktree 中派生独立的 agent 执行特定任务，再派生比较 agent，按评分标准对具体输出进行比较和打分。例如，按照特定标准评估并迭代优化你创建的 skill。

模型与智能路由

创建一个针对你的任务调优的分类器 agent，由它决定使用哪个模型。当任务会涉及大量工具调用时这很有帮助——在执行前先做点研究，就能为任务选出最合适的模型。

例如，"解释 auth 模块的工作原理"这个任务用哪个模型最好，取决于 auth 模块有多少个文件以及代码库的形态。分类器 agent 可以先完成这项研究，再根据任务的预期复杂度路由到 Sonnet 或 Opus。

什么时候不该用动态工作流

工作流是新事物。虽然它在很多用例中能创造超乎寻常的成果，但并非每个任务都需要它，而且可能消耗多得多的 token。

最好是用工作流创造性地拓展 Claude Code 的能力边界，做以前做不到的事。对于常规编码任务，不妨问问自己：它真的需要更多算力吗？比如，大多数传统编码任务并不需要 5 个评审组成评审团。

同样的判断也适用于上一层——架构层面：多 agent vs 单 agent 的决策遵循类似的逻辑——并行化和专业化带来的收益，必须盖过它们的协调成本。

构建动态工作流的技巧

提示词

为动态工作流编写详细的提示词，并运用上文描述的那些具体技巧，效果最好。

工作流并不只用于大型任务。你可以提示模型使用"快速工作流"。例如，可以对某个假设做一次快速的对抗性审查。

与 /goal 和 /loop 组合

使用可重复运行的工作流（例如分诊、研究或验证）时，搭配 /loop 定期执行，并用 /goal 设定硬性的完成要求。

token 用量预算

你可以为动态工作流设置显式的 token 用量预算，限制任务消耗多少 token。可以在提示词中给出预算，比如"使用 10k token"，这会设置上限。

保存和分享动态工作流

在工作流菜单中按 "s" 即可保存工作流。你可以把它们提交到 ~/.claude/workflows，或通过 skill 分发。

要通过 skill 分享，可以把你的 JavaScript 工作流文件放进 skill 文件夹，并在 SKILL.MD 中引用它们。为了更灵活，你可以提示 Claude 把 skill 中的工作流视为模板，而不是必须逐字执行的脚本。
