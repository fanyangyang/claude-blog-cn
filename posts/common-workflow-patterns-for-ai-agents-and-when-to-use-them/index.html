AI agent 的常见工作流模式及其适用场景

Practical guidance on how to structure agent tasks using three common workflow patterns, with tradeoffs and benefits for each.

AI agent 会自主做出决策，而工作流（workflow）则是一种为这种自主性引入结构的手段。它建立了执行模式，将 agent 的能力引导到那些需要协调步骤、可预测结果和精确编排时机的复杂问题上。

当你需要多个 agent 协同工作时，真正的问题在于：哪种模式适合你的问题。

我们与数十个构建 AI agent 的团队合作过。在生产环境中，三种模式覆盖了绝大多数使用场景：串行（sequential）、并行（parallel）和评估器-优化器（evaluator-optimizer）。

每种模式解决不同的问题，选错了会在延迟、token 或可靠性上付出代价。本文将逐一拆解这三种模式，并给出各自的适用场景以及组合使用的方法。

工作流与 agent 如何协同

如果你带过团队，你就已经理解工作流了。

想想制造业的流水线：每个工位都有一名技术娴熟的工人在为自己的具体任务做决策，但整体流程是提前设计好的——即使各个步骤涉及路由或重试这类动态决策。

Agent 工作流的运作方式完全相同。

理解工作流与自主 agent 的区别

工作流并不会取代 agent 的自主性，它塑造的是 agent 在哪里以及如何运用这种自主性。

完全自主的 agent 决定一切：用哪些工具、以什么顺序执行任务、何时停止。

工作流提供结构：它确立整体流程、定义检查点，并为 agent 在每个步骤的运作方式设定边界，同时仍允许在这些边界之内进行动态行为。

工作流中的每个步骤仍然可以发挥 agent 的推理和工具使用能力，但整体编排遵循一条既定路径。工作流模式让你在每个步骤内拥有 agent 的智能，而整个任务则沿着一个可预测的流程推进。

Agent 工作流模式

在生产环境中，我们最常见到的是三种工作流模式。把它们当作积木而非僵化的模板——随着需求演进，你常常会将它们组合或嵌套使用：

  1. 串行工作流——用于按固定顺序执行任务
  2. 并行工作流——用于让多个 agent 同时运行相互独立的任务
  3. 评估器-优化器工作流——用于需要迭代打磨的产出

每种工作流类型都解决特定的问题，并在复杂度、成本和性能上各有明确的取舍。

‍
从能解决问题的最简单模式开始。默认选串行。当延迟成为瓶颈且任务相互独立时再转向并行；只有当你能度量质量提升时，才加入评估器-优化器循环。

串行工作流

串行工作流按预定顺序执行任务。

每个阶段的 agent 处理输入、做出决策、按需调用工具，然后把结果传给下一个阶段。其结果是一条清晰的操作链，输出在系统中线性流动。

适用场景：当任务自然地分解为有清晰依赖的不同阶段时，串行工作流表现出色。你是在用一点延迟换取更高的准确率——让每个 agent 专注于一个特定子任务，而不是试图一次搞定所有事。

以下情况请使用串行工作流：

  • 多阶段流程，每一步都依赖上一步的输出
  • 数据转换管道，每个阶段都增加特定价值
  • 由于内在依赖而无法并行的任务
  • "起草-审查-润色"这类迭代改进循环

避免场景：当单个 agent 就能有效处理整个任务时，或者当 agent 之间需要协作而非按顺序交接工作时，请跳过串行工作流。如果任务并不天然符合这种结构，你却硬把它拆成串行步骤，那就是在增加不必要的复杂度。

示例：当每一步都涉及真正不同的工作时，串行工作流效果很好：

  • 先生成营销文案，再翻译成多种语言——或者从文档中提取数据、对照 schema 校验，然后载入数据库
  • 内容审核管道也很适合串行：提取内容、分类、应用审核规则，然后按相应方式路由

小技巧：先尝试把整个管道交给单个 agent，各个步骤只是提示词的一部分。如果这样就足够好，你便在没有额外复杂度的情况下解决了问题。只有当单个 agent 无法可靠地处理时，才拆分成多步骤工作流。

并行工作流

并行工作流将相互独立的任务分发给多个 agent 同时执行。与其等一个 agent 做完再启动下一个，不如同时运行多个 agent，然后合并它们的结果。

当任务彼此不依赖时，这种模式可以带来速度提升。

这个思路类似于分布式系统中的 fan-out/fan-in 模式：你把相同或相关的工作发给多个 agent，各自独立处理，然后对它们的输出进行聚合或综合。

Agent 之间并不互相交接工作——它们独立运作，各自产出为整体任务做贡献的结果。

适用场景：当你能把工作拆分成可同时处理的独立子任务，或者需要针对同一问题的多个视角时，并行化是合理的。它还能实现关注点分离：不同的工程师可以各自负责并优化单个 agent，互不干扰。对于复杂任务，把每个考量点交给单独的 AI 调用，往往好过在一次调用中试图兼顾一切。

以下情况可以考虑并行工作流：

  • 分片式方案：不同的 agent 负责不同侧面（比如一个处理查询，另一个筛查安全问题）
  • 评估场景：每个 agent 评估不同的质量维度
  • 投票模式：多个 agent 分析同一内容，再聚合它们的评估结果

避免场景：当 agent 需要累积的上下文，或必须在前人工作之上继续构建时，不要使用并行工作流。当 API 配额等资源限制让并发处理不划算时，或者当你没有清晰策略来处理不同 agent 之间的矛盾结果时，跳过这种模式。如果结果聚合变得过于复杂或损害输出质量，并行化就不值得。

示例：并行工作流非常适合：

  • 自动化评估（每个 agent 检查不同的质量指标）或代码审查（多个 agent 分别检查不同类别的漏洞）
  • 文档分析是另一个典型场景：并行执行关键主题提取、情感分析和事实核查，然后综合各路洞见

小技巧：在实现并行 agent 之前，先设计好聚合策略。是采用多数投票？平均置信度分数？还是听从最专业的那个 agent？对结果综合方式有清晰的计划，才能避免拿到一堆相互冲突的输出却无从解决。

评估器-优化器工作流

评估器-优化器工作流让两个 agent 结成迭代循环：一个生成内容，另一个对照特定标准进行评估，生成者再根据反馈加以改进。如此往复，直到输出达到你的质量阈值或触及最大迭代次数。

关键洞察在于：生成与评估是两种不同的认知任务。把它们分开能让每个 agent 各自专精——生成者专注于产出内容，评估者专注于执行一致的质量标准。

适用场景：当你拥有清晰、可度量、AI 评估者能够一致执行的质量标准，并且首次尝试与最终质量之间的差距足够大、足以证明额外的 token 和延迟物有所值时，这种模式很有效。

以下情况可以考虑评估器-优化器工作流：

  • 有特定要求的代码生成（安全标准、性能基准、风格规范）
  • 语气和精确性都很重要的专业沟通
  • 任何初稿质量始终达不到要求的场景

避免场景：当首次尝试的质量已经满足需求时，请跳过评估器-优化器工作流——那是在为不必要的迭代烧 token。不要把这种模式用于需要即时响应的实时应用、基础分类这类简单的例行任务，或者评估标准过于主观、AI 评估者无法一致执行的场景。如果存在确定性的工具（比如检查代码风格的 linter），请直接使用它们。当资源限制重于质量收益时，也应避免这种模式。

示例：评估器-优化器工作流非常适合：

  • 生成 API 文档（生成器撰写文档，评估者对照代码库检查完整性、清晰度和准确性）
  • 撰写客户沟通内容（生成器起草邮件，评估者评估语气和合规性）
  • 编写 SQL 查询（生成器写查询，评估者检查效率和安全问题）

小技巧：在开始迭代之前设定清晰的停止条件。定义最大迭代次数和具体的质量阈值。没有这些护栏，你可能陷入昂贵的循环：评估者不断挑出小毛病，生成者不停修修补补，而质量早在你停止之前就已触顶。要知道什么时候"足够好就是足够好"。

选择合适的工作流模式

合适的工作流模式取决于你的任务结构、质量要求和资源限制。

在选择模式之前，先把任务作为单次 agent 调用试一遍。如果达到了你的质量标准，就到此为止。如果没有，找出它在哪里不足——这会告诉你该用哪种模式。

以下几个问题可以帮你决策：

  • 单个 agent 能否有效处理这个任务？如果能，根本不需要工作流。
  • 任务是否有清晰的串行依赖？使用串行工作流。
  • 子任务能否独立且同时处理，更快的完成速度是否有价值？考虑并行工作流。
  • 质量是否会通过迭代打磨获得显著提升？考虑评估器-优化器模式。

选定模式后，还要考虑：

  • 失败处理：为每个步骤定义回退行为和重试逻辑。
  • 延迟与成本约束：它们决定了你能运行多少个 agent、负担得起多少轮迭代。
  • 度量改进：先用单个 agent 建立基线，这样你才能判断工作流是否真的有用。

模式组合：这些模式并不互斥，可以按复杂度需求嵌套使用。

  • 评估器-优化器工作流可以采用并行评估，让多个评估者同时评估不同的质量维度。
  • 串行工作流可以在某些阶段引入并行处理：在进入下一步之前，先并发执行多个相互独立的操作。

关键在于让模式的复杂度与实际需求相匹配。不要因为"能并行"就加并行——只在并发执行带来明确收益时才加。不要实现评估器-优化器循环，除非它能以你可度量的方式提升输出质量。

审慎地演进你的工作流

我们最好的建议是：从可行的最简单模式开始。如果串行工作流就能满足你的场景，就不要加并行化。如果首次尝试的质量已经够好，就跳过评估器-优化器循环。

这三种模式为需求变化提供了清晰的升级路径。串行工作流可以在瓶颈阶段引入并行处理。agentic 方案可以在质量标准收紧时加入评估环节；而且由于这些模式是模块化的，你不需要完全重写。
