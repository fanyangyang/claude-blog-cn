面向 Claude 5 世代模型的上下文工程新法则

阅读英文原文 →

我此前写过如何最好地为最新一代 Claude 5 模型编写提示词，以及如何与它们迭代协作，去发现你真正想构建的东西。

但当你向 Claude 发送一条消息时，提示词只是它所获得上下文的一小部分。你的上下文大部分来自系统提示词、Skills、CLAUDE.md 文件、记忆以及其他来源。我们将其称为上下文工程（context engineering），无论你是在使用 Claude Code 还是构建自己的智能体，它都会对生成结果产生巨大影响。

与提示词不同，上下文会在大量请求中被通用使用，因此无法做到那么具体。如何为 Claude 构建这些通用提示和指引，尤其是在你不知道用户的提示词可能是什么的时候？

随着 Claude 自身能力的演进，这件事出人意料地变得困难。最近，我们注意到在为最新一代 Claude 模型编写提示词的方式上出现了巨大转变。对于 Claude Opus 5 和 Claude Fable 5 等模型，我们删除了 Claude Code 系统提示词中超过 80% 的内容，而在编码评估中没有任何可衡量的性能损失。

以下是我们对这类新模型提示方式的经验总结，以及你如何利用这些经验来更新你的上下文工程。我们已将这些最佳实践内置到 `claude doctor;` 中；在 Claude Code 中使用 /doctor 命令，即可为你的 skills 和 CLAUDE.md 文件做合理的瘦身。

解除对 Claude 的束缚

总体而言，我们发现过去对 Claude Code 限制过度了——无论是通过系统提示词，还是通过 CLAUDE.md 文件和 skills。 

例如，当我们阅读自己内部使用 Claude Code 的会话记录时，会看到单个请求中出现多条相互冲突的指令，比如"酌情保留文档"或"绝对不要（DO NOT）添加注释"——系统提示词、skills 和用户请求彼此打架。 

通常，Claude 能够理解用户意图并得出正确答案，但 Claude 必须更仔细地权衡这些重叠且冲突的指令，才能决定怎么做。

这些约束在过去是避免最坏情况所必需的，但后来我们发现，可以删掉其中很多条，让模型转而依靠周围上下文和自身判断。

此外，Claude Code 现在拥有多得多的工具。过去 Claude 依赖 CLAUDE.md 作为记忆、信息和指引的来源。现在我们有了记忆、artifacts 和 skills，Claude 可以用它们创造出跨会话加载和共享上下文的新方式。
