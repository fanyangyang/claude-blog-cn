面向 Claude 5 世代模型的上下文工程新法则

We removed over 80% of Claude Code's system prompt for more advanced models. How to apply the lessons we learned to your own context engineering in Claude Code and with your own agents.

我此前写过如何最好地为最新一代 Claude 5 模型编写提示词，以及如何与它们迭代协作，去发现你真正想构建的东西。

但当你向 Claude 发送一条消息时，提示词只是它所获得上下文的一小部分。你的上下文大部分来自系统提示词、Skills、CLAUDE.md 文件、记忆以及其他来源。我们将其称为上下文工程（context engineering），无论你是在使用 Claude Code 还是构建自己的智能体，它都会对生成结果产生巨大影响。

与提示词不同，上下文会在大量请求中被通用使用，因此无法做到那么具体。如何为 Claude 构建这些通用提示和指引，尤其是在你不知道用户的提示词可能是什么的时候？

随着 Claude 自身能力的演进，这件事出人意料地变得困难。最近，我们注意到在为最新一代 Claude 模型编写提示词的方式上出现了巨大转变。对于 Claude Opus 5 和 Claude Fable 5 等模型，我们删除了 Claude Code 系统提示词中超过 80% 的内容，而在编码评估中没有任何可衡量的性能损失。

以下是我们对这类新模型提示方式的经验总结，以及你如何利用这些经验来更新你的上下文工程。我们已将这些最佳实践内置到 `claude doctor;` 中；在 Claude Code 中使用 /doctor 命令，即可为你的 skills 和 CLAUDE.md 文件做合理的瘦身。

解除对 Claude 的束缚

总体而言，我们发现过去对 Claude Code 限制过度了——无论是通过系统提示词，还是通过 CLAUDE.md 文件和 skills。 

例如，当我们阅读自己内部使用 Claude Code 的会话记录时，会看到单个请求中出现多条相互冲突的指令，比如"酌情保留文档"或"绝对不要（DO NOT）添加注释"——系统提示词、skills 和用户请求彼此打架。 

通常，Claude 能够理解用户意图并得出正确答案，但 Claude 必须更仔细地权衡这些重叠且冲突的指令，才能决定怎么做。

这些约束在过去是避免最坏情况所必需的，但后来我们发现，可以删掉其中很多条，让模型转而依靠周围上下文和自身判断。

此外，Claude Code 现在拥有多得多的工具。过去 Claude 依赖 CLAUDE.md 作为记忆、信息和指引的来源。现在我们有了记忆、artifacts 和 skills，Claude 可以用它们创造出跨会话加载和共享上下文的新方式。

过去与现在

不少以往的上下文工程最佳实践已经变成了迷思。其中包括：

过去：给 Claude 定规则

现在：让 Claude 自己判断

我们刚推出 Claude Code 时，必须确保 Claude 避开最坏情况，比如删除文件。这意味着我们会给出特别强硬的指引，而这些指引并不总是成立。例如，系统提示词里我们曾经这样写： 

写代码时，默认不要加注释。绝不要写多段 docstring 或多行注释块，最多一行短注释。除非用户要求，否则不要创建规划、决策或分析文档，从对话上下文出发工作，而不是中间文件。

但对一部分提示词来说，这条指引是错的。就文档而言，用户可能有自己的偏好，或者非常复杂的代码的某些部分确实需要多行注释块。

不过，对较老的模型来说，没有这些护栏，Claude 写出的注释在很多情况下会是错的，我们只能接受这种权衡。但这代新模型判断力更好，不必靠显式规则也能处理好这些决策。 

新的系统提示词里我们这样写：写出读起来像周围代码的代码：对齐它的注释密度、命名和惯用法。

过去：给 Claude 示例

现在：设计接口

工具使用的第一条规则曾经是给 Claude 示范怎么用。对最新的模型，我们发现给示例反而会把它们限制在特定的探索空间里。 

与其给示例，不如多想想工具、脚本和文件本身的设计，Claude 有哪些参数，怎样才能更有表达力？ 

例如，在 Todo 工具里，只把 status 列为 pending、in_progress 和 completed 这三个枚举值，就已经在提示 Claude 该怎么用。要求同一时间只保持一项 in_progress 的指令，则界定了我们期望的行为。

过去：全部放在前面

现在：使用渐进式披露

因为 Claude Code 最初聚焦于编码，系统提示词里包含了如何做代码审查和验证的详细信息。这些信息不总是需要，但一旦需要，就是关键信息。

此后，Claude Code 已经非常擅长使用渐进式披露，在正确的时机加载正确的上下文。例如，我们把验证和代码审查拆成独立的 skills，由 Claude Code 按需调用。

但渐进式披露不只适用于 skills，我们也用在工具上。我们的一部分工具是"延迟加载"的，意思是 agent 必须先用 ToolSearch 搜索完整定义才能使用它们。这样我们就能拥有更多工具（比如 Task 工具），在需要之前不会占用上下文。

同样的做法也可以用在你自己的 CLAUDE.md 和 Skill.md 文件上。一个常见的迷思是，你要把这些文件做成所有可能会遇到的已知实践的中央仓库，否则 Claude 就找不到。其实应当考虑做成一棵可以在正确时机加载的文件树。

过去：反复重复

现在：简洁的工具描述

较早的 Claude 模型有时需要重复的指令，也更可能听从上下文窗口末尾而非开头的指令。这意味着系统提示词里有时会在主系统提示中引用工具，同时工具描述里也有一份指令。 

我们发现可以删掉这些重复示例，把如何使用工具的指令放进工具描述，而不是系统提示词。

过去：把记忆写进 CLAUDE.md

现在：自动记忆

我们曾经鼓励用户用 # 快捷键自动写入 CLAUDE.md，把内容存进 Claude 的记忆。现在，Claude 会自动保存与当前工作和你本人相关的记忆。 

过去：简单的规格说明

现在：丰富的引用

在 plan mode 中，Claude Code 大量依赖带有计划的 markdown 文件。把这些文件存成计划，方便 Claude 在需要时查阅。另一条类似的最佳实践是把规格说明存在代码库里，供 Claude 在较长项目中参考。

但我们发现 Claude 已经能处理越来越复杂的引用。不再只是简单的 markdown 文件，Claude 还可以引用我们新的 artifacts 功能生成的 HTML artifacts。 

你也可以用代码的形式给 Claude 引用。一份规格说明也可以是一套详细的测试套件，或是另一个代码库里 Claude 可能要移植的函数。 

评分标准（rubrics）是另一种引用。评分标准让 Claude 可以通过动态工作流，并拉起带有这些评分标准的验证 agent，去尝试核验你在某个领域的品味（例如，好的 API 设计是什么样的）。

把这些用到你的上下文里

把以上内容合在一起，组装你自己的上下文时会是什么样子？

System Prompt

系统提示词与产品上下文紧密绑定。它告诉 Claude 自己运行在什么产品里、正在做什么。对 Claude Code 来说，你很可能永远不会改它；但如果你在构建自己的 agent harness，这里才是你应该投入大量时间的地方。

CLAUDE.md

让 CLAUDE.md 保持轻量，简要说明仓库是做什么的，把大部分 token 花在代码库内部的坑上。例如，你可能把类型都集中在一个单体文件里，其他地方都没有。避免陈述那些 Claude 看一眼文件系统或仓库就该知道的"显而易见"的事。

大量使用渐进式披露。例如，如果你有若干条关于如何验证工作的独特指令，就创建一个 verification skill，然后从 CLAUDE.md 引用它。

Skills

把 skills 想成轻量指引，让 Claude 在需要时找到信息。除非是极其重要的领域，否则避免把它们限制得过死。 

对于较长的 skills，尽量使用渐进式披露，拆成许多文件并分开存放。

最好的 skills 编码的是属于你、你的团队或产品的特定观点、知识或最佳实践。 

References 

你可以用 @ 提及文件，把它们作为引用纳入。引用让 Claude 能够查阅当前计划的深入信息。 

这可能是规格文件、原型，甚至整个代码库。一般来说，你应该优先选择代码中的文件，因为它用 Claude 非常熟悉的语言提供了清晰、高保真的指令。例如，一个设计的 HTML 原型通常会比设计描述或截图产生更好的结果。

试着简化

在你的系统提示词、skills 和 CLAUDE.md 文件中，你可能也需要像我们一样做简化。我们推出了一个名为 `claude doctor` 的新命令，它也会帮你自动完成这件事。关于专门为更先进的模型编写提示词的更多细节，请参阅我们的 Fable field guide。
