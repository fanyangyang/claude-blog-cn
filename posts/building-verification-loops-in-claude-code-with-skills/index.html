在 Claude Code 中用 Skills 构建验证循环

How to turn your manual checks into skills, so Claude closes its own feedback loop.

大多数 agentic coding 会话都走同一个循环：你要求一处改动，Claude 收集上下文、采取行动、验证结果，必要时再绕回去补上下文。

验证是 agent 在回复之前检查自己工作的方式。Claude 已经会从代码库里的确定性信号做一部分，包括类型检查、linter、测试和运行时错误。它推断不出来的，就变成你手工检查功能时要走的那些步骤。

这些手工步骤可以变成验证循环。在 Claude Code 里，验证循环是一个迭代过程，Claude 检查工作并尝试修好它。

这篇文章会讲最常见的验证循环类型，以及我们在 Anthropic 内部怎么用。然后我们会展示如何把你已经在做的手工检查写成 skills，让 Claude 自己合上反馈环，你就可以在它迭代的时候去做别的事。

刚接触 agent loops？先从 getting started with loops 开始。

什么是验证循环？

验证循环是一段重复周期：AI agent 检查自己的工作，跑测试、linter 或自定义检查，失败的先修好再往下走。在 Claude Code 里，验证循环可以打包成 skills，于是每次会话都自动套用同一套检查，而不依赖人记得去做。

内置验证循环

设计自定义验证循环之前，先了解 Claude 对若干验证循环的内置支持会有帮助。常见能力和做法包括：

  • /verify skill：构建、运行，并观察应用里的改动。
  • Toolchain：Claude 会尽量捕获你提供的任何工具给出的错误码和警告，比如 linter。好习惯是把确切的构建和测试命令写进 CLAUDE.md，这样 Claude 就不必去猜。
  • Code Review (research preview)：一项托管的多 agent 服务，会在你启用的仓库里对 PR 跑一轮自动评审。你可以手动修好发现并推送，也可以在发现上评论 @claude 来合上循环（前提是你已经配置好下面的 GitHub Actions）。
  • GitHub Actions：定义一个用验证 skill 调用 Claude 的 job，你在本地跑的同一套检查就会在每次 push 或 PR 上触发。
  • Spec validation：一个 skill，帮助对照仓库里的 markdown spec 验证每一处改动，并尝试修好违规。
  • Rubrics in Claude Managed Agents (beta)：一项托管的智能体服务，让你用单独的 grader agent 对照 rubric 验证结果。失败会自动绕回去返工。

编写验证循环

当你已经有一个项目，并且发现 Claude 每次给你实现新功能时，你都在做同样的小修正，就该把这些步骤变成自己的自定义验证循环。第一步是把你每次都在做的事全部写下来。

新开项目、还在摸清项目该怎样表现时，也一样。用大白话写出最佳实践版本，就像第一天交给新同事那样。

如果连验证检查本身都很难说清楚，先让 Claude 给出最佳实践，再从那里改。你的版本大概会在几个具体点上不一样，那些差别正是你想抓住的东西。

Pro tip：检查不必是定性的才有资格写在这里。"拒绝任何在没有回填步骤的情况下删列的迁移"是一条确定性规则，通用 linter 抓不到，项目专用的却可以。凡是你一直要靠手工检查去强制执行的，都值得收成循环。

做成 skill

把重复步骤编码成验证循环，最常见的做法是写成 skill。最快的创建方式是安装 skill-creator 插件，让 Claude 采访你：

例如：

/skill-creator Create a skill for verifying frontend changes end-to-end. Interview me about my workflow.

你也可以自己写 skill，把一份 markdown 文件放到项目里的 .claude/skills/。最简单的验证 skill 就是几行 frontmatter 加上正文：

# .claude/skills/verify-log-hygiene/SKILL.md
---
name: verify-log-hygiene
description: Check that error logs include the request ID and never
  include the request body. Use when the diff touches error handling
  or logging.
allowed-tools: [Read, Edit, Grep]
---
Read the error-handling paths in the current diff.

For each log call on an error path, confirm it includes the request ID
and does not pass the request body, headers, or any user-supplied payload.

Report each violation with file:line, then fix it: add the request ID
where it's missing and strip the payload from the log call.

完整 schema 和背后的思路，见我们的 complete guide to building skills。

让检查匹配它运行的位置

接下来要决定验证循环怎么启动：独立、内嵌、串联，还是绑到 PR。

独立（Standalone）

产物已经存在之后，你有意调用它。独立 skill 适合并非每次都适用的横切检查：提交前的安全扫描、PR 前的无障碍审计、全仓库的许可证头验证。凡是你希望在许多工作流里都能用到、又不想每次改代码都开火的，都适合这一类。

代价是每次调用仍是你必须记得走的一个回合。当你每次改完都在跑它，就说明独立模式已经不够用了。到那一步，这套手续该有一个固定位置：内嵌进去，或串联起来。

内嵌（Embedded）

作为产出 skill 的一部分自动开火。检查属于某一个具体工作流，工作流现在会在你不问的情况下跑它。

最简单的版本是在产出 skill 的正文末尾加一行：

# .claude/skills/scaffold-component/SKILL.md
---
name: scaffold-component
description: Scaffold a new React component under src/components/, including the component file, its co-located test, and an index export. Use when the user asks to create a new component.
allowed-tools: [Read, Write, Edit, Bash, Glob]
---

# Scaffold a new React component

Given a component name (PascalCase), create the following under `src/components/<Name>/`:

1. `<Name>.tsx`: function component with a typed props interface and a default export.
2. `<Name>.test.tsx`: React Testing Library test that renders the component and asserts it mounts without throwing.
3. `index.ts`: re-export the default and any named exports.

Follow the patterns in `src/components/Button/` as the reference. Match the import alias style (`@/components/...`) used throughout the codebase.

# code continues...

After creating the component file, run eslint on it and
address any errors before reporting completion.

在一个新任务上调用这个 skill，确认新增步骤作为输出的一部分跑起来，以此来验证内嵌是否生效。如果没有，说明 skill 的 description 或更靠前的指令没有把追加的检查拉进来。

内嵌只适用于你能编辑的 skill：你自己写的，或安装在项目级、SKILL.md 在你控制之下的。内置 skill 和由插件管理的 skill（更新时会被覆盖的那种）不能用这种模式；对那些，改用串联。

跨工作流的检查不要内嵌；那些适合独立，这样你可以从任何上下文调用它们。

串联（Chained）

一个 skill 在结束时调用另一个，若干次经过验证的交接从头跑到尾。

Anthropic 的 Claude Code 团队日常就用这种模式：/code-review 找 bug，/simplify 清理 diff，一个 /verify skill 确认端到端行为，如果改动碰到 UI，再由自定义的 /design skill 对照 DESIGN.md 里的指南检查。

串联也是给你改不了的 skill 加上验证的办法：做一个自定义包装 skill，先调用原来的，再调用你的验证 skill，如下所示：

# .claude/skills/safe-refactor/SKILL.md
Run /simplify on the current diff first.
When /simplify finishes, invoke /verify-no-public-api-changes.

起初只是习惯（"我总是在 /simplify 之后跑 /verify"），后来变成契约（"/simplify 结束时总是跑 /verify"）。这条链自己跑完整段开发周期。只有事情升级回你这里时，你才介入。

如果各步骤独立到你有时只想跑其中一个，就可以跳过串联；串联用灵活性换自动化。串联的验证循环会增加 token 花费，所以最好先测这些循环，再大范围铺开。

在每个 PR 上

链条对你自己的改动已经稳了之后，同一套手续可以跑在每个 PR 上。同事的改动会经过和你一样的关卡，不管他们记不记得去调用这条链。基础设施和你已经写好的链是同一类东西，只是再往前一步：同样的 skills、同样的 rubrics、同样的标准，不再依赖作者是否勤奋。

验证从这里不再是个人基础设施，而变成团队基础设施。你为每周省下两分钟写下的检查，现在在每一处改动上给所有人每周省下两分钟。链还在变动时先别上全 PR 关卡；每一次调整都会变成团队都看得见的事件。

流程跑顺之后，你就可以扩展循环工程。无论你在自动化什么、在什么环境里，创建验证循环的过程都是一致的：

  1. 挑出你这周做得最多的那项手工收尾。
  2. 先试试内置的 /verify skill，看它是否帮得上你的流程。
  3. 用大白话写出手续，就像第一天交给新同事那样。
  4. 交给 skill-creator，或自己把 markdown 文件放到 .claude/skills/。
  5. 在一个新任务上调用它，确认检查作为输出的一部分跑起来，需要就迭代。
  6. 尝试 skill 串联，做成端到端的验证流。

你能为 Claude 编码进去的越多，Claude 的回复就越常在第一次就更接近你要的。那些你不必再动手拨弄的修正，会把注意力还给没有 skill 能替你写下的、只属于你的工作。
