代码不再是瓶颈

各组织已经开始用 AI 以前一年前难以想象的速度编写代码，但围绕代码的流程却没能以同样的速度演进。

许多工程团队仍然保留着同样的审批关卡、评审、交接和策略，这让 Claude Code 等智能体化编码方案带来的生产力提升被卡在了半路。

软件开发生命周期（SDLC）是把软件从想法带到生产的流程。大多数组织都在运行某种版本的同样六个阶段，覆盖软件的规划、设计、构建、测试、部署和维护。传统上，每个阶段都是一个由不同角色负责的独立环节：产品经理撰写需求，技术架构师把需求转化为设计，工程师实现设计，受监管企业的 QA 团队负责验证，发布团队负责上线，运维团队监控线上运行情况。工作通过文档、工单和签核在各阶段之间流转。

传统的软件开发生命周期（SDLC）流程繁重，以确保每一步都有问责和管控。然而，传统 SDLC 的设计初衷是在"编写和实现代码是最耗时、最昂贵的阶段"的那个时代实现效率最大化——如今情况已经变了。PRD、工作量估算仪式和产品安全评审的存在，都是为了在可能长达数周、数月甚至一个季度的开发工作中强行对齐认知。

传统 SDLC 的各种管控手段还默认每个步骤都由人来执行。而那些创造最多价值的组织，已经围绕智能体 AI 当前的能力重建了流程，同时确保人类始终在环（human in the loop）。在本指南中，我们将分享 Applied AI 团队在 SDLC 各阶段内部集成 Claude 的一系列最佳实践，这些实践借鉴自我们与客户合作的经验，旨在加速开发、让流程跑得更快。

当代码不再是瓶颈、构建阶段的运行速度超越了传统 SDLC 所允许的节奏时，有三件事会成为现实：

  • 瓶颈转移到了构建阶段左右两侧的步骤上，主要是规划、评审/测试和部署——它们仍然在以人类的速度运行。
  • 管控手段开始与现实脱节，变得难以维系。当每一行代码都是人写的时候，逐行人工评审是合理的；但当 diff 的大部分都由智能体编写时，这种方式就跟不上了。
  • 治理成本上升，因为各种例外仍然要走每周或每月才开一次会的会议和委员会的流程。

我们以安全瓶颈为例。安全团队的规模是按人类产出配置的，当智能体让代码产量成倍增长时，要么评审队列越积越长，要么代码在没有经过充分评审的情况下就发布了。受监管的组织无法接受任何一种结果，因此其安全与策略检查必须跟上智能体的节奏。

为了更好地收获智能体 AI 的生产力红利并保障其安全，传统 SDLC 生命周期需要经历与实施阶段同等级别的变革。

什么是 AI 原生 SDLC？

AI 原生 SDLC 是一个重新设计过的流程，它把旧的控制目标与新的执行方式结合起来。流程不再是线性流转，而是变成一个环，AI 被嵌入到每个节点。AI 原生 SDLC 推动后续 play 的自动交接和自动触发，从而解决传统 SDLC 各阶段之间人工、笨拙的交接方式。

你也会听到人们把这个转变称作智能体化 SDLC（agentic SDLC）、AI SDLC，或者干脆叫智能体化软件开发——名称各异，描述的却是同一件事。

AI 原生 SDLC 六个阶段的变化

下表列出了由 Claude 支持的传统 SDLC 与 AI 原生 SDLC 之间的两个极端。大多数组织处于两列之间的某个位置。

阶段传统 SDLCAI 原生 SDLC
Plan（规划）由委员会收集需求，通过工作坊和层层签核提炼，再手工撰写成文Claude 直接从原始来源综合痛点，并将其写入人类可读、机器可执行的 intent.md
Design（设计）分析师撰写规格说明，设计师再解析需求与设计压缩为与智能体协作的一场工作会话，由编码为 Skills 并在 git 中做版本管理 的标准来引导
Build（构建）测试与代码均由手写，文档在主体开发完成之后补写测试与代码由 AI 生成，机构知识以带版本管理、机器可读的 CLAUDE.md 文件和 Skills 的形式维护
Test（测试）QA 关卡设在阶段边界处持续评估（evals）贯穿整个实现过程
Deploy（部署）人工逐行评审代码，治理在评审周期中进行，且往往不一致多层级智能体评审，人工评审仅保留给受监管和关键代码。治理在 AI 行动的同时即被强制执行，以 Hooks 作为审批关卡
Maintain（维护）由人盯着生产环境找 bug智能体监控线上部署。任何被突破的控制带都会被诊断，并作为新的 intent.md 写回闭环

贯穿右列的主线是被提交的制品（artifact）。每个阶段都以向版本控制写入一份制品而结束（包括 intent.md、spec.md、plan.md、diff 及其测试、带评审结论的 PR，以及事故记录），下一个阶段则从读取它开始。在早期阶段，.md 文件是主要制品，因为产品负责人和智能体都能读取并在同一个文件上采取行动。从 Build 阶段开始，制品变成了代码及其记录。提交链同时也是审计轨迹：谁要求了什么、智能体产出了什么、谁批准了它。

对于每一个需要判断力的决策，人类仍然承担最终责任。在智能体化的 SDLC 世界里，人类的注意力随着必须评审的制品一起转移。

每个阶段都提交一份下一阶段可读取的制品。意图、规格、计划、diff 和评审结论合在一起，就是完整的审计轨迹。

Play（打法）

这些 play 是本手册的核心，分为六个非线性的阶段（Plan、Design、Build、Test、Deploy、Maintain），合起来覆盖完整的生命周期。

每个 play 涵盖：

  • 发生了什么变化；
  • 如何起步；
  • 具体的实施步骤；
  • 治理方面的考量；以及
  • 如何衡量它是否奏效。

这些步骤是模块化的，各组织可以根据自身独特的需求，选择在不同时间优先改造不同的阶段。每个 play 都会在"前提条件"（Prerequisites）下列出其依赖项，依赖关系图对此有进一步的说明。

一个阶段以提交一份制品结束，而这次提交会启动下一个阶段：一份被接受的 intent.md 触发需求与设计环节，一份被批准的 spec.md 触发计划模式，一个被合并的 PR 触发流水线，生产环境中被突破的控制带则会写下新的 intent.md——如此循环往复。

起初，你可以每一步都手动提示（prompt），最终状态则是一个闭环：每份被接受的制品触发下一道关卡。人类的注意力集中在关卡处，评审智能体标记出的内容，而不是每个阶段都从零开始。

01

Plan（规划）

想法不再需要等人来撰写成文。意图以发起人自己的语言被一次性记录下来，成为一份带版本管理、供下一阶段直接使用的制品。

以 intent.md 的形式捕获

开启软件开发流程的 intent.md 可以经由不同途径进入流程：有人产生了一个想法、有人提交了一张工单，或者某次告警暴露出一个事故（见阶段 6：Maintain）。

当一个人有想法时，他与 Claude 头脑风暴并产出一份 markdown 原型规格。在传统 SDLC 中，这个人接下来还必须说服产品团队的某位成员与他一起（或替他）把想法写成正式文档。

Claude 生成的原型规格人类可读、有版本管理、并且下一阶段可以立即使用。这份原型规格被保存为 intent.md。

无论意图来自事件触发还是来自智能体，步骤都是一样的：产品负责人在提交之前，评审并修正智能体写就的 intent.md。

传统方式一个想法要经过 backlog 条目、用户故事、故事点和需求梳理会议，才能有人对它采取行动。所有权在每次交接时转移，传到工程团队手里的东西已经和发起人的本意相隔了好几步。
AI 原生方式发起人与 Claude 头脑风暴，并把结果以发起人自己的语言写成 intent.md 原型规格。这份制品包含想要什么、为什么，以及在哪些约束之下。重复性的流程通过 Skills 编码固化。
如何起步
前提条件
无。
基础设施
为非工程师人员提供 Claude 访问权限（claude.ai 或 Cowork）；一份约定好的 intent.md 模板；一个共享的、带版本管理的意图存放处（intent home），由产品负责人盯守。对单个产品而言，最简单的存放处是产品代码仓库里的一个 intent/ 目录。这样设置可以让制品链与由它衍生的代码紧挨在一起。只有当意图横跨多个代码仓库时，专门的意图仓库才值得那份额外开销；在 monorepo 中，它就是一个目录。阶段 3：Build 的侧边栏会说明这个存放处与已经承载需求记录的 Jira 或需求工具之间的关系。

搭建这套东西对平台团队或工程团队来说是一次性的工作。需要一名技术团队成员把意图存放处建起来，并决定谁可以写入，因为许多贡献者将来自组织的各个部门。

仓库建好之后，没有 git 经验的贡献者不需要直接使用 git。版本控制系统（如 GitHub）的连接器可以让 Claude 代表他们从 claude.ai 或 Cowork 提交 markdown 文件。

如何执行

  1. 发起人用自己的语言向 Claude 描述问题。发起人可以描述他今天做不了什么、这个想法影响哪些人、更好的样子是什么，或者哪些内容不在范围内。不需要任何正式的语言。
  2. 持续头脑风暴，直到想法足够具体。Claude 会提出分析师会问的问题：范围、用户、约束条件，以及成功是什么样子。
  3. 让 Claude 使用组织的模板（它可以被编码成一项 skill，由技术团队成员搭建、负责人签核）把结果写成 intent.md。模板可以涵盖问题、预期成果、受影响的用户和系统、约束条件，以及开放问题。
  4. 发起人修正 Claude 理解有误的地方。
  5. 把 intent.md 提交到共享存放处。作者和时间戳随之进入记录，产品负责人从那里接手这个想法。
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?

治理考量

证据就是那份被提交的 intent.md，上面列有作者、时间戳和完整的修订历史，记录在意图存放处的 git 历史中。由产品负责人审批，把意图送入阶段 2：Design 的接受或拒绝决定，以合并（merge）或关闭评审的形式被记录下来。

如何衡量
领先指标
从第一次对话到提交 intent.md 之间的时间，从意图存放处的 git 历史读取，其中记录了作者和时间戳。预期是从数周的需求引导与梳理周期缩短到几个小时。
滞后指标
存活率，即被产品负责人接受进入阶段 2：Design（而非被关闭）的 intent.md 所占的比例。接受或拒绝的决定以制品的合并或评审关闭的形式被记录。此外，还要看同一变更的 spec.md 首次提交之后，intent.md 上又发生了多少次修改。
02

Design（设计）

需求与设计坍缩为一场会话。策略在撰写规格的同时就被应用，而不是几周后才在评审中被发现。

需求与设计

一旦产品负责人批准，Claude 就会接过被接受的 intent.md，产出一份需求与设计规格。这个过程由组织在品牌、安全、合规和 UX 方面的 Skills 引导。

产品负责人评审这份规格，但不需要亲自撰写。这个过程的目标是产出一份工程团队可以据此制定计划的规格，并标记出需要关注的区域。

前端工作是最直观的例子。intent.md 被接受后，产品负责人在 Claude Design（beta）中根据 intent.md 做出设计稿，在稿上迭代，然后把它导出到 Claude Code 进行构建。

传统方式需求和设计是由不同团队执行的独立阶段。分析师把想法形式化为需求，设计师再把这些需求解析回设计。这种分离是为了问责，但它既缓慢又有损耗。
AI 原生方式两个阶段发生在同一次受提示驱动的会话中。Claude 接过 intent.md，在组织 Skills 的约束下产出一份需求与设计规格，并标记出需要关注的区域。
如何起步
前提条件
写一个 intent.md 文件，并把品牌、安全、合规和 UX 策略写成 Skills。
基础设施
一名拥有 Claude 访问权限的产品负责人。不需要任何工程技能。

如何执行

  1. 产品负责人开启一个加载了组织 Skills 的会话，并附上 intent.md。
  2. 产品负责人的提示指向 intent.md，点明约束条件，并要求标记出需要关注的问题。起初手动运行，之后把它固化为一个组织级别的斜杠命令（slash command）。再往后，把意图存放处中 intent.md 的接受作为触发器：一个在合并时触发的非交互式任务，加载组织的 Skills 运行这一环节，并把 spec.md 以 pull request 的形式提交（阶段 5：Deploy 中的 CI/CD play 会介绍具体管线）。从那时起，产品负责人的第一次介入就是评审。
  3. 同一位产品负责人对照原始想法评审规格：规格是否解决了所陈述的问题？intent.md 中的开放问题是被回答了还是被延续下去了？
  4. 优先处理被标记的关注点，因为它们正是分析师过去要逐级上报的问题。产品负责人在工程团队看到规格之前，与相应的策略负责人一起逐一解决。
  5. 把 spec.md 与 intent.md 一起提交。这一对文件记录了"要求了什么"和"决定了什么"。
  6. 产品负责人决定规格和意图是否进入构建阶段，对组织认定为较高风险的内容咨询技术负责人。这一决定永远由人类队友做出，而接受规格正是启动阶段 3：Build 中计划模式 play 的动作。

它长什么样（提示词）

Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.

治理考量

现行策略在撰写规格的同时就被读取和应用，而不是几周后才在评审中被发现。组织的 Skills 作为约束被应用到规格上。规格、生成它的提示词，以及当时生效的 Skills 版本，全部记录在版本控制中。产品负责人签核规格，并把被标记的关注点转给指定的策略负责人。

如何衡量
领先指标
同一变更从 intent.md 提交到 spec.md 提交之间的耗时（两个 git 时间戳），与旧的"需求+设计"周期做比较。
滞后指标
构建开始后的需求返工。统计同一变更在首个 plan.md 提交之后日期的 spec.md 提交数量。git log 可以直接给出这个数据。
03

Build（构建）

没有一份被接受的计划，任何东西都不会被实现。机构知识变成智能体可以读取的文件，护栏以代码而非习惯的方式运行。

以 Claude Code 计划模式为默认起点

工程师以计划模式（plan mode）启动 Claude Code 会话，把阶段 2：Design 批准的 spec.md 交给 Claude，让它向自己提问，并在计划上不断迭代，直到工程师满意为止。

传统方式工程师读完设计就开始写代码。这个改动怎么做——具体到改哪些文件、写哪些测试——都留在工程师的脑子里，充其量是工单里的一条评论。没有别人能评审它。评审者看到的第一样东西就是完成的 diff，而到那时返工已经很慢了。
AI 原生方式工作从一份由 Claude 在计划模式下产出的书面计划开始——在该模式下它可以读取代码库但不做任何修改。工程师在代码编写之前修正计划，被批准的版本作为 plan.md 提交，供后续阶段对照检查。
如何起步
前提条件
意图制品（intent.md 或 spec.md，如果存在的话），另外 CLAUDE.md 文件会有帮助。
基础设施
拥有仓库访问权限的 Claude Code。

如何执行

  1. 工程师以计划模式启动与 Claude 的会话。
  2. 工程师把 intent.md 和 spec.md 交给 Claude，要求一份实施计划，其中要指明会改动的文件、工作的顺序，以及用来验证的测试。
  3. 审问这份计划：这个改动可能破坏什么？哪一步风险最高？Claude 还有哪些它没有选择的方案？
  4. 持续迭代，直到一个从未看过这段对话的工程师也能仅凭这份计划实现这个改动。
  5. 把批准的计划作为 plan.md 提交。计划进入审计轨迹，PR 评审 play（阶段 5：Deploy）会把最终的 diff 与它对照检查。
  6. 接受计划，让 Claude 实现。有了一份扎实的计划，实现往往一次就能完成。
  7. 当实现偏离计划时，在同一次提交中更新 plan.md。可以考虑用 hook 来强制两者同步。

它长什么样（plan.md）

# Plan: claims status self-service (from intent.md 2026-06-02)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks

## Proof

approved mock.

治理考量

设计评审发生在任何代码生成之前，此时改变方向还只是编辑一份文档的事。计划模式本身就强制了这一点，因为在工程师接受计划之前，Claude 无法编辑文件。计划及其修订版本，连同接受它的人，都会被记录。常规变更由工程师批准，组织认定为较高风险的任何内容则要交给技术负责人或架构师。

如何衡量
领先指标
在第一轮实现中就直接合并的变更比例，以及从计划批准到 PR 合并的时间（所需数据记录在 PR 元数据中）。
滞后指标
每个变更的返工次数（同样来自 PR 元数据），以及合并后的 diff 与已提交的 plan.md 仍然吻合的频率。

Claude Code 自动模式

Claude Code 还可以在自动（auto）模式下运行：工程师批准计划，并在满意之后，让 Claude 逐项应用变更而不再逐次确认。随着后续各 play 中的护栏逐渐成熟（打磨过的 CLAUDE.md、编码了策略的 Skills、拦截危险操作的 hooks，以及 Claude 可以运行的测试套件），自动接受（auto-accept）就成为常规工作的默认方式：一份紧凑的 spec.md、一个很小的影响半径，以及测试已经覆盖的代码。

此时的转变是：从用户盯着智能体做每次编辑、逐个评审动作，转向在更长的自主会话之后评审制品。自动接受模式配合 worktree 使用时，还能进一步让个人和团队并行工作，它是自主运行 SDLC、并按阶段 6：Maintain 所述闭环的基础。

侧边栏

遗留系统与事实源

适用于流程产出的每一份制品。
现有的 SDLC 流程很可能已经在跟踪各种制品，只是不是以 markdown 文件的形式。工作项可能在 Jira 里，需求在自带监管级追溯能力的工具里，设计在 Figma 里，变更审批在变更委员会那里。这些系统很难被取代，因为审计师和监管机构已经认可它们，其他团队也依赖它们，所以 AI 原生 SDLC 必须绕开现存系统来落地。
向 AI 原生 SDLC 过渡时，流程产出的每一份制品，都要指定一个系统作为事实源（source of truth），其余系统只保存副本或指向原始记录的链接。下列配置都可以做到只有一个事实源，不同制品的选择可以不同：
以仓库为事实源。markdown 制品是权威记录，遗留系统引用各次提交中的文件。对工程主导的组织来说，这可能是最干净的配置之一，因为所有记录都放在一个工具里，只有一个时间戳权威。
以遗留系统为事实源。Jira、ServiceNow 或需求工具持有权威记录，markdown 制品是工作副本。Claude 在会话开始时读取记录，并在产出规格或计划的同一次会话中，通过 MCP 连接器把结果写回去。
以互相链接为最低标准。所有制品都注明记录 ID，所有遗留记录都包含 markdown 文件的 commit SHA。在向 AI 原生 SDLC 过渡时，链接是一个很好的起点，代价是暂时接受两个事实源并存。
遗留系统和 markdown 优先的系统可以共存，只要两者之间有链接，或者其中之一被声明为事实源。

CLAUDE.md

CLAUDE.md 把一名新入职者所需的上下文交给 Claude，涵盖约定、命令、架构，以及团队最常犯的错误。过去存在于人们脑中和 wiki 里的知识，变成了智能体在每次会话开始时都会读取的文件，由整个团队维护，并且每次犯错都会迭代更新。

如何起步
前提条件
无。
基础设施
一个代码仓库、安装好的 Claude Code，以及一位熟悉这个代码库的工程师。

如何执行

  1. 在仓库中运行 /init。Claude 会根据它的发现生成一个初始的 CLAUDE.md。
  2. 把生成的文件裁剪到一名新人在第一天需要的内容。保留构建、测试和 lint 命令，保留真正重要的约定，以及 Claude 反复出错的地方。
  3. 把 CLAUDE.md 提交到仓库根目录的 git 中，这样整个团队共享同一个版本，对它的修改像代码一样被评审。
  4. 这里有一条实用规则：当 Claude 同一个错误犯了两次，就把纠正方法写进 CLAUDE.md。
  5. 把它控制在一页以内，因为 Claude 在会话开始时会读完整个文件，任何过时的内容都在白白占用上下文。

它长什么样（CLAUDE.md）

# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.

治理考量

CLAUDE.md 有版本管理，因此智能体遵循的指令是可评审、可审计的。团队约定通过这个文件被应用，对它的修改记录在 git 历史中，并由 code owner 在 PR 评审时批准。

如何衡量
领先指标
Claude 重复犯下 CLAUDE.md 本应阻止的错误的频率。对 CLAUDE.md 的修正和修改应当在 git 历史中被跟踪。
滞后指标
团队新成员从加入到第一个 PR 被合并的时间（从 PR 历史中读取）。

用 Skills 沉淀机构知识

Skills 是组织把机构知识变成可执行操作的方式。这些指令是显式的、有版本管理的、被广泛应用的，并且在策略变化时集中更新。经验法则：必须被一致执行的机构知识写成 skill；属于 CLAUDE.md 或提示词层面的内容不要写成 skill。

如何起步
前提条件
无硬性要求。有 CLAUDE.md 会有帮助，因为它把智能体的工作知识留在仓库里，但 skill 并不依赖它。
基础设施
一项有明确负责人的策略，以及一份书面的事实源。

如何执行

  1. 挑选一项今天执行得不一致的知识。它可以是一项安全标准、一条 API 设计约定，或一条品牌规则。
  2. 把它写成一个 skill：一个包含 SKILL.md 的目录，其 frontmatter 说明何时触发，正文说明该做什么。由一名工程师根据策略负责人的事实源撰写，可以让 Claude 协助。
  3. 把 skill 放进仓库的 .claude/skills/<name>/，让它随代码一起分发，或者通过 插件在整个组织内分发。
  4. 测试 skill 是否会触发。用不同的方式让 Claude 去做相关任务，确认每次都会加载这个 skill。
  5. 当策略变化时，修改 skill，并由策略负责人签核这次修改。
  6. 工程师在下一次会话中自动用上新版本。

它长什么样（.claude/skills/secure-api-review/SKILL.md）

---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review

When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run scripts/check-endpoints.sh and include its output in your summary.

治理考量

skill 是一种控制手段，不过是咨询性的。它让 Claude 更可能在写代码的同时应用策略，但没有任何机制强制一个会话服从它。必须始终成立的策略需要在 skill 背后有确定性的东西兜底，比如拦截危险操作的 hook，或在 PR 处重新检查策略的评审环节。skill 让违规变得罕见，hook 让违规几乎不可能发生。Skill 的调用记录在会话轨迹中，策略负责人像评审代码一样评审 skill 的修改。

如何衡量
领先指标
从策略负责人批准策略变更，到更新后的 skill 被合并之间的时间，从 skill 目录的 PR 中读取。
滞后指标
PR 评审中引用该策略的发现项数量。一旦 skill 开始在写代码的同时应用策略，这个数字应当趋向于零。如果没有趋向于零，要么是 skill 没有被触发，要么是它的文本与官方策略产生了偏差。

用 Hooks 做构建期护栏

skill 是咨询性控制，而 hook 是它背后确定性的那一层。Claude 的大部分动作是实现过程中的文件编辑和 shell 命令，所以构建阶段是 hooks 触发最频繁的地方。

构建阶段的 hooks 可以：

  • 阻止对受保护路径的编辑，例如生成的类或已冻结的包；
  • 在文件编辑后运行格式化工具和 linter，让偏差永远不会累积；
  • 把凭据挡在 diff 之外。

为所有"策略必须毫无例外地成立"的 skill 配上兜底。hook 会在每个匹配它的动作上运行，所以构建阶段的 hooks 应当快速，并且只作用于被改动的文件。更重的检查，比如完整测试套件，应该放在提交或 PR 环节。

需要请求人类批准的 hook 属于阶段 5：Deploy 中的关卡，因为构建过程中弹出的批准提示，会把人重新拉回所有并行运行会话的关键路径上。

并行会话与子智能体

一名工程师可以同时推进多条工作流。

并行会话是另一个完整的 Claude Code 实例，在它自己的 git worktree 中处理一个独立任务。每个独立会话对其他会话一无所知，唯一把它们联系在一起的，是掌控它们的工程师。

子智能体（subagent）运行在单个会话内部，是一个有自己上下文窗口和工具限制的受限帮手，适合在多个任务中反复出现的工作，比如验证应用是否按预期运行。

并行会话提升了工程师可以同时推进的任务数量，子智能体则让每个会话专注于自己的任务。工程师的工作是为它们所有人掌舵和做评审。

传统方式一名工程师一次只做一个任务，一天或一周中相当一部分时间花在构建、测试和等评审上。等待期间切换到别的任务当然可行，但上下文切换太累人，很少有人真的这么做。
AI 原生方式一名工程师同时运行多个 Claude 会话，每个会话在自己的 worktree 里做自己的任务。重复性工作变成有独立上下文和工具限制的子智能体。工程师的工作转向编排，并最终转向构建和监控闭环。
如何起步
前提条件
CLAUDE.md，因为所有会话都会读这个文件。反馈回路（阶段 4：Test）在这里也有帮助，因为当会话能验证自己的工作时，就不太需要工程师盯着。
基础设施
一个 git 仓库——隔离来自 worktree；还要调好权限设置，让会话不会在组织认为安全的命令上等待批准提示。

如何执行

  1. 工程师把工作拆成触及不同文件的任务，利用计划模式 play（阶段 3：Build）产出的计划判断哪些工作是独立的。共享文件的任务放在同一个会话中依次执行。
  2. 每个并行任务有自己的 worktree，比如在一个终端里运行 claude --worktree feature-auth，在另一个终端里运行 claude --worktree fix-rate-limit。worktree 是位于自己分支上的独立检出，可以避免会话之间在文件上发生冲突。
  3. 两三个会话是合理的起点。实际的上限是一个人能认真评审多少条工作流，所以只在评审还跟得上的时候增加会话。
  4. 把重复性工作变成子智能体，以 .claude/agents/ 中的 markdown 文件定义，每个都有名称、何时使用的描述，以及它可以使用的工具。例如：一个在主智能体完成后剥离不必要复杂度的代码简化器；一个运行应用并检查行为的验证器；一个探索代码库并汇报、不淹没主上下文的研究员。把这些定义提交进 git，让整个团队共享。

它长什么样（.claude/agents/verifier.md）

---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.

治理考量

会话更多意味着产出更多，因此控制必须来自仓库中的配置。那里的 hooks 和权限设置对所有会话生效，会话的行为都会被记录，并归属于运行它的工程师。

如何衡量
领先指标
在评审质量保持稳定的前提下，每位工程师的并发会话数（从 OpenTelemetry 导出数据统计），以及一天中花在掌控而非等待上的时间占比。
滞后指标
每位工程师每周合并的变更数，与按 PR 历史得出的返工率一起阅读。
04

Test（测试）

每个会话在人类看到结果之前先自查，而引导智能体的那份配置也会像它写的代码一样接受回归测试。

给 Claude 一个反馈回路

永远给 Claude 一种验证自己工作的方式，无论是测试、构建，还是截图比对。会话在工程师看到之前，先检查自己的工作、修正自己的错误。

不要把反馈回路与验证器子智能体（阶段 3：Build）混为一谈。反馈回路贯穿整个任务，跟随工作运行的次数可以任意多。而验证器子智能体是打包"最终检查"的一种方式：当会话认为工作完成后，用一个全新的上下文窗口运行一次。这样，结论就不会被生成代码时的那些假设所影响。

传统方式"代码能跑"这个信号来得很晚：CI 在几分钟后，测试人员在几天后，生产环境在几周后。当智能体生成代码时，迟到的信号意味着必须有一个人去检查它的全部产出，这个人就成了瓶颈。
AI 原生方式会话在人看到之前就获得了自查的方式。跑测试、跑构建、截屏。Claude 会迭代到检查通过为止，因此到工程师手里的东西已经通过了检查。搭建这个回路的任务落在运行会话的工程师身上，下面的步骤就是为他们写的。
如何起步
前提条件
无。
基础设施
能用一条命令在本地运行的测试套件和构建。对 UI 工作，让 Claude 能看到结果的方式至关重要——要么是浏览器工具，要么是通过 MCP 接入的截图工具。

如何执行

  1. 如果今天检查工作需要一串命令和一些环境知识，就把它封装成一个单一目标，比如 "make test" 或 "npm test"，失败时以非零退出码结束。
  2. 在 CLAUDE.md 的 Commands 一节中，列出每条命令，并附上一个健康输出的示例。
  3. 设定一个可量化的目标，让 Claude 无需询问你就能检查工作，例如："test_status.py 中的所有测试通过"、"截图与附带的 mock 一致"，或"端点返回 200 且带上了新字段"。
  4. 修 bug 时，先写失败的测试。让 Claude 把 bug 复现为一个测试，运行它，确认它是因为你预期的原因失败的。提交这个测试。然后才让 Claude 在不修改测试的前提下让它通过——最后一步的测试文件 hook 会强制这个约束。一个在修复之前就存在、且智能体无法改写的测试，就是 bug 已被消灭的证据。
  5. 做 UI 工作时，用视觉检查闭环。给 Claude 浏览器或截图工具，把 mock 给它，让它迭代：实现、截图、比对、调整。两三轮很正常，而且结果应该一轮比一轮好。
  6. 把验证变成"完成"定义的一部分。指令写在 CLAUDE.md 里：报告任务完成之前先跑测试，并展示输出。
  7. 最后，这个回路本身需要保护，因为修代码的智能体绝不能有能力削弱对这段代码的检查。一个在修复任务中阻止编辑测试文件的 hook 可以做到这一点。另一种办法是在评审时检查 diff，拒绝任何触及测试的改动。

它长什么样（CLAUDE.md 验证区块）

## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
治理考量
强制执行什么
任务报告完成之前的验证，以及修复期间智能体不得编辑测试文件的禁令——在组织需要保证的地方，两者都以 hooks 实现。
证据是什么
Claude 运行并粘贴的 "make test" 字面输出、构建日志或截图比对，即证据直接来自工具链。
记录在哪里
会话转录（由 OpenTelemetry 导出转发到组织的可观测性体系）以及 PR 的 check run，评审者和之后的审计师都能看到。
谁来批准
评审 PR 的 code owner。因为机械性证据已经附上，他可以把精力集中在意图和风险上。
如何衡量
领先指标
智能体所写变更的 CI 首次通过率，CI 系统本身就能提供这个数据。
滞后指标
每个 PR 的评审时间（来自 PR 元数据）——一旦测试接住了过去评审者要接住的问题，这个数字应当下降——以及来自事故跟踪系统的变更失败率。

在 CI 中做持续评估

评估（evals）是阶段关卡式 QA 的 AI 原生等价物。在实践中，它意味着一套在智能体配置变化时运行的测试套件。当新模型被换入、或提示词被重写时，评估套件会告诉你智能体是否仍以同样的标准完成工作。

这些评估应被视为一套活着的套件。随着模型进步，曾经有区分度的用例会失去区分度，必须根据持续监控的结果补充新的用例。

取决于具体场景，有些团队可能更愿意按固定节奏离线运行这些评估，而不是在每次变更时运行。下面的步骤针对持续评估。

如何起步
前提条件
CLAUDE.md 和反馈回路（阶段 4：Test）。
基础设施
能以非交互方式运行 Claude Code 的 CI，以及一个有评估运行预算的 API key。

如何执行

  1. 平台工程师从最近的工作中收集 20 到 50 个真实任务，连同它们的预期/可接受结果。
  2. 把每个任务写成一个评估，即提示词加上定义"可接受"的检查（测试通过、lint 干净、行为不变、遵循策略）。
  3. 套件在 CI 中按计划运行，并且在 CLAUDE.md、skills 或 hooks 有任何变更时运行，因为这份配置引导着智能体，理应获得与代码同等的回归测试。
  4. 用结果给配置变更设卡。一个导致通过率下降的 skill 修改，必须先经过评审才能合并。
  5. 每起生产事故都要转化为一个评估，由负责该事故的团队编写，并作为回归测试留在套件中。

它长什么样（.github/workflows/agent-evals.yml）

name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

05

Deploy（部署）

评审双向进行，治理在智能体行动的同时被强制执行。智能体做生产关卡之前的所有事，关卡之后的事一件不做。

PR 评审回路中的 AI

Claude 既给出评审，也接受评审。它按照组织的策略评审进来的 PR，也处理自己 PR 上的评审意见。这让工程师在 PR 评审中专注于行为——归结起来就是判断意图和风险。

传统方式评审容量是按人类产出规划的。PR 要等评审者读完所有内容，评审质量随评审者负荷波动，作者追着要评审，积压越积越多。
AI 原生方式所有 PR 都得到同一套评审过程，发现项按严重程度排序。人类的注意力上移一层：这个变更是否做到了计划想要的，风险是否可接受。
如何起步
前提条件
阶段 3：Build 中更新过的 CLAUDE.md 文件；如果评审过程要执行书面策略，还需要 skills，以及定义好的子智能体。
基础设施
一个装好了 Claude 集成的仓库——要么是由管理员开启的托管式 Code Review（research preview）服务，要么是在你自己的 CI 中运行的 claude-code-action，需要时模型调用可经 AWS Bedrock、Google Vertex 或 Microsoft Foundry 路由（CI/CD play 会介绍部署选项）。配置要求 code owner 批准的分支保护策略也值得启用。

如何执行

  1. 托管式 Code Review 服务是最快的起点：管理员启用它并选择仓库。当你需要掌控流水线，或希望 API 调用走自己的云协议时，可以用 claude-code-action 在自己的 CI 中运行评审（CI/CD play 会介绍相关管线）。
  2. 技术负责人把评审策略写成仓库根目录的 REVIEW.md，按组织关心的维度拆成多个评审过程：bug 与逻辑错误；安全与漏洞；对照规格（需求 play 的 spec.md）、实施计划（计划模式 play 的 plan.md）和设计原则的合规性。REVIEW.md 还要定义什么算 Important、什么算 Nit，以及哪些内容可以跳过。
  3. 技术负责人设定人工阈值。发现项本身既不批准也不阻塞 PR，分支保护仍然要求 code owner 批准。想要根据发现项给合并设卡的平台工程师，可以读取 check run 发布的严重程度计数——它是一份机器可读的汇总。
  4. 当评审者或作者在评审评论中标记 @claude，Claude 就处理这条意见并推送修复。PR 会话同时记录请求和变更。这个修复回路通过 claude-code-action 运行。在托管服务中，评论 @claude review 则是请求一次全新评审。对于 Claude 自己开的 PR，可以更进一步，让 Claude 照看这个 PR 直到合并。一些团队把这个回路包装成自定义斜杠命令：扫描 PR 上未解决的评审评论和失败的检查，逐一处理并推送修复，直到 PR 变绿、只等 code owner 批准。
  5. 评审发现项回流到 CLAUDE.md。当某个错误第二次被评审标出，纠正方法就作为那次评审的一部分写入 CLAUDE.md；因为评审会读 CLAUDE.md，从下一个 PR 起这个错误就会被拦住。评审还会标记 CLAUDE.md 因某次变更而过时的情形。
  6. 技术负责人每月一次对设置做调优：为发现项打分让评审者进步，并在 REVIEW.md 中限制 Nit 数量。生成的路径和 CI 已强制的内容被排除在外。

- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

治理考量

职责分离得以保留，因为写代码的智能体没有能力批准它。REVIEW.md 中的评审策略应用于所有 PR，发现项、修复、评分和批准都记录在 PR 历史中，因此 PR 本身就是审计记录。批准来自人类，通过分支保护完成，并以发现项作为参考。

关于这些控制手段如何在生产规模上组合，请参阅Anthropic 如何保障其 AI 原生 SDLC 的安全。

如何衡量
领先指标
首次评审时间（应当缩短到分钟级），以及不需要人触碰分支就得到解决的评审评论占比（数据直接存储在 Git 上）。
滞后指标
合并前拦下的缺陷与漏洞，对比逃逸到生产的那些，数据来自 PR 历史和事故跟踪系统。

用 Hooks 做审批关卡

构建阶段把 hooks 用作护栏，在无人类参与的情况下放行或拦截动作（阶段 3：Build）。hook 也可以"询问"——把动作挂起，直到特定的人批准——这正是发布门控所需要的。

这个 play 放在阶段 5：Deploy，是因为发布关卡是最典型的场景，但 hooks 并非部署专用：Claude 在哪里行动，它们就在哪里运行。比如在阶段 3：Build 中，hooks 可以在没有变更工单的情况下阻止对迁移和基础设施的编辑；在阶段 4：Test 中，可以阻止智能体在修复任务中编辑测试文件。

如何起步
前提条件
无。
基础设施
一份书面清单，列出变更流程所要求的各项审批。

如何执行

  1. 工程管理层会同变更管理和合规部门，列出必须保留的人工审批关卡，例如变更管理签核、发布授权，以及对受保护路径的编辑。
  2. 平台工程师把每个关卡表达为一个 hook——一段在 Claude 行动之前运行的脚本，可以放行、询问或拦截。
  3. 团队级的 hooks 放进 git 中的 .claude/settings.json，没有商量余地的 hooks 放进由平台或 IT 管理员持有的托管设置（managed settings），个别工程师无法关掉它们。
  4. 拦截应当自我解释：当 hook 拦下一个动作时，原因和获得批准的途径会出现在 Claude 的输出里。

治理考量

Hooks 就是审批关卡。关卡条件每一次、对每一个人都被强制执行。放行和拦截的决定连同时间戳一起被记录。关卡还定义了什么算作批准——是一张已批准的变更工单，还是发布经理的签核。

CI/CD 集成与部署

在 CI/CD 流水线内以非交互方式运行 Claude Code，对执行做沙箱隔离，让长时间运行的智能体安全工作，通过 MCP 集成暴露部署能力，并在智能体真正需要之前预演回滚路径。

传统方式流水线运行确定性的脚本，任何需要判断力的事情都等人来处理，例如分诊 flaky 测试、撰写 changelog，或排查构建为什么挂了。部署和回滚是人顶着压力照着执行的 runbook。
AI 原生方式Claude 在流水线内部以非交互方式处理需要判断的步骤，运行在带受限凭据的沙箱中。部署工具通过 MCP 暴露给智能体，因此编写并测试了这次变更的那条工作流，也能在组织按环境定义的关卡之内发布它、回滚它。
如何起步
前提条件
Claude 进入 PR 评审回路，以及用 hooks 做审批关卡——因为在自动化加速通过之前，关卡必须先存在。
基础设施
装好 claude-code-action 的 CI 平台，或任何能调用 claude -p 的 runner；通过 API 或 Bedrock、Foundry、Vertex 获得模型访问（当流量必须留在组织的云协议内时用后者）；面向部署目标的 MCP 服务器；一个不给常驻生产凭据的智能体任务沙箱配置。

如何执行

  1. 平台工程师从只读的判断型步骤开始：在流水线任务中用 claude -p 分诊失败的构建、总结 flaky 测试，或起草 changelog。
  2. 在既有关卡之后加入写入型步骤，比如修 lint、更新生成的文档，或通过 @claude 提及处理评审意见。智能体写入的任何内容都以 PR 的形式到达，经过分支保护，智能体没有任何途径直接推送到 main。
  3. 执行被沙箱隔离。智能体任务运行在带网络策略的容器中，使用短时效的受限令牌，默认不持有任何生产凭据。
  4. 通过 MCP 暴露部署。部署、状态和回滚变成按环境限定的工具，智能体的部署权限是一份白名单，而不是一个揣着凭据的 shell 脚本。
  5. 按环境分层放权。在开发环境，智能体自由部署；在生产环境，智能体准备发布、发布经理授权，一个 hook 强制执行生产关卡；staging 介于两者之间。
  6. 回滚应当是流水线中被演练得最多的路径：一条智能体也能运行的单一命令，并且经常在 staging 中演练。闭环 play（阶段 6：Maintain）会在控制带被突破时调用这个回滚，所以它必须提前被证明可用。

治理考量

治理原则是：智能体可以一路行动到生产关卡，但不能越过它。以下控制手段强制执行这条原则。

  • 分支保护把智能体写入的任何东西都变成 PR，没有直达 main 的路径。
  • 生产部署 hook 会一直拦截发布，直到指定的发布经理授权。每次非交互运行都以智能体自己的身份进行，因此流水线日志能区分智能体做的事和触发它的工程师做的事。
  • 按环境的权限分层，决定智能体在通往关卡的路上能做多少。
如何衡量
领先指标
无需叫醒人就完成分诊的流水线故障占比，数据取自 CI/CD 流水线日志。
滞后指标
DevOps Research and Assessment（DORA）指标，CI 系统和部署工具本身就会产出。
06

Maintain（维护）

闭环合拢。一个触发器在无人参与的调用路径下唤起 Claude，它发现的东西以 intent.md 的形式重新进入流水线。

维护与闭环

到目前为止，我们讨论的都是如何把 Claude 加入 SDLC 的每个阶段，每个阶段都需要一个人来启动最初的步骤。而这个阶段的重心，转向让 Claude 自主运行、把环闭合起来。

例如，一个持续运行的监控智能体可以在一张 bug 工单创建之后，据此写出 intent.md，并一路走完需求、计划、构建、测试和评审各环节。阶段 6：Maintain 以无人值守（headless）方式运行，各阶段之间设有一道独立的置信关卡——一次确定性检查或一个对抗式评审智能体——来决定上一阶段的产出是继续流转，还是上报给人类。

传统方式维护是被动的。所有工单或事故都等着人来处理并重启流程。凌晨三点的告警可能被错过，工单可能一直躺在 backlog 里无人认领，而复盘产出的行动项只要又起了别的火，可能根本到不了代码库。
AI 原生方式控制带被突破、工单、频道消息或日程表这样的触发器，在路径中无人的情况下唤起 Claude。Claude 做诊断，只通过受关卡约束的路径行动，并把发现写成 intent.md，随后走上面描述的各个阶段。人负责分诊和评审这些工作，而不再需要发起它们。

闭环

一个确定性脚本盯着生产环境，在控制带被突破时唤起 Claude。对"突破的监控"是这个闭环自主运转模式的一个好例子，本阶段末尾的 Claude Tag（public beta）小节则覆盖经其他渠道到来的工作。

如何起步
前提条件
intent.md——它给闭环一个结构化的输出来重新启动；Claude 加速过的 PR 评审；作为行动边界的 hooks；以及 CI/CD 的回滚路径（最高自治层级会调用它）。
基础设施
一个检测脚本可查询的指标存储（Prometheus、CI 系统的 API 或等价物）；仓库的读权限；在 CI 中以非交互方式运行 Claude Code 的途径，或用于接收 webhook 的服务的 Agent SDK。

如何执行

  1. 服务负责人或平台工程师挑选一个滚动基线稳定的指标，例如 CI 测试失败率、部署后 5xx 率，或 PR 周期时间。
  2. 他们编写检测脚本，通常是在滚动窗口上计算均值和标准差，并配上规则（Western Electric 或类似规则），让控制带既能抓到尖峰也能抓到缓慢漂移。脚本有版本管理和单元测试，检测完全确定性，不涉及任何模型。
  3. 响应分层定义在有版本管理的配置里（下面的 bands.yaml）。1σ 时脚本只记录日志；2σ 时它以只读方式调用 Claude 做诊断；3σ 时 Claude 可以行动，但仅限于向评审关卡发起 PR，或触发一个预先批准的 runbook。
  4. 触发层可以是 GitHub 或 GitLab 中的定时工作流、现有监控体系发来的 webhook，或网络内的 Cron Job。Claude 以无状态方式运行——要么作为 CI runner 上的非交互步骤，要么作为沙箱容器中的 Agent SDK 服务——CI/CD play 介绍了部署和模型访问的选项。因为运行是无状态且非交互的，一个闭环可以在没有任何人启动的情况下开始和结束。
  5. 智能体把诊断写成阶段 1：Plan 格式的 intent.md，涵盖异常及其证据、预期结果、受影响的系统和任何开放问题。从那里起，这个发现和别的东西一样走完整条流水线。
  6. 服务负责人或值班工程师分诊队列，把面向产品的发现转给产品负责人。立即修、排期，还是驳回。驳回会反过来校准控制带，帮助降低噪声。
  7. 修复上线时，为这次事故补一个评估（持续评估 play），确保此类问题今后有防护。

            routes: [pull_request, runbook:rollback-deploy] }

治理考量

分层边界从有版本管理的配置中强制执行，权限和托管设置拒绝生产访问。调用、发现和分诊决定连同时间戳一起被记录。由服务负责人分诊并批准发现，产出的变更走正常的 PR 评审关卡，智能体可以触发的 runbook 都是事先批准过的。

如何衡量
领先指标
从控制带突破到 intent.md 进入分诊队列的时间，与旧的从事故到复盘行动的时间对比。检测脚本的日志记录了突破的时间戳和事故层级。
滞后指标
最终变成已合并修复的发现占比（分诊队列对照实际 PR 历史），以及同类事故的重复发生次数——随着修复把用例补进评估套件，它应当下降。

示例

  • 当 CI 测试失败率突破 3σ，智能体隔离 flaky 测试或发起一个 revert PR，由评审关卡裁决。
  • 当部署后 5xx 率在窗口内有部署的情况下突破 3σ，智能体触发现有的回滚流水线。
  • 当 PR 周期时间触发漂移规则，智能体给工程管理层写一份报告——这说明这套机制对流程指标和对生产指标一样有效。
检测保持确定性。控制带一旦被突破就唤起 Claude，由层级决定它可以做什么。

定期代码库扫描

一次安全扫描，是"某个代码库在某个模型之下"的时点性结论，而这两半都会过期：代码每周都在变，而每一代模型都能发现上一代漏掉的漏洞。AI 原生的答案是按计划运行扫描，调用路径中没有人类，并把发现的东西送进与代码库其他变更相同的那套关卡。

Claude Security 是定期扫描的托管形态。连接一个 GitHub 仓库，扫描就会在 Anthropic 的基础设施上以 Claude Mythos 5 运行，每个发现先经过验证再上报，并附带置信度评分。建议的补丁在网页版 Claude Code 中评审和应用。组织不需要接触模型本身就能拿到这些发现。

传统方式安全扫描是一个事件：发布或审计之前发起一次扫描。报告送进跟踪系统，靠人工消化 backlog 直到下一个事件。期间写的代码，只能靠 PR 评审碰运气来覆盖。
AI 原生方式扫描按计划对每个已连接的仓库运行，用的是当前能力最强的模型，发现项在任何人读到之前就经过验证。每个发现都按控制带被突破的方式来处理：一个 PR 装得下的修复走评审关卡，更大的改动变成 intent.md。覆盖时间从上一次运行算起，而不是从第一次。
如何起步
前提条件
PR 评审关卡和作为审批关卡的 hooks（阶段 5：Deploy），让发现项像其他变更一样走评审；来自 阶段 1：Plan 的 intent.md 格式，用于装不进单个 PR 的大型发现。
基础设施
Claude Security 已面向 Claude Enterprise 组织开放 public beta。它需要在目标仓库（云端托管的 github.com）上安装 Anthropic GitHub App、启用网页版 Claude Code、开启 Extra Usage 并设置支出上限、为运行扫描的人员配备高级席位，并由管理员在 claude.ai/admin-settings/claude-code 打开该功能。扫描按 Mythos 5 费率按量计费，因此支出上限应与仓库的数量和规模相匹配。

如何执行

  1. 安全负责人连接各仓库，并按仓库、服务或团队把它们组织成项目，这样发现项的归属从一开始就是清楚的。
  2. 对最关键的仓库做首次全量扫描，包括那些曾被其他工具或更早的模型扫描过的。把首次扫描当作基线。第一次扫描很可能在被认为干净的代码里翻出发现项。
  3. 按项目设置计划。对活跃开发的服务，每周是一个合理的默认值；仓库很大或内容混杂时，把扫描范围限定到某个目录或分支。
  4. 拿着置信度评分分诊发现项。驳回时要写明理由，让驳回被记录下来，同一个发现就不会在下一次运行中作为新发现再次出现。
  5. 对于边界清晰的发现项，在网页版 Claude Code 中打开建议的补丁，评审它，然后像其他任何变更一样送进 PR 评审关卡。提出修复的智能体没有任何途径批准它。
  6. 对于超出单个补丁范围的问题，比如架构弱点或跨服务重复出现的模式，按阶段 1 的格式写成 intent.md，从 Plan 开始走流程。
  7. 当修复发布到生产环境时，把这一类漏洞的用例补进持续评估 play 的套件，从此引导智能体的那份配置就针对这一类漏洞接受了测试。
  8. 把发现项导出为 CSV 或 Markdown，或使用 webhook，让组织现有的跟踪和审计系统继续充当系统记录——审计师本来就预期它们在那里。

治理考量

扫描在组织的管理员控制之下运行：连接哪些仓库、谁持有扫描席位、支出上限是多少，都集中设定。每个发现项都有验证结果和置信度评分，每次驳回都有理由，因此扫描历史本身就是一份审计记录：发现了什么、修复了什么，以及有意识地接受了什么。

修复经由 PR 评审关卡和分支保护抵达生产，而不是从扫描本身直接出去。Claude Security 是对现有静态分析和依赖扫描的增强。确定性检查留在 CI，模型驱动的扫描则覆盖那些上下文相关的、确定性检查天生找不到的漏洞。

如何衡量
领先指标
已纳入定期计划的已连接仓库占比，以及从发现项被报告到其补丁进入 PR 评审关卡的时间，数据来自扫描历史和 PR 元数据。
滞后指标
定期扫描发现的漏洞，对比生产环境或外部报告发现的漏洞（来自事故跟踪系统）；以及经过多轮扫描的仓库上"每次扫描发现项"的趋势——随着修复和评估的累积，它应当下降。

用 Claude Tag 让 Claude 值班

事故也可能经由其他渠道到来，比如 Slack 或 Teams 这类办公沟通应用。事故可能是晚上十点事故频道里一条要求紧急修复的 Slack 消息，现在它可以被立即处理。Claude Tag（目前已在 Slack 开放 public beta）让 Claude 以自己的身份成为这些频道的成员，于是每起新事故都有了一个第一响应人，而响应过程本身也成为闭环的一部分，成为未来事故的记忆。

对话和机构知识留在频道里，频道中的任何人都可以引导并执行响应。任何团队成员都可以实时验证假设、探索新方案、开展调查，频道历史同时增强了可审计性。借助对 MCP 的访问，Claude 确认指标回到基线并在会话里确认，把复盘写进一份带版本管理的经验教训文件，供未来的调查读取。

Claude Tag 接的活不止事故。无论是通过 MCP 在工单上被标记，还是在频道里被问到，Claude 都以同样的方式分诊工作：一个小的、边界清晰的修复以 PR 的形式走评审关卡；更大的改动写成 intent.md 进入阶段 1：Plan。到这一步，闭环开始自我供给。参见：Claude Tag 如何在 Anthropic 为 CI/CD 值班。
