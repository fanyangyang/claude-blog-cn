Claude Fable 5 实战指南：发现你的未知项

Anthropic 团队分享的 Claude Fable 智能体式编码实践：如何在实现之前、之中和之后发现你的未知项。

使用 Claude Code 时，我常常想起地图与疆域（the map and the territory）的区别。

地图是对待完成工作的描绘，是我的提示词、Skills 和上下文，也就是我交给 Claude 的东西。疆域则是工作真正发生的地方——代码库、真实世界，以及它实际存在的约束。

地图与疆域之间的差异，我称之为未知项（unknowns）。当 Claude 遇到未知项时，它需要基于对我意图的最佳猜测来做决定。要做的工作越多，Claude 可能遇到的未知项就越多。

Claude Fable 是第一个让我觉得：工作质量的瓶颈，在于我阐明这些未知项的能力的模型。

重要的是，仅靠提前规划并不总是足够。你可能在实现深处才发现未知项，也可能这些未知项恰恰在提示你：这个问题其实应该换一种方式来解决。

我发现，与 Fable 协作是一个迭代的过程：在实现之前、之中和之后，不断发现我的未知项。 

认清你的未知项

你的未知项是什么？当我带着一个问题来找 Claude 时，我通常会从 4 个方向拆开：

  • Known Knowns：基本上就是我提示词里已经写明的东西。我告诉 agent 我想要什么？
  • Known Unknowns：哪些事情我还没想清楚，但我知道自己还没想清楚？
  • Unknown Knowns：哪些事情太理所当然，我永远不会写下来，但一旦看见就能认出来？
  • Unknown Unknowns：哪些事情我根本没考虑过？我不知道自己还缺哪些知识？我知不知道一件事能做到多好？

最出色的 agentic coder 未知项相对很少。看 Boris 或 Jarred 写提示词，我一眼就能感觉到他们非常清楚自己要什么。他们和代码库、和模型行为都处在深度同步的状态。 

但他们也会把未知项算进计划里。在很多方面，减少未知项、并为未知项做准备，就是 agentic coding 这项技能。好在这是一项可以练的技能，而且练的方式就是和 Claude 一起工作。

帮 Claude 帮你

给 Claude 下指令需要一种精细的平衡。太具体，Claude 会照着走，哪怕中途转向更合适；太含糊，Claude 又常常按行业最佳实践做选择和假设，而这些未必适合你手头的任务。

如果你没有把未知项算进去，两种情况都会失手。你不知道哪段路会布满障碍，也不知道哪段路其实很畅通，但你仍然希望 Claude 拐一拐。

Claude 能帮你更快发现未知项。它可以极快地检索你的代码库和互联网，对大多数主题知道的也比你多。它从失败里迭代，也比你更快。

这个过程最重要的一步，是把你的起点告诉 Claude。比如，告诉它你现在想到哪一步了；说明你对这个问题和代码库的经验；让它像思想搭档一样和你一起想。

实现前

Blind Spot Pass

开工时最有用的事情之一，就是搞清楚自己的盲区。比如，你要在代码库一块不熟悉的地方写功能，或用 Claude 帮你做设计迭代这类不熟悉的工作，你很可能有大量unknown unknowns。

你可能不知道该问什么问题、好的标准是什么、历史上做过哪些工作，或该躲开哪些坑。

这种时候，可以让 Claude 帮你找出 unknown unknowns，并解释给你听。我喜欢直接用 “blind spot pass” 和 “unknown unknowns” 这两个词。把你是谁、你已经知道什么告诉它，通常很重要，这样 Claude 才知道该怎样开始和你协作。

示例提示词：

  • “I'm working on adding a new auth provider but I know nothing about the auth modules in this codebase. Can you do a blind spot pass to help me figure out my relevant unknown unknowns and help me prompt you better.”
  • “I don’t know what color grading is but I need to grade this video. Can you teach me to understand my unknown unknowns about color grading, so that I can prompt better?”

头脑风暴和原型

当我在一块充满unknown knowns 的领域工作时，也就是那些标准只有看见才说得清的标准，我喜欢让 Claude 和我一起头脑风暴、做原型。 

在原型阶段尽早识别并说清 unknown knowns 非常值钱，因为拖到实现阶段再发现，（相对来说）会贵很多。功能或规格上的小变化，会在代码里带来完全不同的实现，而让 agent 回退先前的改动也会更难。

比如，你可能只想看看在一个 frame 上加一颗按钮长什么样，并不想接后端路由，也不想在前端再维护一份状态。

另一个例子是视觉设计。对我来说，它很难用语言讲清楚，但我看见就知道自己要什么。这种时候，我会要同一件 artifact 的几种设计方向。 

我几乎每次编码会话都会先做一轮探索或头脑风暴。这能帮我带着意图去界定项目范围。Claude 常常会找到我自己会漏掉的高价值路径，有时也会只见树木不见森林。头脑风暴能避免我把范围定得太窄或太宽。 

示例提示词： 

  • "I want a dashboard for this data but I have no visual taste and don't know what's possible. Make me an HTML page with 4 wildly different design directions so I can react to them.”
  • “Before wiring anything up, make a single HTML file mocking the new editor toolbar with fake data. I want to react to the layout before you touch the real app."
  •  "Here's my rough problem: users churn after onboarding. Search the codebase and brainstorm 10 places we could intervene, from cheapest to most ambitious. I'll tell you which ones resonate."

访谈

头脑风暴做够之后，我多半仍有未知项。

这时我会让 Claude 就任何未知项或含糊之处采访我。让 Claude 采访你时，尽量把问题的上下文给它，好引导它的问题。 

‍示例提示词：

  • "Interview me one question at a time about anything ambiguous, prioritize questions where my answer would change the architecture."

参考

有时你没法把想要的东西讲细。比如你没有那套语言，或事情太复杂，讲清楚要花很久。

这时最好的办法就是参考。你可以放示意图、文档或图片，但最好的参考绝对是源代码。 

如果你有一个以某种方式实现某事的库，或一个你很喜欢的设计组件，直接把 Fable 指到那个文件夹，告诉它该看什么，哪怕语言不同也没关系。相比截图，这能给 Claude 丰富得多的标记和结构细节。

示例提示词：

  • "This Rust crate in vendor/rate-limiter implements the exact backoff behavior I want. Read it and reimplement the same semantics in our TypeScript API client."

实现计划

当我觉得可以动手实现时，我通常会让 Claude 先写一份实现计划给我审。计划会聚焦那些最可能改动的部分，比如数据模型、类型接口或 UX 流程。这样 Claude 就能把我真正可能要改的东西摊开来。 

示例提示词：

  • "Write an implementation plan in HTML, but lead with the decisions I'm most likely to tweak with: data model changes, new type interfaces, and anything user-facing. Bury the mechanical refactoring at the bottom, I trust you on that part."

实现中

实现笔记

计划满意之后，我会开一个新会话，把相关 artifact 放进提示词。这样 Claude 有一个干净的上下文窗口，同时又带着规划阶段整理出的全部信息。比如，我可能会放入一份规格文件和一个原型，然后让 agent 去实现。

但事实是，无论你规划多少，未知的未知项总会藏在某处。agent 可能在工作中发现，因为代码里的某个边界情况，必须换一条路。

我会让 Claude Code 维护一份临时的 ‘implementation-notes.md’（或 .html）文件，记下它做的决策，好让我们下次尝试时能学到东西。 

示例提示词：

  • "Keep an implementation-notes.md file. If you hit an edge case that forces you to deviate from the plan, pick the conservative option, log it under 'Deviations', and keep going."

实现后

提案和讲解

把东西做出来之后，最重要的一步往往是拿到认同和批准。  在最终文档里做提案和讲解 artifact 能帮你：

  • 当评审者一开始带着和你一样的未知项时，加快他们的理解
  • 当专家想确认你已经考虑到他们会预见到的未知项和常见失败点时，加快批准

示例提示词：

  • "Package the prototype, the spec, and the implementation notes into a single doc I can drop in Slack to get buy-in. Lead with the demo GIF."

测验

一次长会话之后，Claude 可能已经做完了远超我意识到的工作。只看代码 diff，我对发生了什么只能有浅层理解，因为很多行为取决于已有的代码路径。

先给 Claude 一批上下文，再让它就这次变更考我，能帮我搞清楚到底发生了什么。我只有在测验全对之后才会合并。

示例提示词：

  • “I want to make sure I understand everything that's happened in this change. Give me a HTML report on the changes for me to read and understand with context, intuition, what was done, etc. and a quiz at the bottom on the changes that I must pass.”

这些如何凑在一起：发布 Fable

Fable 的发布视频从头到尾都是用 Claude Code 剪的。这对我是一个新领域，我也绝不是专家。  

所以我从自己已经知道的地方起步。我知道 Claude 能用代码剪视频、做转写，但不确定够不够准。然后我让 Claude 给我讲 Whisper 这类转写是怎么工作的，以及我能不能用 ffmpeg 准确切掉 um、长停顿之类的东西。

我希望 Claude 做一个和我说的词对齐的 UI，但不确定做不做得成，于是我让 Claude 用 Remotion 加一份转写做一段原型视频，看看能不能跑通。

最后，视频本身看起来有点闷，我知道这和调色有关，但我其实不太懂什么是调色。我第一轮想让 Claude 先做几个变体给我选，后来发现自己并不知道调色里的「好」长什么样。于是我改让 Claude 教我调色，好发现我的未知项。 

让地图对上疆域

模型越好，正确方法能做成的事就越多。当一项长周期任务交回来是错的，多半是你需要花更多时间定义未知项，或写一份能让你和 Claude 在未知项里调整的实现计划。 

每一份讲解、每一次头脑风暴、每一场访谈、每一个原型、每一份参考，都是在修复成本变高之前，便宜地找出你不知道的东西。 

所以，下一个项目开始时，先让 Claude 帮你找出未知项。
