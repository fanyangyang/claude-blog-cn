用 MCP 构建能触达生产系统的 agent

Patterns for building effective MCP integrations: server design, OAuth with CIMD and vaults, context-efficient clients, and skills. Plus where MCP fits alongside direct API calls and CLIs for connecting agents to your systems.

Agent 的价值取决于它能触达的系统。团队在将 agent 连接到外部系统时，往往会收敛到三种方式——直接 API 调用、CLI 和 MCP。这篇文章将梳理各自的适用场景、为什么生产级 agent 最终往往落在 MCP 上，以及构建这类集成的一些有效模式。

将 agent 连接到外部系统

我们大体上看到三种连接 agent 与外部系统的路径：直接 API 调用、CLI 和 MCP。每种都有其合理的使用场景，取决于你在构建什么。关键的区别在于：agent 与服务之间是否存在一个公共层，以及这个层能覆盖多远。

直接 API 调用

Agent 直接调用你的 API——要么在代码执行沙箱中编写发出 HTTP 请求的代码，要么通过一个通用的函数调用工具。这是大多数团队的起点，在单个 agent 对接单个服务、或者少量无需跨 agent 平台复用的集成场景下运转良好。
规模一大，问题就来了。由于 agent 与服务之间没有公共层，每一对 agent 与服务的组合都成了一次定制集成，各自需要处理认证、工具描述和边界情况——这就是 M×N 集成难题。

命令行界面（CLI）

Agent 在 shell 中运行你的命令行工具。这种方式快速、轻量，还能复用既有的工具链。它非常适合本地环境和沙箱容器——任何有文件系统和 shell 的地方。这提供了一个公共层，但这个层很薄。
在触达那些不提供容器的移动端、Web 或云端托管平台时，CLI 会遇到硬性限制；认证则依赖 CLI 自身的机制——通常是磁盘上的凭证文件。这种方式最适合本地环境中快速、权限宽松的集成。

模型上下文协议（MCP）

MCP 以协议的形式提供这个公共层。Agent 连接到一个暴露你系统能力的服务器，认证、能力发现和丰富的语义都是标准化的。一个远程服务器可以触达任何兼容的客户端（Claude、ChatGPT、Cursor、VS Code 等），适用于任何部署环境。

它需要一些前期投入，回报则是集成的可移植性，以及功能丰富的 agent 集成所需的语义能力。

生产级 agent 运行在云端

越来越多的生产级 agent 运行在云端，以便能够弹性扩缩并持续运转。它们需要触达的系统也在云端：数据存放的地方、工作被跟踪的地方、基础设施运行的地方。这些系统往往是远程的、需要认证的，而这正是 MCP 提供公共层的地方。 当这些系统位于私有网络而非公共互联网上时，Claude Managed Agents 中的 MCP 隧道可以通过仅出站（outbound-only）连接将 agent 接入它们——无需暴露任何端口或公共端点。

我们已经从实际采用中看到了这一点。MCP SDK 的月下载量最近突破了 3 亿次，而年初只有 1 亿次，企业和主流 agentic 平台都在大量采用。每天有数百万人通过 Claude 使用 MCP，该协议也是我们最近发布的众多产品的基础，包括 Claude Cowork、Claude Managed Agents，以及 Claude Code 中的 channels。

随着 MCP 持续支撑生产级 agentic 系统，我们在这里分享一些把这些集成做好的模式：从构建高级服务器到上下文高效的客户端，以及 skills 在哪些方面与协议互补。

构建高效的 MCP 服务器

我们的目录中有超过 200 个 MCP 服务器，每天有数百万人使用。通过与在该协议上构建的企业和开发者密切合作，我们总结出了几个决定 agent 能否可靠使用一个服务器的设计模式。

构建远程服务器以获得最大触达

远程服务器才能真正带来分发能力——这是唯一能在 Web、移动端和云端托管 agent 上运行的形态，也是所有主流客户端优化对接的目标。构建远程服务器，让 agent 在任何运行环境中都能使用你的系统。 

按意图而非端点组织工具

数量更少、描述清晰的工具，效果始终好于一整套 API 的镜像。不要把 API 一比一地包装成 MCP 服务器——按意图组织工具，让 agent 用两三次调用就能完成一项任务，而不是把一堆原语拼接起来。一个 create_issue_from_thread 工具胜过 get_thread + parse_messages + create_issue + link_attachment。完整模式的更多内容请参阅为 agent 编写高效的工具。

当操作面很大时，为代码编排而设计

如果你的服务需要数百种不同的操作——比如 Cloudflare、AWS 或 Kubernetes——按意图分组的工具集很可能覆盖不过来。此时应暴露一个接受代码的薄工具面：agent 编写一段简短的脚本，你的服务器在沙箱中针对你的 API 运行它，只返回结果。Cloudflare 的 MCP 服务器是参考范例——两个工具（search 和 execute）用约 1K token 覆盖了约 2500 个端点。

在有价值的地方提供丰富语义

MCP Apps 是第一个官方协议扩展，它允许工具返回交互式界面——如图表、表单或仪表盘——并直接内嵌渲染在聊天界面中。提供 MCP apps 的服务器，其采用率和留存率往往明显高于只返回纯文本的服务器。用它把你的产品 UI 在关键时刻呈现给 agent 或最终用户——该扩展已在 Claude.ai、Claude Cowork 和许多其他主流 AI 工具中获得支持。

‍Elicitation 允许你的服务器在工具调用中途暂停，向用户征求输入。Form 模式发送一个简单的 schema，由客户端渲染原生表单——用它来补齐缺失的参数、确认破坏性操作或澄清选项。URL 模式则把用户引导到浏览器——用它来完成下游 OAuth、支付，或收集任何绝不应经过 MCP 客户端的凭证。这两种模式都让用户留在原有流程中，而不是被甩到一个设置页面。Form 模式已被广泛支持；URL 模式已在 Claude Code 中获得支持，更多客户端正在跟进。

依赖标准化认证

标准化认证让 MCP 对云端托管的 agent 切实可行。如果你的服务器需要 OAuth，最新的 MCP 规范支持 CIMD（Client ID Metadata Documents）用于客户端注册——它给用户带来快速的首次认证流程，也大幅减少了出人意料的重复认证提示。这是我们推荐的认证方式，该能力已在 MCP SDK、Claude.ai 和 Claude Code 中获得支持，并正在业界得到广泛采用。
用户完成授权后，下一个问题是云端托管的 agent 如何在运行时持有并复用这些令牌。Claude Managed Agents 中的 Vaults 解决了这个问题：只需注册一次用户的 OAuth 令牌，在创建会话时按 ID 引用 vault，平台就会向每个 MCP 连接注入正确的凭证并代你刷新——不需要自建密钥存储，也不需要在每次调用时传递令牌。

让 MCP 客户端更省上下文

MCP 标准化了 AI agent（客户端）连接并使用所需工具和数据源（服务器）的方式。服务器安全地暴露一系列能力，客户端则负责编排这些能力并管理上下文。如果你在构建 MCP 客户端，可以用渐进式披露（progressive disclosure）的模式让它更省上下文。

用工具搜索按需加载工具定义

工具搜索（Tool search）不预先加载所有工具，而是推迟把它们装入上下文的时机，让 agent 在运行时检索工具目录，按需拉取相关工具。在我们的测试中，工具搜索通常能减少 85% 以上的工具定义 token，同时保持很高的选择准确率。 

用程序化工具调用在代码中处理工具结果

程序化工具调用（Programmatic tool calling）在代码执行沙箱中处理工具结果，而不是把原始结果直接返回给模型。这让 agent 可以用代码在多次调用之间循环、过滤和聚合，只有最终输出进入上下文。在我们的测试中，这在复杂的多步骤工作流上能减少约 37% 的 token 用量。

这些模式可以自然地组合并跨多个服务器发挥作用：更精简的上下文、更少的往返、更快的响应。完整分析请参阅 advanced tool use。

将 MCP 服务器与 skills 搭配使用

Skills 与 MCP 是互补的。MCP 让 agent 能够访问外部系统的工具和数据，而 skills 则教给 agent如何用好这些工具来完成实际工作的过程性知识。最强大的 agent 会同时使用两者，而 skills 能让 MCP 服务器的价值扩展到远不止几条连接。组合它们有两种通用模式：

将 skills 和 MCP 服务器打包为插件

Claude 的 插件（Plugins）是一个有用的抽象，让开发者可以把 skills、MCP 服务器、hooks、LSP 服务器和专用 subagent 打包成一种易于消费的分发方式。采用这种方式，是以最小摩擦统一多个上下文提供方的最佳途径。
把 MCP 服务器与 skills 结合起来，能让 Claude 的表现更像一位领域专家：通过 MCP 获得工具，再通过 skills 让 Claude 端到端地编排工作流。可以参考我们为 Cowork 提供的数据插件作为示例，它由 10 个 skills 和 8 个 MCP 服务器组成，覆盖 Snowflake、Databricks、BigQuery、Hex 等应用。

通过 MCP 服务器分发 skills

越来越常见的做法是服务提供方在发布 MCP 服务器的同时附带一个 skill，这样 agent 既能获得原始能力，也能得到一份用好这些能力的最佳实践手册。Canva、Notion、Sentry 等都已在 Claude 中这样做了，在我们的网页目录中，skill 就列在它们的连接器旁边。

为了让这种搭配在每个客户端间都可移植，MCP 社区正在积极推进一项扩展，支持直接从服务器分发 skills。这样客户端就能自动继承相关的专业知识，并随其依赖的 API 一起进行版本管理。我们预计随着该扩展趋于稳定，这种模式会得到广泛采用。

复利累积的那一层

文章开头我们讲了连接 agent 与外部系统的三条路径。实践中，成熟的集成会三者兼有：以 API 为基础，为本地优先环境提供 CLI，用 MCP 服务云端 agent。

随着生产级 agent 迁移到云端，MCP 成为关键的一层，而且是能够复利累积的一层。今天，一个远程服务器可以触达任何部署环境中的所有兼容客户端，认证、交互性和丰富语义都由协议处理。随着更多客户端采用规范、更多扩展落地，同一个服务器无需你发布任何新东西就会变得更强。

在构建集成时，如果你的目标是让云端的生产级 agent 触达你的系统，那就构建一个 MCP 服务器，并用上述模式把它做到出色。每一个构建在 MCP 之上的集成都在强化这个生态：需要独自解决的边界情况更少，需要维护的定制集成也更少。
