使用 Claude Code：会话管理与 1M 上下文

阅读英文原文 →

我们发布了 /usage，一个新的斜杠命令，帮助你了解自己在 Claude Code 中的使用情况。这个功能的诞生源于与客户的多次交流。 

在这些沟通中反复出现的一个话题是：用户管理会话的方式千差万别，尤其是在 Claude Code 新近升级到 100 万上下文之后。

你是只开一两个会话一直挂在终端里，还是每条提示词都开个新会话？你什么时候用 compact、回退（rewind）或 subagent？什么会导致一次糟糕的压缩或糟糕的会话？

这里的细节多得惊人，而这些细节实实在在地决定了你使用 Claude Code 的体验，而且几乎全部源于管理你的上下文窗口。

上下文、压缩与上下文腐朽速览

上下文窗口是模型在生成下一条回复时能一次性"看到"的全部内容。它包括系统提示词、到目前为止的对话、每一次工具调用及其输出，以及所有已读取的文件。Claude Code 拥有一百万 token 的上下文窗口。

遗憾的是，使用上下文会轻微影响性能，这种现象常被称为"上下文腐朽"（context rot）。上下文腐朽指的是：随着上下文增长，模型性能会下降，因为注意力被摊薄到更多 token 上，而较早的、已不相关的内容会开始干扰当前任务。

上下文窗口是硬性上限，所以当你接近上下文窗口的尽头时，你一直在做的任务会被自动总结成一段更短的描述，模型随后在新的上下文窗口中继续工作。我们称之为压缩（compaction）。你也可以自己触发压缩。

每一轮都是一个分叉点

假设你刚让 Claude 做完一件事——此时上下文里已经有一些信息（工具调用、工具输出、你的指示），而下一步怎么做，你拥有的选项多得惊人：

  • 继续——在同一会话中发送下一条消息
  • /rewind（连按两次 esc）——跳回之前的某条消息，从那里重新来过
  • /clear——开一个新会话，通常附上你从刚才的收获中提炼出的简报
  • 压缩——总结当前会话，然后在摘要的基础上继续
  • Subagent——把下一块工作委托给一个拥有干净上下文的 agent，只把它的结果拉回来

虽然最自然的做法是直接继续，但另外四个选项都是为帮你管理上下文而存在的。

什么时候该开新会话

什么时候保持一个长会话，什么时候另起一个？我们的经验法则是：开始新任务时，也应该开始新会话。

100 万的上下文窗口意味着你现在可以更可靠地完成更长的任务，比如从零构建一个全栈应用，但上下文腐朽仍可能发生。 

有时你会做一些相关联的任务，其中部分上下文仍然必要，但并非总是如此。例如，为你刚实现的功能编写文档。虽然你可以开个新会话，但那样 Claude 就得重新读一遍你刚实现的那些文件，反而更慢也更贵。

用回退代替纠正

在 Claude Code 中，连按两次 Esc（或运行 /rewind）可以让你跳回之前任意一条消息并从那里重新提示。该节点之后的消息会从上下文中丢弃。 

回退往往是比"口头纠正"更好的做法。例如，Claude 读了五个文件，尝试了一种方案，行不通。你的直觉可能是输入"这不行，改试 X"。但更好的做法可能是回退到刚读完文件之后，带着你学到的东西重新提示："别用方案 A，foo 模块没有暴露那个接口——直接上 B。" 

你也可以使用"从这里开始总结"或 /rewind 斜杠命令，让 Claude 总结它的经验教训并生成一份交接信息——有点像未来的 Claude（试过某方案失败了）给上一版 Claude 留的话。

压缩还是另起全新会话

会话一旦变长，你有两种办法甩掉多余的上下文：/compact 或 /clear（重新开始）。它们感觉相似，行为却大不相同。

压缩是让模型总结到目前为止的对话，然后用摘要替换历史。它有信息损耗，但你无需亲自动笔，而且 Claude 或许会把重要的经验教训和文件收录得更全面。你也可以通过传入指令来引导它（/compact focus on the auth refactor, drop the test debugging）。

使用 /clear 时，由你写下重要的内容（"我们在重构认证中间件，约束是 X，关键文件是 A 和 B，方案 Y 已被排除"），然后干干净净地开始。这更费工夫，但留下的上下文正是你判断为相关的内容。 

什么会导致糟糕的自动压缩？

如果你经常运行长会话，可能已经注意到某些时刻压缩效果特别差。我们发现，糟糕的压缩往往发生在模型无法预判你工作方向的时候。 

在上面的例子中，自动压缩在一场漫长的调试会话后触发，把调查过程做了总结，而你的下一条消息是"现在修复我们刚才在 bar.ts 里看到的另一个警告"。 

但由于整个会话都聚焦在调试上，那个警告可能已经在摘要中被丢掉了。

这尤其棘手，因为受上下文腐朽影响，模型在压缩时正处于智能的最低点。 有了 100 万上下文，你就有更充裕的时间带着对接下来要做什么的描述去主动 /compact。 

Subagent 与干净的上下文窗口

Subagent 在你预知某块工作会产生大量后续不再需要的中间输出时，往往很好用。

当 Claude 通过 Agent 工具生成一个 subagent 时，这个 subagent 会获得自己全新的上下文窗口。它想干多少活都行，最后把结果综合好，只有最终报告会回到父级那里。

我们在 Anthropic 内部常用的判断标准是：我之后还需要这些工具输出本身，还是只要结论？ 

虽然 Claude Code 会自动调用 subagent，但你可能需要明确让它这么做。例如，你可以告诉它：

  • "生成一个 subagent，根据以下规格文件验证这项工作的结果"
  • "派一个 subagent 通读另一个代码库，总结它是如何实现认证流程的，然后你自己照着同样的方式实现"
  • "派一个 subagent 根据我的 git 改动为这个功能编写文档"
