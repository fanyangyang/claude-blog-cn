构建 Claude Code 的经验：我们如何使用 Skills

我们在 Anthropic 内部构建并规模化数百个 skills 的收获。

Skills 已经成为 Claude Code 中使用最广泛的扩展机制之一。它灵活、易于创建，也易于分发。

但这种灵活性也让人难以判断怎样用才最有效。什么样的 Skills 值得去做？Skill 应该如何组织结构？什么时候适合分享给他人？

在 Anthropic，我们大规模地在 Claude Code 中使用 Skills，目前处于活跃使用状态的就有数百个。以下是我们利用 Skills 加速开发的经验总结。

什么是 Skills？

Skills 是由指令、脚本和资源组成的文件夹，智能体可以发现并使用它们，从而更准确、更高效地完成任务。本文假设读者已了解 Skills 的基础知识；如果你是新手，建议先学习我们在 Skilljar 上的智能体 Skills 入门课程。

我们经常听到一个关于 Skills 的误解：它们“只是一些 markdown 文件”。实际上，Skills 是文件夹，可以包含脚本、素材、数据等，智能体能够发现、探索并操作这些内容。 

在 Claude Code 中，Skills 还拥有丰富多样的配置选项，包括注册动态 hooks。

我们发现，Claude Code 中最有效的一些 Skills，正是充分利用了这些配置选项和文件夹结构的那些。

Skills 的类型

把 Anthropic 内部的 Skills 全部盘点一遍之后，我们注意到它们聚成九类。最好的 Skills 干净地落在其中一类；想做太多的那些会横跨好几类，并把智能体搞糊涂。这不是一份定论清单，但它是一个有用的框架，用来找出你自己的 Skills 库还缺什么。 

1. 库与 API 参考

这类 Skills 解释如何正确使用某个库、CLI 或 SDK。对象既可以是内部库，也可以是 Claude Code 有时不太会用的常见库。它们通常会带上一文件夹参考代码片段，以及一份给 Claude 写脚本时避开的陷阱清单。

例如：

  • billing-lib — 你的内部计费库：边界情况、踩坑点等。
  • internal-platform-cli — 内部 CLI 包装器的每一条子命令，以及何时使用它们的示例。
  • sandbox-proxy — 为开发工作配置组织的出口网关：哪些主机可达，如何调试 “connection refused”，如何加一条 allowlist 条目。

2. 产品验证

这类 Skills 描述如何测试或验证你的代码是否在工作。它们常常和 playwright、tmux 或其他外部验证工具配对。

在我们内部，验证类 Skills 对 Claude 输出质量的可测影响最大。值得让一位工程师花上一整周，只把验证 Skills 做到出色。

可以考虑让 Claude 把自己的输出录成视频，这样你能精确看到它测了什么；也可以在每一步对状态强制做可编程断言。这些通常靠在 Skill 里放进各种脚本完成。

例如：

  • signup-flow-driver — 在无头浏览器里走完注册 → 邮箱验证 → 引导，并在每一步用 hooks 断言状态
  • checkout-verifier — 用 Stripe 测试卡驱动结账 UI，验证发票真的落到正确状态
  • tmux-cli-driver — 用于需要 TTY 的交互式 CLI 测试

3. 数据拉取与分析

这类 Skills 接到你的数据和监控栈。它们可能包含带凭证拉取数据的库、具体的仪表盘 id 等，以及常见工作流或取数路径的说明。

例如：

  • funnel-query — 「要看注册 → 激活 → 付费，该 join 哪些事件」，以及真正持有规范 user_id 的那张表
  • cohort-compare — 比较两个队列的留存或转化，标出统计显著的差异，并链到分群定义
  • grafana — 数据源 UID、集群名、问题 → 仪表盘查找表
  • datadog — 字段对照（@request_id vs trace_id）、服务列表、指标前缀约定

4. 业务流程与团队自动化

这类 Skills 把重复工作流收成一条命令。它们通常是相当简单的指令，但可能对其他 Skills 或 MCP 有更复杂的依赖。对这类 Skills 来说，把以往结果存进日志文件，能帮助模型保持一致，并对照该工作流的历史执行做反思。

例如：

  • standup-post — 汇总工单系统、GitHub 动态和此前的 Slack → 格式化站会，只报增量
  • create-<ticket-system>-ticket — 强制 schema（合法枚举值、必填字段），再加上创建后工作流（提醒审查者、在 Slack 里贴链接）
  • weekly-recap — 已合并 PR + 已关闭工单 + 部署 → 格式化周报

5. 代码脚手架与模板

这类 Skills 为代码库里的特定功能生成框架样板。你可以把它们和可组合的脚本搭配使用。当你的脚手架带有自然语言要求、单靠代码覆盖不住时，它们尤其有用。 

例如：

  • new-<framework>-workflow — 用你们的注解脚手架出一个新服务/工作流/handler
  • new-migration — 你们的迁移文件模板，外加常见陷阱
  • create-app — 新建内部应用，预接好你们的鉴权、日志和部署配置

6. 代码质量与审查

这类 Skills 在组织内强制代码质量，并帮助审查代码。它们可以包含确定性脚本或工具，以追求最大稳健性。你可能希望它们作为 hooks 的一部分、或在 GitHub Action 里自动运行。 

  • adversarial-review — 拉起一个新上下文的子智能体来挑刺，落实修复，迭代到发现只剩吹毛求疵为止
  • code-style — 强制代码风格，尤其是 Claude 默认不太会写好的那些。
  • testing-practices — 关于如何写测试、测什么的说明。

7. CI/CD 与部署

这类 Skills 帮助你在代码库里拉取、推送和部署代码。它们可能引用其他 Skills 来收集数据。

例如：

  • babysit-pr — 监控一个 PR → 重试不稳定的 CI → 解决合并冲突 → 打开自动合并
  • deploy-<service> — 构建 → 冒烟测试 → 按错误率对比逐步放量 → 回归时自动回滚
  • cherry-pick-prod — 隔离 worktree → cherry-pick → 解决冲突 → 按模板开 PR

8. Runbooks

这类 Skills 接住一个症状（比如 Slack 线程、告警或错误签名），走完一次多工具调查，并产出结构化报告。

例如：

  • <service>-debugging — 为流量最高的服务把症状 → 工具 → 查询模式映射起来
  • oncall-runner — 拉取告警 → 检查常见嫌疑人 → 格式化发现
  • log-correlator — 给定一个 request ID，从所有可能碰过它的系统里拉出匹配日志

9. 基础设施运维

这类 Skills 执行例行维护和操作流程，其中一些涉及破坏性动作，因而受益于护栏。它们让工程师在关键操作里更容易按最佳实践走。

例如：

  • <resource>-orphans — 找出孤儿 pod/volume → 发到 Slack → 浸泡期 → 用户确认 → 级联清理
  • dependency-management — 你们组织的依赖审批工作流
  • cost-investigation — 「为什么存储/出口账单突然飙了」，带上具体的 bucket 和查询模式

制作 Skills 的技巧

决定要做哪个 Skill 之后，该怎么写？下面是 Claude Code 团队制作 Skills 的一些最佳实践、技巧和窍门

别说显而易见的事

Claude 已经会写代码，也能读你的代码库。一个只是复述 Claude 默认就会做的事情的 Skill，只会增加上下文，不增加价值。如果你发布的 Skill 主要关乎知识，就把重点放在能把 Claude 推出惯常思路的信息上。

frontend design skill 是很好的例子；它由 Anthropic 的一位工程师和客户反复迭代，用来提升 Claude 的设计品味，避开 Inter 字体和紫色渐变这类经典套路。 

建一个 Gotchas 小节

任何 Skill 里信号最强的内容，都是 Gotchas 小节。这些小节应当从 Claude 使用你的 Skill 时常见的失败点长出来。理想情况下，你会随时间更新 Skill，把这些陷阱收进去。

例如：

“subscriptions 表是只追加的。你要的那一行是 version 最高的那条，不是 created_at 最近的那条。”“这个字段在 API 网关叫 @request_id ，在计费服务叫 trace_id。它们是同一个值。”“即使 Stripe webhook 其实没处理成功，预发环境也会返回 200。真实状态去查 payment_events 。”

利用文件系统和渐进披露

正如前面所说，一个 Skill 是一个文件夹，而不只是一个 markdown 文件。你应当把整个文件系统想成一种上下文工程和渐进披露。告诉 Claude 你的 Skill 里有哪些文件，它会在合适的时候去读。

最简单的渐进披露，是指向其他 markdown 文件给 Claude 用。例如，你可以把详细的函数签名和使用示例拆到 references/api.md。

另一个例子：如果最终产出是一个 markdown 文件，你可以在 assets/ 里放一份模板文件，让它复制后使用。

你可以准备参考文档、脚本、示例等文件夹，帮助 Claude 更有效地工作。

描述写给模型看，不是写给人看

Claude Code 启动一次会话时，会列出每个可用 Skill 及其 description。这份清单就是 Claude 扫描「这次请求有没有对应 Skill？」的依据。因此 description 字段不是摘要，而是何时触发这个 Skill 的说明。

帮 Claude 记住

有些 Skills 可以通过在内部存数据，带上某种记忆。你可以存进只追加的文本日志或 JSON 文件这么简单的东西，也可以存进 SQLite 数据库这么复杂的东西。

例如，一个 standup-post Skill 可以维护一份 standups.log，记下它写过的每一条，于是你下次再跑时，Claude 会读自己的历史，并说出从昨天到现在变了什么。 

你可以用环境变量 ${CLAUDE_PLUGIN_DATA} 拿到一个稳定目录来存数据，关于在 Skills 里持久化数据的更多内容见： https://code.claude.com/docs/en/plugins-reference#persistent-data-directory。

使用按需 hooks 

Skills 可以包含只在该 Skill 被调用时激活、并且只在本次会话期间有效的 hooks。把它们留给那些你不想一直开着、但有时极其有用的、更有态度的 hooks。

例如：

  • /careful — 通过 Bash 上的 PreToolUse matcher 拦截 rm -rf、DROP TABLE、force-push、kubectl delete。你只想在知道自己在碰生产时打开它——一直开着会把人逼疯。
  • /freeze — 拦截不在指定目录里的任何 Edit/Write。调试时很有用：「我想加日志，却总是一不小心把无关代码也『修』了。”

分发 Skills

Skills 最大的好处之一，是你可以和团队其他人分享它们。

和别人分享 Skills，大致有两种方式：

  • 把 Skills 检入仓库（放在 ./.claude/skills）
  • 做成 plugin，并准备一个 Claude Code Plugin marketplace，让用户可以上传和安装 plugins（详见文档）

对跨不多几个仓库工作的小团队来说，把 Skills 检入仓库就很好用。但每一个检入的 Skill 也会给模型上下文添一点东西。规模上去之后，内部 plugin marketplace 让你可以分发 Skills，让团队自己决定安装哪些，还可以带上初始化流程。

管理 Skills marketplace

如何决定哪些 Skills 进 marketplace？人们怎样提交？

在 Anthropic，我们没有一个中心团队来拍板；我们试着让最有用的 Skills 自然长出来。如果有人有一个想让别人试试的 Skill，他们可以把它上传到 GitHub 的 sandbox 文件夹，并在 Slack 或其他论坛里把链接指给大家。

一旦一个 Skill 有了势头（这由 Skill 所有者自己判断），他们就可以提 PR，把它搬进 marketplace。

组合 Skills 

你可能希望 Skills 互相依赖。例如，你可能有一个上传文件的 Skill，还有一个生成 CSV 并上传的 Skill。这类依赖管理目前还没有原生做进 marketplace 或 Skills，但你可以直接按名字引用其他 Skills，只要它们已安装，模型就会调用它们。

衡量 Skills

为了了解一个 Skill 表现如何，我们用一个 PreToolUse hook 记录公司内的 Skill 使用情况（示例代码在此）。这样我们就能找出受欢迎的 Skills，或触发次数低于预期的那些。

开始使用

Skills 的最佳实践仍在演进。我们最好的 Skills，大多始于几行字和一个陷阱，然后因为人们在 Claude 撞上新边界情况时不断往里加东西而变好。 

理解 Skills 最好的办法就是动手、试验，看看对你什么管用。
