在 Google Cloud 上管理 Claude Code 成本并展示 ROI

在 Google Cloud 上管理 Anthropic 的 Claude Code 成本并衡量投资回报的最佳实践。

随着组织将越来越多的任务委托给 Claude Code，支出也随之增长，平台团队既需要控制成本，也需要理解其影响。受 与 Google Cloud 合作的近期网络研讨会 (opens in new tab) 的启发，我们在此分享使用 Claude Code 的组织如何在 Google Cloud 上更好地跟踪和优化这些考量，包括三大核心杠杆：控制（Control）、跟踪（Track）和证明（Prove）。

控制 Claude Code 支出

Claude on Google Cloud 采用按用量计费的模式，因此你的账单直接反映了开发者在你的 Google Cloud 环境中使用了多少 Claude。采用推动使用；使用量正是你所支付的，也是价值所在。

你的 Claude Code 账单取决于任务消耗的 token 数量以及处理这些任务的模型。Token 消耗随任务复杂度和对话长度而增长。聊天是问答式对话。像 Claude Code 这样的代理（agentic）工具在每项任务上消耗的 token 比聊天更多，因为它要做多步骤的工作：读取文件、运行工具，并在整个任务中进行推理。与此同时，每个模型都有各自的每 token 价格，因此让模型匹配任务是另一项主要的成本控制手段。

每月影响组织账单的 token 与模型选择，可以通过 Claude apps gateway 和 Google Cloud 服务进行查看。你可以通过三个相互独立的杠杆来治理支出、管理成本：

  • 控制（Control）。建立护栏来引导使用，而不是过度限制访问、意外地挡住用户。
  • 跟踪（Track）。在账单到来之前，对支出发生在哪里、以及未来将流向哪里进行细粒度监控。
  • 证明（Prove）。识别你的组织从这些 token 支出中获得的价值，并精确归因其来源。

以下是如何将控制 → 跟踪 → 证明这一框架应用到你自己在 Google Cloud 上的 Claude Code 部署中。

治理工具箱

Claude on Google Cloud 提供了用于控制、跟踪和证明支出价值的工具与能力。

Google Cloud 已经提供了许多可用于跟踪和控制 Claude 支出的原生能力：

  • 按项目计费（Per-project billing）。允许你为 Claude Code 托管一个专用项目，作为跟踪成本的干净方式。
  • 账单预算与提醒（Billing budgets and alerts）。允许你设置预算提醒，并在实际支出超过你设定的阈值时收到通知。
  • 支出上限（预览版，Spend caps (Preview)）。允许你强制执行服务级别的 Google Cloud 支出预算，并支持手动解除上限。
  • BigQuery 导出。让你可以将 Claude 支出与其余云成本一起分析。
  • 配额（Quotas）。Google Cloud 上的 Claude 模型对每个模型系列和端点位置，在请求、输入 token 和输出 token 上设有每分钟限制。
  • 预置吞吐量（Provisioned throughput）。为预留容量支付固定费用，而不是按量付费。

Claude Code 和 Claude apps gateway 则提供了各自的跟踪与控制能力。Gateway 是一项自托管服务，随开发者已经在使用的同一个 claude 二进制发布，运行在你 Google Cloud 项目中、位于 Claude Code 与 Claude on Google Cloud 之间。开发者通过你的身份提供商（例如 Google Workspace）登录，因此每个请求都带有经过验证的身份。这使你能够按 IdP 组设置模型白名单，并按用户、IdP 组或组织设置每日、每周或每月的支出上限。

以下是如何选择并组合这些能力，以管理衡量你在 Claude on Google Cloud 上的 AI 投资成本与 ROI 的三大杠杆：

杠杆一：控制

控制杠杆的核心是提供引导开发者在 Claude Code 使用中的护栏，而不是用任意的上限来限制他们。

引导而非限制之所以重要，是因为高成本会话未必是坏事——事实上，它们往往具有高价值，尤其是在 Claude Code 中。这些会话通常来自你的高级用户，他们站在前沿，使用新的工作流，从 Claude 中获得大量价值，也完成了大量工作。

浪费往往集中在重度使用者的中间地带。例如，他们用 Fable 处理一个 Sonnet 就能轻松搞定的日常任务；或者他们忘记了某个不再关心的定时任务，而它还在继续自动运行。

有四个功能可以为你提供引导用户而非限制用户的护栏：

  • 支出上限（Spend limits） (opens in new tab)。Claude apps gateway 允许你按用户、IdP 组或组织范围设置每日、每周或每月的支出上限。组和组织级上限是每位开发者继承的默认值，而非共享池。
  • 阈值提醒（Threshold alerts）。与 Claude apps gateway 配合使用时，Claude Code on Google Cloud 会在开发者接近上限时发出警告，先是超过 75% 时，再是超过 95% 时。这些是面向开发者的 CLI 内警告，而 Google Cloud Billing 提醒则面向管理员。达到上限时，gateway 会返回 429，直到周期重置或管理员提高上限；你也可以通过 gateway 的管理 API 编写脚本来自动提高上限。
  • 模型默认值与白名单（Model defaults and allowlists）。通过 Claude apps gateway 指定每个 IdP 组可用的模型，gateway 会在服务端对每个请求强制执行白名单。我们发现设置模型默认值效果非常好，因为大多数人会坚持使用默认模型；如果他们想切换模型，通常是出于某个原因。你可以将模型默认值与模型白名单搭配使用，或单独使用其中一种。
  • Gateway 管理 API（Gateway Admin API）。Gateway 提供了支出上限管理 API (opens in new tab)，因此你可以通过编程方式设置和更改上限，例如使用工单工作流。

组合这些能力来控制你的整体账单，但要记住，控制只是第一个杠杆。每 token 价格并不能给你全貌。最重要的指标是每任务成本（cost per task），它可以通过跟踪使用情况来监控和分析。

杠杆二：跟踪

这个杠杆的核心是看清支出的去向以及它是如何被使用的。好消息是，你可以跨组织跟踪 Claude Code 的使用量、成本和工具活动。主要的跟踪策略包括：

  • 使用量与成本的可观测性（Usage and cost observability）。Claude Code 的 OpenTelemetry 指标与事件 (opens in new tab)会按技能（skill）、插件（plugin）、agent 和 MCP server 报告使用量和估算成本。通过 OpenTelemetry 收集器或由 Claude apps gateway 转发（用于集中式 OpenTelemetry 配置），以 OpenTelemetry Protocol (OTLP) 将这些数据发送到你已在运行的工具（例如 Google Cloud Monitoring）。
  • 终端用户使用视图（End-user usage view）。开发者可以直接在 Claude Code 中看到自己的支出并在触及限制前收到使用警告。
  • 向现有系统导出数据（Data export to your existing systems）。Google Cloud Billing 导出到 BigQuery 的功能让你可以按模型和 token 类型过滤 Claude SKU，将 Claude 支出与你其余的云和 AI 支出放在一起。OTel 数据流向你的可观测性（O11y）技术栈，而 gateway 管理 API 可以将支出上限状态直接送入你的工单系统。

Claude Code——无论是在开发者机器上还是在云工作站上运行——一旦启用即可导出 OpenTelemetry 数据，包括会话、活跃时间、代码行数、提交、拉取请求、token 和成本，并按用户、团队和模型细分。Claude Code 的最新版本还按技能、插件、agent 和 MCP server 细分使用情况，让你不仅能看到整体 Claude Code 使用量，还能看到你组织内部技能和插件的采用情况。使用 Claude apps gateway 时，你无需配置每台机器。在 gateway 上设置一个遥测目标，它就会为已登录的开发者开启遥测。它还会用开发者登录时验证过的邮箱和 IdP 组标记每次导出，而不是使用客户端配置的值。

要将使用量归因到你自己的成本中心和部门，可以设置 OTEL_RESOURCE_ATTRIBUTES 环境变量（例如 department=engineering,cost_center=eng-123）。Claude Code 会将这些标签添加到每个指标和事件中，因此你可以按这些标签进行过滤和聚合。这些指标会带着这些自定义属性落入 Google Cloud Monitoring（或其他监控方案，如 Grafana 或 Splunk）。

典型的采用视图会显示活跃开发者数量、过去 24 小时的会话数以及消耗的 token 总数。橙色框显示的是开发者在触及 gateway 强制执行的支出上限时被阻止的请求。该指标与现有的工单系统搭配得很好，可以作为允许开发者申请提高上限的工作流。

如需现成的 Cloud Monitoring 仪表盘，请参考 Claude Code Monitoring 模板 (opens in new tab)，它将 Claude Code 的 OpenTelemetry 指标转化为采用情况、编码活动和 token 使用量及估算支出的单一视图，让你在 Google Cloud 上推广 Claude Code 时能够按用户和模型跟踪使用量与成本。你可以直接从 Cloud Monitoring 控制台复制该模板。

若要在 Google Cloud 上设置自定义的 Claude Code 遥测，可以从 Claude Code OTel 快速入门 (opens in new tab)开始。用它来配置 Claude Code，将 OpenTelemetry 直接导出到 Google Cloud 可观测性套件（包括 Cloud Logging 和 Cloud Monitoring）。该快速入门还会将日志路由到分区 BigQuery 表（每种事件类型一张表：API 请求、工具决策、工具结果、助手响应和已完成的 hook 执行），并提供用于按开发者/模型分析支出的 SQL 查询，以及工具成功率与延迟、hook 等待时间、每轮和每会话分析。

杠杆三：证明

控制杠杆负责治理和分配使用量与成本；跟踪杠杆让你可视化这些支出。证明杠杆则是将使用情况映射到 Claude Code on Google Cloud 的 ROI。

平台工程师最关心的 Claude Code 衡量指标包含三个维度：使用情况、开发者满意度和影响。

采用与使用（Adoption and usage）指标衡量组织中人们如何使用 Claude，包括已激活用户及其每周和每日使用情况。这些指标揭示诸如使用深度、随时间的用户留存情况，以及谁是你们组织的 Claude Code 高级用户等信息。这些指标全部来自 Claude Code 的 OTel 数据。

满意度（Satisfaction）指标监控工程师的用户体验，包括他们对 Claude Code 的满意度、感知的时间节省、对输出的信心，以及可能遇到的摩擦。满意度指标来自推广前后运行的一次简短调查，以及后续的持续用户回访。

影响（Impact）指标评估 Claude 如何交付可衡量的工程成果，将吞吐量、周期时间和评审速度与基线进行比较，并对特定的工作成果进行定性衡量。

一套起步用的影响指标

以下是一套起步用的影响指标，分为三个领域：时间、投入和产出量。

时间（Time）衡量工作交付的速度：PR 从创建到合并的周期时间，以及代码评审周转时间。

投入（Effort）衡量每项变更投入的工作量：每个 PR 的评审迭代次数、每个 PR 的评审评论和返工量。

产出量（Volume）衡量释放出来的产能带来了什么：每位工程师的 PR 数、部署频率，以及具名工作成果（named bodies of work）：团队用释放出的产能交付的具体积压事项。这些在数量之外增加了定性视角。

这些是方向性的参考点，而非硬性规则，但它们是衡量 Claude Code 在你组织中影响的良好起点。你需要的基线已经存在：你在源码控制和工单系统中的交付历史。

定义你的工作单元

这些指标大多统计 PR 数量，但一个错别字修复和一个功能发布都是一个 PR。因此，改为统计某一明确定义类别的已合并 PR：Claude 打开 PR，由人来决定它是否发布。诸如 hotfix 或 feature release 之类的标签、工单 ID，以及 Claude 是否参与其中，都能让你在你已运行的系统中轻松找到这些 PR。并非每个工作单元都是 PR；服务切换或从根因上关闭的事故也是例子。同样的规则适用：统计一件完成的事，落在哪里就在哪里统计。

Claude Code 原生遥测

在落实成本治理和使用跟踪之后，下一步是将这些映射到 ROI。Claude Code 的原生遥测帮助你捕获贡献度和生产力指标，从而记录你的组织获得的价值。

Claude Code 的 OTel 指标让你能够跟踪或推导出代码建议接受率、修改的代码行数、创建的提交数、创建的 PR 数、单位产出的成本以及每位用户的 PR 数。

所有这些原生指标都提供了有用且可操作的信息。当这些信息与通过 Claude Code telemetry on Google Cloud (opens in new tab) 捕获的诸如用户提示和工具决策等记录事件相结合时，会更有价值。例如，记录用户提示是了解你的用户群正在尝试构建什么的好方法，因为并非每个工作单元都必然是 PR。请注意，由于提示可能包含敏感内容，用户提示不会自动记录；你必须显式选择启用。

举个例子：如果你是一名 SRE，可以用 Claude Code 排查事故；如果你是一名销售工程师，可以用它生成现场演示的示例数据。这些会话不会产生 PR，但它们确实加速了这些团队的工作流。请记住，Claude Code 的 PR 指标统计的是 Claude Code 创建的 PR，而不是最终合并的 PR。你的源码控制和工单系统仍然是交付结果的记录来源，因此请将 Claude Code 遥测与 GitHub 或 GitLab 以及你的工单跟踪器关联起来，才能获得全貌。

以下是一些 Claude on Google Cloud 客户通过 Claude Code 取得的可衡量影响。

  • Delivery Hero (opens in new tab) 的一个团队重构了横跨 100 个 UI 组件的设计系统。Claude Code 用几分钟完成了通常需要工程师一周时间的工作。
  • Shopify (opens in new tab) 的工程师借助 Claude Code 更快地构建，但非工程师也在用几分钟而不是几天的时间构建内部工具。Claude Code 正在扩大 Shopify 中"谁能构建"的范围，而不仅仅是加快已经在构建的人的速度。
  • Fifth Dimension (opens in new tab) 的工程师普遍在 Google Cloud 上使用 Claude Code。他们合计每月编写超过 30 万行代码，接受率达 98%。

开始使用

这篇文章的目标是帮助你熟悉现有的工具和能力，以便管理 Claude Code on Google Cloud 的成本并展示 ROI。作为平台工程师，这套体系不仅用于观察用户群中的行为，还为你提供动态调整治理和设置所需的知识。

这是一个持续循环：从合理的默认值开始，例如组织范围的支出上限、默认模型和模型白名单，然后随着使用数据的到来，按角色和团队进行细化。通过跟踪实际使用情况并将指标与你从 Claude Code 获得的价值相关联，你就可以将这些交付给需要分析使用 Claude Code 的 ROI 和业务影响的相关方。

随着我们委托给 Claude 的工作量和类型不断加深、日趋多样，组织如何使用 Claude Code on Google Cloud 以及从这种使用中获得的价值也都会不断演变。这里概述的 控制 → 跟踪 → 证明框架是衡量你 Claude Code 部署的每个方面和成果的稳定起点。
