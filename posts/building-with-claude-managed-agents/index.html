智能体界面的演进：使用 Claude Managed Agents 构建生产级智能体

As model intelligence and agentic harnesses evolve, Anthropic's Claude Managed Agents allows teams to build and deploy agents in production environments reliably at scale. Here’s why and how teams are using it.

让一个智能体进入生产环境，靠的不只是一个好提示词。智能体需要一个地方来运行它写的代码、访问你数据所需的凭证、可观测的会话，以及能随用量扩展的基础设施。在 Applied AI 团队，我们的工作正处于产品、研究与基于 Claude 构建的客户的交汇点——我们反复看到同一种模式：基础设施是原型与生产级智能体之间的分水岭。太多团队把开发周期耗费在安全、状态管理、权限控制和 harness 调优上。 

Claude Managed Agents 是我们用于构建和部署生产级智能体的一套可组合 API，它把经过性能调优的智能体 harness 与生产级基础设施结合在一起，让团队能够在几天而非几个月内从原型走到上线。本文将介绍 Anthropic 智能体构建模块的演进历程、我们为什么构建 Claude Managed Agents，以及团队如今如何在生产中使用它。 

智能体架构的演进

2023 年我们向开发者开放 Claude 时，API 的设计刻意保持了简单：token 进，token 出。你发送一个提示词，Claude 返回一段补全，harness 和底层基础设施都由你自己搭建。

此后几年，API 的能力稳步增强，但底层契约从未改变：一次请求、一个模型回合，接下来发生什么由你的应用决定。很长一段时间里，这就够了。总结一份文档、对一个支持工单分类、改写一段文字——这些都是能轻松装进单个回合内的工作。

然而渐渐地，人们想交托出去的任务不再装得进单回合了。他们希望 Claude 把任务从头做到尾：查资料、动手执行、观察变化、决定下一步。他们还希望它运行在工作本就依赖的那些系统之中，比如代码库、内部 wiki 或工单系统。

在纯 API 的世界里，把 Claude 变成智能体意味着构建你自己的循环：问模型该做什么、运行工具、把结果喂回去，如此往复。你还要负责构建和部署智能体的脚手架，并随着模型演进不断调优。对需要完全定制化的智能体来说，这条路径是合理的。但对于那些更可预测、复杂度更低的智能体工作负载来说，随着模型和产品演进而不断优化 harness 就变得乏味了。 

Claude Code 是我们 2025 年推出的智能体编码工具，让 Claude 能直接与你的代码库交互。它内部包含了我们自研的那套 harness：循环、工具执行、子智能体、上下文管理，以及让它成为高效智能体的丰富能力。开发者自然希望能在自己的领域中，为自建智能体获得类似的 harness 机制。

为了支持团队在 Claude Code harness 之上构建智能体，我们发布了 Claude Agent SDK。Claude Agent SDK 让开发者能够用运行 Claude Code 的同一套机制构建自己的智能体，而不必维护自制的循环。对许多团队而言，智能体正是从这时起变得切实可行：harness 天然针对 Claude 调优，自带基础设施原语，并且随着 Claude Code 的演进而持续改进。

不过，即便有了 harness，在生产环境中部署智能体仍然充满挑战，原因有以下几点：

  • 托管与扩缩。智能体在哪里运行？一个耗时数小时的任务，进程能存活多久？用量增长时靠什么扩容？ 
  • 会话管理。智能体的历史和进度存在哪里？一次运行能否在中断后恢复并继续？你能否回头查看之前会话里发生了什么？
  • 文件系统管理。真正干活就意味着产出制品：改代码、写文件、构建输出。智能体在哪里获得可操作的工作区？运行之间这个工作区又会怎样？
  • 执行隔离。Claude 写的代码必须在某处执行。如果代码出错，影响范围（blast radius）有多大？在生产环境中，什么样的隔离边界才真正值得信任？
  • 凭证。智能体需要访问你的系统。它如何获得访问权限，又不把你敏感的信息暴露给它自己生成的代码？
  • 可观测性。当智能体自主工作了一小时并做出意外举动时，你能否还原它走过的每一步？

借助 Agent SDK，上述生产基础设施中的许多要素都通过 Claude Code 的机制来提供。智能体获得一个真实的文件系统来工作，会话状态可持久化到本地或外部存储，可观测性则可通过 OpenTelemetry 导出到你现有的任何监控体系。

然而，随着越来越多团队的智能体从本地开发走向生产，他们需要一种方式在托管基础设施上规模化部署这些智能体。同时，模型及其周边 harness 变得越来越先进——运行时间更长、执行代码更多、触达系统更多、采取行动更多——扩缩、安全和沙箱化的难度也随之上升。

这些障碍中有几个都源于同一个架构决策：智能体 harness 往往与它所操作的文件系统运行在同一个容器里。容器必须先启动（付出启动成本），Claude 才能开始思考；智能体连同代码执行紧挨着你的凭证运行；容器一旦消亡，这次运行也随之湮灭。

Managed Agents 通过把大脑与双手解耦解决了这些问题。调用 Claude 的 harness 与执行代码的沙箱分开运行，而会话——一份只追加的日志，记录每一次模型调用、工具调用和结果——将两者连接起来。Claude 可以在任何容器存在之前就开始推理，沙箱与你的凭证保持足够距离，而一整次运行在任何时刻都可以从其会话中完整重建。

何时以及为何使用 Claude Managed Agents 

使用 Managed Agents 构建时，用户定义任务、工具和护栏，由 Anthropic 在我们的基础设施上运行智能体，并处理底层的智能体循环：如何为智能体提供调用工具的执行环境、出现故障时如何恢复、多智能体编排，等等。

当 harness 没有随模型智能同步演进时，智能体就会掉链子。在 Claude Sonnet 4.5 上，智能体临近上下文末尾时会仓促收尾，宁可提前结束工作也不用完剩余空间——这一模式被称为“上下文焦虑”（context anxiety）。我们的修复是在 harness 中加入上下文重置（context resets），把“Claude 在临近限制时需要帮助来保持连贯”这一假设直接内置进去。但这个假设没能活过下一代模型。到了 Claude Opus 4.5，这种行为消失了，我们加上的重置机制反而成了纯粹的负担。

对大多数组织来说，维护 harness 是一种无法为产品带来差异化的额外开销。harness 必须针对特定模型行为调优；压缩（compaction）、工具执行、缓存等原语在 Claude 上的工作方式与其他模型不同。有了 Claude Managed Agents，harness 会随模型一同演进，团队得以专注于真正让智能体产生差异化的东西：上下文管理和领域专业知识。 

为了让开发者能够配置构建高效智能体所需的上下文和工具，Managed Agents 围绕三种核心资源构建：智能体（agent）、环境（environment）和会话（session）。智能体是一份配置：一个模型、一个提示词、一组工具，以及围绕它们的护栏。环境是智能体运行所处的执行上下文：沙箱容器、它的网络规则和预装的软件包，托管在我们的云上或由你控制的基础设施上。每次运行是一个会话，它把一个智能体与一个环境配对，并获得自己独立的沙箱实例。会话在服务端持久化完整的事件历史、沙箱状态和输出，因此长时间运行的工作可以暂停、干净地恢复，事后还能逐步追溯。使用 Managed Agents，你可以只定义一次智能体和环境，然后随着工作负载的增长，在同一份配置上运行大量会话。

在 Managed Agents 上构建生产级和可扩展的系统

在 Applied AI 团队，我们见证智能体从原型走向生产，既发生在 Anthropic 内部，也发生在客户的系统里，横跨编码、财务、支持、法务等十几个领域。这让我们能清楚看到演示与生产就绪的智能体之间的差别，以及团队最容易卡住的地方。

下面我们分享在 Claude Managed Agents 这类托管服务上构建的最常见理由： 

1. 凭证不进入沙箱。当所有东西都跑在同一个容器里时，Claude 生成的代码就紧挨着你的凭证，提示词注入可能诱导模型读取自己的环境变量，从而泄露 token。我们固然可以在同一容器内设置严密的护栏来防范，但解耦架构提供了一条更安全的路径：让凭证完全留在沙箱之外。MCP、CLI 和 GitHub 仓库等工具所需的 token 存放在独立的 vault 中，由代理按需获取并解密。Managed Agents 提供Vaults，开箱即用地处理凭证，你无需自建密钥存储、无需每次调用都传输 token，也不会弄不清某个智能体是代表哪位终端用户行事的。Vault 中的凭证在存储前经过信封加密（envelope encryption）保护，取用时则需要经过签名的请求 token 进行验证。

2. 消除沙箱开销，降低延迟。延迟是许多企业团队最关心的指标，因为用户对等待 Claude 响应的感知非常敏锐。没有 Managed Agents 架构时，每个会话都必须启动一个容器——哪怕智能体只需要思考、根本不会运行任何工具。这部分启动时间纯属浪费，用户感受到的就是首个响应前的延迟。而使用 Managed Agents，Claude 立即开始推理，环境在并行中启动，从不运行工具的会话则完全跳过容器。这意味着用户看到第一个 token 无需等待容器启动，而当智能体需要运行什么时，环境已经就绪。在我们的测试中，中位数场景（p50）下首个 token 的时间缩短了约 60%，最慢场景（p95）下缩短超过 90%。 

3. 可靠、持久的会话，支撑会话管理、可观测性和记忆。Managed Agents 的思维方式不是请求/响应，而是事件。一个会话是一条持续的事件流：每一次模型调用、工具调用和结果，都会追加到一份位于智能体进程之外的日志里。基于这种架构，你可以在智能体工作时随事件流入获得实时更新，也可以稍后恢复任意会话，无需管理任何数据库或存档点。历史记录在交互之间一直保留（除非你删除会话），会话闲置时其容器会被打快照（checkpoint），你可以从暂停处干净地继续。而且由于整次运行本身就是一份事件记录，可观测性和记忆随之而来：Claude Developer Console 提供智能体会话的原生可视化时间线视图，以及让你深入检查任意会话记录的调试体验。Managed Agents 还附带记忆（Memory）和 Dreaming 等同样依赖这种会话持久性的功能。Dreaming 是一个按计划运行的进程，它会审阅你的智能体会话和记忆存储、提取模式并整理记忆，让智能体随时间不断进步。Dreaming 在会话之间打磨记忆，通过读取持久化的会话日志，从反复出现的错误和用户偏好中学习改进。

4. 在 Anthropic 托管或自托管云容器之间灵活选择。默认情况下，使用 Managed Agents 时，你可以把编排和工具执行都交给 Anthropic 托管的云容器。这让托管和扩缩变得简单省事，提供了更快的投产路径。正因为 Managed Agents 中大脑与双手是解耦的，双手可以放在任何地方——包括你自己的虚拟私有云（VPC）内。因此，我们也为希望掌控工具执行的团队提供自托管沙箱（self-hosted sandboxes），让智能体的代码、文件系统和网络出口永不离开你的环境。我们还提供 MCP tunnels，让你能把 Claude 连接到运行在你私有网络内的 Model Context Protocol（MCP）服务器。所以，自托管沙箱控制的是智能体代码在哪里执行，而 MCP tunnels 控制的是Anthropic 如何触达你网络中的 MCP 服务器，两者配合，让你能精确控制什么留在你的边界之内。

除上述功能外，还有更多能力，包括让智能体按评分标准（rubric）给自己打分的 outcomes、多智能体编排、权限策略和 webhooks。更多详情请见这里。

客户如今如何在 Managed Agents 上构建

在各个行业中，客户已经在用 Claude Managed Agents 把智能体推向生产。以下是几个例子：

  • Notion 在 Managed Agents 上运行其 Custom Agents：团队直接从任务看板给 Claude 派活，Claude 收集每个任务相关的文档、会议记录和已连接的数据，完成的代码、演示文稿和站点会回到工作区中等待审阅。数十个任务并行运行，他们团队曾这样描述一个早期原型：把大约十二小时的工作压缩成了二十分钟。
  • Rakuten 使用 Managed Agents 在产品、销售、营销和财务领域上线了多个专业智能体，每个都在大约一周内投入使用。 
  • Sentry 将其 Seer 调试智能体与一个负责编写补丁并发起 PR 的 Claude 智能体配对，由一名工程师在数周（而非数月）内建成。 
  • Asana 构建了在项目内认领任务的 AI Teammates，而 Atlassian 则把开发者智能体接入了 Jira 工作流。 

开始使用 Claude Managed Agents

我们构建 Managed Agents 的目标是：让你能通过 Claude Code 和 Claude Developer Console（platform.claude.com）尽可能轻松地启动智能体。例如，Console 的快速入门功能让你可以从智能体模板开始，或用自然语言描述一个智能体，然后把它变成一个可在几分钟内完成加固和部署的生产就绪智能体。

在 Claude Code 中，/claude-api skill 默认提供，为 Claude 提供构建 Claude Managed Agents 应用的详细、最新的参考资料。我们强烈建议你利用它获取设置 Managed Agents 应用的最佳实践。运行 /claude-api managed-agents-onboard 即可开始，它会以访谈式引导的方式，带你从零设置一个新的 Managed Agent。

托管智能体构建的未来

随着各团队分享他们在 Managed Agents 上的构建成果，我们看到：过去花在生产基础设施上的时间，如今投向了真正让智能体产生差异化的地方——管理上下文、为用户量身打造体验。现在，新模型发布后，你只需更新智能体让它使用新模型、重跑你的评测，就能把改进发布上线，完全不必触动底层架构。
