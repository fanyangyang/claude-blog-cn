如何以及何时在 Claude Code 中使用 subagent

A practical guide to Claude Code subagents: when they help, how to direct them, and the signals that tell you delegation is worth it.

Claude Code 擅长处理复杂的多步骤项目，但长会话会不断累积负担。读过的每个文件、走过的每条岔路、每个没想完的念头，都留在上下文窗口里，拖慢响应速度、推高 token 成本。

假设在一个大型 TypeScript monorepo 中开发一个新功能。主线工作是写实现，但支线任务层出不穷：查一下现有服务是怎么处理认证的、找一下格式化日期的共享工具函数、看看设计系统里有没有现成可用的相近组件。这些都不需要完整的项目上下文，放在主会话里执行只会增加噪音。要是能让它们并行运行呢？

subagent（子代理）应运而生。subagent 是一个拥有独立上下文窗口的隔离 Claude 实例。它接到任务、完成工作，然后只返回结果。可以把 subagent 理解为 Claude Code 会话的浏览器标签页：一个可以追踪岔路而不丢主线的去处。

在本文中，我们会讨论什么时候适合用 subagent、如何调用它们，以及什么时候不值得付出这点开销。

什么是 subagent？ 

subagent 是拥有各自上下文窗口、可独立运作的 agent。当 Claude 派生出一个 subagent 时，这个助手会独立地读文件、探索代码或进行修改。任务完成后，subagent 只把相关结果返回给主对话。

每个 subagent 都从头开始，不受会话历史或已调用 skills 的拖累。多个 subagent 可以并行运行，而且各自可以有不同的权限：一个研究型 subagent 可能只有只读权限，而一个实现型 subagent 则拥有完整的编辑能力。

Claude Code 内置了若干 subagent 类型，包括：

  • 通用 agent（General-purpose），用于复杂的多步骤任务
  • 计划 agent（Plan），在给出实现策略之前先研究代码库
  • 探索 agent（Explore），针对快速、只读的代码检索做了优化 

Claude Code 常会自行派生 subagent 来处理分配的任务。你也可以显式地引导这一行为，定义可复用的专家角色，让 Claude 自动把任务委派过去。知道什么时候该用 subagent，才能真正发挥这个功能的价值。 

什么时候应该用 subagent？ 

有几类工作明显受益于 subagent 委派。学会识别它们，能让这个功能的效果大幅提升。

研究密集型任务

当理解某件事的运作方式是修改它的前提时，subagent 可以探索代码库并返回一份摘要，而不是把几十个文件一股脑塞进对话。

信号：收集上下文需要读几十个文件。

收益：主对话保持干净，收到的是提炼后的结论而非原始内容。

多个相互独立的任务

修复多个文件中的错误、更新多个组件里的模式，或者做彼此不依赖的修改时，并行 subagent 能更快完成任务。

信号：子任务之间没有依赖关系。

收益：三个 subagent 同时工作，通常总耗时更短。

需要全新视角

当目标是获得对某份实现不带偏见的评审时，subagent 能提供一张白纸，因为它不继承主对话中的假设、上下文或盲区。

信号：需要验证，但不想让会话历史影响分析。

收益：更干净、更客观的反馈。

小技巧：/clear 命令同样会重置上下文和会话历史，提供类似的 unbiased 白纸，但代价是完全丢失这些历史。而 subagent 在获得同样全新视角的同时，主对话原封不动。

提交前的验证

在最终确定修改之前，一个独立的 subagent 可以验证实现是否存在过拟合测试或遗漏边缘情况的问题。

信号：提交代码前需要第二意见。

收益：能抓住因熟悉代码而被忽略的问题。

流水线式工作流

当任务有明显阶段划分（比如先设计、再实现、后测试）时，每个阶段都能从专注投入中受益。

信号：阶段按序推进，且有清晰的交接。

收益：每个 subagent 专注于自己的阶段，不被其他阶段的上下文干扰。

‍小技巧：当一项任务需要探索十个以上的文件，或包含三块以上相互独立的工作时，这就是让 Claude 转向 subagent 的强烈信号。

如何引导 subagent 的使用

调用 subagent 的方法有好几种，从简单对话到自动化工作流不等。正确的起点取决于你的工作流，随着模式逐渐清晰，可以逐步叠加更精细的手段。

对话式调用

最灵活的方式就是在对话中直接让 Claude 使用 subagent。这在所有 Claude Code 界面上都可行：终端、VS Code、JetBrains、网页版和桌面应用。 

能可靠触发 subagent 的自然语言表达包括：

  • “用一个 subagent 探索这个代码库里认证是怎么实现的”
  • “让一个单独的 agent 评审这段代码的安全问题”
  • “并行研究这个问题。同时检查 API 路由、数据库模型和前端组件”
  • “派几个 subagent 把不同 package 里的这些 TypeScript 错误修掉”

表达明确很重要。界定清楚范围，任务独立时明确要求并行执行，并描述期望的输出。

自定义 subagent
当同一类 subagent 被反复需要（一个安全评审员、一个测试编写者、一个文档校对员），就可以把它一次性定义为自定义 subagent。 
之后只要任务匹配其描述，Claude 就会自动委派给它，无需额外提示。
自定义 subagent 以 markdown 文件的形式存在，放在 .claude/agents/ （项目级，与团队共享）或 ~/.claude/agents/ （用户级，跨所有项目可用）。每个 subagent 拥有自己的系统提示词、工具权限，还可以配置专属模型。

CLAUDE.md 指令
自定义 subagent 定义了专家是谁，CLAUDE.md 文件则定义了 Claude 何时应该启用他们的规则。如果每次代码评审都应经过一个只读 subagent，或每个架构问题都应先触发一轮研究，CLAUDE.md 就是这条策略的安身之处。Claude 在每次对话开始时都会读取它，因此这一行为在会话之间、团队成员之间保持一致，谁都不必记得开口要求。
当满足以下情况时，CLAUDE.md 适合用来放置 subagent 指令：
  • 代码评审应始终使用只读 subagent

  • 需要在各成员和各会话之间保持行为一致

Skills
对于反复运行的复杂多步骤工作流，skills 提供了可复用的接口。在 .claude/skills/ 中定义一次 skill，之后用 /skill-name 调用，或者在任务匹配其描述时让 Claude 自动加载。
Skills 与 CLAUDE.md 文件的区别在于作用范围。CLAUDE.md 文件始终加载，塑造每一次交互；而 skill 按需加载——要么被显式调用，要么是 Claude 把当前任务与 skill 的 description 字段匹配上了。因此，那些“应该可用、但不必应用于每个提示词”的工作流，更适合放进 skills。
Skills 适合以下场景：
  • 某些操作会定期执行
  • 不同团队成员需要使用同一套复杂操作
  • 需要在团队内标准化某些任务的执行方式

Hooks
Hooks 是用户自定义的 shell 命令、HTTP 端点或 LLM 提示词，会在 Claude Code 生命周期的特定节点自动执行。Hooks 可以基于事件自动化 subagent 工作流。Hooks 在特定动作上触发，无需手动调用即可运行 subagent 任务。
Hooks 适合以下场景：
  • 每次提交在创建之前都应被自动评审
  • 安全检查应该自动运行，不依赖任何人记得开口
  • 希望把 CI 式的质量门禁纳入本地开发流程

什么时候不该用 subagent？ 
subagent 固然有用，但也有开销。每个 subagent 都要启动自己的上下文、消耗 token，并在开发者和工作之间增加一层间接。只有当上下文隔离、并行或全新视角确实有帮助时，才值得付出这份成本。 
对于较小的或严格串行的任务，通常留在主对话里更简单，例如： 
  • 串行的、相互依赖的工作。当第二步需要第一步的完整输出、第三步又需要前两者时，用一个会话串完整个链条，通常比让一串 subagent 通过文件传递状态更干净。
  • 同一文件的编辑。两个 subagent 并行编辑同一个文件是冲突的温床。这种场景下，把紧密耦合的修改放在同一个上下文窗口里。
  • 小任务。对于快速修复或一个聚焦的问题，委派的开销超过了收益。直接在主对话里提问或下达指令即可。  
  • 专家 agent 太多。为所有事都定义一个自定义 subagent 很有诱惑力，但给 Claude 太多选项反而让自动委派变得不可靠。大多数团队最终只会留下少数几个边界清晰的 agent，而不是一张臃肿的花名册。
  • 需要 agent 之间相互协调的工作。subagent 只能向主对话汇报，彼此之间无法交流。如果任务要求 subagent 之间通信，请使用 agent teams。在 agent teams 中，subagent 在各自独立的会话之间协调，而非在同一会话内，因此更重、更贵。关于何时用 subagent、何时用 Agent Teams 的更多指引，请查阅我们的 Claude Code agent teams 文档。
前文提到的那些信号（需要第二意见、子任务之间没有依赖、需要大量研究）可以清楚地告诉你什么时候值得委派给 subagent。
从对话开始，之后再自动化
subagent 的全部价值在于有意识地使用。Claude 提供的自动调用固然有用，但知道何时委派研究、并行推进工作、请求全新视角，比听天由命能产出更好的结果。
使用 subagent 时，先从对话式提示词开始。留意哪些请求反复出现，随着模式明朗再逐步构建自动化。目标是让 subagent 委派变得毫不费力，让你的注意力始终集中在真正重要的工作上。
