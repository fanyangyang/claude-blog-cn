最大化你的 Claude Code 会话价值

如何运行高效会话，让每一个 token 都花在真正要做的事上。

TL;DR

  • 任务之间跑 /clear 。这样可以避免把先前无关的上下文再发给模型，从而降低 token 用量。
  • 开始之前先设好模型和努力级别。 对话中途改其中任何一个，都可能打爆你的 prompt cache，从而抬高 token 成本。
  • 用 @ 提及文件，而不是只写文件名。 文件会直接附到你的消息上，省掉一次 Read 调用，或省掉 Claude 去找它时的一次搜索。 
  • 给吵闹的命令加上安静标志，或把它们放到 subagent 里跑。 命令输出会像文件一样加入对话，并在会话剩余时间里一直待着。
  • 在全新会话里跑一次 /context。 它会显示已加载的内容（CLAUDE.md、MCP 工具定义），这样你就能砍掉不必要的东西。
  • /compact 离开键盘休息前先跑。 prompt cache 一小时后过期，趁对话还在缓存里时做摘要，便宜得多。

把价值用足

直到相当近的时候，你写代码用的工具还是一口价（或免费）。那个下午你修一个测试还是五十个，编辑器的费用都一样，所以单独一项任务并没有自己的价格。 

有了 Claude Code 这类智能体编程工具，情况变了。同一件做完的任务，也会因为你怎么用它而花掉不同的钱。 

在一次会话里，Claude 读测试和它覆盖的文件，改完就结束，只用了几轮。另一次会话里，它先在仓库里 grep 一圈，读了十来个文件才走到那同样两个，而那每一轮还会拖着从早上到现在读进对话的其它所有东西。

修的是同一处，但你花的 token 数量不同，而且模型一直还得想着十个它并不需要的文件。

对 token 高效，并不意味着总体上少用它们。它意味着确保你用掉的那些，都花在你真正要求的事情上。

所以我们先看是什么决定一个 token 的价格，再看是什么决定一次会话会发出多少，一路上再看这对你怎么跑会话意味着什么。

是什么决定一个 token 的价格

你按 token 计费，但你实际付的是 inference：GPU（或 TPU，或模型碰巧跑在上面的任何东西）拿你的 token 跑模型所花的时间。 

三件事决定一个 token 要占多少这样的时间：你跑的是哪个模型、它是输入 token（进去）还是输出 token（出来），以及它是否被缓存。

模型

更大的模型在输入和输出 token 上都做更多工作。哪种模型配哪种工作值得另说，我们在 在 Claude Code 中选择 Claude 模型与投入档位 里讲过。 

就这篇文章而言，你只需要知道：下面要讲的其它一切，都会乘上模型的价格。问题确实很难或含糊时用更大的模型，工作很常规时用较小的。

输入和输出 token

一次请求在 GPU 上经过两个阶段，费用不同。 

首先是 prefill，模型读取你的请求和上下文：系统提示词、你的 CLAUDE.md、你的消息，以及此后加入对话的一切（Claude 读过的文件和它跑过的命令的输出）。那些是你的输入 token。

然后是 decode，它写出输出 token：它的 thinking、它发出的 tool calls，以及你看到的文本。这一个 token 一个 token 地发生；一段 200 token 的回复就是模型连续跑 200 次。按每个 token 计，decode 让 GPU 忙得久得多，所以输出的定价大约是输入的 5 倍。

一次会话里很多输出 token 是 thinking token，而模型每轮思考多少，正是努力级别所控制的。和模型一样，你用 /effort 选的级别也会作为下一次会话的默认值留下来。

提示： 在全新会话里跑一次 /model 和 /effort，看看你实际处在什么设置上。两者都会记住你上次选的，而你希望这个决定是有意识的。
提示： 如果你已经知道这次会话会是粗活，MAX_THINKING_TOKENS=0 claude 会为这一次会话关掉 thinking（Fable 5 除外），这比 /effort low 还低一档。

Prompt caching

如果一次请求以和服务端刚见过的请求完全相同的 token 开头，那段共享开头的状态会一样，所以服务端可以沿用上次的状态，只 prefill 后面新增的部分。这叫 prompt caching。

从缓存读取的费用是输入价格的 0.1 倍，因为服务端加载状态而不是重新计算。把 token 写入缓存比普通输入贵一点，最多 2 倍，因为服务端之后还得把状态留着。但写入对每个 token 只发生一次，0.1 倍的读取发生在此后的每一轮。

Claude Code 在每次请求上管理 prompt cache，没有开关可开。不过你可以把它打断，所以重要的是知道如何避开这些成本尖峰。

假设我们输入“修 utils.test.ts 里失败的测试”。Claude Code 为此发出的是：

  1. Claude Code 用系统提示词（含工具定义）、你的 CLAUDE.md 和你的消息组装第一次请求并发出（输入 token）。缓存里还什么都没有，所以全部被 prefill 并写入缓存。
  1. 模型修不了它没见过的测试，所以它想一会儿，用对 utils.test.ts 的一次 Read 调用回应（输出 token）。Claude Code 读文件，把它追加到对话，再把整份东西发回去（输入 token）。这一次，请求 1 里的一切都以十分之一的价格从缓存读回，唯一按全价 prefill 的是新增部分：Read 调用和那个文件。
  1. 现在模型想要被测文件（输出）。又一次 Read，又一次追加，然后整份再发出去：请求 1 和 2 走缓存，第二个文件按全价（输入）。
  1. 模型用一次 Edit 回应（输出）。Claude Code 应用它，追加结果，再把一切发回去。同样的故事：Edit 和它的结果是新的，它们前面的一切都是缓存读取（输入）。
  1. 模型跑 npm test （输出）。Claude Code 追加测试输出，再把一切发回去，只有测试输出是新的部分（输入）。
  1. 测试通过，模型用一段短摘要回应（输出）。没有 tool call 意味着没什么可追加，也没有请求 6，所以结束了。

一次小修复就是五次请求，每一次都带着截至当时的整段对话。典型的一轮是偏斜的：进去几万 token，出来几百。但只有该轮新增的部分按全价 prefill。 

这就是整笔按轮账单：历史上的缓存读取、新增部分的全价输入，以及回复的输出价格。

这在订阅上也成立。你不会直接看到这些价格，但同样的请求就是在消耗你的额度。

缓存必须从请求最开头向前匹配，而请求始终按同一顺序发出：工具定义，然后系统提示词，然后对话（CLAUDE.md 在对话最前面）。 

如果那个前缀里有任何东西变了，它后面的一切都要重新 prefill。追加到对话末尾的工具结果是理想情况，因为后面没有东西。会丢掉缓存的，是任何改到请求更靠前位置的东西，或改了缓存键的东西：

  • /model：每个模型有自己的缓存，所以下一轮整段对话都会按全价重新 prefill。（这包括 opusplan，它在你进出 plan mode 时每次都会切换模型。）
  • /effort: 努力级别也是缓存键的一部分，所以故事一样。这就是为什么 /model 和 /effort 在对话中途切换时会要你确认。
  • Fast mode：也是键的一部分，而且重新 prefill 按 fast mode 价格发生，所以如果你要开，就在一开始开。（再关掉在缓存意义上是免费的。）
  • /compact：对话被换成更短的一份，所以里面没有任何东西还能对上（它前面的系统提示词会留下来）。只要旧对话还在缓存里，写这份摘要本身就便宜，所以在长休息之前做，比之后做便宜得多。
  • 时间：每一轮都会重置计时，但缓存在订阅上过一小时过期，在 API key 上过五分钟过期（ENABLE_PROMPT_CACHING_1H=1 会把它变成一小时）。回来得比这更晚，下一轮就会重新 prefill 整段对话。恢复旧会话几乎也总会这样：那时缓存通常已经没了，而且系统提示词在启动时本来就会重建。

这并不意味着你永远不该切换模型或努力级别。它意味着有便宜的时机去做，比如会话开始或刚 /clear 之后；也有昂贵的时机，比如一段长对话的中间。

提示： 如果最近几轮走到了你不想留下的地方，用 /rewind 回到它们之前，而不是跑 /compact。Rewind 只从末尾切掉那些轮，所以它们前面的一切仍在缓存里，而且不花钱。Compact 会重写整段对话，所以总会花一点。

是什么决定一次会话发出多少 token

这里要知道的主要一点是：没有什么只发一次。最终进入对话的一切，无论是 Claude 读过的文件还是它跑过的命令输出，都会在此后每一轮再发一遍，直到会话结束。 

它是缓存过的，所以每一次重发都便宜，但便宜不是零，而且它还占着上下文的位置，模型每一轮都得绕着它思考。

这其实就是一次会话的全部成本模型：有多少 token 进入上下文、它们在那里待多少轮，以及你同时跑着多少个上下文。

什么会进入上下文

上下文里有一部分在你打字之前就在了：工具定义、系统提示词、CLAUDE.md，以及启动时加载的其它东西。

提示：在全新会话里跑 /context，看看你还没打字时里面有什么。把 CLAUDE.md 留给具体指令，把工作流专属的指令移到 skills，它们只在被用到时才加载。如果这次会话不需要某个 MCP server，用 /mcp 关掉它。

会话期间加入的几乎所有其它东西都是工具结果：Claude 读的文件，以及它跑的命令的输出。

Claude 读多少，主要取决于它必须自己弄清楚多少。如果你说“测试失败了”，它得先找出是哪些测试：grep 一两下，打开几个文件看看哪个相关，而这些结果在不再有用之后还会在上下文里待很久。 

“修 utils.test.ts 里失败的测试”会跳过搜索，只花一次对该文件的 Read 调用，而“修 @utils.test.ts 里失败的测试”连这次 Read 调用也不花。

提示：提到文件时，用 @ 提及它，而不是打路径。Claude Code 会在任何东西发出之前把文件附到你的消息上，所以它在第一次请求里就在了，也不需要为它做 Read 调用。文件本身在上下文里占的位置两种方式都一样，所以每次对话只需要提及一次：它会待在那里，后来再 @ 一次通常会再附上一份副本。

另一件把上下文填满的事，是 Claude 跑的命令的输出。每次它跑你的测试、一次构建或一次 git log，打印出来的东西都会像它读过的文件一样追加到对话，并同样待那么多轮。

真的很大的输出其实没问题：超过 30,000 个字符后，Claude Code 会把输出写到文件里，对话里只放一段短预览和路径（想改的话用 BASH_MAX_OUTPUT_LENGTH）。 

问题是低于这个阈值的一切。一个一次一行打印 400 个通过测试的测试运行器会落在限制以下，于是那 400 行现在成了此后每一轮的一部分。 

Claude 常常会自己用标志和 tail 处理这件事；如果你宁可不把它交给 Claude，文档里有一个小 hook，会在吵闹的命令运行前改写它们，让只有要紧的行回来。

提示：把你整天都在跑的那两三个命令写进 CLAUDE.md，连安静标志一起，就像你自己会打的那样（“用 npx vitest run <file> --reporter=dot 跑单个测试文件”）。这是很小的补充，但此后每次会话都能省下一轮和几百行输出。

它在那里待多少轮

一次长会话比把同样的工作摊到几次短会话里更贵，而且贵得超出你的想象，因为第 40 轮也在重读前面的 39 轮。你希望会话里的上下文短而相关，所以不要把一项任务的上下文带到下一项：开始新事情时 /clear ，同一任务的前半段做完时 /compact。

提示：如果你以后还想找回这次会话，/clear 之前先 /rename。当你 /compact 时，告诉它该留下什么；如果每次都一样，就在 CLAUDE.md 里放一节 “Compact instructions”。如果你在用 1M 模型，又希望把自动 compact 的安全网放回原来的位置，/autocompact 200k 可以把它放回去（需要 Claude Code v2.1.221+）。

也留意那些你没在打字时发生的轮次。/loop 会作为你设置它的那次会话里的完整一轮触发，每次都带着整段对话；如果距上一轮已经超过一小时，上面还会再加一次缓存未命中。在另一个终端开一次全新会话，从那里跑 loop。

Subagents

另一种把东西挡在你的上下文之外的办法，是让它发生在另一个上下文里，这就是 subagent 的用途。subagent 有自己的上下文窗口，带着自己的系统提示词、工具和你的 CLAUDE.md，但没有你的对话。它跑自己的轮次，回到主会话的只有它的答案。其它一切在它完成后都会丢掉。

没有你的对话的坏处是，subagent 有时得重读主会话已经有过的东西，而且它在这么做时要为自己的轮次付钱。对小活来说，这只是开销。 

当一份工作会产生大量你不需要留下的输出时，比如过一遍日志，它就划算了。那种事 Claude 常常会自己去找一个 subagent，它没这么做时你也可以直接要求（“在一个 subagent 里过一遍这份日志”）。只要记住，主会话只拿回 subagent 选择报告的内容。

提示：如果有一份吵闹的工作你一次次交出去，给它单独一份 subagent 定义，并设 model: haiku（或 sonnet）。否则它会跑在你主会话正在用的模型上。
