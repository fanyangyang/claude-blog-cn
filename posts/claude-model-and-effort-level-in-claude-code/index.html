在 Claude Code 中选择 Claude 模型与投入档位

要点：

  • 选择 Claude 模型，就是选择那一组固定的 weights，也就是模型整体能力范围。虽然可以给模型提供上下文或加以引导，但模型的整体知识库和能力是既定的。
  • Effort 不只是“思考时间”。它控制 Claude 为你的请求总共做多少工作，包括读取多少文件、使用哪些工具，以及在回头找你之前走多少步。
  • 更常规的任务选较小的模型，更复杂或含糊的任务选较大的模型。先从每个模型的默认努力级别开始，再按你日常工作类型做整体偏好调整，而不是逐任务微调。
  • 如果 Claude 已经掌握了所有相关上下文、也明显试过了，结果仍然错，这是该换更强模型的信号。如果错是因为跳过了某个文件、没跑测试，或重构做到一半就停了，那就提高努力级别。

Claude Code 的努力级别与模型选择

Claude Code 有两个看起来能“让答案更好”的设置：模型设置和努力级别。你可能以为更大的模型（比如 Claude Fable 5）会比 Claude Sonnet 给出更聪明的输出，而更高的努力级别意味着 Claude 在回答前会想得更久。

第一个假设是对的。按行业标准基准，我们最大的模型能力更强。

但 effort 不只是“思考时间”。努力级别控制 Claude 为你的请求总共做多少工作。这当然包括模型思考多久，也包括：

  • 它读多少文件；
  • 它做多少验证；以及 
  • 在多步任务里，它会推进多远才回头找你。 

努力级别更高时，Claude 会在回来找你之前多做这些动作（例如读文件、跑测试、再核对一遍）。努力级别更低时，它更愿意向你要更多上下文，而不是自己花 token 把事情弄清楚。

模型选择如何工作

你按下回车时，Claude Code 会把你的消息和系统提示词、工具定义、你的 CLAUDE.md、对话历史以及上下文中的任何文件组装在一起。所有这些作为一次请求发给 API。

不过模型从来不会把这些当成纯文本来看。服务器上发生的第一件事是 tokenization；文本被切成片段，每个片段映射到模型训练时所用固定词表中的一个整数。const 可能映射到 1978，await 可能映射到 4293。从这里开始，你的提示词就是一个整数数组。

模型的工作是接过这个数组，预测下一个 token。它会为词表里的每一个 token 计算一个概率，再从顶部选取。在 const x = await 之后，训练良好的模型会给 fetch 很高的概率（非常可能），给 banana 接近零的概率（几乎不可能）。

把输入 token 变成这些概率的，是 weights（也叫parameters）。它们是组织成大型矩阵的数十亿个数字。要预测一个 token，模型会把你的输入送过这些矩阵，经过一长串矩阵乘法，最后读出概率。模型“知道”的一切都住在这些 weights 里。

每个模型的 weights 在训练期间就定下来了，等你开始发请求时，它们已经是只读的。你的提示词、CLAUDE.md 或上下文里的任何东西都不会改变它们。（如果你见过 inference 这个词，它的意思就是：训练结束后使用模型，weights 固定不变。）

Claude 对 TypeScript、常见框架、地道的 Go 或任何其他通用编程知识的了解，都是在训练时编码进那些 weights 的。 

你的提示词和上下文仍然可以引导预测（把真实代码摆到 Claude 面前就是引导，而且非常有效），但它们不会给 weights 本身增添任何东西。 

如果某个库在模型训练时还不存在，它就不在 weights 里。你可以把文档放进上下文，Claude 会用它们，但那是引导，不是教学。Claude 的回复只会受当次请求影响；底层模型并没有记住这些信息。

所以当 Claude 自信地调用一个并不存在的 API（幻觉）时，那是 weights 根据训练模式生成了一段看起来合理的 token 序列，而不是一次失败的查找。

那么更换模型实际做了什么？它换的是哪一组冻结的 weights 来处理你的请求。 

模型不会一次生成整段答案。它预测一个 token，把它接到序列后面，再把整套计算重跑一遍以得到下一个。一段 200 token 的回复，就是对 weights 的 200 次独立遍历。这个循环，就是你大部分等待时间和输出费用的来源。

所以模型设置决定哪一组 weights 处理你的请求，也决定每个输出 token 的价格。 

它不决定会生成多少 token。对同一条提示词，这个数字可以差很多，取决于 Claude 决定做多少工作。 

这就是努力 级别所控制的：Claude 每一轮决定做多少工作。  

Claude Code 努力级别如何工作

Claude Code 处理任务时，它生成的 token 分成几类：

  • Thinking：你看到的、在动作之前和之间流式输出的推理。
  • Tool calls：结构化块，点名某个工具（如 Read 或 Edit）及其参数，随后由 Claude Code 解析并执行。
  • 给你看的文本：计划、进度更新、结尾的摘要。

这些都是同一循环里的普通输出 token，按同一费率计费。例如，thinking token 的生成方式和其它输出 token 完全一样，并在该轮剩余时间里留在上下文中。 

当 Claude 转去写代码时，它先前的推理会像它读过的文件一样，成为输入的一部分。

努力级别怎样改变这些？努力级别会作为请求的一部分发给模型，就在你的提示词旁边。模型经过训练，懂得在每个努力级别上该怎么表现，这种学到的行为已经烘焙进冻结的 weights。 

请求到达时，努力级别是模型会响应的又一项输入，方式和它响应你的提示词文本一样。这设定了 Claude 在认为任务完成之前，需要做到多彻底、多有把握。 

每一轮都会这样考虑，并 因此消耗更多 token，以产出更高置信度的答案。

在更高的努力级别上，Claude 常常会先制定计划，而努力级别会影响这份计划的深度和广度。不过计划并不是钉死的。随着 Claude 从自己的动作中拿到结果，它会更新已完成的进度，以及它对累积结果有多确定。 

所以当一个三假设调试计划的第 1 步就找到了 bug，“调查假设 2 和 3”可能就不再必要。Claude 通常会明确说出来，“第一次检查就找到了，所以剩下的检查不需要了”，然后往前跳。你在 Claude Code 里看到任务列表在运行中被改写，就是这种情况。

更高努力级别会让 Claude 更倾向于再核对额外假设或验证正确性，但一般不会在简单任务上为了更高努力级别而人为抬高用量。事实上，我们的团队在模型训练中会密切关注“overthinking”，因为它会降低有效性。

如何选择努力级别 

我们的建议是，大多数任务应使用模型的默认努力级别。默认级别是 Claude 会按大多数人愿意为一件事花的量，来缩放 token 用量的那个级别。 

把 effort 想成一个手动覆盖项，用来缩放 Claude 工作得多努力、多长久。当你基于自己的领域或工作类型，对彻底程度或速度有强烈偏好时，再有意识地去选。把它当成一种整体偏好，而不是逐任务决策。

在 Claude Opus 4.8 发布之后，有些实务观察或许能帮到你：我们的测试发现，对同一任务使用 Opus 4.8 的默认努力设置，相比使用 Opus 4.7 的默认努力设置，能在大约相同的 token 数量下得到更好的结果。 

Claude 出错时该改什么

当 Claude 出错时，你的第一反应不该是拧旋钮，而是检查你提供的上下文。提示词是否太含糊？Claude 是否连上了正确的工具？是否配备了正确的 skills？

如果你在一件本不该需要更高努力的任务上调高 effort，修复往往在更上游：你的上下文、CLAUDE.md，或任务如何界定。 

但假设你已经提供了清晰上下文，Claude 仍然出错，那该问自己的是：它是不够努力，还是不够懂？ 

模型：问题太难了

问题确实很难时，选更大的模型。例如隐蔽的 bug、不熟悉的领域，或架构决策。当较小模型无论你给多少上下文都自信地给出错答案时，更大的模型会有帮助。 

更大的模型也更擅长处理含糊之处，而对较小模型来说，用具体指令指导执行，成功率更高。

工作很常规时，选较小的模型。例如你能精确描述的编辑、机械性改动，或关于已经在上下文中的代码的问题。没有理由为任务并不需要的能力付钱。
如果 Claude 已经掌握了所有相关上下文，也明显试过了，结果仍然错，这是该换更大模型的信号。如果你已经在用更大的模型，而工作已经常规了一段时间，降下去会更快，通常也能在不影响输出质量的情况下降低成本。  

Effort：Claude 不够努力

如果 Claude 错是因为跳过了某个文件、没跑测试，或没有再核对自己的工作，就提高努力级别。如果你选的努力级别低于模型默认值，这一点尤其相关。

Fable vs. Opus vs. Sonnet：专家中的专家、专家，和通才

我喜欢这样理解这两个设置之间的关系：Fable 是几乎没人见过那些问题的专家中的专家，Opus 是专家，Sonnet 是非常优秀的通才。努力级别决定他们中的任何一个会在你的任务上花多少时间。

低努力的 Opus 就像只给你五分钟，去见一位深谙此类问题的专家。他们带来的知识并不在你的代码库里：以前见过的模式、知道该检查的坑，那种只有解决过大量类似问题才会有的东西。但只给他们五分钟，意味着对你的代码只会快速扫一眼，而不是仔细读。

高努力的 Sonnet 就像给一位非常优秀的通才整个下午。他们会读完所有东西、跑一遍、再核对自己的工作，最终把你这份具体代码吃得很透。他们带得比较少的，是那种“我正好见过这个”的辨识。

Fable，即使是低努力，也是那位专家中的专家朝人人卡住的问题扫一眼，仍然能看出别人看不出来的东西。那种辨识是你付得最贵的部分，所以值得留给真正需要它的任务。

这些都不是普遍更好。模型设置大致是能力多强；努力设置大致是有多彻底。大多数真实任务两边都需要一点。

Effort、模型与 token 消耗

那么模型选择、effort 和 token 消耗如何相互作用？这取决于任务。

在同样的努力级别上做常规工作，两个模型一般都能做对。更大的模型会多做一些验证步骤，消耗更多 token，而且每个 token 更贵。这就是为什么在常规阶段降到较小模型能省下真金白银，又不损失质量。

在更难的多步工作上，账就不同了。较小的模型必须磨到自己能力的极限，烧掉一轮又一轮，而更大的模型用更少的步数就能达到同一质量门槛。 

更大的模型每个 token 更贵，但在那些确实把较小模型撑满的任务上，单任务总成本可能反而更低。而且更重要的是，更大的模型能完成较小模型即使开到最高努力设置也做不到的任务。

这一点在 Fable 上最明显。在长的、多步的工作上，它甩开得最远。在我们的测试中，它完成了 Opus 和 Sonnet 在任何努力级别都到不了的工作。它每个 token 也最贵，这是另一个该把它留给真正需要它的工作的原因。

上面这些图的关键点是：努力级别决定 Claude 愿意沿曲线走多远，但这并不意味着 Claude 必须走那么远才能完成任务。 

还有一层细微差别：effort 会塑造 token 消耗，但不会限制它。系统里唯一的硬上限是 max_tokens，一旦触及就会把回复从中途截断。这是一把钝器，主要和 API 开发者有关。更软的控制，比如 task budgets，或在提示词里请 Claude 写短一点，是更有用的工具。它们是模型受过训练会去遵循的指引——接近上限时它会设法收束任务——而不是一堵撞上去的墙。

先从默认值开始，再去拧旋钮

大多数时候，你不该去想这两个设置。当结果没打中时，问一句“Claude 是不够懂，还是不够努力？”然后按需调整。
