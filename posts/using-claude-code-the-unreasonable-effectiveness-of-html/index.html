使用 Claude Code：HTML 意外地好用

Claude Code 团队成员为何以及如何用 HTML 替代 Markdown，做出更丰富、更好读、更易分享的产出。

Markdown 已经成为智能体与人类沟通时占主导地位的文件格式。它简单、可移植，有一定富文本能力，也容易编辑。Claude 甚至出人意料地擅长在 Markdown 文件里用 ASCII 画图。

但随着智能体越来越强，我发现 Markdown 越来越束手束脚。具体来说，超过一百行的 Markdown 文件我很难读下去；我想让 Claude 生成更丰富的可视化、颜色和图表；我也希望能更轻松地分享这些产出。

我也越来越少亲自编辑这些文件，而是把它们当规格和参考文件用。真要改的时候，我通常是提示 Claude 去改，这就拿掉了 Markdown 最大的好处之一。

于是，我开始更愿意用 HTML 而不是 Markdown 作为输出格式，也越来越多地在 Claude Code 团队里看到别人用同样的做法。这篇文章分享我们团队为何以及如何用 HTML 做出更丰富、更好读的 Claude Code 产出。如果你想跟着做，也可以先用这些面向常见场景的 HTML 文件模板。

为什么用 HTML？

有几件事让 HTML 比 Markdown 更适合我现在用 Claude Code 做的工作，包括需要或涉及以下内容的任务： 

信息密度

与 Markdown 相比，HTML 能传达丰富得多的信息。它当然能做标题和格式这类简单文档结构，也能表示各种各样的其他信息，例如：

  • 用表格呈现表格数据
  • 用 CSS 呈现设计数据
  • 用 SVG 做插图
  • 用 script 标签放代码片段
  • 用带 javascript + CSS 的 HTML 元素做交互
  • 用 SVG 和 HTML 呈现工作流
  • 用绝对定位和画布呈现空间数据 
  • 用 image 标签放图片

在我看来，几乎没有哪一类 Claude 能读懂的信息，你不能用 HTML 高效地表示出来。这让它成为模型向你传达深入信息、以及你审阅这些信息的一种非常高效的方式。

我发现，做不到这一点时，模型可能会在 Markdown 里做更低效的事，比如 ASCII 图，或者——我最喜欢的——用 unicode 字符估颜色。

‍

视觉清晰度与易读性 

‍

随着 Claude 能接手更复杂的工作，它也能写出越来越大的规格和计划。我发现自己往往读不完超过 100 行的 Markdown 文件，更别提让组织里其他人去读。 

但 HTML 文档好读得多，因为 Claude 可以用标签页、插图和链接，把结构在视觉上组织成最适合浏览的样子。它甚至可以做移动端响应式，让你按设备形态换一种读法。

便于分享

Markdown 文件相当难分享，因为大多数浏览器并不能很好地原生渲染它们。你常常得把它们作为附件加到邮件或消息里。

只要你上传了 HTML 文件，就可以轻松分享链接。同事可以在任何想打开的地方打开它，并轻松引用。 

如果你的规格、报告或 PR 说明是 HTML，别人真正读它的概率会高得多。

双向交互

‍

HTML 还能让你与文档交互；例如，你可能想让它加上滑块或旋钮来调整设计，或让你微调算法里的不同选项看看会发生什么。你也可以让它把这些改动复制成一段提示词，再贴回 Claude Code。 

在有用的时候，这能让你为手头这个具体问题做出单独的编辑环境。

数据摄入

用 Claude Code 而不是 Claude.ai 或 Claude Design 来做 HTML 文件，最大的理由之一，是 Claude Code 能摄入的全部上下文。例如，写这篇文章时，我让 Claude Code 读遍我的代码文件夹，找出我生成过的所有 HTML 文件，分组归类，再做成一份带图表的 HTML 文件，表示每一种类型。你在这篇文章里看到的图，就是直接出自那次。

除了文件系统，Claude Code 还能用你的 MCP（如 Slack、Linear 等）、你的网页浏览器（配合 Claude in Chrome）以及你的 git 历史，找到额外上下文。 

开始使用

有一点值得说明：你不需要做太多就能让 Claude 生成这样的 HTML。你可以直接提示它「做一份 HTML 文件」或「做一个 HTML artifact」。关键是知道你希望这个 artifact 做什么、你会怎么用它。时间久了，围绕反复出现的模式做一份 skill 也许说得通，但先从零提示开始，是感受它在不同用例里如何工作的好办法。

用例

为了让这种方法更具体，下面是一些我认为用 HTML 文件比 Markdown 更合适的示例用例。你也可以对照 GitHub 上的用例画廊，在这里。

规格、规划与探索

HTML 是 Claude 深入一个问题的丰富画布。当我开始处理一个问题时，我期待的不是一份简单的 Markdown 计划，而是一张 HTML 文件网。例如，我可能先让 Claude Code 头脑风暴，并做出几种不同选项的探索。然后让它把其中一个展开得更多，也许做出界面类型的线框或示例。最后，我觉得可以了，再让它写一份实现计划。我对计划满意后，会开一个新会话，把这些文件全部传进去让它实现。

验证时，我也会让验证智能体读入这些文件，它会对需要什么有宽得多的上下文。

‍

示例提示词：

  • 我不确定引导页该往哪个方向走。生成 6 种明显不同的方案——在布局、语气和密度上拉开差异——并在一份 HTML 文件里排成网格，方便我并排比较。给每一种标出它在做的取舍。
  • 在一份 HTML 文件里写一份详尽的实现计划，务必做一些线框、展示数据流，并加上我可能想审阅的重要代码片段。让它好读、好消化。

适用于： 

  • 探索用代码实现某件事的其他方式
  • 一次试验多种视觉设计

代码审查与理解 

代码在 Markdown 文件里很难读，但有了 HTML，我们可以渲染 diff、批注、流程图和模块。  用 HTML 来理解智能体写的代码、审查代码，或向正在审查你代码的人讲解一个 PR。

‍

示例提示词： 

帮我审查这个 PR，做一个 HTML artifact 来描述它。我对 streaming/backpressure 逻辑不太熟，所以把重点放在那里。把实际 diff 渲染出来，加上行内边距批注，按严重程度给发现上色，以及任何其他有助于把概念讲清楚的东西。

适用于： 

  • 创建 PR
  • 审查 PR
  • 理解代码里的一个主题

设计与原型

Claude Design 建立在 HTML 上，因为 HTML 在设计上极具表现力，哪怕你的最终界面并不是 HTML。Claude 可以先用 HTML 勾出设计，再写成你选择的语言，无论是 React、Swift 等。

你也可以做交互原型，比如动画、动作等。可以考虑让 Claude 做出滑块、旋钮等，精确调到你想要的效果。

‍

示例提示词： 

我想给一个新的结账按钮做原型，点击后播放一段动画，然后很快变成紫色。做一份带若干滑块和选项的 HTML 文件，让我试这段动画的不同参数，并给我一个复制按钮，把效果好的参数复制下来。

适用于：

  • 创建设计系统 artifacts
  • 调整组件
  • 可视化组件库
  • 做动画原型

报告、研究与学习

Claude Code 非常擅长把多个数据源的信息综合起来，并转化成好读的报告。你可以提示 Claude 搜索你的 Slack、代码库、git 历史或互联网，并用它生成好读的报告。

你可以把它做成一份长 HTML 文档、一份交互式讲解，甚至一份幻灯片/deck。让 Claude 用 SVG 做图表来帮助可视化。

示例提示词：

我不理解我们的限流器实际怎么工作。读相关代码，做出一页 HTML 讲解：一张 token-bucket 流程图、3–4 段带批注的关键代码，以及底部一节「易踩坑」。按只读一次来优化。

适用于：

  • 写功能摘要
  • 生成讲解
  • 起草周报 
  • 做事故报告 
  • 产出 SVG 插图、流程图和技术图，

定制编辑界面

有时很难只在一个文本框里说清你想要什么。对这种用例，我经常让 Claude 为我手头正在做的那一件事做一个用完即弃的编辑器：不是产品，也不是可复用工具，而是一份单一 HTML 文件，专为这一份数据而建。

诀窍总是以导出收尾：一个「复制为 JSON」或「复制为提示词」按钮，把我在 UI 里做的事变回可以贴进 Claude Code 或提交到文件的东西。你仍在循环里，但循环紧得多。

示例提示词：

  •  我需要重新排这 30 张 Linear 工单的优先级。给我一份 HTML 文件，每张工单做成可拖拽卡片，分到 Now / Next / Later / Cut 四列。先按你的最佳猜测预排。加一个「复制为 Markdown」按钮，导出最终排序，并为每个桶附上一行理由。
  • 这是我们的功能开关配置。给它做一个表单式编辑器，按领域分组开关，展示它们之间的依赖，如果我打开一个前提未开的开关就警告我。加一个「复制 diff」按钮，只给我改过的键。
  •  我在调这份系统提示词。做一个并排编辑器：左边是可编辑提示词，变量槽高亮，右边三个样例输入，实时重渲染填好的模板。加一个字符/token 计数器和一个复制按钮。

适用于：

  • 重新排序、分拣或分桶任何东西（工单、测试用例、反馈）
  • 编辑结构化配置（功能开关、环境变量、带约束的 JSON/YAML）
  • 带着实时预览调提示词、模板或文案
  • 策展数据集——批准/拒绝行、给样例打标签、导出所选
  • 给文档、逐字稿或 diff 做批注并导出批注
  • 挑选用文字很难表达的值：颜色、缓动曲线、裁剪区域、cron 计划、正则

常见问题

这些是我最常被问到的、关于在 Claude Code 里用 HTML 的问题，配上我落到日常习惯上的实用做法：

这不是更低效吗？

Markdown 往往用更少 token，但我发现 HTML 多出来的表现力，加上我真正去读它的概率高得多，意味着我总体得到更好的产出。有了 Opus 4.7 的 1MM 上下文窗口，增加的 token 用量在上下文窗口里几乎感觉不到。

你现在什么时候还用 Markdown？

老实说，我几乎已经彻底不用 Markdown 了，但我大概站在 HTML 最大化那一头很远的地方。

这就是你取代规划的方式吗？

我发现，我往往不是只有一份计划，而是针对计划的不同部分/阶段有几份不同的 HTML 文件。例如，我可能先用 HTML 做一份实现计划，再另做一份文件探索 UI，最后再做一个列出每一种设计的 HTML 组件。我倾向于把这些文件留着当日后参考，也用在验证里。

与 Claude 保持在循环中

以上种种要说的是，我用 HTML 而不是 Markdown 的真正原因，是它让我感觉与 Claude 的循环贴得更紧。随着 Claude 接手得更多，我注意到自己读计划越来越不仔细，我想要一种方式继续参与它的选择，而不是直接交出去。HTML 恰好就是那个方式。我现在比以往任何时候都更感觉自己在循环里。"
