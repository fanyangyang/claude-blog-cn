AI 正在重塑 CI 

Anthropic 工程师平均每季度交付的代码量是 2021-2025 年期间的 8 倍。其中 80% 的代码由 Claude 编写，Claude 还在审查和批准 PR 方面发挥着重要作用。 

除此之外，我们代码库中的测试数量增长了 10 倍，而我们只增加了少量工程师。这一切导致 CI 任务量在六个月内增长了 25 倍（如果你想算这笔账：并不是每个测试都会在每个 PR 上运行，我稍后会解释）。

这几次险些压垮我们的测试影响分析服务。为了避免成为下一个瓶颈，我们把整个服务推倒重来，重新设想了它的架构。但这一路并不平坦，我们从三个快速修复方案开始，它们分别撑了 70 天、29 天，然后不到一天。 

随着智能体继续加速代码生成和审查，扩展 CI 将是更多工程团队很快就会面临的挑战。我预计，随着运行智能体的团队产生更多 PR 和更多测试，水平扩展的测试选择架构将成为行业标准。

在这篇文章中，我将讨论我们如何在 Anthropic 扩展测试影响分析服务，以及我吃一堑长一智学到的教训：永远要为指数级增长做规划。具体的扩展技巧——购买更大的机器、并行化进程、或重启服务（没错，这个居然仍然很有效）——都很常见，并不是这篇文章要传达的洞察。 

重点是：这些技巧中每一项所能争取到的时间，都只有一年前的几分之一。另一方面，彻底改造和完全重新设计一个服务，所需时间同样只有原来的几分之一，而且在写代码不再是瓶颈的今天，这样做要可持续得多。 

你越能预判这种压力、越能规划好架构如何随之演进，在治标不治本的方案上浪费的时间就越少。 

测试影响分析架构

我的许多同行所在的组织，仍然在每次变更时运行全部测试。这在某种程度上可行，但无法扩展：CI 门槛会变得越来越慢、越来越贵、越来越不可信。

此外，人类很擅长判断哪些测试失败与自己无关，而智能体需要更多上下文和指导。当智能体获得一组具体的有效测试时，它们可以更有效地自我验证和迭代。

在 Anthropic，我们构建了一个确定性的测试影响分析（test impact analysis）或者说测试选择服务，它根据历史表现和包相关性，决定每次变更要运行哪些测试。这并非罕见的做法，市面上已经有一类供应商提供这方面的产品。

我们的服务依赖两个确定性组件保持同步： 

  • “监听器”（listener）记录每次 CI 运行的测试结果。 
  • “选择器”（selector）读取测试结果历史，决定哪些测试在哪些已开启的 PR 上运行。

这很有效，但当每秒有多个 CI 任务运行时，监听器会越来越跟不上 PR 队列。对于AI 原生 SDLC 来说，一点点滞后就会产生很大影响。例如，20 分钟的监听器滞后，可能意味着数以万计的测试更新没有应用到选择器上。 

  • 如果有问题的变更被合并，那么某个测试就会开始对其他人失败，引发多次不必要的排查。
  • 如果某个依赖开始出现不稳定，那么不稳定的失败就会开始阻塞合并。
  • 如果某个测试被修复或新增了测试，在监听器追上之前它不会运行，存在回归风险。

所有这些都作为单个进程运行，因为要为每个测试维护持续的历史记录，意味着需要单个写入者来应用结果。这种 v0 设计使我们无法进行水平分片。

通往重新设计的崎岖之路

到去年 10 月，这个服务已经显露出吃力的迹象，我们连续两天被传呼（paged）。

补丁 1：更大的机器

第一个修复很简单：我们把运行该服务的核心数翻了一倍。我们也知道这只是权宜之计。

即使趋势线已经很清晰，所有权依然模糊不清。没有人愿意再多负责一块基础设施。而且，CI 团队有更棘手的问题要处理。

补丁 2：分片

此时，由于该服务监听器中的滞后不断累积，我们被传呼的频率相当高。为了推动一些长期修复，我在内部版 Claude Tag 中开启了一个专门监控该服务的长期会话。每当监听器滞后超过 50,000 个任务时，Claude 就会提醒我，并继续我们关于下一步的对话。 

这种情况持续了好几个月，而且不必不断提醒它过去的努力或背景，确实很有帮助。Claude 经常主张彻底改造，但我们通常还是选择再打一个补丁。 

到了 2 月，CI 任务的指数级增长再次开始给服务带来压力。这一次，我们决定并行化。

监听器并不需要单个写入者来正确排序测试结果，它需要的是每个包一个写入者，来正确排序我们代码库各部分的测试结果。Claude 为我们生成了代码，把每个包的状态拆分为一个带有独立 worker 的分片。

我们也知道这个修复只是权宜之计，但我们没想到它只撑了 29 天。 

补丁 3：每日重启

到了 3 月，这个进程在大多数工作日的下午就达到了内存上限。我们再次寻找快速修复方案，但是：

  • 我们只发现了四个 bug。
  • 作为快速手段更换内存分配器毫无作用。我们试图优化垃圾回收，但那并不是真正的解决方案。 
  • 我们不想冒险对一个已经处于高负载下的单例进行内存剖析。 
  • 重启只为我们争取了不到一天的时间。

我们还发现，每日重启导致服务逐渐越落越远。当它落后超过一个小时（这种情况发生过好几次）时，大量任务结果没有被监听器记录。 

需要说明的是，这并不意味着 CI 从未在这些 PR 上运行，也不意味着未测试的代码被推到了生产环境。它的意思是，监听器没有捕捉到一些结果，这意味着我们的测试选择组件在使用过期数据来决定 PR 上该运行什么、不该运行什么。大多数情况下，这表现为我们运行了那些本来就已经非常不稳定或大面积失败的测试。 

重新设计

（早就）到了重新设计这个服务的时候，我们采纳了 Claude 的建议：给测试选择服务一个数据库，准确地说是一个内存数据存储。这样一来，我们有效地分担了单例过去需要做的大量内存处理。 

现在，任何监听器 worker 都可以处理任何结果，将其追加到内存存储中的日志（journal）里，然后继续处理下一个，无需在内存中保存任何东西——无状态，因此可以水平扩展。一个独立的小型消费进程每隔几秒把日志汇总为每个测试的历史记录，选择器可以快速查询相关的结果历史。 

这种分布式架构运行成本更高，但相比摇摇欲坠的单例，它更容易扩展和进行内存剖析。这个项目只花了一位工程师三周时间。一年前，这大概需要一个季度。

还有一些微调（确定日志的大小和 worker 数量），这些基本上是由 Claude 自主完成的，但我们的服务此后一直保持稳定。

如果重来一次，我会怎么做 

如果我能回到 2025 年 10 月，以我现在掌握的信息，我会以不同的方式处理这个项目和其他项目。 

第一个不同是，我会把 AI 指数效应纳入考量。随着每位工程师平均使用的智能体数量上升，以及 PR 批准速度的加速变得越来越成熟，CI 任务量呈指数级增长。 

这改变了 Anthropic 中 PR 的形态，因为 Claude 倾向于更小、更细粒度的 PR（这也是不在每个 PR 上运行全部测试的另一个好理由）。这转化为每天更多的 CI 任务。此外，由于智能体在夜间和周末也会持续工作，活动水平的下限被抬高了，但活动仍然是突发性的，因为人类工程师仍然驱动并批准着相当一部分 PR。

我给工程团队的建议是：无论自研还是购买，都要假设你的架构会在两个季度内承受 25 倍的负载。过度工程化（over-engineering）这个概念正在开始逐渐淡化，或者说，门槛正在大幅提高。只要预算允许，你现在就可以在 v0 设计中考虑 10-20 倍于预估规模的余量。 

为你的服务做好可观测性（instrumentation），让它们充当 Claude 的耳目。这让 Claude 能够以比我们手动操作更好、更快的方式爬山式（hill-climb）地渐进修复问题。特别是要确保进入的 CI 任务数量和出去的保持一致。 

从一开始就把状态移出进程。我还建议，除非你能对它进行度量并做金丝雀（canary）变更，否则不要把任何关键服务作为单实例运行。CI 演进得太快了，容不得别的做法。
