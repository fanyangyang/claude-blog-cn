Anthropic 如何用 Claude Code 执行大规模代码迁移

用 AI 智能体跑大规模代码迁移的分步指南，包括 Bun 百万行 Zig 到 Rust 的移植。

代码迁移——把生产代码库移植到一门新语言的项目——直到不久前还是以年计的工程。

就在上个月，Anthropic 的几位开发者用 Claude Fable 5、Claude Opus 4.8 和dynamic workflows，完成了 10 个代码包的迁移，每个包从几万行到几十万行代码不等。本文将介绍其中两个案例，以及从这些项目中总结出的最佳实践。

Bun 联合创始人、Anthropic 技术团队成员 Jarred Sumner 使用 Claude Code 把 Bun 从 Zig 迁移到了 Rust。不到两周产出了上百万行代码，合并前 Bun 现有测试套件在 CI 中 100% 通过。合并后暴露出 19 个回归，均已修复。Rust 版本已于六月随 Claude Code 发布。 

Anthropic Labs 联合负责人 Mike Krieger 在一个周末把一个 Python 代码库迁移成了 16.5 万行 TypeScript。整个过程动用了数百个智能体、八个阶段关卡、三轮对抗性审查，以及最后一轮一致性检查——把每条命令的输出与 Python 原版逐一比对。 

Claude Code 的新能力改变了这些被长期搁置项目的账本。以下是我们如今使用的六步流程，提炼自这些迁移项目的经验。

核心洞见是：你不去修代码，你去修产出这套代码的流程（循环）。

什么是 AI 代码迁移？

AI 代码迁移是指用 AI 智能体把生产代码库移植到新语言或新框架。工程师不再逐文件手工翻译，而是编写迁移规则和验证循环；智能体随后不断翻译、编译、测试，直到新代码的行为与原版一致——把以年计的项目压缩到以周计。

为什么迁移语言、何时迁移

在讲怎么做之前，值得先聊聊何时做和为什么做，因为围绕这类项目的假设已经变了。 

团队发起迁移，是因为从最初构建到今天，技术格局变了：要么某个已知的权衡开始掣肘，要么出现了更好的路线，要么原有生态在萎缩。 

比如，Jarred 当年选择 Zig，是因为它在 C 级性能之外还极为简洁，对于"前 LLM 时代、在奥克兰狭小公寓里打算一年写完 Bun 的独立创始人"来说非常理想。这种简洁附带着已知的取舍，他在这里写到了。 

时间快进到 2026 年。Bun 的 CLI 月下载量已超过 1000 万，并被 Claude Code 大量使用。 

就在上个季度，这些取舍还不足以让人下决心冻结路线图、为一个多季度的项目投入资源。语言迁移固然能带来更小、更快、更安全的系统，但没人愿意买单。

软件工程师还得面对这类昔日巨石工程固有的职业风险：你可能要维护两套并行代码库几个季度甚至几年，而如果最终结果只做到 90% 的一致性，你手上的烂摊子比开工时还大。

而现在，最坏的情况不过是删掉分支、重来一次。

当然，仍然需要有说得通的业务理由。百万行级的迁移虽然不再像过去那样在四年项目周期里烧掉 300 万到 400 万美元的工程资源，但仍要花上几万到几十万美元甚至更多。例如，Bun 的迁移消耗了 59 亿未缓存输入 token 和 6.9 亿输出 token——按 API 价格约合 16.5 万美元。Mike 迁移的主体部分消耗了 2700 万 token。

不过，迁移的理由不再非得是生死攸关。更新日志里一年的内存 bug 补丁，或者一个长期存在的瓶颈，现在就足以立项。

编译步骤正是 Mike 项目的动因。他团队维护的内部工具以单一二进制文件的形式交付给用户。用 Python 工具链产出这个二进制，每个平台大约要 8 分钟，每次发布在构建矩阵上的总等待时间达 30 分钟。迁移之后，同样的编译只需约 2 秒，二进制启动速度快了 6 倍，团队还得以砍掉一条独立的部署管道。

为什么 AI 改变了代码迁移的账本

Claude Fable 5 是我们最强的一般可用（GA）模型。Fable 和 Opus 4.8 尤其擅长用子智能体（subagent）去委派、指挥和验证并行工作流，并能为既定目标寻找多条路径。 

大型代码迁移是这些先进模型格外有效的用武之地，原因如下：

  • 工作是可并行的。任务可以拆到数千个独立单元（如文件和 crate）上执行，智能体可以同时开工，而不是一个等一个。
  • 上下文清晰而完备。旧代码就是给模型的绝佳规格说明。它同时也是构建翻译智能体行动指南的核心参照。
  • 自带裁判。很多大型代码库都带有测试套件，智能体可以用它来验证自己的工作。当验证标准客观时，智能体的表现最好，因为模型可以对着一个 ground truth 连续打磨几天，无需人来仲裁质量。
  • 待办队列自动生成。编译器或测试一旦失败，失败项就成了智能体下一个要修的任务。
  • 要求一致性与边界情况处理。整个流程的设计让漂移无处藏身：审查者引用规则来支撑每一条发现，于是违规不再是悄悄的偏离，而是队列里的一个任务项。而当智能体真的撞上一个边界情况，修复方案就会变成之后所有智能体都要遵守的规则。

正如下文将看到的，Mike 和 Jarred 都在迁移过程的关键步骤用到了 Fable，尤其是顾问模式（advisory pattern）——用多个模型级别组合来优化 token 消耗。

大规模代码迁移的六步

下面的流程已经泛化，以便适用于多种语言和场景。更多细节可以读 Jarred 的博客。你也可以拿到 Migration starter kit。 说明：starter kit 是对上述流程的泛化模板，并不是这两次具体移植当时跑的那套。

先决条件

开始迁移项目之前，先决条件是手头有一个够强的裁判，否则你既没有退出条件，也没有成功度量。 

这个裁判必须能在同等条件下评估原代码和目标代码。用原语言写的测试套件，常常依赖目标代码里不会存在的内部函数。 

要建这个裁判：

  • 给现有测试分类。用 Claude 识别哪些测试可以表达成外部调用，哪些依赖不会被移植的内部实现。 
  • 改写成可移植断言。把面向外部的测试转成能同时对着原版和移植版跑的断言。用对抗性智能体核验改写后的测试没有把断言变弱。
  • 校验裁判。先对着原代码跑，确认它通过。再对着故意弄坏的代码跑，确认它失败——抓不住破坏的裁判，就不是裁判。

Jarred 有一套用第三种语言（TypeScript）写的大型测试套件，但大多数项目不会有这种条件。在 Python 到 TypeScript 的移植里，Mike 做了一个由七个真实场景组成的一致性 harness，并把任何行为变化都当成必须修的 bug。 

进入各阶段之前，这张图可能帮你跟上节奏。它大体沿用 Jarred 的方法，每个阶段都有审查和关卡。Mike 用了类似的整体结构和类似的循环工作流，但他把整次迁移从头跑到尾，再根据结果改规则和工作流，然后重跑——每次都丢掉产出，直到第三次。

第 1 步：编写规则手册、依赖图和缺口清单

这一阶段我们在打迁移的地基：一份需要重构而不是只做翻译的位置清单、一本如何翻译代码的规则手册，以及一张用来给迁移实现工作流排序的依赖图。 

顺序很重要：规则手册必须先于缺口清单。缺口清单由规则手册的默认值覆盖不到的地方定义，两者会在一次联合审计里一起被检验。

规则手册

规则手册的具体形态，取决于你一开始必须做的关键架构决策。其中最重要的是：新代码是沿用同样的结构，还是彻底重新设计。 

如果是前者（Jarred），规则手册主要会是查找表，在语言之间翻译类型和惯用法，并把更难翻译的部分指向缺口清单。如果是后者（Mike），它会是一份设计文档。 

Jarred 通过和 Claude 对话来写规则手册，为每个含糊地带形成一条政策。他还用了八个子智能体，专门按他自己的直觉审查八类常见失败模式。

依赖图

你需要理解文件依赖，才能有效拆出并行迁移的工作流，知道哪些文件先迁、哪些文件放进同一批次。有些语言和代码库有显式清单，这会很容易；但对遗留代码库，以及 C/C++ 和 Python 这类流行语言，这些依赖需要被发现并画出来。

Claude Code 可以派出智能体去创建并运行一个确定性脚本，产出这张图。migration kit 里的提示词用一个工作流来创建审查-修复循环。 说明：starter kit 是对本文流程的泛化模板，并不是这两次具体移植当时跑的那套。

缺口清单与怀疑派审查者

新语言有旧语言必须被满足的不同要求。Zig 到 Rust 的差别是手动内存管理（C 和 C++ 也是同样的工作方式）。例如：

Zig

fn readConfig(allocator: std.mem.Allocator) ![]u8 {
    const buf = try allocator.alloc(u8, 1024);
    // ...fill buf...
    return buf; // caller must free this — but only the comment says so
}

// A caller that forgets 'defer allocator.free(buf)' still compiles — the leak only surfaces at runtime.

Rust

fn read_config() -> Vec<u8> { 
let buf = vec![0u8; 1024]; 
// ...fill buf... 
buf // ownership moves to the caller; memory is freed automatically 
} 
// Use it after it's moved? Free it twice? Neither compiles. 
// Forget to free it? There's no free call to forget — drop is automatic.

Python 到 TypeScript 的缺口是接口和契约。Python 不要求声明它接受什么形状的对象、返回什么，TypeScript 要求。例如：

Python

def register(handler):
    handler.setup()
    return handler.run({"retries": 3})

# Any object with .setup() and .run() works here. Which objects actually get passed in? Read the whole codebase to find out.

TypeScript

interface RunResult { ok: boolean } 

interface Handler 
{ setup(): void; 
run(opts: { retries: number }): Promise<RunResult>; 
} 

function register(handler: Handler): Promise<RunResult> { 
handler.setup(); 
return handler.run({ retries: 3 }); } 

// The contract must be written down before this compiles

Jarred 和 Mike 都做了缺口清单文件，把这类隐含知识记下来。Jarred 事先盘点这些缺口，也就是我们这里的做法；Mike 选择先翻译，再通过事后审计做缺口清单。你可能两边都得做。 

可以看这份用来创建缺口清单文件的 Claude Code 提示词示例。

第 2 步：把规则压测一遍 

这一步是一次迷你迁移，相当于更大迁移的「试航」。 

在这一步，Jarred 用一个智能体按规则手册翻译三个文件，用一个智能体「像资深 Rust 工程师那样」翻译三个文件，再用一个智能体根据 diff 写出新的翻译规则。这个阶段他抓住了两个关键问题，如果扩散到全部 1,448 个文件，会造成大量麻烦。

提示词可以类似这样。

这类压测只对保持结构的迁移有效，因为同一文件的两次翻译可以逐行比较。  如果你的规则手册是重新设计——像 Mike 那样——对等的测试是用对抗性审查者直接攻击设计文档，再用一次可丢弃的端到端运行来验证它。

无论如何，翻译出来的文件都扔掉。目标是打磨规则，不是做增量进度。

第 3 步：翻译全部 

接下来的步骤，你跑的是同一套多智能体循环架构：实现、审查、修复。 

你可以把实现工作卸给更小的模型，把审查留给更大的模型。例如，Mike 在主迁移里铺开 12 个子智能体时用了 Claude Sonnet。 

工作队列应当是机械的。一段批处理脚本通过检查翻译后的文件是否已在磁盘上，来决定什么算做完，再把待处理文件切成批次交给实现智能体。因为队列每次都从磁盘重建，迁移从构造上就是可恢复的。

这个阶段，智能体对自己做多少工作可能过于谨慎。修法可以是一条直白、加重语气的提示指令，并说明编译器会在下一步抓住错误。

翻译者没法有把握执行的任何东西，都用 // TODO(port): <reason> 标出来，留到第 4 步处理。从这里开始，待办清单会自己写出来：编译器枚举错误，冒烟测试找出崩溃，套件报告失败。

两个对抗性审查者在彼此隔离的上下文里评估实现者的工作，审查者之间的分歧交给第三个智能体。当审查者在多个文件里反复抓住同一类错误时，修的不是单个文件。你往规则手册里加一句话，并重新生成受影响的批次。规则手册在这一步会持续变长；代码从不被手工打补丁去迁就它。

这一步要注意的一个重要设计决策是编译器放在哪里。Mike 在每个循环里都跑 TypeScript 编译器，因为它几秒就能检查一个单元。Jarred 完全禁止循环里出现编译器，把它推迟到下一步，因为 cargo 要花几分钟。

到这一步，重活已经做完大半，提示词也开始变短。

第 4、5、6 步：编译、运行，并对齐行为

这三步共用同一套循环架构，需要的人工判断也越来越少，所以我们放在一起讲。

例如，第 4 步常常会溶进第 3 步，这取决于语言和迁移规模。 

取决于编译步骤的规模和难度，智能体可能根本不跑这一步。Jarred 用一个编排脚本在整个工作区调用一次编译器。然后「修复智能体」并行扫错误列表，并做对抗性审查。构建再跑一遍，如此循环。 

审一眼错误列表，有助于抓住可能需要调整的系统性问题。例如，Jarred 在修掉 Zig 惰性编译能容忍的循环导入之后，撞上了数千个 Rust 模块错误。他通过编码一段逻辑来分类哪些依赖该删、该挪、该重构边界，从而修好了这个循环。 

第 5 步也有类似编译器错误列表的机械事实来源：冒烟测试里的崩溃。同样，循环的修法是把问题归成类，这里按根因分组，再交给对抗性子智能体审查。 

第 6 步也是这个故事的结尾：比较两套代码库上的程序行为。

文件现在已经翻译、编译、冒烟测试过了。接下来把它们分片，并对着它们跑（先决条件阶段准备好的）测试套件。用「修复智能体」对照两套代码库审查失败的测试。对抗性审查者检查它们的修复。

这个循环的下一阶段是 build daemon，它是唯一被允许重建二进制的进程。修复者写补丁；daemon 把它们打成批，重建一次，重跑受影响的测试，再把结果喂回去。这把最贵的操作串行化了，而不是让多个智能体各自触发。

当同一失败在许多测试里重复出现时，修复往上游走：你修改产出这个 bug 的那条规则，并只重新生成这条规则碰过的文件。

Mike 的做法在这里很重要，因为很多开发者不会有一套已经建好或已经移植的测试套件。Mike 让 Claude 写了一个小脚本，对着新移植版和原来的 Python 代码库跑 7 个真实场景，并 diff 结果。每个失败场景都有自己的修复智能体，循环一直跑到七个都通过。

然后他又往前走了一步。Claude 设计了自己的端到端测试套件，并连续四个晚上自主跑、修坏掉的部分、再跑。结果，它抓住了任何场景清单都预料不到的那些纸割伤。

教训是：缺少测试套件并不会挡住这一步。如果你继承不到裁判，就让 Claude 建一个。无论哪种，你的原代码库都是 ground truth。

代码迁移最佳实践

每一次运行都会教给我们上一次没有的东西。可以相当有把握地说，你下一次迁移也会教给你这份指南写不到的东西。但有几条实践在每个项目里都站得住：

  • 别盲目照着这份指南走。每一次迁移都不同。把它当作起点，在投入之前先和 Claude 一起规划你这次具体的迁移。
  • 别盯着单个失败。单个失败是循环的工作。修复智能体把它们烧掉。你的注意力应该放在模式上。 
  • 让审查对抗化，让验证机械化。对抗性审查让任务能跑得更久，也常常值得那份 token 消耗。让脚本——编译器、diff、测试套件——当裁判。 
  • 别处处都用最大的模型。token 花费集中在循环里，所以要刻意设计它们。较小的模型很适合高通量的实现铺开；把最大的模型留给审查者，以及任何会写出其他智能体要遵守的规则的环节。
  • 把人工时间压到前面。规则手册和压测最耗时间。之后大多是队列在往下烧。 
  • 让工作队列机械且可恢复。做完应当意味着「输出文件已经在磁盘上」。 

审循环结果，而不是审代码

Jarred 的 Bun 迁移现在已经在生产里跑，尽管每次迁移都有取舍。例如，大约 4% 的 Rust 代码坐在 “unsafe” 块里，大多是 C/C++ 边界上的单行指针操作。

但新代码库可以量得出地更好。团队工具能检测到的每一个内存泄漏都已修好：一个重复构建 2,000 次的基准，内存从 6,745 MB 降到 609。Linux 和 Windows 上的二进制小了 19%。跨语言优化还让 HTTP 服务以及 next build、tsc 这类真实工作负载快了 2–5%。 

想想是不是时候重新算一遍你那份被长期搁置的迁移账。挑出你一直在容忍的那个代码库，问问 Claude 对它来说迁移流程会是什么样。
