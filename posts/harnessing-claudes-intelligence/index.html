Agent harness 设计：驾驭 Claude 智能的三种模式

阅读英文原文 →

Anthropic 联合创始人 Chris Olah 曾说过，像 Claude 这样的生成式 AI 系统与其说是被"构建"出来的，不如说是被"培育"出来的。研究者设定引导其成长的条件，但最终涌现出的具体结构或能力并不总是可以预测的。

这给基于 Claude 的构建工作带来了一个挑战：agent harness 会将各种假设固化其中，假设 Claude 自己做不了什么，但随着 Claude 能力的提升，这些假设会逐渐过时。

Agent harness 是围绕模型搭建的软件脚手架：包括循环、工具、上下文管理和护栏，它们把原始的智能转化为一个可运行的 agent。Agent harness 设计要做的事情，就是决定哪些东西应该放进这个脚手架，以及随着模型进步，哪些东西可以从中拿掉。

在本文中，我们分享三种模式，帮助团队在构建应用时跟上 Claude 不断演进的智能，同时兼顾延迟与成本：善用 Claude 已经掌握的东西、不断追问哪些工作可以停止做，以及通过 agent harness 谨慎地划定边界。

1. 依靠模型而非 harness：善用 Claude 已有的知识

我们建议使用 Claude 熟悉的工具来构建应用。

2024 年底，Claude 3.5 Sonnet 仅凭一个 bash 工具和一个用于查看、创建和编辑文件的文本编辑器工具，就在 SWE-bench Verified 上取得了 49% 的成绩——在当时是业界最先进水平。Claude Code 正是基于这些相同的工具构建的。Bash 并不是为构建 agent 而设计的，但它是 Claude 知道如何使用的工具，而且随着时间推移用得越来越好。

我们看到 Claude 将这些通用工具组合成能解决不同问题的模式。例如，Agent Skills、programmatic tool calling 和memory 工具都是基于 bash 和文本编辑器工具构建的。

2. 精简你的 agent harness：不断追问哪些工作可以停止做

Agent harness 会固化各种假设，假设 Claude 自己做不了什么。随着 Claude 能力增强，这些假设应当被重新检验。

让 Claude 编排自己的行动

一个常见的假设是：每个工具的返回结果都应该回流到 Claude 的上下文窗口中，用来指导下一步行动。但以 token 的形式处理工具结果可能很慢、很贵，而且没有必要——如果结果只需要传给下一个工具，或者 Claude 只关心输出中的一小部分。

设想读取一张大表格来推理其中的一列：整张表都会进入上下文，Claude 要为每一行它并不需要的数据支付 token 成本。这个问题可以通过工具设计来解决，比如使用硬编码的过滤器。但这并没有触及问题的本质：agent harness 正在替 Claude 做一个编排决策，而这个决策由 Claude 自己来做更合适。

给 Claude 一个代码执行工具（例如 bash 工具或特定语言的 REPL）可以解决这个问题：它让 Claude 能够编写代码来表达工具调用以及调用之间的逻辑。这样，不再由 harness 决定每个工具调用的结果都作为 token 处理，而是由 Claude 决定哪些结果直接传递、过滤或管道式地送入下一次调用而不经过上下文窗口。只有代码执行的最终输出才会进入 Claude 的上下文窗口。

编排决策从 harness 移交给了模型。由于代码是 Claude 编排行动的通用方式，一个强大的编码模型同时也是一个强大的通用 agent。采用这一模式后，Claude 在非编码类评测上也表现出色：在 BrowseComp（一个测试 agent 浏览网页能力的基准）上，让 Opus 4.6 具备过滤自身工具输出的能力，将其准确率从 45.3% 提升到了 61.6%。

让 Claude 管理自己的上下文

任务特定的上下文会引导 Claude 对 bash 和文本编辑器工具等通用工具的使用。一个常见的假设是，系统提示词应当由人工精心编写任务特定的指令。问题在于，把指令预先塞进提示词的做法无法扩展到大量任务：每增加一个 token 都会消耗Claude 的注意力预算，而用很少用到的指令预先填满上下文是一种浪费。

让 Claude 能够访问 skills 可以解决这个问题：每个 skill 的 YAML frontmatter 是一段预先载入上下文窗口的简短描述，提供该 skill 内容的概览。如果任务需要，Claude 可以通过调用读文件工具来渐进式地读取完整的 skill。

如果说 skills 给了 Claude 自由拼装自己上下文窗口的能力，那么上下文编辑（context editing）则是反向操作：它提供了一种选择性移除已过时或无关上下文的方式，比如旧的工具结果或思考块。

借助 subagents，Claude 越来越善于判断何时该切换到一个全新的上下文窗口，以隔离特定任务的工作。在 Opus 4.6 上，生成 subagent 的能力使其在 BrowseComp 上的成绩比最佳单 agent 运行提升了 2.8%。

让 Claude 持久化自己的上下文

长时间运行的 agent 可能超出单个上下文窗口的限制。一个常见的假设是，记忆系统应当依赖模型外部的检索基础设施。而我们的许多工作都聚焦于给 Claude 一些简单的方式，让它自己决定持久化哪些内容。

例如，compaction（压缩）让 Claude 能够总结过去的上下文，从而在长周期任务中保持连续性。经过多个版本的迭代，Claude 在选择记住什么方面越来越好。例如在 BrowseComp（一个 agentic 搜索任务）上，无论我们给 Sonnet 4.5 多少压缩预算，它的成绩都稳定在 43%。而 Opus 4.5 在同样的设置下达到了 68%，Opus 4.6 则达到了 84%。

记忆文件夹（memory folder）是另一种做法，它允许 Claude 将上下文写入文件，之后按需读取。我们看到 Claude 将其用于 agentic 搜索。在 BrowseComp-Plus 上，给 Sonnet 4.5 一个记忆文件夹将准确率从 60.4% 提升到了 67.2%。

长周期游戏（例如宝可梦）是 Claude 更好地使用记忆文件夹的一个例子。Sonnet 3.5 把记忆当成流水账，记录的是 NPC（非玩家角色）说过的话，而不是真正重要的信息。跑了 14,000 步之后，它留下了 31 个文件——包括两个内容几乎重复、关于毛毛虫宝可梦的文件——而且人还在第二个城镇：

caterpie_weedle_info:
- Caterpie and Weedle are both caterpillar Pokémon.
- Caterpie is a caterpillar Pokémon that does not have poison.
- Weedle is a caterpillar Pokémon that does have poison.
- This information is crucial for future encounters and battles.
- If our Pokémon get poisoned, we should seek healing at a Pokémon
  Center as soon as possible.

后来的模型则会写下战术笔记。Opus 4.6 在同样的步数下，拥有按目录组织的 10 个文件、三枚道馆徽章，以及一份从自己的失败中提炼出来的经验教训文件：

/gameplay/learnings.md:
- Bellsprout Sleep+Wrap combo: KO FAST with BITE before Sleep
  Powder lands. Don't let it set up!
- Gen 1 Bag Limit: 20 items max. Toss unneeded TMs before dungeons.
- Spin tile mazes: Different entry y-positions lead to DIFFERENT
  destinations. Try ALL entries and chain through multiple pockets.
- B1F y=16 wall CONFIRMED SOLID at ALL x=9-28 (step 14557)

3. 在 harness 设计中谨慎划定边界

Agent harness 为 Claude 提供结构性约束，以保障 UX、成本或安全。

设计上下文以最大化缓存命中

Messages API 是无状态的。Claude 看不到之前轮次的对话历史。这意味着 agent harness 需要在每一轮将新的上下文连同过去的所有操作、工具描述和指令一起打包发给 Claude。

提示词可以根据设定的断点（breakpoint）进行缓存。也就是说，Claude API 会把断点之前的上下文写入缓存，并检查这些上下文是否与之前的缓存条目匹配。

由于缓存 token 的成本只有基础输入 token 的 10%，在 agent harness 中遵循以下几条原则有助于最大化缓存命中：

为 UX、可观测性或安全边界使用声明式工具

Claude 并不一定了解应用的安全边界或 UX 界面。Claude 发出工具调用，由 harness 来处理。bash 工具给了 Claude 广泛的程序化操作能力去执行动作，但它只给 harness 一个命令字符串——每个动作的形态都一模一样。把动作提升为专用工具，harness 就获得了针对具体操作的钩子，拿到带类型的参数，可以拦截、把关、渲染或审计。

需要安全边界的动作是专用工具的天然候选。可逆性往往是一个好的判断标准，难以撤销的操作（例如外部 API 调用）可以通过用户确认来把关。像 edit 这样的写入工具可以加入过期检查，防止 Claude 覆盖自上次读取后已被修改的文件。

当一个动作需要呈现给用户时，工具同样很有用。例如，可以把工具调用渲染为弹窗，向用户清晰地展示问题、提供多个选项，或者阻塞 agent 循环直到用户给出反馈。

最后，工具对于可观测性也很有价值。当动作是一个带类型的工具时，harness 就能拿到结构化的参数，用于日志、追踪和回放。

是否把动作提升为工具，这个决策应当被持续重新评估。例如，Claude Code 的 auto-mode（发布时处于研究阶段）为 bash 工具提供了安全边界：由另一个 Claude 读取命令字符串并判断其是否安全。这种模式可以减少对专用工具的需求，但只应用于用户信任其总体方向的任务。对于某些高风险操作，专用工具依然有其价值。

Agent harness 设计的未来

Claude 智能的前沿始终在变化。每当它的能力出现一次阶跃式提升，关于"Claude 做不了什么"的假设都需要重新检验。

这样的模式在不断重演。在我们为长周期任务构建的一个 agent 中，Sonnet 4.5 会因为察觉到上下文极限临近而提前收尾。为了应对这种"上下文焦虑"，我们加入了重置机制来清空上下文窗口。而到了 Opus 4.5，这一行为消失了。我们为弥补缺陷而构建的上下文重置，反而成了 agent harness 中的累赘。

清除这些累赘很重要，因为它们可能成为Claude 性能的瓶颈。随着时间推移，我们应用中的结构或边界应当基于一个问题来修剪：哪些工作我可以停止做？
