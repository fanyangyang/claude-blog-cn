Claude Code 如何在大型代码库中工作：最佳实践与入手指南

阅读英文原文 →

Claude Code 已经在生产环境中运行于数百万行的 monorepo、有数十年历史的遗留系统、横跨数十个仓库的分布式架构，以及拥有数千名开发者的组织中。这些环境带来了较小、较简单代码库不会遇到的挑战，比如每个子目录的构建命令各不相同，或者遗留代码散落在没有共同根目录的多个文件夹中。

本文总结了我们在实践中观察到、并已帮助 Claude Code 大规模成功落地的模式。我们所说的“大型代码库”涵盖多种部署形态：数百万行的 monorepo、数十年间逐步构建的遗留系统、分散在多个仓库中的数十个微服务，或上述情况的任意组合。其中也包括使用一些团队通常不会与 AI 编码工具联系起来的语言的代码库，例如 C、C++、C#、Java、PHP。（在这些场景下，Claude Code 的表现比大多数团队的预期要好，尤其是最近发布的模型版本。）虽然每个大型代码库的部署都受到其具体的版本控制、团队结构和长期积累的惯例的影响，但本文所述模式具有普遍适用性，对于正在考虑采用 Claude Code 的团队来说是一个很好的起点。

Claude Code 如何在大型代码库中导航

Claude Code 像软件工程师一样在代码库中工作：它遍历文件系统、读取文件、使用 grep 精确查找所需内容，并顺着代码库中的引用追根溯源。它在开发者本地机器上运行，不需要构建、维护代码库索引，也不需要把索引上传到服务器。 

基于 RAG 的 AI 编码工具的原理是对整个代码库做嵌入（embedding），并在查询时检索相关片段。在大规模场景下，这类系统可能失效，因为嵌入管道无法跟上活跃工程团队的节奏。当开发者查询索引时，索引反映的是几周、几天甚至几小时之前的代码库状态。检索结果于是会返回团队两周前就已重命名的函数，或引用上个冲刺里已删除的模块，而且不会提示这些信息已经过时。

Agentic 搜索（智能体搜索）可以避免这些失败模式。当数千名工程师持续提交新代码时，没有需要维护的嵌入管道或集中式索引。每个开发者的实例都直接基于实时代码库工作。 

但这种方式也有取舍：只有当 Claude 拥有足够的起始上下文、知道该往哪里找时，它才能发挥最佳效果。这意味着 Claude 导航能力的优劣取决于代码库的设置是否完善，比如是否用 CLAUDE.md 文件和 Skills 分层提供上下文。如果你让它在一个十亿行的代码库中查找某种模糊模式的所有实例，工作还没开始就会撞上上下文窗口的限制。在代码库设置上投入精力的团队，效果明显更好。

harness 与模型同等重要

关于 Claude Code 最常见的误解之一，是认为它的能力完全由所用的模型决定。团队往往关注模型的基准测试成绩以及在测试任务上的表现。而实际实践中，围绕模型构建的生态系统——也就是 harness（运行框架）——比模型本身更能决定 Claude Code 的表现。

harness 由五个扩展点构成——CLAUDE.md 文件、Hooks、Skills、插件和 MCP 服务器——各自承担不同的职能。团队搭建这些组件的顺序很重要，因为每一层都建立在前一层的基础之上。此外还有两项能力——LSP 集成和 Subagents——可以进一步完善整套设置。下面我们逐一说明这些组件和能力的作用： 

CLAUDE.md 文件要最先建立。这是 Claude 在每次会话开始时自动读取的上下文文件：根目录文件提供全局视角，子目录文件承载局部约定。它们为 Claude 提供做好任何事情所需的代码库知识。由于无论任务是什么它们都会在每次会话中加载，让它们聚焦于具有广泛适用性的内容，可以避免拖累性能。

Hooks 让整套设置能够自我改进。大多数团队把 hooks 当作防止 Claude 犯错的脚本，但它们更有价值的用途是持续改进。一个 stop hook 可以回顾会话中发生的事情，趁着上下文还新鲜，提出 CLAUDE.md 的更新建议。一个 start hook 可以动态加载团队特定的上下文，让每个开发者无需手动配置就能获得适合自己模块的环境。对于 lint、格式化这类自动检查，hooks 以确定性的方式执行规则，比指望 Claude 记住某条指令的结果更稳定一致。

Skills 让合适的专业知识按需可用，又不会撑大每次会话。在包含数十种任务类型的大型代码库中，并非所有专业知识都需要出现在每次会话里。Skills 通过渐进式披露（progressive disclosure）解决这一问题：把原本会争夺上下文空间的专业工作流和领域知识剥离出去，只在任务需要时才加载。例如，安全审查 skill 只在 Claude 评估代码漏洞时加载，而文档处理 skill 只在代码发生变更、需要更新文档时加载。

Skills 还可以限定在特定路径下生效，只在代码库的相关部分被激活。负责支付服务的团队可以把他们的部署 skill 绑定到该目录，这样当有人在 monorepo 的其他位置工作时，它绝不会自动加载。

插件 让行之有效的配置得以分发。大型代码库的一个挑战是，好的配置可能只在小圈子里流传。插件把 Skills、Hooks 和 MCP 配置打包成一个可安装的包，新工程师入职第一天安装这个插件，就能立即获得与老用户相同的上下文和能力。插件更新可以通过托管市场在整个组织内分发。 

例如，与我们合作的一家大型零售企业构建了一个将 Claude 接入其内部数据分析平台的 skill，让业务分析师无需离开工作流就能拉取绩效数据。在向业务部门全面推广之前，他们先把它作为插件分发。

语言服务器协议（LSP）集成让 Claude 拥有与开发者在 IDE 中相同的导航能力。大多数大型代码库的 IDE 本来就运行着 LSP，支撑着“转到定义”和“查找所有引用”功能。把这些能力暴露给 Claude，就赋予了它符号级的精度：它可以顺着函数调用找到定义、跨文件追踪引用，并区分不同语言中同名的函数。没有 LSP，Claude 只能做文本模式匹配，可能会定位到错误的符号。我们合作过的一家企业软件公司在全面推行 Claude Code 之前，先在整个组织内部署了 LSP 集成，专门为了让 C 和 C++ 的导航在规模化场景下可靠工作。对于多语言代码库来说，这是最有价值的投资之一。

MCP 服务器扩展一切。MCP 服务器是 Claude 连接内部工具、数据源和 API 的方式，否则它无法触达这些资源。最成熟的团队构建了 MCP 服务器，将结构化搜索暴露为 Claude 可直接调用的工具。另一些团队则把 Claude 接入内部文档、工单系统或数据分析平台。

Subagents 把探索与编辑分离。Subagent 是一个拥有独立上下文窗口的隔离 Claude 实例，接收任务、完成工作，然后只把最终结果返回给父实例。一旦 harness 就绪，一些团队会启动一个只读 subagent 去摸清某个子系统并把发现写入文件，然后让主 agent 在掌握全貌的情况下进行编辑。

来自成功部署的三种配置模式

如何为大型代码库配置 Claude Code，很大程度上取决于代码库的结构。不过在我们观察到的部署中，有三种模式反复出现。

让代码库在规模化场景下可导航

Claude 在大型代码库中的助力上限，取决于它找到正确上下文的能力。每次会话加载过多上下文会降低性能，而上下文太少则会让 Claude 盲目摸索。最有效的部署会提前投入精力，让代码库对 Claude 可读。有几种模式屡见成效：

  • 保持 CLAUDE.md 文件精简且分层。Claude 在代码库中移动时会叠加式地加载它们：根目录文件提供全局视角，子目录文件承载局部约定。根目录文件应只包含指引和关键陷阱，其余内容都会沦为噪音。
  • 在子目录而非仓库根目录初始化。Claude 在限定于与任务真正相关的代码库范围内时表现最佳。在 monorepo 中，这可能有些反直觉，因为工具链通常假设拥有根目录权限；但 Claude 会自动向上遍历目录树并加载沿途找到的每个 CLAUDE.md 文件，因此根级别的上下文不会丢失。
  • 按子目录限定测试和 lint 命令。当 Claude 只改了一个服务却运行完整测试套件，会导致超时，并把上下文浪费在无关输出上。子目录级别的 CLAUDE.md 文件应写明适用于该部分代码库的命令。这种做法非常适合每个目录都有独立测试和构建命令的面向服务的代码库。在存在深度跨目录依赖的编译型语言 monorepo 中，按子目录限定较难实现，可能需要针对项目的构建配置。
  • 使用 .ignore 文件排除生成文件、构建产物和第三方代码。把 permissions.deny 规则提交到 .claude/settings.json 意味着这些排除规则纳入了版本控制，团队中每个开发者无需自行配置就能获得同样的降噪效果。在有些代码库中，生成文件本身就是开发工作的对象。从事代码生成器开发的开发者可以在本地设置中覆盖项目级排除规则，而不影响团队其他人。
  • 当目录结构本身不够用时，构建代码库地图。对于代码没有归入常规目录结构的组织，可以在仓库根目录放一个轻量级的 markdown 文件，列出每个顶层文件夹及其内容的单行描述，让 Claude 在打开文件之前先扫一遍这份目录。对于有数百个顶层文件夹的代码库，最好采用分层方式：根文件只描述最高层结构，子目录的 CLAUDE.md 文件提供下一层细节，随 Claude 在目录树中移动按需加载。对于较简单的场景，直接 @ 提及 Claude 应参考的具体文件或目录也能达到同样效果。
  • 运行 LSP 服务器，让 Claude 按符号而非字符串搜索。在大型代码库中 grep 一个常见函数名会返回数千条匹配，Claude 得逐个打开文件来判断哪条重要，白白消耗上下文。LSP 只返回指向同一符号的引用，过滤发生在 Claude 读取任何内容之前。 配置方法是为你的语言安装代码智能插件及对应的语言服务器二进制文件；Claude Code 文档列出了可用插件和故障排查方法。

一点提醒：在一些极端情况下，即使是分层 CLAUDE.md 方案也会失效，例如拥有数十万个文件夹、数百万个文件的代码库，或使用非 Git 版本控制的遗留系统。我们会在本系列后续文章中讨论这些挑战。关于遗留系统，可参阅 AI 如何打破 COBOL 现代化的成本壁垒。

随模型智能演进，持续维护 CLAUDE.md 文件 

随着模型演进，为当前模型编写的指令可能对未来的模型产生反作用。那些曾引导 Claude 走出其过去薄弱环节的 CLAUDE.md 文件，在新模型发布后可能变得多余，甚至成为束缚。例如，一条要求 Claude 把每次重构拆成单文件变更的 CLAUDE.md 规则，或许曾帮助早期模型保持正轨，却会阻止新模型完成它本已擅长处理的跨文件协同编辑。 

为弥补特定模型局限（无论是模型推理能力还是 Claude Code 自身工具）而构建的 Skills 和 Hooks，在这些局限不复存在后就成了负担。例如，在 Perforce 代码库中通过拦截文件写入来强制执行 p4 edit 的 hook，在 Claude Code 原生支持 Perforce 模式之后就变得多余了。

团队应预期每三到六个月做一次认真的配置审查，而在重大模型发布后感觉性能停滞不前时，也值得做一次。 

为 Claude Code 的管理和推广指定负责人

仅靠技术配置无法推动普及。做得出色的组织在组织层面同样投入了精力。

推广最快的团队在开放大规模访问之前，都先做了专门的基础设施投入。一个小团队（有时甚至只有一个人）提前把工具链搭好，开发者第一次接触 Claude 时它就已经融入了工作流。在一家公司，几位工程师构建了一整套插件和 MCP，第一天就可用；在另一家公司，一个专门管理 AI 编码工具的团队在推广开始前就把基础设施准备就绪。在这两个案例中，开发者的初次体验都是高效而非受挫，普及也由此展开。

目前承担这项工作的团队大多隶属开发者体验或开发者 productivity 部门，这通常也是负责新工程师入职和构建开发者工具的职能。多个组织中出现了一个新兴角色——agent manager：一个专门管理 Claude Code 生态的混合型 PM/工程师职能。对于没有专职团队的组织，最小可行版本是一个 DRI（直接负责人）：一个人对 Claude Code 配置拥有所有权，有权就设置、权限策略、插件市场和 CLAUDE.md 规范做出决策，并负责让它们保持更新。

自下而上的推广能激发热情，但若没有人来集中沉淀有效经验，就会碎片化。你需要由个人或团队来整理并推广正确的 Claude Code 规范（例如标准化的 CLAUDE.md 层级，或一套精选的 Skills 和插件）。缺少这项工作，知识会局限于小圈子，普及也会停滞。 

在大型组织尤其是受监管行业中，治理问题会很早浮现，例如：谁来决定哪些 Skills 和插件可用？如何防止数千名工程师各自重复造轮子？如何确保 AI 生成的代码与人工编写的代码走同样的评审流程？为了尽早应对这些问题，我们建议从一组明确批准的 Skills、强制代码评审流程和有限的初始访问权限开始，随信心建立逐步扩大。 

我们观察到，推广最顺畅的组织会尽早建立跨职能工作组，把工程、信息安全和治理方面的代表召集到一起，共同定义需求并制定推广路线图。

将这些模式应用到你的组织

Claude Code 围绕传统软件工程环境设计：工程师是代码库的主要贡献者，仓库使用 Git，代码遵循标准目录结构。大多数大型代码库符合这一形态，但非传统设置——例如包含大量二进制资源的游戏引擎、采用非常规版本控制的环境，或由非工程师向代码库贡献代码的场景——需要额外的配置工作。我们的建议以常规设置为前提，所描述的模式已在众多客户处得到验证。  余下的复杂性需要结合你的代码库、工具链和组织具体情况来判断。Anthropic 的 Applied AI 团队正是为此与工程团队直接合作，把这些模式转化为符合你组织具体需求的方案。
