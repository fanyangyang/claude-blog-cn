驾驭 Claude Code：何时使用 CLAUDE.md、skills、hooks 和 subagents

驾驭 Claude Code 的七种方式——CLAUDE.md 文件、rules、skills、subagents、hooks 等——以及按上下文开销和约束力判断该用哪一种。

Claude 的设计初衷就是顺应你的工作方式，而在 Claude Code 中，你还可以对它进行自定义。

指导 Claude 行为的方法共有七种：CLAUDE.md 文件、规则（rules）、技能（skills）、子智能体（subagents）、钩子（hooks）、输出样式（output styles），以及追加系统提示词。

每种方法各自控制：

  • 指令何时被加载到上下文中； 
  • 它能否在长会话中持续存在（压缩行为）；以及 
  • 它拥有多大的约束力。

下表快速概括了各方法之间的关键差异，本文其余部分则提供更多细节，以及一套判断每条 Claude 指令该放在何处的决策框架。

七种传递指令的方法

自定义 Claude Code 行为的方式共有七种：CLAUDE.md 文件用于常驻的项目上下文，规则用于硬性约束，技能用于可复用的流程，子智能体用于委派工作，钩子用于确定性自动化，输出样式和系统提示词追加则用于全局性变更。

每种方法都在上下文开销与约束力之间做权衡。这些方法影响 Claude 的行为，而另外两个独立的旋钮——你选择的模型和努力级别——则决定它的能力上限和工作投入程度。

CLAUDE.md 文件

CLAUDE.md 是位于项目根目录的 markdown 文件。它在会话开始时加载进上下文，并在整个会话期间一直留在那里。

构建命令、目录布局、monorepo 结构、编码规范和团队约定都很适合放在这里。

它有两种类型，加载方式各不相同： 

  • 始终加载：第一类是根目录的 CLAUDE.md 文件，可以放在共享仓库中，也可以本地保存针对某个项目的个人偏好。这些文件都会在会话开始时加载，且在长会话中不会丢失或衰减。当 Claude Code 压缩对话时，会重新读取这些文件。
  • 按需加载：位于会话初始化目录之下各子目录中的 CLAUDE.md 文件。例如，app/api/CLAUDE.md 会在 Claude 读取 app/api 下的文件时加载，而不是在会话开始时。它的压缩行为与路径范围规则相同：丢失，直到再次触及该子目录。 

在共享仓库中，CLAUDE.md 会像任何无人维护的配置文件一样不断膨胀：每个团队都在往里追加自己的指令，却没人删除任何内容。其成本会随规模不断累积。

文件中的每一行都会加载到在这个仓库中工作的每位工程师的每个会话里，无论与其任务是否相关。这既消耗 token，也稀释了对真正重要的指令的遵循度。随着文件增长，应把团队专属的规范移入路径范围规则，把流程移入技能，让它们只在相关时才加载。

提示：将 CLAUDE.md 控制在 200 行以内，指定负责人，并像审查代码一样审查对它的修改。内容本身应遵循与任何提示词相同的规则：撰写有效的提示词意味着表述明确、解释约束背后的原因，并给出示例。

可以把这个文件看作给 Claude 的一份代码库概览，或者一个指向其他文件的索引，让 Claude 在需要时自行查阅更多信息。

在 monorepo 中，为每个团队的目录配置独立的子目录 CLAUDE.md，这样各团队只加载自己的规范；开发者还可以使用 claudeMdExcludes 设置，跳过那些其代码从不涉及的团队的文件。

对于必须适用于组织中每个仓库的标准——安全策略、合规要求——可以通过 MDM 或配置管理将集中管理的 CLAUDE.md 部署到开发者机器上，且无法被个人设置排除。

关于设置 CLAUDE.md 的更多内容，参见我们的博客文章《CLAUDE.md 文件：为你的代码库定制 Claude Code》。

规则（Rules）

规则（Rules）是 .claude/rules/ 中的 markdown 文件，用来给 Claude 设定具体的约束或规范。

未限定范围的规则行为类似 CLAUDE.md：会话开始时始终加载，压缩时重新注入。这会在任务并不相关时仍加载上下文，浪费 token。

路径范围规则允许你通过添加 paths 字段来控制加载时机，只在相关时才加载规则指令。

例如：限定在 src/api/** 的规则，在只处理文档的会话中不会进入上下文。只有当 Claude 读取 src/api/ 目录下的文件时才会加载。

看起来是这样：

---
paths:
  - "src/api/**"
  - "**/*.handler.ts"
---
All API handlers must validate input with Zod before processing.

提示：针对特定文件的约束，比如“migration 只能追加、不能改写”，最适合做成带 paths frontmatter 的规则。当指令涉及横切关注点，或某类文件出现在代码库的多个（但不是全部）角落时，优先用路径范围规则，而不是嵌套的 CLAUDE.md 文件。

技能（Skills）

技能（Skills）存放在 .claude/skills/ 中，是包含指令、脚本和资源的文件夹，由 Claude 动态加载。每个技能都有一个带名称、描述和正文的 SKILL.md 文件。

会话开始时只加载名称和描述；完整正文在 Claude 调用该技能时加载，既可以是斜杠命令（/code-review），也可以是自动匹配到当前任务。

例如，/code-review 是内置技能，会审查当前 diff 并报告发现，但不会编辑文件。技能定义了这套打法，所以每次调用时 Claude 都会按同样的结构化方式执行。

压缩时，Claude Code 会在所有已调用技能的共享预算内重新注入它们。如果一次会话里调用了很多技能，最早的会先被丢掉。 

提示：流程性指令，比如部署工作流、发布检查清单或审查流程，应该放进技能，而不是 CLAUDE.md。

Claude Code 自带一些技能，你也可以编写自己的自定义技能。我们的构建 Claude 技能完全指南会告诉你怎么做。

子智能体（Subagents）

子智能体（Subagents）是 .claude/agents/ 中的 markdown 文件，用来定义处理特定旁路任务的隔离助手。每个文件使用 YAML frontmatter（name、description，以及可选的 model 和工具访问字段），后面跟着正文，正文会成为该子智能体的系统提示词。

子智能体和技能类似：名称、描述和工具列表在会话开始时加载，但正文里更大块的上下文不会自动调用。Claude 通过 Agent 工具调用它们，并传入一段提示词字符串。 

子智能体正文里那块更大的指令上下文不但不会自动调用，也根本不会进入父对话。

随后子智能体在自己全新的上下文窗口中运行，回到主会话的只有子智能体的最终消息（往往是许多子任务汇总后的结果）加上元数据。 

这种模式可以扩展：子智能体最多可以嵌套五层，动态工作流可以编排数十到数百个后台智能体，而不需要你把子智能体架构的每个细节都指定清楚。编排计划和中间结果放在脚本变量里，而不是 Claude 的上下文窗口中，这样既能扩展规模，又不会丢掉指令保真度。

提示： 这种隔离，正是你该选子智能体而不是技能的主要原因之一。当旁路任务（比如深度搜索、一轮日志分析或依赖审计）会把你不会再引用的中间结果塞满主对话时，用子智能体。当你希望流程在主线程里展开、以便你能看见并引导每一步时，用技能。

钩子（Hooks）

钩子（Hooks）是用户定义的命令、HTTP 端点或 LLM 提示词，通过在Claude 生命周期中的特定事件上触发（比如文件编辑、工具调用或会话开始），对 Claude 的行为提供更确定的控制。 

你可以在 settings.json、托管策略设置，或 skill/agent 的 frontmatter 中注册钩子。 

钩子有几种类型：command、HTTP、mcp_tool、prompt 和 agent。所有钩子都是确定触发的。前三种确定执行，后两种 prompt 和 agent 则依靠 Claude 的判断而不是一组规则来决定输出。

钩子的上下文开销很低，因为配置或指令位于主上下文窗口之外。harness 会按钩子类型运行 handler（command、http、mcp_tool），或用单独的窗口做模型调用（prompt、agent）。 

有些钩子的输出可能会写入主上下文窗口。例如，阻断型钩子的标准错误会保存在上下文中，好让 Claude 知道这次调用为何被拒绝。 

但大多数钩子不会把输出写入主窗口，除非配置明确要求返回。如果你在压缩前用 PreCompact 事件把聊天历史备份到另一个文件供日后查阅，Claude 并不会知道历史保存在哪个文件里。 

这让这些钩子类型与 CLAUDE.md、规则和技能有本质区别。更多内容见我们的文章 如何配置 hooks。

提示：凡是应当确定发生的事，都用钩子：编辑后跑 linter、完成后发 Slack、或在特定命令执行前拦截。一个 PreToolUse 钩子可以检查任意工具调用，并以退出码 2 拒绝它。

它们上下文开销低，因为它们是 harness 运行的代码，而不是加载进上下文、交给 Claude 的指令。技能和钩子也是设计智能体循环的构建块——那些会重复运行、直到满足停止条件才结束的工作流。

输出样式（Output styles）

输出样式（Output styles）是 .claude/output-styles/ 中的文件，会把指令注入系统提示词。它们从不被压缩，每个会话开始时都会加载，并在会话内首次请求后被缓存，因此上下文开销中等。

因为它们坐在系统提示词里，输出样式在我们目前介绍过的方法中具有最高的指令遵循权重，应当谨慎使用。

更改输出样式会替换默认输出样式（除非你在样式的 frontmatter 中设置 keep-coding-instructions: true）。

在 Claude Code 中，这会去掉那些告诉 Claude 它正在帮助用户完成软件工程任务的指令，以及其他关键的默认指令，例如：

  • 如何界定改动范围； 
  • 何时添加或省略代码注释；
  • 如何处理安全问题；以及 
  • 验证习惯，比如在宣称工作完成之前先跑测试。 

默认情况下，自定义输出样式会丢掉这一切，Claude Code 会更像通用助手，而不是软件工程助手。 

提示：写自定义输出样式之前，先看看内置样式。Proactive、Explanatory 和 Learning 覆盖了最常见的需求（自主性、教学模式、协作编程），你不必自己维护一份样式文件。

追加系统提示词

修改输出样式之外的另一种做法是 append-system-prompt 标志。修改输出样式文件可能对 Claude 的行为造成很大、非预期的改变，而追加标志只是在原始系统提示词上做加法。它不改变 Claude 的角色，只是给默认角色加上指令。 

它也是在调用时传入的，只对当次调用生效，而不会作为文件跨会话持久保存。 

与其他传递指令的方法相比，追加系统提示词的上下文开销可能更高。它会增加输入 token，不过提示词缓存会在会话中首次请求之后降低这项成本。如果要求 Claude 用更冗长或更长的风格，也会增加输出 token。 

提示：追加系统提示词最适合补充具体的编码标准、输出格式或领域知识。请记住，用这种方法追加得越多，遵循度的边际收益越低。一般而言，用这种方法给的指令越多，Claude 遵守得就越不严格，尤其是其中存在相互矛盾时。

何时使用每种方法

如果你发现自己在做下面这些事，可能该考虑给指令换个位置：

在 CLAUDE.md 里写“每次 X，总是做 Y”。如果行为必须可靠发生，比如每次编辑后跑 prettier，或完成后发 Slack，请改用 settings.json 里的钩子。模型选择去跑格式化工具，和格式化工具自动跑起来，不是一回事。

在 CLAUDE.md 里写“永远不要这样做”。当事情绝对不能发生时，指令是错误的工具。大多数时候 Claude 会遵守指令，但在压力下、长会话或含糊情境中，或任务所访问的文件里出现提示词注入时，模型可能跟不上被提示出来的规则。真正的护栏必须是确定的，执行手段是 hooks 和 permissions。一个 PreToolUse 钩子可以检查一次调用，并以退出码 2 阻断它。托管设置（Managed settings） 走得更远：它们由管理员部署，不能被用户的本地配置覆盖，也是强制执行确定的、组织范围护栏的唯一方式。

CLAUDE.md 里有一段 30 行的流程。流程属于技能。CLAUDE.md 放的是 Claude 应当一直记住的事实：构建命令、monorepo 布局、团队约定。部署 runbook 或安全审查检查清单应当放在 .claude/skills/，正文只在调用时加载。

一条没有 paths 的 API 专属规则。如果规则只适用于 src/api/**，用 paths: 限定范围，就能在无关工作期间把它挡在上下文之外。未限定范围的规则在机制上等同于把内容放进 CLAUDE.md：始终加载，始终消耗 token。

把个人偏好写进项目级 CLAUDE.md 文件。 所有基于文件的方法都有用户级对应物，无论你在哪个仓库，每次 Claude Code 会话都会加载。个人偏好用本地文件（始终使用语义化提交信息）。项目级文件留给全团队、但只针对某个代码库的偏好。
