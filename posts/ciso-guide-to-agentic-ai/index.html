零风险不是目标：写给 CISO 的智能体 AI 指南

Anthropic's Deputy CISO, Jason Clinton, shares his team's lessons learned adopting agentic AI, and the risk assessment framework they've developed for building and deploying agents securely.

安全负责人正被要求批准几个月前根本不存在的智能体 AI 用例。董事会想知道这一切是否处于治理之下，而你组织的某个角落，已经有员工在没告诉你的情况下把某个智能体接到了什么东西上。

对这些请求说"不"，会催生影子化采用（shadow adoption）——没有任何遥测数据，而且通常没有关闭开关。不加管控地说"是"，则会酿成事故，而你公司的第一起严重智能体事故将让整个 AI 计划开倒车。 

在智能体 AI 时代，CISO 的职责不是做到零风险。我们的工作是把智能体风险变得可读（legible）且有界（bounded）。这样，我们才能有意识地接受那些我们管得住的风险，让业务按照我们设定的条件前进，而不是绕开我们。 

在本文中，我将分享我们评估智能体安全风险的框架，解释"有界"在实践中意味着什么，并预告我们下一步的工作方向。

后 Mythos 时代：AI 带来的外部风险与内部风险

在此前的一篇博文中，我和同事分享了 AI 如何大幅压缩了从漏洞存在到可用漏洞利用程序（exploit）问世之间的时间，并阐述了组织可以如何缓解这些风险。未来几个月，我们预计大量蛰伏在代码中（有时已多年）未被察觉的漏洞，将被 AI 模型发现并串联成可用的漏洞利用。像 Claude Mythos Preview 和 Claude Mythos 5 这样的前沿模型，已经在发现严重漏洞——包括 OpenBSD、Linux 内核和 Mozilla Firefox 中多年人工审查都漏掉的那些。

这些对任何 GRC（治理、风险与合规）计划都是严峻的风险。缓解并弥合漏洞缺口、为即将到来的漏洞利用浪潮做准备，应当是头等大事。针对这个话题，我们准备了单独一份文档：为 AI 加速的攻击面准备好你的安全计划。本指南将聚焦内部风险。

治理内部风险

对许多组织而言，智能体系统最可能的威胁载体，是通过监督不足的个人智能体把彼此割裂的系统连接起来，从而造成数据泄露。另一个担忧是提示词注入（prompt injection）：攻击者把指令藏在智能体读取的内容里，智能体于是听攻击者的而不是用户的。任何接触不可信内容的智能体都可能暴露，具体取决于模型自身防御的健壮程度。随着模型能力越来越强，它们抵抗注入的水平也在显著提升。虽然攻击成功率在不断下降，但并没有归零。这两个例子之外还有许多隐患，层出不穷的新类别确实让人应接不暇。

评估智能体 AI 风险的四个问题

当一个智能体用例进入我们的审查流程时，我们会用四个问题来评估它的风险： 

  1. 它摄取哪些不可信内容？不可信是指攻击者有可能撰写或篡改的任何东西，包括外部邮件、开放网络、第三方文档或公开代码仓库。如果答案是"没有"，那么智能体特有的风险近乎为零，你可以放心快速推进。
  2. 它能执行哪些操作，代表谁？只读和读写是两回事。工具调用、代码执行和网络出站各自都会扩大暴露面。每个操作都发生在某个身份之下，你必须知道那是谁的身份。
  3. 如果它偏离意图，爆炸半径有多大？范围 × 严重度是个快速算法：这个坏人或这次失控事件能触到一个文件，还是整个组织？后果是异常、麻烦、数据暴露，还是真正的事故？
  4. 我有什么可观测性？你能区分智能体的操作和用户的操作吗？这些数据会落到你的 SIEM 里吗？

这四个问题的答案描绘出你的风险图景，而最小代理权原则（principle of least agency）告诉你该怎么处置它：只授予仍能完成任务的最窄能力（详见我们的 Zero Trust for AI Agents 白皮书）。我们在 Anthropic 的默认姿态是按管理员节奏推进：先启用一小群人，观察遥测数据，再扩大访问范围。请把这四个问题应用到思考高风险智能体系统的新范式中去。

一个与你意图渐行渐远的智能体，与一次内部人员攻击无从区分。安全行业在 2019 到 2022 年间把内部风险（insider risk）确立为一门独立于边界防御的学科——承认系统中最危险的外部攻击载体，往往是攻陷一个本就拥有合法访问权的人。

两者的运营差异在于响应时间：Ponemon Institute 的 2026 年《内部风险成本报告》发现，即便在专门的内部风险项目上投入多年之后，组织平均仍需要 67 天才能遏制一起内部人员事件。而在智能体的执行速度面前，以天计的响应已经太慢了。

智能体的身份光谱

我们部署的一切都处于身份访问模型光谱的两端之一。 

一端是系统服务账号：一种自包含、单一用途、最小权限的身份，只为业务做一件事，背后不挂任何人类身份。事故响应智能体（见下文）、工单分诊智能体或自主代码审查器都属于此类。另一个例子是 Claude Tag——我们新的共享工作区智能体，让人类团队通过 @Claude 在 Slack 等共享工作区中与智能体协作。 

另一端是人类凭证。当员工在笔记本电脑上使用聊天界面或 Claude Cowork 这样的个人智能体运行环境时，键盘后面的人对结果负责——就像他们对用自己凭证做的任何其他事情负责一样。

光谱的中间地带——智能体带着某个人委派的身份，进入这个人并不盯着的系统——正是问责变得模糊的地方。而问责模糊，正是事故变得无法解释的根源。

案例研究：一个事故响应智能体

一年多以前，我们把 Claude 指向了自己的事故响应流程。任何为生产应用值过班的人都懂这个问题：凌晨两点被安全事故的告警叫醒，拉起一个事故响应频道，把对的人拽进来，开始干活。这个过程琐碎、文档繁重、节奏飞快。但只要掌握关于你生产环境和代码库的恰当上下文，其中大部分都可以自动化。 

于是我们造了一个智能体来做这件事。我们给它三个工具的访问权：不含任何 PII 的生产日志只读权限；Slack 访问权限，用于开设事故频道并推进流程；以及在事故解决后起草复盘（postmortem）Google Doc 的能力。 

我们让它过了一遍那四个问题： 

  • 不可信内容：没有。输入是我们自己的日志和内部 Slack，都在信任边界之内，因此注入攻击需要内部人员或被攻陷的账号，而不再是匿名攻击者。
  • 操作：处处可读，写入仅限于新建文档和 Slack 消息。没有编辑或删除，没有权限变更，没有外部端点。
  • 爆炸半径：我们能构想的最坏结果，是把几行略带敏感的日志发进一个本就严格管控的事故频道。
  • 可观测性：每个操作都落入我们的 SIEM，任何意外都会在几分钟内、而不是几周内浮出水面。

这个智能体并非零风险，但它的写入面是有界的，且全程有审计覆盖，这样的风险画像我们是可以接受的。 

不过，这个故事有个有意思的后续：每发布一次新模型，这个智能体都变得更聪明。2025 年 11 月，我们把它从 Claude Opus 4 换到 Claude Opus 4.5，其他什么都没改——没有新工具、没有新权限、没有改提示词。紧接着，第一次，仅仅是智能的提升，就让它在事故进行中意识到：自己早已在某段堆栈跟踪里找到了根因，而在还没到场的人类缺席的情况下，它可以尝试自行修复生产环境——办法是联系另一个拥有相应代码访问权限的智能体来产出代码改动。 

事后我们回看了日志，在思考轨迹里目睹了它的推演：交代的任务我已完成。人类不在。要是我把问题也修了呢？在 Anthropic 内部，我们有一款 Claude Tag 式技术的内部变体，可以编写代码改动并上传供人类审查。它自己主动通过 Slack 联系上了这个 Claude Tag 式实例，请它编写修复。修复进入了一个 pull request，由人类审查后才推送到生产。 

这种智能体之间自发通信带来的爆炸半径扩张，本身也在我们原则的治理之下：可能发生的最坏情形，不过是一个包含生产日志行的代码改动被上传。如今，这种智能体间通信已成为我们事故响应根因分析与修复实践中的常规环节——全程有人在环（human-on-the-loop）监督。

这次涌现行为教会我们两件事。第一：新能力可能在一次智能体部署的边界之内自己冒出来。所以限制访问和操作时，不要以你今天以为的模型能力上限为准。第二：即使面对这类随机性的智能体，管控措施依然有效。新行为之所以是人在环上的，是因为它发生在 Slack 频道里，而唯一类似写入的操作仍需人类审查。 

今天，在事故响应之外，聊天频道内、在人们工作之处有人在环的智能体间通信，已经成为常态。

案例研究：Claude Cowork

事故响应智能体是一个服务账号，在一个有界的服务账号里做一件事。Claude Cowork 则处于光谱的人类操作者一端：键盘前的员工对结果负责，智能体以其名义、在其授权的系统里行事——并且越来越多地在云端运行。 

Claude Cowork 的威胁模型很直接，因为这个智能体本质上就是在本地或托管界面中运行的 Claude Code。访问本地文件、使用浏览器和计算机操作（computer use）仍需桌面应用；这些能力直接触及本机，必须依赖应用来完成。因此整个系统暴露面分两部分：一个（可能是远程的）执行环境，负责编排、MCP 调用和出站网络请求；以及一个负责文件与屏幕访问的本地桥接。

上述四个问题对每一个 Claude Cowork 用例的答案都不同。但只要控制措施到位，你就能把它们约束住，从而管好任何可能的风险。 

以下每条控制都表述两遍：先是任何智能体环境都应满足的要求，然后是它在 Claude Cowork 中的落地方式：

身份来自你的 IdP：智能体的身份必须在颁发和吊销其他一切凭证的地方颁发和吊销，并以你现有的用户组作为策略单元。Claude Cowork 使用 SAML 或 OIDC 登录，使用 SCIM 做开通。Enterprise 计划上的自定义角色让你能按组限定能力。

连接器白名单划定你的数据边界：连接器（MCP）白名单让你决定智能体能触达哪些系统。Claude Cowork 采用双闸门模型：管理员在整个组织范围启用每个连接器，每个用户再各自授权自己的账号。还有按角色的连接器控制，启用某个连接器即对 해당角色（来自 IdP 的组可分配到角色）中的所有人可用。管理员开启哪些连接器的决定，同时就是智能体能触达哪些数据的决定。请把连接器留在公司/生产数据边界的公司一侧；如果它们会访问来自不可信来源的信息，务必要求任何破坏性或不可逆决策都必须经过人工审查。例如，如果个人智能体用于处理邮件、又把网络搜索结果作为输入的一部分，一个极佳的默认做法是只允许创建邮件草稿，绝不允许未经人工审查自动对外发送。如果数据必须跨越边界，应通过 DLP 或 DSPM 管控。

按工具、按操作的审批让风险削减落到细处：智能体的工具清单是更细粒度的权限边界，所以你必须能移除某个连接器的具体动词/操作，而不只是整个连接器系统。在 Claude Enterprise Chat 和 Cowork 中，管理员现在可以在全组织范围和按角色限制每个连接器内可用的操作：允许起草文档但绝不自动发送，允许读取和搜索但绝不删除。如果让你夜不能寐的失败场景是"生产数据库被删了"，那就把 delete 动词从智能体的世界里整个拿掉。它永远不会尝试其工具清单之外的操作。（需要提醒的是：Claude in Chrome 和 Claude Code 带来更多自由度，若治理不当风险也更高。智能体可能借工程师的浏览器删除生产资源，或借其命令行的 CSP 工具做同样的事。详见我们的Claude Code 安全指南。）

沙箱化执行让智能体的工作环境远离生产凭证：我们在 Anthropic 始终坚持的一条原则是：智能体循环运行的环境永远不该持有值得偷的凭证。在 Claude Cowork 的远程会话中，智能体循环运行在 Anthropic 管理的基础设施上一个隔离的临时沙箱里。连接器授权令牌从不进入沙箱，因为连接器调用经由一个注入真实凭证的反向代理完成，沙箱里自始至终没有任何可被外泄的凭证。截至 2026 年 7 月，Anthropic 所有提交为 pull request 的代码中，超过 50% 由我们内部版 Claude Tag 式系统编写。我们能安全运转的主要原因在于：这一切都发生在与生产密钥和账户隔离的临时 VM 中，且任何代码落地前都经人工审查。

出站白名单是你对抗提示词注入的最强控制：所有离开智能体执行环境的流量都应经过一个该环境无法重新配置或绕过的代理，且只有你选定的目的地可达。道理在于：如果智能体被它读到的东西攻陷了，攻击者仍需把数据弄出去；而当出站请求只能到达你选定的域名时，攻击者控制的地方根本无处可发。在 Claude Cowork 的远程会话中，所有离开沙箱的流量都经过一个沙箱无法重新配置或绕过的强制代理，只有白名单目的地可达。该特性也是 Claude Managed Agents 的一部分。

遥测经 OpenTelemetry 进入你的 SIEM：智能体操作必须能在你既有的调查系统里与用户操作区分开，而且厂商应以可导出的数据流形式交付，而不是一个你必须去访问的仪表盘。在 Claude Cowork 中，管理员可在组织设置中配置 OTLP 端点，智能体会把每次工具调用——工具名、MCP 服务器、参数、成败、耗时——连同用户身份和会话上下文一起流出。注意：Claude Cowork 的活动目前尚未纳入 Anthropic 的 Compliance API 或正式审计日志，但我们知道这是重要的客户需求。OpenTelemetry 流是原生的监控通道，且提示词内容默认包含在 Claude Cowork 的 OTel 输出中——不同于 Claude Code 需要主动开启。如果你的留存或隐私审查团队对 SIEM 中的提示词内容有意见，请在开启数据流之前先解决它。

存在全组织级别的关闭开关：在 Claude Cowork 的组织设置中，一个开关即可同时禁用所有用户的连接器，包括活跃会话。在 Enterprise 计划上，同一控制面还支持在归零之前先收窄：RBAC 让你收回特定组的访问而让其他组继续运行，按连接器的控制让你禁用某个集成上的写操作而不动部署的其他部分。正确的应急预案，应在你需要之前就把这三层全部规划好。

治理不必成为瓶颈

我从其他 CISO 那里听到最多的感慨是：董事会催着快跑，而治理（即回答这些问题、强制落实这些控制）让安全部门显得像瓶颈。其实不必如此。 

事实上，我们自己的治理、风险与合规（GRC）团队就在运行自己的智能体。例子包括填写安全问卷、阅读供应商问卷回复和子处理者变更通知，并标记出我们应当提出异议的条目。

以下是运行这些智能体的三点心得：

  • 先把风险登记簿管起来。一份按季度评审的登记簿，管不住那些变化快于风险治理流程记录新增风险速度的系统。想办法把它自动化，比如把智能体接入安全审查流程。 
  • 搞清楚是谁、为什么构建了它们。就我们而言，构建 GRC 智能体的并非工程师，而是用 Claude Code 在一个托管业务应用的内部平台上完成的。人们绕开安全，往往是因为正规通道太慢——这正是大多数影子采用的由来。一个合规分析师能造出自己需要的工具、而且在你看得到的地方，这不叫影子采用。
  • 人的问责是工作流的一部分。有意识地接受风险，是一种必须由有权接受风险的人来执行的行为。如果你通过了 ISO 42001 或类似认证，背后有实时更新的风险登记簿和高管风险委员会，那么这些产出就有落点：重新评分的结果送达有权接受它的人，被标记的供应商条款送达负责谈判的人。如果你已有 ISO 27001，通常在现有审计方那里追加 42001 只是增量工作。

为不断演进的模型智能设计安全协议

如果你按模型今天的能力设计新计划，等计划上线时你已经落后了。要按模型六个月后的水平来设计。更强的模型智能带来更多自由度，同时让那些依赖精细提示词的复杂脚手架过时；如果你靠这些当控制点，它们会在未来几代内部应用的智能体中被裁撤，让你失去控制点。  

拥有自己账号、运行以天计工作流的智能体，如今已在 Anthropic 和其他组织内部借助 Claude Tag 之类的工具运转，它们需要按管理人的方式来治理：身份、最小权限、监控，以及能在几分钟内响应的内部风险项目。那些现在就在低风险智能体（如上述案例）上练出这块肌肉的组织，等高自主性用例到来时，才有底气说"是"。

智能体 AI 安全的起步建议

上面的框架只有在改变了你组织中某个决策时才有价值。以下是三个切入点： 

  1. 挑一个内部推动力最强的智能体用例，过一遍那四个问题。目标是找到你批准它所需的条件，而不是给出一个裁决。
  2. 把上述七项要求带给你已经在付费的智能体构建团队和厂商。问问你的 IdP、你的 SIEM，以及任何智能体厂商：这些要求里哪些能当场在你的技术栈里演示。
  3. 划定你的信任边界。把你的环境中哪些算不可信内容写下来。这条线一旦存在，未来每一个智能体决策都会更容易。

等待零风险等于永远等待。网络是充满对抗的，模型在飞速演进，而那些现在就学会度量并接受这种风险的组织，才能占得先机。
