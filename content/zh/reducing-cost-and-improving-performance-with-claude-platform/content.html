性能和成本常常被看作一种权衡:想花得更少,就得接受更差的结果。在实践中,我们发现许多使用 Claude Platform 的应用程序可以通过三个调整来降低成本而不牺牲性能:最大化提示词缓存命中率、在升级到前沿 Claude 模型时清除提示词中的反模式,以及按任务校准 effort(推理投入)。我们已将这些建议整理进了 claude-api skill。在本文中,我们展示了 Claude Code 配合 claude-api 如何常常能找到在保持甚至提升性能的同时降低成本的方法。

提示词缓存

在 Claude 生成回复之前,它首先会把你的提示词处理成内部工作状态。这一步称为 prefill(预填充),是处理输入的昂贵环节。提示词缓存会保存该状态(即 key-value,或 KV 缓存):当请求以相同前缀开始时,Claude 会直接读回缓存而不是重新计算。缓存读取的计费价格只是完整输入价格的一小部分。

要有效使用提示词缓存,有几个实际的注意事项。首先,提示词缓存绑定于特定模型。其次,缓存读取必须在提示词的完整跨度上做到字节级完全一致。最后,提示词缓存有有限的生存时间(TTL)。

考虑到这些要点,这里有一些实用建议:

  • 避免在对话中途更改 effort 或思考设置。这些设置会被渲染到提示词内容之前,因此它们是缓存前缀的一部分。具体到 Claude Opus 5 和 Fable 5.1,你可以在对话中途更新 effort 而不会破坏缓存。
  • 不要把易变的值放进前缀。系统提示词中的动态时间戳或 ID 可能随模型调用而变化,从而破坏缓存。 
  • 避免会自我重排的工具定义。使用 Claude Messages API 时,提示词按固定顺序组装,工具定义渲染在最前面。工具定义的任何改动都会破坏缓存。 
  • 分叉对话时要小心。子代理和分支只有在分叉的前缀字节级一致、使用同一模型且使用相同 effort 时,才共享父级的缓存。 
  • 避免同步工具调用和超过缓存 TTL 的子代理。如果智能体阻塞在长时间运行的工具调用或子代理上,缓存可能在结果返回前就过期了。下一轮就得按 1.25 倍正常输入价格重写缓存(1 小时缓存为 2 倍),而不是享受便宜的读取价格。

如何修复

我们在提示词缓存管理上积累了一些经验: 

  • 仔细监控提示词缓存命中率。Claude Console 提供提示词缓存诊断,包括缓存未命中的原因说明(图 1)。如果命中率意外下降,缓存诊断 API 会精确告诉你两个请求是在哪里分叉的。
  • 延迟加载不常用的工具。把工具都声明在前,但将不常用的标记为 defer_loading:它们不进入缓存前缀,只在 Claude 通过工具搜索查找时才被追加到对话中,从而保留缓存。
  • 用消息的方式应用系统提示词更新。Claude Platform 允许你在对话中途以消息形式添加系统指令,而不是编辑系统提示词,这样可以保留缓存。
  • 精心安排请求布局,让稳定部分保持稳定。先把静态上下文(工具定义和系统提示词)放在前面,再把不断增长的对话放在后面(图 2)。
  • 在提示词缓存本来就会被破坏时才更改模型或 effort。某些操作,如上下文压缩,本来就会重写缓存的大部分内容(对话)。这是切换模型或 effort 的好时机,因为反正你都要为一次未命中买单。
  • 随对话增长移动缓存断点。借助 Claude Platform,你可以设置自动缓存,自动将缓存断点应用到最后一个可缓存块。 
  • 预热缓存。为降低延迟,发送一个 max_tokens: 0 并带显式缓存断点的请求。这会在不生成任何内容的情况下处理提示词并将其写入缓存。如果你在会话开始时运行它(例如在用户打字时),第一个真实请求就会命中热缓存。
  • 不要超过提示词缓存 TTL。5 分钟缓存 TTL 从请求开始时计算。如果智能体阻塞在运行超过 5 分钟的工具调用或子代理请求上,父级的缓存在结果返回前就会过期。这种情况下,可考虑为前缀设置 1 小时 TTL。

指令

提示词会不断积累一些用于修补模型弱点的指令。这些指令可能相对于最新 Claude 模型的能力逐渐脱节。以下是一些常见的提示词"反模式",它们会拖累前沿 Claude 模型,并可能在无意中增加成本:

  • 验证仪式。像"复核你的工作"或"回答前验证两遍"这样的指令常常被前沿模型字面理解,从而浪费 token。
  • 详尽与强调放大器。"尽可能彻底"、"关键:你必须始终……"这类表述在使用前沿模型时可能导致冗长输出和多余的工具调用。
  • 强制流程与草稿本脚手架。固定步骤流程(例如"在草稿本中逐步思考")或推理模板是前沿模型并不需要的仪式。这些脚手架会叠加在原生推理之上,消耗不必要的 token。
  • 过时的示例。针对旧模型故障模式调优的 few-shot 示例,可能会教会前沿模型在并不需要的请求上模仿冗长的推理链。
  • 相互矛盾的规则。前沿模型更擅长遵循指令。相互矛盾的指令("在政策范围内一律退款" vs. "未经升级审批绝不退款")可能被前沿模型更字面地执行,导致性能下降。  
  • 过时的配置。为旧版 Claude 代际编写的设置(例如手动思考预算)在升级到前沿模型时可能被 Claude Platform 拒绝。

如何修复 

我们为 claude-api skill 新增了一条命令,专门排查这些反模式。在 Claude Code 中运行 /claude-api prompt-audit,针对你的提示词、skills 或工具描述进行审计。审计覆盖工作目录中的一切内容,包括调用 Claude API 的应用程序代码以及 Claude Code 自身的配置(例如 CLAUDE.md 或 skills)。

举个例子,我们在一个客户支持基准上测试了从 Opus 4.8 到 Opus 5 的模型迁移。我们从干净的提示词出发,一次植入一个反模式(一个已停用的思考设置、一对矛盾的退款规则、一个手写草稿本、"验证两遍"、"尽可能彻底",以及一个强制六步流程),得到六份遗留提示词。 

我们分别在 Opus 4.8 上、仅更改模型 ID 的 Opus 5 上,以及每个提示词各运行一次 /claude-api prompt-audit 之后的 Opus 5 上运行了它们(图 3 显示六者的平均值)。

图 3 | 从 Opus 4.8 迁移到 Opus 5 时提示词反模式的影响。

使用 Opus 5 时,验证仪式("验证两遍")通过每次退款时重复查询订单而消耗不必要的 token。强调放大器("尽可能彻底")变成了几十次无谓的知识库搜索。 

运行 /claude-api prompt-audit 清除反模式后,成本平均降低 14.6%,准确率平均提升 5.3%。成本下降是因为多余的工貝调用和重复推理被消除了。准确率上升有三个原因:已停用的思考设置让 API 直接拒绝了每一个路由请求;相互矛盾的退款规则导致 Opus 5 在四笔本应退还的退款上扣住不放,反而要求客户确认;手写草稿本与 Opus 5 的内置思考发生冲突:在三个工单上,它把工具调用写进了推理过程,却从未真正执行。

Effort

Effort(推理投入)告诉 Claude"要多努力地工作"。在低 effort 下,Claude 通常更快得出结论。在高 effort 下,Claude 在回答前会深思、验证并探索替代方案。 

单一模型在不同 effort 水平上的成本与性能比可能差异很大。例如,在 FrontierCode Diamond(最难的 50 道题)上,Claude Fable 5 在低 effort 下得分 11.5%,每任务成本 $5.35;在最大 effort 下,Fable 5 得分 30.9%,每任务成本 $19.00;调整 effort 大约带来 2.7 倍的得分提升(+19 个百分点),代价是约 3.5 倍的成本(图 4)。 

在 Claude Fable 5.1 上,Humanity's Last Exam(不使用工具)呈现出陡峭的曲线,最后一步收益递减。它在低 effort 下得分约 53%,每问成本约 $0.30;在最大 effort 下得分约 61%,每问成本约 $2.23;最后一步提升到最大大约增加半分,成本却多 46%。这最后的增益落在基准自身运行噪声范围内,也就是说你多付了钱却没有可测量的收益。

Effort 校准可能朝两个方向出错:

  • 默认认为越高越好。高 effort 可能导致过度思考。Claude 花在深思上的时间超过了任务所需,这会增加成本/延迟,并可能降低答案质量。深思只有在仍有证据可寻时才有帮助。 
  • 偏向低 effort。设得太低,Claude 会在证据不足时就停下来。它减少工具调用,可能只根据第一个搜索结果而非第三个来回答。它在难题上思考更少,并跳过它通常会自行执行的检查。答案看起来完整,但建立在片面的信息之上。 

如何修复 

校准 effort 有一些有用的方法: 

  • 在低 effort 下测试更强的模型。低 effort 的更强模型可能比高 effort 下死磕的较弱模型更便宜。例如,在 CursorBench 3.2 上,低 effort 的 Claude Fable 5.1 达到了高 effort 的 Fable 5 的性能,而成本只有三分之一(图 5)。新模型更便宜有两个原因:在低 effort 下它每个任务做的工作更少,而且 Fable 5.1 的提示词缓存读取定价为每百万 token $0.25,而 Fable 5 是 $1.00。即使按 Fable 5 的价格计算,低 effort 下的 Fable 5.1 也大约便宜 40%。
  • 了解你的任务形态。在一系列 effort 水平上测量应用程序性能,是理解特定任务成本-性能权衡的有效方式。在一个未饱和的评测上,如果不同 effort 水平下的性能-成本曲线是平坦的,说明任务不受思考算力约束;提高 effort 并无益处。

这种校准通常需要在不同模型和 effort 水平上运行评测。在 Claude Code 中,/claude-api hillclimb 会替你完成这个搜索:它把你的评测拆分为训练集和测试集,提出配置更改,并阅读失败的训练样例来修复发现的问题。

我们在一个客户支持基准上运行了它,起点是默认(高)effort 的 Opus 4.8。爬坡器首先尝试了低 effort 的 Opus 5,应用 prompt-audit 清除了强制工具调用仪式、草稿本步骤和相互矛盾的规则。这样就超越了 Opus 4.8 的基线,训练准确率达到 98.9%,成本降到每工单 2.6 美分。

然后它降级到低 effort 的 Sonnet 5,成本更低,每工单 1 美分,但准确率降到 88.9%。通过阅读失败的训练工单,Claude 在提示词中添加了路由规则和一个退款上限交叉引用,让 Sonnet 5 以同样的成本回到 98.9%。

在搜索从未见过的 14 个预留工单上,最终配置得分 90.5%,而原始配置只有 78.6%,成本约为原来的五分之一。

自动化成本优化

提示词缓存、指令和 effort 是降低成本的常见手段。我们的文档覆盖了更多内容。为了对使用 Claude API 的应用程序代码进行全面的成本审计,我们新增了 /claude-api cost-optimize:它会分析你的花费去向,应用成本削减措施,并且如果你提供评测,还会展示节省与性能之间的权衡。

cost-optimize 首先找出你的 token 花在哪里:如果你有 Claude Admin API 密钥,就从你组织的用量与成本报告入手;如果你的应用记录了响应,就从每个 API 响应的 usage 对象入手;两者都不可用时,就读取你的请求构建代码进行估算。

然后它对可用的节省项排序,从提示词缓存开始,再精简每个请求携带的内容(包括一次 prompt-audit)、限制输出长度,以及用批处理处理无人值守的工作。如果你提供评测,它还会进一步计算不同 effort 水平和模型选择下的成本与性能。 

我们在四个公开基准上运行了它,以 Sonnet 5 作为基线(图 7):

  • LegalBench(成本降低约 58%): cost-optimize 建议跨任务缓存共享前缀、设置低 effort,并通过 Batch API 处理任务。思考 token 从 102,779 降到 8,284,通过率保持在噪声范围内,成本下降约 58%。
  • tau2-bench retail(成本降低约 73%): 通过实现带显式断点放置的提示词缓存,cost-optimize 在通过率持平的情况下将支出减少了 73%。
  • OfficeQA Pro(成本降低约 52%): cost-optimize 增加了批处理和文档缓存,把成本从 $136.20 降到 $64.87。 
  • SWE-bench Verified(成本降低约 55%): cost-optimize 发现默认配置已经正确缓存。节省来自将 effort 设为中等,并把智能体的输出限制为几句简洁的话。每任务中位步骤数从 29 降到 17,提示词 token 从 75.2M 降到 33.7M。

开始使用

当你迁移到前沿 Claude 模型、想检查现有提示词是否适配时,从 /claude-api prompt-audit 开始。它会扫描工作目录中的提示词、skills 和工具描述。这些可以是调用 Claude API 的应用程序代码,也可以是 Claude Code 的配置(CLAUDE.md、skills)。它会清除那些拖累前沿模型的常见反模式。

当你的应用程序使用 Claude API、想要做一次成本审计时,使用 /claude-api cost-optimize。它会分析 token 花费,然后测试不同的手段:应用 prompt-audit,同时检查是否可以通过提示词缓存、批处理无人值守工作或限制输出来降低成本。如果你提供评测,它还会衡量 effort 和模型选择的权衡。

最后,使用 /claude-api hillclimb 在成本与性能之间进行迭代搜索。给定一个评测,Claude 会把它拆分为训练集和测试集,然后提出旨在降低成本的同时保持基线性能的应用程序更新。Claude 会阅读失败的训练样例来引导搜索,最终配置在预留的测试集上评分。
