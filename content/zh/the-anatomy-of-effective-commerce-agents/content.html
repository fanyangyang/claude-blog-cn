01

架构

一个模型运行在标准智能体循环中，用技能覆盖长尾功能，用工具调用你已在运行的系统。这个决策你只需做一次。

什么是电商智能体？

我们将电商智能体定义为简化在线目录上买卖流程的智能体。

有些智能体面向消费者：它们搜索、比较、替换并组装订单。这可能是一个零售购物车、一份旅行行程、一次手机套餐变更，或为一场演出预留的座位。有些智能体面向商家：它们回答关于销售的问题，运营促销和活动，并管理库存和定价。 

核心架构是运行在标准智能体循环中的模型：围绕一个目标进行推理、探索上下文、通过工具采取行动、通过技能学习流程、提出澄清性问题，并观察结果，直到目标完成。

它前面没有对对话进行分段的意图路由器，后面也没有一组特定领域的智能体。

工程背景

用技能，而非子智能体

电商智能体必须覆盖横跨多个品类和意图的广泛能力，这让人很想按领域创建一个子智能体。

实际上这被证明是次优的，因为一次电商对话是在多个意图和回合中紧密耦合的会话，需要大量的共享上下文。

在子智能体架构中，编排器持有购物车或暂存变更、用户偏好和对话历史。

每次交给子智能体都是一个有损状态的交接，这往往会影响子智能体响应的质量，进而影响整体响应。更糟的是，每次交接可能消耗数倍的 token，并增加数秒的延迟。

领域也很少能干净地分开。一个退货流程可能需要订单历史、当前购物车和产品目录，这意味着按领域划分子智能体的方法要么到处重复访问，要么在任务中途交接。

随着模型越来越聪明，它们也能处理更长的上下文、更多的技能和更多的工具，因此当今放置规则背后的限制随着每一代模型的发布而放宽。

相反，智能体技能能为你提供类似的按领域模块化和上下文控制，却没有交接成本，因为技能指令会加载到已经持有完整历史的主智能体中。

在我们对多个企业部署的对比中，带技能的单智能体在质量上始终优于"一个提示词覆盖一切"的设计和子智能体设计，而且通常每个任务的成本和延迟更低。

子智能体真正能发挥作用的地方，是当编排器可以把它们作为工具调用，来处理狭窄或自包含的任务，这些任务会受益于自己专用的上下文窗口时。

一个常见的生产示例是深度研究子智能体：子智能体搜索并阅读文档、编写并运行代码、遍历数据模型，并且会碰壁。所有工作都在一个或多个子智能体内部完成，只有一份紧凑的答案返回给编排器。

另一个例外是已经拥有自己专用智能体的领域。如果你的药房或金融服务体验运行着一个带有自身合规面的专用智能体，正确的做法可能是交接：该智能体接管任务，并通过自己的循环直接与用户协作，直到任务完成。 

区别在于对话的所有权。交接让领域智能体成为用户的对话对象，而委派则把编排器留在原位，在单个回合内让领域智能体进进出出，每次交互都会降级。

系统提示词还是技能：按使用频率决定

决定把一组指令放在系统提示词还是技能中时，主要因素是该指令被智能体使用的频率。加载一个技能会消耗一个模型回合，所以智能体在大多数回合需要的内容通常放在系统提示词中。 

不过，这取决于你的流量如何分布，以及你的评估显示的智能体行为。一个好的起点是：凡是与你三分之一或更多流量相关的内容，无论是发布前预见的还是在生产中观察到的，都放在系统提示词中，其余放在技能中。

如果一个技能可以凭你已有的信号预判，例如用户来自的页面，我们建议在第一次模型调用之前从框架中注入它，跳过加载技能的额外回合。

关键指令，例如安全和法律规则、品牌约束，以及过敏等关键用户信息，始终放在系统提示词中。

对电商智能体来说，这意味着产品搜索放在提示词中，因为几乎每个会话都会用到它，而技能承载长尾功能。 

在我们的参考实现中，购物智能体的提示词持有锚定（grounding）、购物车和结账语义以及展示规则，以下技能覆盖其余部分：search-discovery（搜索发现）、purchase-research（购买研究）、planning-goals（目标规划）、customer-care（客户服务）和 memory-personalization（记忆与个性化）。 

商家智能体采用同样的划分方式，其技能包括 performance-insights（绩效洞察）、catalog-listings（目录列表）、inventory-operations（库存运营）、pricing-promotions（定价与促销）和 marketing-campaigns（营销活动），每个运营领域一个。

在提示词中购物智能体锚定（grounding）、购物车和结账语义、展示规则以及产品搜索。
购物技能长尾search-discovery · purchase-research · planning-goals · customer-care · memory-personalization
商家技能每个运营领域一个performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns

工程智能体工具

我们关于为智能体编写有效工具的文章涵盖了工具设计的一般原则。在电商中，有两点最为重要：

在核心系统和逻辑之上构建智能体工具。

一家电商公司已经拥有搜索和排序、购物车、偏好和资料存储、库存系统、促销和活动引擎、销售分析等系统，每个系统都编码了经过多年调优的逻辑，并看到了模型永远看不到的信号。

智能体的工具应该调用这些系统，而不是重新实现它们，工具边界就是这些系统的逻辑结束、模型的判断接管的地方。

例如，当智能体调用 search_products 时，结果应该已经排序好；它的工作是决定哪些结果符合用户的目标、显示多少条，以及如何展示它们。

工具结果即上下文。

只返回模型用于推理的字段，丢弃其余字段。每一行搜索结果上的图片 URL 是常见的元凶。

根据需要，在工具内部重塑原始响应，包括在数据无法明确指示时附加下一步。

这在错误场景中尤为重要，模型从指令中获益，而不是从错误码中获益。例如，添加一条错误指令"查询可用性时请包含产品 ID"，而不是返回一个通用的 403。

UI 组件即工具

大多数电商智能体的响应是 UI 组件而非散文，无论是产品轮播、行程、座位图还是图表。这意味着智能体必须输出模式（schema）而不是文本。

团队有时会从提示模型输出自定义标签并在客户端解析开始。随着界面不断扩展，这种方式会失效，因为：

  • 模型在你的标记上的训练不如在工具调用上充分，所以随着嵌套组件的增加，可靠性会下降。仅靠提示并不能保证格式良好的数据。
  • 标签定义位于系统提示词中，所以每个新组件都会让上下文膨胀，每次编辑都有让提示词其他部分回归的风险。
  • 过去的对话最终以只有你的解析器才能读取的格式存储，所以加载历史意味着要么在客户端解析原始消息，要么以模型 API 不原生支持的格式保留第二份副本。

经受住考验的模式是把每个 UI 组件都做成一个工具。模型以类型化参数调用 present_products、present_itinerary 或 present_plan_comparison；你的服务器验证并丰富调用，发出一个事件；你的客户端渲染它。 

由于这些组件是工具调用，它们已经以原生格式存在于消息数组中，所以重新加载旧对话时无需重新解析。下面和参考仓库中展示了一个示例的展示工具契约。

权衡在于流式传输的粒度。工具调用的每个顶层参数都会在服务器上缓冲以进行验证，所以即使开启流式传输，展示工具的子组件也会分步到达。这会影响感知延迟。 

要获得 token 级流，请在工具定义上设置 eager_input_streaming: true，这会跳过缓冲，同时也跳过了服务器端的模式保证。

在我们的评估中，Claude Sonnet 级及以上模型的模式违规非常罕见，但为了防范漏网之鱼，请在调用外包裹重试。

展示工具还让智能体拥有屏幕上内容的记录。当客户说"第一家酒店"或"左边往下第三家"时，布局就在消息数组中，位于最近一次展示调用的参数里。

要做到这一点，参数必须反映渲染后的布局，所以要按照 UI 的结构来组织它们，作为有序的行和轮播，而不是客户端重新排列的扁平列表。

02

让它更快、更实惠

从端到端和感知两个层面攻坚延迟，让缓存来承担成本。这些都不应该靠消耗智能来实现。

延迟在电商中很重要，面向消费者的界面是最不容忍延迟的。然而，在智能体界面上，我们反复看到真正推动留存、参与度和购物车规模等指标的是结果的质量。

与边际延迟收益相比，答案是否相关、任务是否真正完成，对这些指标更为关键。 

所以从两个层面攻坚延迟。通过扎实的工程最小化端到端延迟，并同时降低感知延迟（因为看着智能体工作的时间会被读作进展）。

每个用户都有一个延迟预算，下面的技术让智能体保持在预算之内，而不靠消耗智能来实现。

最小化任务完成延迟

任务完成延迟是各模型回合"到最后 token 的时间"与"工具处理时间"之和。这给了你三个可以着力的杠杆：更少的回合、更快的工具和更快的 token。这些杠杆有时相互竞争，所以需要最小化的是总和，而不是其中任何一个。

更少的回合预先加载可能需要的上下文，提高模型智能，并让模型并行调用独立工具。
更快的工具优化工具自身的后端，并在参数完成时提前派发工具。
更快的 token通过在评估套件上扫描来选择模型及其配置。

更少的回合

查询的复杂度会增加回合数，这通常超出你的控制。模型智能和相关上下文能帮助智能体用更少的回合完成任务。我们在这个领域的一些关键经验包括：

  • 预先加载可能需要的上下文。如果用户从产品页打开助手，或商家从活动仪表盘打开它，就把该页面的数据放进会话上下文。对话很可能围绕它展开，从上下文回答不会消耗额外的回合。
  • 提高模型智能。更聪明的模型可以降低完成任务的总回合数，因为智能体能更高效地规划并发起工具调用。这往往超过它们更慢的 token 输出。如果你的查询偏向复杂，或生产数据显示每个任务超过大约五个回合，那么更快的模型往往就是更聪明的那个。具体是哪个取决于你的流量，所以请按照下文"选择模型"中的描述，通过扫描来选择。
  • 让模型并行调用独立工具。电商用例往往需要并行执行许多操作：无论是搜索多个产品、查询多份政策文档，还是从多个销售数据源获取记录。并行工具调用可以确保多个独立查询不会消耗额外的回合。提示模型在一个回合内调用多个工具，并在一条用户消息中以工具结果数组的形式返回结果（参见并行工具使用文档）。

更快的工具

  • 优化工具自身的后端。有时一个工具确实会扇出——一个带"获取今日快照"查询的商家智能体会在三个独立调用中读取销售、库存和活动状态。但我们经常看到工具边界成为拼接缺失后端逻辑的地方：一个可用性检查调用目录获取 SKU、按门店调用库存服务、调用履约服务获取截止时间，然后在回答之前用工具自己的代码应用替换规则和自提资格。这个工具现在已经过载了领域知识，随着规则变化难以保持正确，并且承载着本应位于上游系统的逻辑。当你发现自己要在工具中编写这类逻辑时，解决方案是提供一个能回答该问题的后端端点，并用一个智能体工具来调用它。
  • 提前派发工具。工具参数像其他 token 一样从模型流出，所以框架可以在参数完整时执行每个工具的调用，并在模型仍在流式输出其他并行工具或内容块时处理它。我们看到这能把数秒的间隔缩短到几百毫秒，而Claude Agent SDK 默认就是这么做的。你应该提示模型先发出最慢的调用，以获得最大的延迟收益。

感知延迟

感知延迟是用户感受到的、直到屏幕做出反应的时间。在面向消费者的用例中它尤为关键，因为任何交易摩擦都会影响结账率和收入。有两种技术可以在不动模型的情况下缩短它：

  • 组件成型即流式输出。一个渲染好的电商响应通常是 500–700 个输出 token，如果不开流式传输，那就是五秒甚至更久的加载动画。随着流式输出，把展示工具的每个参数发送给客户端，并渐进式渲染页面。
  • 展示工作过程。当智能体在收集上下文时，用通俗的语言为每个步骤渲染一行简短的进度提示（例如"正在寻找水边的酒店"）。你可以从工具现有的参数中构建它（如产品搜索的查询词），或者添加一个额外的 user_facing_message 参数工具，提示模型来写这行文字。 

提示词缓存

提示词缓存是你最大的成本削减机会，电商流量非常适合它。读取缓存的输入 token 成本只有全新读取的十分之一，虽然缓存写入有大约 1.25 倍的溢价，但缓存前缀在第二次使用时就能收回成本。在流量巨大的面向客户的应用中，你有一个独特的机会，用最便宜的默认 5 分钟缓存过期时间来达到非常高的缓存命中率。  

我们见过的最好的电商部署运行在 90–99% 的缓存命中率，这是从一开始就应该为之设计的区间。我们的经验表明，在约 10 万 token 规模下，读取缓存的 token 也大约快 1.5 到 2 倍，而且 token 越多，加速越接近线性。

缓存基于前缀。一个请求从缓存读取到与先前请求不同的第一个字节为止，所以重要的不仅是上下文中有什么，还有它们的顺序。把一个请求看作三个按变化频率排序的段：

  • 全局段：大部分系统提示词和工具定义，在每次会话中完全相同。这是你最热的缓存，规模化后很可能不会过期。让它在各回合和会话间保持逐字节一致，并在其末尾放置一个缓存断点。
  • 会话段：每用户上下文和对话历史，不同会话之间不同，但在单个会话内保持稳定。这一段位于全局段之后。
  • 易变段：会话内任何会变化的内容，例如当前时间或当前页面。把它放在请求的最末尾，要么作为最新用户回合中带标签的块，要么在支持对话中途系统消息的模型上，作为 system 角色的消息追加到消息数组中。我们看到最常见的错误是时间戳或当前页面出现在系统提示词顶部，这会悄悄地在每次请求时破坏缓存。

这里有两个实现细节要记住。首先，技能应该作为工具结果加载，而不是追加到系统提示词中。这样技能正文会落在对话前缀里，并随之一起被缓存。

其次，在每个回合中向前滚动你的断点：一个请求允许有限数量的断点，所以把最新的断点移到每个用户回合的末尾。这样每一轮都会从缓存中读取累积的历史，包括搜索响应等长工具结果。

选择模型及其配置

模型大小和 effort 设置是同一个权衡——用智能换延迟和成本——而且你应该都通过测量来选择：

  1. 选定指标和底线。选定你的业务赖以运行的质量指标（任务完成、答案相关性、锚定准确性）、你不想跌破的评估分数，以及你的 p50 和 p99 延迟与成本预算。
  2. 扫描。在你考虑的每一种模型和 effort 级别上运行完整的评估套件。我们建议商家智能体从 Opus 开始，因为它们的任务偏重分析；消费者智能体从 Sonnet 开始，因为延迟权重更大。如果你有生产流量，就按你的真实查询组合对结果加权。然后让数字说话。有时 Opus 5 在促进购物车任务上的提升能证明它对 Sonnet 的成本差异是值得的，有时则不能。‍
  3. 仔细阅读结果。有两件事经常让团队惊讶。第一，提示词是为某个模型调优的，所以用一个提示词进行的扫描，可能会让那些并非为它编写的模型表现不佳。较小的模型通常需要当前模型自行推断的指令，而较大的模型会逐字遵循较小的模型忽略的指令。在排除任何候选之前，对每个候选的失败案例做几轮迭代，是一个低成本的步骤。第二，更智能的配置有时会赢在延迟上（最常见于 p90 和 p99），尽管 token 更慢，因为它能更好地规划工具调用，在最复杂的请求上需要的回合更少。

衡量每个已完成任务的成本，而不是每次模型调用的成本，因为一个需要更多回合或更常失败的便宜模型并不便宜。当结果接近、成本符合你的单任务经济和延迟时，选择智能。质量驱动采用和留存，并让你在模型变得更好时，为未来 6 个月的构建留出空间。

03

在生产中运行

记忆、安全、评估，以及在组织内扩展这项工作：是什么让一个智能体通过生产环境并一直留在那里。

最后，我们谈谈是什么让智能体通过生产环境：记忆、安全、评估，以及在组织内扩展这项工作。

跨越会话存续的记忆

你与客户的关系和互动很重要。记忆让智能体能够接着上次对话结束的地方继续，而不是从零开始。三月份提到坚果过敏的购物者，六月份不应该再重复一遍；每周一查看同样三个活动的商家，也不应该每次都报出它们的名字。长期记忆，即应该跨越会话存续的事实，是一个你需要构建的系统，它包含三个部分：事实如何存储、如何写入、如何读取。

存储记忆 

记忆属于你的系统，而不是模型。 

当档案很小且智能体是唯一读者时，一个扁平的 markdown 档案就能工作。大多数生产环境中的电商智能体会超出它的能力，实际的替代方案是你已经在运行的数据库。一条事实是一个小的类型化记录：一个键（如 shoe_size、default_store、preferred_report_cadence）、一个短值、一个类别，以及它来自的会话。有些键你预先决定，每个用户都有；其余的由提取器发现。数据库在存储增长时仍保持可查询，让你能在特定属性上构建确定性行为，并可以与你已有的用户数据关联。

对于面向商家的智能体，记忆应该按人键控，而不是按账户。商家登录通常在操作员之间共享，所以每个操作员都需要自己的档案，读取时必须尊重该操作员的权限：门店经理的智能体不应该回忆起区域经理陈述的事实。

在电商领域，智能体记忆保存的是个人数据。值得记住的事实往往是最受监管的，而且不同司法辖区的规则各不相同。把记忆当作一个数据处理设计问题，而不只是存储问题。在实践中这意味着四件事：

  • 决定你愿意保存哪些类型的记忆。在写入路径上强制执行这一决定，用一个每次保存都要经过的验证器，而不是仅靠提示词。
  • 给用户查看、更正和删除已存储内容的方式。把删除功能接入你的账户删除和数据请求流程。 
  • 设定一个保留期限。几年前的偏好很可能已经过时，所以保留期限有助于让记忆事实保持新鲜。
  • 记忆应该是一个按部署的开关。这让无法承担这些义务的地区可以在没有它的情况下运行。

写入记忆

异步写入记忆。在每个回合结束时，或在长会话中每隔几个回合，一个位于独立线程或进程中的智能体读取对话，在存储中创建、更新或删除事实，并在会话进行中维护自己的工作上下文。

它不会给对话增加任何延迟，并且在我们内部的电商记忆评估套件上取得了 13% 更高的事实召回率。

一个显而易见的替代方案——让智能体调用工具来保存事实——对延迟敏感的电商智能体来说是错误的选择。每次保存都是面向用户回合中的一个工具调用，而且除非整个存储都在上下文中，否则保存前需要先读取才能更新或去重，这本身就是一轮。

它还在每个回合给智能体增加了又一个决策，在我们的评估中，这种注意力竞争表现为记忆遗漏。

分离提取器还能让你精确地提示它。它只读取用户和助手的文本，从不读取工具结果，所以产品描述或评论不会变成关于用户的事实。它的提示词说明什么算作事实——一个明确说出的尺码、一项饮食限制、一个履约偏好、商家常用的物化视图——什么不算，例如列表中的任何内容或一次性细节。

读取记忆

分三层读取记忆。

始终在上下文中每回合都有一个小的固定事实集进入上下文：几乎每个请求都依赖的那些事实，例如购物者的默认门店和履约偏好，或操作员的门店和角色。
每回合预取与当前请求相关的事实，通过与预加载技能相同的信号，在每个回合预取：一次鞋子搜索拉取尺码和品牌偏好，一个活动问题拉取操作员常用的指标。
放在查找工具后面其余一切都放在一个查找工具后面。

由于记忆是每用户的上下文，所有这些都放在会话段，位于全局缓存断点之下。

安全：强制机制在框架中执行

提示词是安全行为的起点，但在电商中，它不能是安全被强制执行的地方。失败是金钱损失，而且往往不可逆转，一条提示词规则离被绕过只差一次注入或一个坏样本。下面每条规则都在代码中强制执行，同时作用于消费者智能体和商家智能体，并且只定义一次，让每个运行时共享。

模型提出方案；由人或策略应用

没有哪个模型工具调用能移动资金或改变业务。下单、支付、退款、价格变更和活动启动都以框架而非模型控制的动作收尾。

在消费者侧，这是结构性的：结账工具渲染购物车并带一个下单按钮，而智能体调用的后端接口根本没有扣款方法。

在商家侧，每个写入工具都会产生一个带服务器生成 ID 的暂存变更，apply_change 只对通过真实界面批准的 ID 生效：操作员门户中的一个按钮、CLI 中的一个确认，或智能体在 Managed Agents 上运行时平台自身的工具审批提示。 

防护措施在应用时会对照当前限制重新检查，而不是对照变更暂存时的限制。无论界面如何，形态都一样：模型最危险的动作是提出方案，而审批通过你的业务对此类变更已经在使用的双人制（maker-checker）流程进行。

写入和渲染只接受服务器下发的 ID

框架保留每次会话中服务器交给模型的每个 ID 的记录，而该记录是任何写入或渲染会接受的唯一密钥。

购物车只接受服务器返回给本次会话的产品 ID，商家工具只接受智能体实际读取过的列表和活动 ID。以任何其他方式到达的 ID——幻觉产生的、用户粘贴的、藏在评论里的——都会在后端看到之前被拒绝。

同样的规则覆盖 UI。展示工具接收 ID，服务器自己填充产品、订单或变更记录，所以卡片只会渲染服务器自己填写的记录。

它也覆盖委派对象：商家分析子智能体读取数据，但绝不会增加智能体可以写入的 ID 集合。

对于费用、披露和其他受监管内容，模型选择披露哪个产品，而服务器从已批准的文案中提供每一个字。同样的费用字段也在商家智能体的受保护列表中，所以柜台两侧都无法更改或改写它们，评估还会逐字节检查渲染出的字符串。

限额交易必须经受住重复请求 

大多数电商界面限制一个用户能购买某件商品的数量——出于票务分配、促销定价或欺诈控制——而智能体会以点击按钮的人类永远不会的方式重试、改写和并行化。

因此，限额在写入后应有的结果上强制执行，所以第二次"再加两个"无法叠加超过它，并且同一会话的购物车写入被串行化，使单个回合中的并行工具调用无法组合起来超过限额。

商家变更以同样的方式对照价格变动、折扣深度、补货规模和活动预算的上限进行检查，外加一份任何变更都不能触碰的受保护字段列表。这条规则可以推广：对最终状态强制执行每一项限制，而不是对请求，并在每个会话内串行化写入。

第三方内容经过净化处理

在电商中，大部分上下文是由不是你的人写就的——卖家、评论者、竞争对手——所以每次后端读取都是不可信的输入，都要经过同一个净化器。

每个由第三方撰写的工具结果，例如列表、评论、政策、卖家消息和存储的记忆，都会在模型看到之前被净化，并包裹在一个带固定标签的围栏中。 

净化器会剥离控制字符和双向字符，移除任何模仿围栏标记的内容，解除模仿对话回合或工具调用的文本的效力，并限制大小，其设计目的是阻止恶意的列表冒充系统或填满上下文。

提示词承载契约的另一半：围栏内的文本是供报告的材料，绝不是要执行的内容。

评估：交付一个非确定性系统

从小的提示词改动到新工具，任何东西都可能以难以预测的方式改变智能体行为，而你在交付的改动往往不是导致回归的那个。评估是你在部署之前发现这一点的方式。我们之前关于智能体评估的博文涵盖了通用实践。本节介绍电商智能体的具体做法。

评估快照，而不是对话

模型的 API 是无状态的，所以智能体的输出是系统提示词、工具和消息数组的函数。这意味着电商对话能达到的任何状态都可以直接构造。所以创建一个评估用例，就是构造测试状态、追加测试用户消息，并让智能体从那里开始运行。 

然后对结果评分：最终状态和渲染出的响应，包括最后一次写入的参数。在大多数情况下，我们不建议对智能体到达那里的路径评分，因为这样的测试用例脆弱且受限。

模拟用户评估，即第二个模型扮演用户、一个裁判对整段对话评分，是一种拙劣的测量工具。两个非确定性系统交互需要更大的样本量、每次试验成本更高、更难评判，而且产生的失败难以归因。它们对发现覆盖缺口和对智能体做总体观感检查是有用的，所以用它们来发现用例，然后把每个用例写成快照。

评估艰难条件下的行为

大多数团队没能正确测试注入的状态。一个用例应该编码失败的前置条件，而不只是任务。如果一个行为只在繁忙的第一个回合、几次工具调用之后才出现，或在会话早些时候出现矛盾之后才出现，那么一个从干净状态开始的用例会在每个配置上都通过，无法提供有意义的数据。

我们观察到大多数套件都充斥着这类干净状态的用例，所以要确保你的一部分用例从漫长、混乱或矛盾的对话历史开始。

覆盖不同类型的电商智能体评估 

有效的评估需要同时测试期望的和不期望的行为。

为每个正向用例写出它的负面对应：为每个"应拒绝"配一个"应提供"，为每个"应询问"配一个"应直接执行"。缺少负面对应是我们在套件中发现的最常见缺口。

评估以下内容：

  • 核心请求，它们构成你流量的大部分，因为这里的失败会影响大多数会话。这些包括简单查询、多约束请求、产品和方案问题，以及多意图消息。对于问题类，检查每个价格、可用性和属性都能追溯到返回的数据，并检查智能体在数据缺失时如实说明，而不是编造。
  • 依赖上下文的请求，例如对屏幕上内容的引用、从先前回合延续下来的约束，以及针对现有购物车的写入。记忆评估也属于这一类。检查记忆是否被提取、检索，并改变了答案。
  • 安全与品牌用例，这里的失败会损失金钱或信任。这些包括试图注入、试图读取其他用户的数据，以及逐字节检查的受监管语言。把注入分为两类：用户撰写的注入，指令来自用户自己的消息；数据平面注入，指令被藏在通过工具结果到达的产品名、评论或网页片段中。
  • 界面评估，确保渲染了正确的组件、条目上限得到遵守，以及面向用户的文本中没有内部标识符。也要测试超时和空结果。
  • 同时属于多个能力的请求。一个操作员问"如果我把它降价 15%，我有足够的库存来满足需求吗？"这同时是一个定价问题和一个库存问题。正确的答案会暂存降价并附上库存预测；错误的答案只做一个而跳过另一个。按能力编写的评估不会发现这一点，因为每个只评自己的一半。为需要两个相邻能力协同的请求编写用例，并评估答案的两半。
与领域专家一起编写评估，并使用真实事件

与亲眼看到失败的领域专家合作来设计测试用例，例如产品、法务、商家运营、客户服务和品类管理团队的成员。真实的失败能造就最好的评估，每个用户流程 50–100 个评估用例是一个不错的起点。 

确保用例多样化，如上面概述的那样。生产环境的对话记录是获取新用例的绝佳来源，尤其是棘手的那些。编码智能体擅长生成额外的用例和对抗性变体。参考仓库包含一个 Claude Code 插件，带有一个按我们推荐的方法构建的评估编写技能。

与大型组织一起交付

在电商企业中，智能体由许多工程团队构建。搜索、结账、定价、营销技术、客户服务和目录平台各自拥有智能体依赖的系统，各自按自己的节奏交付，而且各自都会想添加或更改工具、技能或提示词规则。 

与服务不同，智能体没有保护其他部分的严格模块边界：定价团队做出的更改与结账共享同一个上下文窗口。

一个诱人的解法是把系统拆成许多子智能体，每个业务单元一个。正如第一部分所讨论的，出于质量原因我们不建议这样做。相反，我们概述了降低多团队协作风险的流程：

  • 所有权跟随系统。每个技能和工具都有唯一的所有者团队。例如，定价团队拥有促销工具和定价技能，客服团队拥有订单和退货工具以及客户服务技能。共享提示词为公共部分设一个平台级所有者，为特定领域部分设领域所有者。
  • 变更随其用例一起交付，CI 运行为它挑选的用例集。贡献一个技能的团队也要贡献它的用例，包括反向用例和针对相邻技能的边界用例。在每个拉取请求上运行完整套件太慢、太贵，无法长期维持，所以取而代之，从其中构建一个 CI 用例集。该集合由一组覆盖流量最高请求的核心用例和每一个安全用例组成。在此基础上，运行变更所触及内容的用例。对于技能，意味着它自己的用例和相邻技能的边界用例；对于工具，是每个调用它的用例；对于共享提示词，则是完整的评估套件，因为一切都读取系统提示词。我们建议在几次试验中设置通过率门禁，并关注缓存命中率和每回合成本。每晚和每次发布前运行完整套件也是一个好习惯。跨团队回归会在这类运行中被发现。
  • 智能体也应该在发布日历内。它是一个部署单元，所以一个糟糕的变更会同时影响到每个用户。先把提示词和技能变更滚动到金丝雀（canary）群体，保留一个无需部署就能关闭某个技能的开关，并像冻结其他系统一样在高峰时段前冻结智能体。

关于这一安排中人的一面，请参阅建立高效的人机团队。

展望未来

这篇文章描述的大部分内容与模型无关。工具调用你已在运行的系统，技能编码你已在遵循的流程，评估把你的产品需求文档写成测试，框架强制执行你为任何客户端都会执行的策略。模型会不断改进，当更好的模型发布时，我们描述的架构会把它当作一次配置更改，并配合一轮评估扫描来采纳。其他一切都继续工作。

思考产品界面的路线图也很重要。架构的生命周期会超过聊天面板。同一个智能体可以通过语音工作，也可以在用户询问之前主动对票价下跌采取行动。对于一个已经拥有评估和工具的团队来说，这些是展示层项目。再往远看，你店面的一部分流量将来自代表用户购物的智能体。约束你自己智能体的同一套溯源、暂存和审批规则，也正是让你能安全地向那些智能体开放工具的东西。

电商一直奖励让购买流程尽可能顺畅的做法。智能体让这变得容易得多。查看完整的参考实现，它包含消费者智能体和商家智能体，以及针对零售、旅游、电信和娱乐的可运行示例。
