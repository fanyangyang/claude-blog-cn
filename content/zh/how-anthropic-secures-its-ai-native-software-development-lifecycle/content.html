在 Anthropic，代码量和部署速度都已呈指数级增长。我们的软件工程师现在平均每季度交付的代码量是 2021 至 2025 年期间的 8 倍。

我们的审查、监控和其他安全流程也必须随这种节奏同步扩展，否则就会成为瓶颈的根源（阿姆达尔定律）。

我们的软件开发流程也发生了翻天覆地的变化。Claude 已从编码助手演变为主要的创作者和审查者。如今合入我们代码库的代码中，约 80% 由 Claude 编写。

超过一半的代码由我们的内部版 Claude Tag 合并，而人类工程师则专注于把控方向、设定意图，并对最终批准负责。

这意味着我们的安全团队必须防御一个急速扩张的攻击面，并加固一个以非确定性、持续演化的智能体为核心的软件生命周期。在本文中，我将介绍保障软件开发生命周期（SDLC）安全的策略。

（本文可与我们近期发布的 Zero Trust for Agents（智能体零信任）框架结合阅读；本文中的所有实现都采用了该框架中的安全设计思想。）

我们要防范的威胁非常具体：被攻陷或遭受提示词注入的智能体引入恶意变更；智能体把供应链和依赖投毒当作可信输入吸收进来；以及那些人们熟悉的各类应用漏洞正以更高的频率涌现。下文的每一项控制措施都至少对应其中一种威胁。

为了在不明显拖慢开发速度的前提下达成目标，我们部署了几项总体策略，包括：

  • 安全左移，与代码开发阶段全面整合；
  • 用严格的访问与身份边界来控制爆炸半径；
  • 在生产上线前后，结合自动化的确定性审查与智能体审查；
  • 在杠杆率最高的节点引入人参与环节。

本文将介绍我们在软件开发生命周期各具体阶段实施的安全流程，以及其背后的核心原则。这些原则更经得起时间考验，因为随着模型能力的演进，安全团队必须不断重新审视、甚至重塑自己的流程。 

不断演变的软件开发生命周期

我们的开发团队已经详细介绍过其软件开发生命周期的变化，这里只做一个简要铺垫，之后再逐个阶段深入。 

概括而言，我们的软件开发生命周期被大幅压缩。它更多由原型和内部试用（dogfooding）驱动，而非冗长的规划周期。想法来自组织的各个角落，传统角色（前端、后端、设计）的边界也变得模糊。审查和批准环节依然有人类参与，但同样由智能体循环来驱动。

虽然每个阶段都已被 Claude Code 和 Claude Tag 彻底改造和加速，但对来自传统组织的开发者来说，各阶段的名称和用途并不陌生。这些天然的关卡，也被我们用作 AI 原生 SDLC 安全流程的一部分。

规划（Plan）

我们最早的安全自动化之一，是一个简单的、由 Claude Opus 驱动的 PSR（项目安全审查）Web 应用。它接收项目设计文档，对照 MITRE ATT&CK 框架进行分析，识别潜在漏洞并给出缓解建议。

后来我们将其连接到内部知识索引，从而获得覆盖全组织政策、历史决策和相关系统的更深上下文，系统得到了显著增强。 

这让我们能更好地理解潜在风险，同时也能补全 PSR 中缺失的信息。仅这一个实现就为 AppSec 团队节省了大部分时间。当我们确信 Claude 的风险评估足够准确后，便允许团队自行批准项目——前提是 Claude 判定上线风险足够低。

在这里可以看到 AI 原生 SDLC 带来的第一个关键转变。PSR 最初的设计目的，是在漫长而昂贵的编码过程之前拦截安全问题——在这个阶段发现问题，可以省下数月的返工。 

如今，主要功能的多个原型在几小时内就能做出来，详细的架构审查不再是那么关键的关卡。把 PSR 应用连接到知识索引，可以捕捉到原本可能遗漏的上下文，又不会制造不必要的减速带。而做成 Claude Code skill 之后，Claude 还能进一步向外展开，从上下文所在的任何地方获取补充信息。 

持久原则：把安全智能体接入组织上下文。当规划周期被压缩后，更有效的做法是让这些智能体去找上下文本来所在的地方——聊天记录、过往审查、代码库——而不是在可能已不再需要的阶段强求详尽的文档。无论如何，智能体都需要代码之外的上下文。

编码（Code）

在 AI 原生工程组织里，安全人员多了一根杠杆：他们可以直接塑造代码的生成方式，从源头堵住漏洞。 

过去，团队观察到反复出现的漏洞后会写安全编码指南，但这些指南很难强制执行，也很少标准化。 

在 Anthropic，这些指南被写进 CLAUDE.md，并引用全组织共用的 skills，于是代码一生成就按这些最佳实践走。这是一个闭环。智能体一旦发现某类 bug，相关文件就会更新，防止以后再写出同类问题。

当然，这并不意味着所有代码一出来就是完美的。我们团队一开始在 CLAUDE.md 里要求智能体在开 PR 前最后跑一遍 /security-review。这条现已对外提供的命令，是我们内部审查工作流的产品化版本：它会查找攻击者可能控制的输入入口，扫描可疑链接，再核验自己的发现。 

如今，这些审查发生在 Claude 生成代码的过程中。安装 security guidance plugin 之后，Claude 会边写边看对话和代码，在同一次会话里提出安全改进，并处理常见漏洞。

PR 阶段的另一些提示，会把内部非技术团队推向我们的低代码应用托管平台，避免过去长期困扰安全团队的影子 IT。

有些客户选择把 /security-review 和 PreToolUse hook 绑在一起，把这一步做成更硬的关卡。这也有效，但我们团队选择把硬性代码审查关卡放在周期的测试/CI 阶段。

除了塑造和审查代码，这一阶段我们最关心的另一件事是控制爆炸半径。做法是在身份周围划出硬边界（监控一节会再讲），并让开发者在虚拟机上写代码。 

把编码搬到远程 VM 相对轻松，也比只靠笔记本多了控制和可见性。这些 VM 上的智能体流量走 egress allowlist。  

当智能体在读可能带提示词注入载荷的不可信输入时，这种收紧的出口控制尤其重要。被注入的指令到不了互联网上的任意目的地：外泄路径被限制在一小撮受监控的服务上。 

这里又能看到 AI 原生 SDLC 的明确调整。远程编码过去主要用于保护知识产权，如今更成熟的 AI 编码团队采用这些环境，是为了把智能体圈住。 

持久原则：在 AI 原生工程组织里，安全左移意味着把漏洞发现和更新指令闭环起来，用这些指令定制 Claude 如何生成代码。用合适的硬边界限制爆炸半径（最小代理原则）以及智能体能接触到的东西。

测试（CI）

以我的经验，测试或 CI 阶段很快会变成 AI 原生转型中工程团队最痛的瓶颈。在 Anthropic，一旦大多数开发者开始用智能体编码工具、并且同时跑多个智能体，团队能跑多快就立刻取决于人能审多快。

说清楚：人类问责仍然是我们流程的核心。我们做的是用自动化的智能体审查加上确定性审查来加快评审，把人工审查留给受监管或真正关键的代码。 

历史上，人工代码审查一直被当作标准，但实证证据表明它并不完美。安全 bug 仍在世界各地的软件里上线。我们的审查流程能覆盖更多代码，也能抓住特别复杂的问题，从而降低这些风险。

随着我们要求智能体为自己的发现写出有效证明、对结论更有信心，获得实质性审查评论的 PR 比例从 16% 升到了 54%。我们还判断，过去 claude.ai 事故背后大约三分之一的 bug，会被我们现在落地的自动化流程抓住。

发现这一点的并不只是我们。Intercom 分享过，它自动批准了 19% 的 PR。部署量翻倍，由破坏性代码变更导致的停机下降了 35%。CircleCI 得出了类似结论，他们在 Claude 上构建了自主智能体 Chunk，用来解决 CI/CD 维护问题，并在人类看到之前先验证自己的修复。这一做法让智能体任务转成已完成 pull request 的比率翻了一倍。

在 Anthropic，PR 一打开，多个智能体就会自动审查。每个审查智能体都被设计成只盯一个狭窄焦点，并用 RAG 补上围绕过往事故的额外上下文和记忆。 

这比一个超级提示词或超级安全智能体有效得多，原因包括：

  • 它们不共享偏见和盲区
  • 如果其中一个被攻陷或出错，其他审查者可以抓住
  • 精力不会被摊得太薄、同时照顾多个焦点

需要说清：智能体并不是不受约束地把代码合入生产。我们按风险给代码库分层，并刻意决定哪些部分自动化。有些整库仍有严格的人工批准流程。

对于由 Claude 审查并合并的代码，人类问责仍然是核心。 每一次批准都会记录所用信号和推理过程，并按风险加权抽样给人类复核。另一轮测试盯住不变量，比如「用户 A 永远不能读用户 B 的数据」，并触发额外的人工审查。我们还把智能体扫描和 SAST 工具结合使用，后者直接在 PR 上发评论。 

大多数扫描方式，无论是智能体还是确定性的，都按用量计费。代码吞吐量上去，成本就会上去，团队需要决定对自己合适的覆盖水平。 

在 Anthropic，我们接受这里的成本会随代码速度上升，但预期单位成本会下降。今天的模型写代码的能力远好于几年前的所有模型，我们预期这个趋势会继续。

持久原则：自动化审查是另一种风险，控制方式也不同（多道关卡，以及上下文窗口彼此隔离的多个智能体）。人仍然在环里，但根据代码库的性质，人所在的生命周期位置可能不同。 

当 CI 真的坏了，Claude Tag 会充当我们的 CI/CD 故障第一响应者。

部署（CD）

Anthropic 维持着一套扎实的预发环境，并在这里执行常见的安全最佳实践，比如重大上线的外部渗透测试，以及定期 DAST 扫描，以抓住静态扫描漏掉或看不见的逻辑 bug。 

和其他 SDLC 阶段一样，AI 给安全团队同时带来新的挑战和解决方案。一方面，到达这一阶段的漏洞更少了。另一方面，活下来的漏洞往往最隐蔽、最难抓。 

再加上更大体积的代码更频繁地发布，定期的动态测试看起来就不那么「动态」了。 

好消息是，AI 模型更擅长多步、跨组件的推理，能抓住更大比例的这类复杂漏洞。例如，今年二月我们披露，Claude 发现并帮助修复了超过 500 个高危开源漏洞。

在 Anthropic，我们正在预发环境落地持续的 AI 驱动 DAST 扫描。它们在系统层面寻找漏洞，也就是两个或多个服务之间的假设不对的地方。今天已有不少厂商提供这类能力。

持久原则：动态测试应当跟上部署节奏。 

监控（Monitor）

任何像样的安全团队都知道，代码推到生产并不等于工作结束。我们可以假定，任何漏洞都会被越来越老练的攻击者很快发现。

我们的安全团队在这里落地的项目属于标准做法，比如公开漏洞赏金计划、红队模拟攻击，以及定期扫描依赖、密钥、供应链、云姿态和容器中的漏洞。 

Claude 在这些工作里扮演了很大角色，但我们会把笔墨放在 AI 原生 SDLC 带来的监控层面更大变化上：告警分流和代码迁移。

在 Anthropic，告警一响，Claude 就会开始：

  • 审阅生产日志
  • 定位 bug 根因； 
  • 撰写事后复盘；并且在某些情况下
  • 写出修复这个 bug 的代码变更。 

这个智能体不能做的，是自动部署修复。它是一个单用途系统账户智能体，只有三项权限：可以写新文档、在公司频道发帖，以及访问生产日志。 

修复必须来自另一套智能体加人类审查的系统。原因又回到身份、权限和硬边界的管理：把代码推进生产时，控制爆炸半径很重要。把智能体拆开是关键，因为一个（或多个）智能体会成为对另一个的检查。 

这对 CISO 也是重要一课，而且是我吃过亏才学会的。考虑智能体的硬边界时，必须把它对其他智能体的访问算进去。

一次模型升级之后，事件响应智能体主动通过 Slack 联系了另一个 Claude 实例。它要求那个能写代码的智能体去推修复。这按设计被拦在了人工审查关卡，但这次经历告诉我们，边界要画在访问和动作周围，而不是画在模型指令、或我们以为模型能做什么周围。如今在 Anthropic，Slack 上的智能体对智能体通信已经是常态，我们也会认真思考智能体身份模型。

第二个重大变化是团队对待迁移的方式。每个安全工程团队都经历过那种时刻：忽然意识到必须做一次代码迁移，才能修掉公司运作方式里的系统性缺陷。过去，CISO 得开始游说，并向每个部门要几个季度的一小部分工程资源才能把它修掉。 

迁移的经济成本下降了，跨公司协调的成本也下降了。Claude 把迁移过程自动化了，几万行代码，几天就能完成。 

持久原则：给每个智能体一个单用途身份，权限只够干它的活。如果你允许智能体互相协调，让它们走和人类一样的通道。 

治理（Governance）

我们自动化了许多安全流程，但人类仍然是保障安全软件开发生命周期不可或缺的一部分。只不过注意力不再放在审代码和看 bug 报告上，而是放在 Claude Tag、循环和仪表盘上。

这凸显了强治理的重要性。如果一个 skill 过期了，发现的 bug 类别从未写回 CLAUDE.md，或者智能体的决策从未被抽样，整套结构就会退化。我们靠下面这些办法避免：

  • 按风险给代码库分层，再按这个层级自动化审查。
  • 所有新的 AI 审查者先走影子模式。新智能体先发评论等人批准，直到赢得信任。我们的团队也会对它们做「红队」，试图塞进恶意变更。
  • 抽样一定比例的全部自动批准。
  • 盯住生命体征。我们维护并密切监控一块仪表盘，汇总每个安全流程和工作流的关键指标。
  • 把每个智能体动作路由到 SIEM。每一次自动批准、工具调用和智能体对智能体消息，都会带着所用信号记入日志并落入 SIEM，因此任何决策事后都能归因、可审计。我们用这些数据，把这些智能体当作一类新的内部威胁来对待，并在它们行为偏离时拉高告警。

持久原则：安全工程师的工作，从监控 bug 演变成监控循环。

这些控制背后的评估框架，见 CISO 的智能体 AI 指南。

模型持续演进时，如何守住 AI SDLC 的安全

软件开发生命周期以及加固它的手段演进有多快，怎么强调都不为过。模型能力每个月都在前进，同时带来新的挑战和解决方案。 

今天不太管用、或经济上还不太划算的事情，很可能很快就会行得通。给团队的正确问题不是「我们扫得起所有东西吗」，而是「如果扫描几乎免费，我们会跑什么？」按那个目标来规划。
