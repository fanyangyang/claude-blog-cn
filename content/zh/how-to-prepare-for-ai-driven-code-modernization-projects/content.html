在 Notes from the Field 系列中，Anthropic 的前沿部署工程师（forward deployed engineers）分享源自真实客户部署的最佳实践。本文中，我们分享管理大型代码现代化项目的经验。

代码现代化（code modernization）曾经需要规划多年、全员投入，如今可以在数月（甚至数周）内完成，但项目前后所涉及的组织性工作往往并未改变。 

例如，对关键银行系统的每一次变更都必须经过变更管理、审查和审批。这是一套严谨的流程，因为监管机构、审计方和业务部门都要求如此。 

正是这些流程让关键系统值得信赖，而它们建立在这样的假设之上：每项变更都由人编写、每个差异（diff）都由人审查。一旦智能体加速了变更的编写，瓶颈就从"产生变更"转移到了"围绕变更动员整个组织"。

本文介绍企业在现代化开始之前必须完成的工作：定义"完成"意味着什么、每项变更必须携带哪些证据、已认证的变更如何进入生产环境，以及需要准备哪些条件才能让运行启动。 

我们将这一过程拆分为六个步骤：

  1. 定义目标：现代化后的代码必须具备的技术栈和行为。 
  2. 制定认证标准（certificate）：变更在目标状态下被视为正确所需满足的条件。 
  3. 设定推广策略（promotion policy）：已认证变更以与产出速度相匹配的节奏进入生产环境的路径。 
  4. 落实前置条件：环境、CI/CD、审查能力和审批。 
  5. 构建并打磨智能体工作流：定制的 Claude Code 动态工作流（dynamic workflow），将现代化任务分发到许多更小的并行子智能体工作流中，由它们产生变更。这一环节围绕目标、认证标准和推广策略构建。
  6. 运行现代化：在代码库的一个小分区上端到端验证工作流，然后扩展。 

第 1 步：定义目标

目标（target）是现代化的最终状态。期望的最终状态决定了你正在进行的属于三种现代化类型中的哪一种，详见下表。 

确定现代化类型

该选择哪种现代化类型，往往在组织内部争论不休。根据我们的经验，最贴近生产的人希望更换技术栈而保持行为不变，以控制风险（转型式现代化）。另一方的立场通常来自长期与代码库打交道的工程师，他们希望现代化能偿还技术债；此外还有业务相关方，他们希望借机提出新的需求（重塑式现代化）。 

两种立场都合理，但如果这个问题悬而未决，它会在之后重新浮现为"某项变更是否'正确'"的争论。就选择哪条路径达成共识会增加前期的摩擦，但会让整个项目更加顺畅。

梳理代码库并编写行为规格说明

理解现有系统往往是定义目标的第一步。提取旧代码实际做了什么，并建立当前行为的清单，可以轻松判断哪些部分应当修改或删除，从而确定现代化属于转型还是重塑。这通常还会暴露出未知的业务逻辑和边界情况。 

Claude 可以完成大部分这类发现工作，例如映射依赖关系、记录没人记得是谁构建的工作流。代码现代化插件（code modernization plugin）的 assess、map 和 extract-rules 命令会挖掘带源码引用的业务规则，工程师随后可以审查。 

然而，仅靠 Claude 的发现可能无法完整捕捉旧系统的行为。与业务用户和开发者的访谈、内部文档可以填补这些空白。收集上下文在前期可能需要一些时间，但这段上下文的质量决定了工作流之后每一个决策的质量。

对于重塑式现代化，定义目标还需要额外的工作：应该写出详细的行为规格说明，并与用户群体达成一致。

确立项目的正当性与目标

在定义目标的同时，组织还应该考虑为什么值得开展这次现代化。现代化改造遗留系统可以降低持续的维护和运营成本，但根据我们的经验，成本削减并不是大多数现代化项目的主要驱动力。

降低风险往往是现代化最重要的收益。在讨论是否开展项目时，请考虑不进行现代化的风险。 

例如，一个带有未修补漏洞的系统可能意味着网络入侵或严重到危及业务本身的停机。不受支持的运行时，或熟悉该系统且不断缩小的工程师群体，都会加剧这种风险。 

Claude Code 这样的智能体编码工具缩短了现代化周期，但预算仍然难以估算，这导致了惯性。我们已经公布了一些大规模现代化的成本，其他公司也有公布。这些可以作为粗略的基准，本指南末尾还有关于预算预测的更多建议。 

启动这类项目的主要挑战，通常是在拥有该系统的团队和依赖该系统的团队之间建立内部共识与承诺。通常在领导层面构建商业案例、设定项目目标，会让这一环节更加顺利。这也有助于为之后的认证标准和推广策略中的权衡锚定基准。当相关方对一项变更能承担多大风险产生分歧时，"不进行现代化的风险"就是那个平衡砝码。 

第 2 步：制定认证标准

认证标准（certificate）是每项现代化变更必须满足的条件或测试集合。请选择能提供最强累积证据、证明变更相对于目标而言是正确的那些条件。 

每项条件都应该在无人介入的情况下可检查，这样智能体工作流才能反复迭代一项变更，直到满足认证标准；如果无法满足，则标记为需要人工审查。 

认证标准包含什么取决于目标，但通常来自以下清单：

  • 原有测试套件通过
  • 现代化过程中由 Claude 编写的测试全部通过
  • 测试覆盖率满足约定的阈值
  • 性能基准保持在约定的范围之内
  • Claude 在全新的上下文窗口中独立进行的对抗性审查未发现阻塞性问题
  • 对于用户界面，由 Claude 驱动的计算机操作（computer use）未发现回归
  • 当前版本与目标版本对相同输入产生相同输出，可以来自线上数据、录制数据或由 Claude 生成
  • 持久化状态和线上格式（wire format）可以在当前版本与目标版本之间往返转换
  • 变更在预发环境（staging）运行约定的时长，错误率、延迟或告警均无回归
  • 静态分析和安全扫描未发现新的问题
  • 对于编译型目标，构建干净且类型检查通过
与负责审查变更并将其推广到生产环境的人一起编写认证标准。在认证标准和智能体工作流仍在设计时，就邀请现在依赖该代码库的开发者、用户群体和业务负责人参与。 

他们的专业经验决定了认证标准衡量什么，而他们的早期参与正是在变更进入审查时赢得他们支持的关键。检验最终认证标准是否合格的一个好方法，是看他们是否愿意仅凭认证标准的证据就放心合并。如果他们在其中看到了自己的标准，第 3 步的推广策略就可以更轻量。 

认证标准对照什么、如何对照，取决于现代化类型。 

  • 对于升级式现代化，对等性（parity）是相对于原始代码库的，原始测试套件可以作为认证标准的核心。 
  • 对于转型式现代化，对等性同样是相对于原始代码库的，但原始测试套件很少能在新技术栈上运行。生产流量回放、新旧之间的差分测试（differential testing）以及生产并行部署（prod-parallel deployment）承担了大部分工作。 
  • 对于重塑式现代化，认证标准锚定在行为规格说明上。这是最困难的情况。规格说明作为对照物不如现有系统客观，因此涉及更多模型判断，可能导致结果更加多变。此时认证标准依赖从规格说明编写的测试、Claude 对照规格说明逐项检查变更的独立对抗性审查，以及在新系统保留旧系统行为的差分检查。随着规格说明不断澄清，预期需要修订认证标准：规格说明中的空白会最先在这里显现。

老旧系统往往测试覆盖薄弱、测试不稳定、遥测（telemetry）稀少。定义认证标准的一部分就是识别这些空白。如果难以支撑一套强有力的认证标准，这一步最有用的做法之一是借助 Claude 构建缺失的证据，无论是搭建生产并行环境、构建回放工具，还是编写更多测试。 

第 3 步：设定推广策略

智能体产生变更的速度，远超任何人类团队逐条 diff 审查的能力。推广策略是一条分层的审查路径——预先书面确定并达成一致——为变更设定人工审查的深度，让现代化能够在可接受的时间线上完成。 

与认证标准一样，这一步要与审查者共同推进，并尽可能纳入组织现有的变更管理流程。具体细节因组织及其面临的风险权衡而异，但有几条规则放之四海而皆准：

  • 根据爆炸半径（blast radius）和智能体置信度对变更分层。如果组织有自己的变更或风险分类，就使用它。关键路径保留完整的人工审查。
  • 在源头修复反复出现的标记。持续对标记出的变更进行分组分析。当同一种标记反复出现时，修复智能体工作流或认证标准中的根源，而不是逐条审查。
  • 与审查者共同设计输出格式。就哪些信息和格式能让审查最快、哪些信号比其他信号更能增强信心达成一致。让他们在第 5 步审查早期样本输出。
  • 有效分配领域专家（SME）的时间。领域专家不会阅读每一份最终 diff，但他们的判断仍然是稀缺资源。让他们能够直接跳转到风险最高层级的变更，以及每个层级内被标记的智能体决策，而无需在大量 diff 中翻找。这样少数几个小时的专家投入就能覆盖风险最大的变更。

这些规则中有许多通过让领域专家早期参与来前置他们的时间投入。他们的反馈会在全面现代化开始之前调校认证标准和智能体工作流。

他们对样本的签字认可，也会成为在高置信度区域采用更轻量审查路径的进一步依据。这与传统的非智能体模式相反——传统模式中审查发生在最后。

推广策略还应反映现代化在速度与审查深度之间的定位。一个赶着硬性截止日期（例如运行时即将失去支持）的现代化项目，需要更快的策略、更轻的人工审查，并明确同意每项变更承担更多风险。 

时间线较长的现代化项目则可以承受更深的人工审查和更慢的切换。相关方会根据各自的风险偏好和约束落在这一光谱的不同位置，因此在工作开始前锁定这一点是值得的。

在受监管的环境中，对任何变更采用更轻量的人工审查路径都可能引起切实的不安。单个审批人犹豫不决，因为他们承担着坏变更的风险，而领导层承担着系统老化的更大风险。 

根据我们的经验，推广策略的指令最好来自组织最高层。也最好事先达成一致，这样进入生产的 bug 的责任是分担的，而不是落在某个批准变更的人身上。

所有这一切仍然依赖于足够详细的认证标准，使其能作为真正的证据，也依赖于那些对 Claude 如何得出某项变更理解到足以信任它的审查者。 

第 4 步：落实前置条件

这一步的很多工作要经由现代化之外的团队完成：平台或基础设施团队负责宿主环境，QA 或发布工程团队负责测试能力，安全和合规团队负责审批。这些团队通常各有各的待办清单或审批流程，所以要尽早开启对话——一旦你识别出需求就立即开始，往往在第 1 步到第 3 步仍在进行时就要启动。

环境

  • 一个专用远程宿主，用于运行工作流，让 Claude 能够访问代码库和其他相关数据源
  • 认证标准所需的测试能力
  • 任何能增强认证标准的东西：生产遥测、生产并行环境，或用于回放的生产数据

代码库与 CI/CD

  • 代码库的依赖关系图，以构建和编译日志、导入分析或运行时追踪为依据。注意：插件的 map 命令是一个很好的起点，但根据代码库的规模和年代，可能还需要更广泛的前期工作
  • 对任何依赖或包的计划处理方式，作为目标定义的一部分
  • 如需要，准备好加入 CI/CD 的兼容性检查
  • 如果要在原位置（in place）进行现代化，达成一致的代码冻结（code-freeze）策略
  • 面向活跃开发者的沟通计划，涵盖任何代码冻结和新的兼容性要求

团队与审查

  • 依赖该代码库的其他团队就其参与方式达成一致，例如签署认证标准或按推广策略进行审查，并为审查者预留时间

安全与合规

  • 经批准可访问源代码的 Claude Code 模型访问路径
  • 智能体工作流的最小权限访问：只对现代化分支有写权限，不持有生产凭据
  • 现代化分支中的机密和 PII 已清除或脱敏
  • 每项变更都可追溯，PR 关联到智能体记录和认证标准证据
  • 对新依赖进行许可证和漏洞检查

第 5 步：构建并打磨智能体工作流

使用 Claude Code 开发定制化的动态工作流（dynamic workflow）来实现代码库的现代化。 

我们建议从代码现代化插件入手，并把工作流可能需要的一切都放到文件系统或 MCP 上，让 Claude 能够触达。这包括目标、认证标准、推广策略、代码库、文档，以及认证标准要求的任何数据源或工具。你也可以把本文作为上下文提供给 Claude。这构成了项目的核心知识库。

有了这些之后，构建现代化工作流就是简单部分了。让领域专家按需审查 Claude 的工作，包括任何代码库专属技能或提取出的规则，确保在下游依赖它们之前先完成审查。 

通过在代码库的小范围上应用你所构建的内容来打磨它，由领域专家审查其产生的变更、智能体的过程，以及认证标准得到满足的证据。 

问题浮现时，你应该修改的是工作流，而不是每一项变更。目标是建立起这样的信心：一旦规模化，变更几乎处处都能满足认证标准，审查者在推广策略下也会放心合并。 

第 6 步：运行现代化

首先，在代码库的一小部分上端到端完成现代化，包括通过推广策略审查并落地这些变更。趁成本还低，修复一切不顺畅的地方，重复这一过程直到你有信心，然后扩展到整个代码库。 

转型和重塑式现代化需要与现有系统并行构建目标、完成后切换；而升级式现代化还有第二个选项：在开发继续进行的同时，在线上代码库上原地进行现代化。 

当系统不能停机，或代码库变化太快、难以让一份独立的现代化副本保持同步时，通常就选择这种方式。我们观察到有效做法是：将代码库从叶子向内划分为逻辑分区；一次冻结并现代化一个分区；对 CI/CD 设置门禁，让新提交无法撤销已经完成现代化的分区。 

关于成本的说明

我们经常被问到这样的现代化在 token 消耗上要花多少钱。每次现代化各不相同，但主要的成本驱动因素包括：

  • 代码库中有多少需要被读取而非被修改；
  • 认证标准有多复杂（在受监管环境中，验证——而非编写变更——通常占据更大的份额）；
  • 认证标准要求多少新增测试编写和测试修复；以及 
  • 在运行期间，其他团队围绕你进行合并所产生多少协调（reconciliation）工作。
在代码库的一小部分上完成现代化时，测量 token 用量，并以此推算其余部分。把试点无法看到的东西——例如线上代码库上的协调——视为未知数。这样你就能得到整个现代化成本下限的估算。 

试点的测量数据还能显示在哪里针对成本优化你的智能体工作流。找出消耗 token 最多的工作流环节，考虑如何让它们更高效。把计算密集的验证信号移到更便宜的关卡之后，让它们只在更简单的检查通过后再运行。 

考虑使用 Sonnet 这样的模型来平衡成本与能力，处理认证标准完全覆盖的机械性、高重复度工作。把更智能的模型留给困难的转型，以及验证正确性的对抗性审查。 

当较便宜的模型无法满足认证标准时，你也可以升级到更昂贵的模型，但要在试点期间仔细分析重试率，因为几次便宜的尝试可能比一次昂贵的尝试花费更多。如果你让 Claude 同时访问工作流和试点数据，它可以与你一起完成大部分这类分析。 

现代化之外

现代化后的代码库只是一项产出。其他产出还包括：产生它的工作流、一份界定何为正确的书面认证标准、你的变更管理流程已经接受的推广策略，以及每项落地变更的证据链。把这套打法固化为可复用的资产，这样下次升级或重写时模式就已经就位。

我们的前沿部署工程师会在客户最关键的系统上与客户一起走完这些步骤。如果你正在准备一次现代化，与我们的团队聊聊。
