要让 AI 智能体在人机协作团队中发挥最佳水平，它需要获得与人类相同的工具、文档和上下文访问权限。 

在“单人”AI 体验中（一个人与一个助手对话），这很简单：你连接自己的账号，智能体代表你行事。但在 Claude Tag 这类“多人”AI 体验中，Claude 同时置身于一个由许多人共享的频道里，它调用的是属于整个工作区而非任何个人的工具和上下文。 

要让多人体验运转起来，Claude 需要拥有这些工具的独立账号，由管理员创建并与工作区绑定。我们称这种访问模型为智能体身份（agent identity）。

在这篇文章中，我们将解释智能体身份如何运作、它如何将权限从按用户划分转变为按频道划分，以及如何在你自己的工作区中合理地设定其范围。

为什么“代表用户行事”会失效

当你把 AI 用作个人助理时，你可以连接 Google Drive、GitHub 和日历等平台，让模型使用你的访问权限在其中读写。 

这种模型对 Claude Tag 并不适用，原因有二：

  • 智能体自主性不断提升。 AI 智能体能够可靠独立完成的任务时长，大约每四个月翻一番。如今，智能体可以自行安排稍后执行的任务，也可以在提出请求的用户早已下线很久之后响应事件。虽然用户会设置在特定情况下触发其行动的例行流程，但智能体的工作在很大程度上是自主的。 
  • 多人协作团队。 Claude Tag 将 Claude 引入团队已经在协作的共享空间——例如一个由三名工程师和一位产品经理共同排查 Bug 的频道。但当不止一个人在指挥时，应该以谁的权限为准？无论选择哪个人，都无法在所有情况下都正确。因此，这种模型让管理员可以独立于相关的人类成员来定义智能体在 Slack 中能做什么，并对 Slack 中执行的操作进行独立的追踪。 

Claude 以自身身份行事

在启用了 Claude Tag 的频道中，Claude 并不代表某一个用户行事。它在涉及的每个系统中都有自己的账号：它以 Claude 应用的身份在 Slack 中发帖，以 Claude GitHub App 的身份创建 pull request，并以管理员配置的服务账号查询你的数据仓库。

而且，由于不涉及任何个人用户凭据，共享频道永远不可能成为窥探他人私密文档的旁门左道。

继承权限

在智能体身份模型中，管理员在工作区层面定义一个身份——即 Claude 在所有场景中持有的基准连接与技能集合——每个频道默认继承该身份。然后，在合适的地方，他们可以在频道层面进行覆盖，比如授予工程频道访问 GitHub 和数据仓库的权限，或将 CRM 连接限定在单个私密频道中。

除凭据外，管理员还需定义： 

  • 仓库访问权限：Claude 可以读写哪些仓库。
  • 连接器：Claude 用来完成工作的工具和 API 密钥。在整个组织中，不同的 API 密钥可以以不同的权限级别连接同一服务（例如，Claude 在通用频道中可能只被授予数据仓库的只读权限，而在数据团队的私密频道中拥有写入权限）。
  • 技能与插件：Claude 动态加载的指令、脚本和资源文件夹，用于提升其在专项任务上的表现。
  • 常驻指令：针对每个频道的自定义指令和上下文。

由于该模型建立在独立的 Claude 身份之上，撤销某个身份即可终止 Claude 在所有使用该身份之处的访问权限。相比在数十个用户账号之间逐一审计智能体的操作，这种方式的管理成本要低得多。

智能体身份模型如何运作

智能体身份将“这个用户能做什么？”的问题替换为“这个智能体在这个分区里能做什么？”这与按用户划分的访问控制列表（ACL）有所不同：即使某个频道成员没有仓库的直接访问权限，只要该频道的配置授予了 Claude 相应权限，他就可以让 Claude 去读取该仓库。

这确实不同寻常，但我们认为，这是迈向适用于自主、多人协作智能体的访问模型的必要一步。下面，我们概述如何思考这些边界的设定。

身份边界如何运作

Claude Tag 为每个私密频道创建独立的身份；工作区中的公开频道则共享一个工作区级别的身份。Claude 在法务频道中的身份无法触及未在该处授权的代码，它在工程频道中的身份也无法读取未在该处授权的法务文档。记忆和访问权限都遵循这些边界：Claude 在私密频道中学到的东西绝不会出现在更广泛的工作区中。

身份属于频道，因此频道中的任何成员默认都可以 @Claude，而管理员可以将每个频道的配置限定到权限最小的成员级别。在 Enterprise 计划中，基于角色的访问控制让管理员可以更进一步，决定哪些成员能够调用 Claude，这样一个频道既管住了智能体能触达什么，也管住了谁可以提出请求。

对工具和上下文的宽松默认访问

在 Anthropic 内部运行 Claude Tag 的过程中，我们发现它的价值会随工具和上下文访问权限的扩大而复利增长。每接入一个系统，其他系统都会变得更有用，因为 Claude 可以跨系统整合上下文——把 Slack 里的一条线索、Drive 里的一份文档、追踪器里的一个工单、仓库里的一条查询，汇成一个任何单一工具都无法给出的答案。

从 Claude 中获益最多的团队，恰恰是从一开始就授予其充分访问权限的团队，之后再根据组织的管理偏好逐步收缩。智能体身份赋予管理员足够宽的范围，让 Claude 能开展有用的跨系统工作，同时边界又足够牢固，访问权限绝不会蔓延到未被授权的地方。我们的建议是：先在少数频道中建立一个基准配置，阅读审计日志，然后在工作确有需要之处逐步扩展访问权限，每一次授权都深思熟虑。

对于需要更细粒度控制的组织，管理员可以在特定频道中禁用 Claude Tag，也可以应用基于角色的访问控制（RBAC），将 Claude Tag 的使用限定于特定用户。

私信

在 Claude Tag 中，私信的运作方式与共享频道不同。私信基于用户各自的 claude.ai 账号运行——使用他们自己的连接器、凭据，结果也以其名义呈现。这使得私信成为处理那些绝不该出现在频道中的任务和工具的正确场所，比如邮件草稿，或只有你本人持有许可证的软件。

安全与审计

当管理员向某个频道的配置添加连接时，凭据会被独立存储并映射到该频道的身份，然后在请求时于网络边界注入。任何发往管理员未允许的主机的出站流量都会被直接拦截。在审计方面，使用智能体凭据执行的每一个例行流程、每一次记忆写入和每一次网络调用都会被记录，而且由于 Claude 以自己的服务账号行事，这些操作也会落入每个被连接系统自身的日志中。

下一步计划

智能体身份是 Claude Tag 访问模型的基石。未来，我们计划强化 Claude Tag 的安全能力，包括即时凭据授权（just-in-time credential grants）——让用户可以在当下批准单次敏感操作，而无需永久扩大智能体的权限范围——以及面向具有更复杂权限审批结构的组织的身份感知层。它将在智能体的权限范围之上叠加用户级别的校验，只有当频道配置和提出请求的用户自身的权限都允许时，Claude 才会行动。

Claude Tag 等产品从单人 AI 到多人 AI 的转变，使长时间运行、以团队为单位的工作成为可能。智能体身份确保 Claude 对工具的访问足够宽泛以发挥作用，又足够收敛以在企业规模下保证安全。
