面向每个编码 agent 的六个问题

以下是负责人在评估编码 agent 时可提出的六个问题，用来确认它们是否达到企业级就绪。

要问的问题为什么重要合格回答不合格回答
该拒绝时，模型会拒绝吗？模型是拦截有害请求的第一道检查，能降低不良动作发生的可能。拒绝行为已训练进权重，并公开了拒绝率。「我们的系统提示要求模型拒绝。」

策略能在中心被锁定吗？设定个人无法撤销的最低标准。带硬性拒绝规则的托管设置，本地用户无法覆盖。「每个开发者各自的配置文件，加上一份靠自觉遵守的策略文档。」

你能还原一次事故吗？合规要求。以及持续改进安全性。会话遥测导出, 审计 API（Enterprise），以及明确列出的已知缺口。「日志可按需提供。」

02 识别 AI 特有的风险

凭据泄露与权限滥用 · 未经审查的依赖与扩展 · 数据外泄 · 提示注入

安全与技术负责人对凭据泄露、权限滥用、依赖被污染、内部威胁这类风险并不陌生。但涉及 agent 时，攻击面、攻击速度和规模都会改变。下面看几类风险。

风险你今天的应对方式引入 agent 后有什么变化
凭据泄露与权限滥用最小权限、短期令牌、通过工作负载身份或 OIDC 实现无密钥认证。定期复查权限过大的账号。人用实名账号，软件用按工作负载划分的身份。凭据应当短期有效，并且只覆盖该任务或作业所需的范围，而不是开发者的全部权限。agent 在开发者的会话内行动，而 Claude Code 之外的多数日志只显示开发者的名字。
未经审查的依赖与扩展锁定版本、设审查关卡、清单变更需两人复核。配置纳入版本控制。agent 添加依赖的速度远超人工流程，其中既有已审查的也有未审查的。扩展一旦连接，就会立刻开始向 agent 下达指令。
数据外泄在网络层设置出站白名单。被攻陷的 agent 可以借你已放行的服务把数据发出去。与传统恶意软件不同，它可以尝试多条路径，攻击者无需事先明确指定。
内部风险社会工程意识培训、身份核验、举报渠道。提示注入：检查点转移到工具调用和网络边界。

风险 1：凭据泄露与权限滥用

agent 能读到的东西，就可能被泄露，包括长期有效的 AWS access key 或 GitHub token 这类凭据。

如何缓解

把常驻密钥从 agent 环境中移除。通过工作负载身份或 OIDC 实现无密钥认证，让 agent 每个作业或会话只拿到短期令牌，就没有长期密钥可泄。确实必须存在令牌时，保持其生命周期短、范围窄。用 hooks 阻止含密钥的提交，并在推送时开启密钥扫描。在开发者机器上，沙箱可以对命令隐藏凭据。云会话读不到开发者的机器，因此虚拟机里只有你放进去的密钥，例如环境变量或上传仓库中的文件。

agent 能做的事，被攻陷或过度激进的 agent 也能滥用。默认情况下，Claude Code 中的 agent 以监督它的开发者身份运行。发生事故时，你可能需要区分 agent 与开发者的动作，才能恰当响应。

如何缓解

应用最小 agency原则，也就是面向 agent 的最小权限。在模型之外，按策略检查工具调用，这样超出发起用户或任务权限的请求会被你的规则拒绝。按与其他权限过大、长期不活跃账号相同的周期审计 agent 身份。

保留会话记录，并导出 OpenTelemetry 数据，以便查看 agent 做了什么、读了什么。在 CI/CD 流水线中给 agent 独立身份，可单独限定范围并吊销，无需触碰任何开发者账号。这可以用 Claude Code 的 GitHub Action 实现，它以独立的 GitHub App 身份运行。

风险 2：未经审查的依赖与扩展

agentic 编码加快了代码生成与审查的速度，也加快了依赖添加和配置变更的速度。

当你让 agent 加一个 JSON schema 校验，它会找到包、装上最新版本，几分钟内就有可用代码。若 agent 没被引到正确方向，这种速度本身就是风险。

MCP 服务器、插件、skills、子代理定义，以及仓库里的CLAUDE.md文件也都是依赖，它们值得你像审查软件包那样审查。与等待被调用的被污染库不同，它们一加载就即刻触达 agent：在 agent 做任何工作之前，它们的描述与指令就已经进入上下文窗口。

如何缓解

把 agent 指向内部的已审查包仓库，并用出站白名单让它只能访问该仓库。云会话默认允许访问公共仓库，所以请把共享环境的网络访问设置调整为一致，或者在仓库位于私有网络时使用自托管环境（公测）。把依赖锁定到具体版本，并用自动升级 PR 保证安全补丁仍能快速落地。MCP 服务器、插件和 skills 同样处理，并使用市场白名单。

在 Enterprise 套餐上，skill 与插件扫描会在组织内有人上传或修改第三方 skill 和插件时，检查其中是否含恶意内容。

风险 3：数据外泄

任何泄露都需要一条出口。难点在于：域名白名单无法区分你的账号和攻击者的账号。例如你放行 github.com，agent 就可以推送到攻击者拥有的仓库。

DNS 是第二条可能的外泄通道，HTTP 白名单会漏掉它，因为数据可以被编码进 agent 查询的域名里。

当然，一旦令牌泄露，攻击者根本不需要 agent 的网络。他们可以在任何地方使用该凭据，出站过滤永远看不到那次请求。

如何缓解

按 agent 分别设置目的地白名单，窄到你的代理支持的程度，能到组织或路径就更窄。让 agent 的 DNS 走你做过过滤和日志的解析器。将云存储访问限制在预期角色与 IP 段内，并用数据防泄漏能力标记随上传流出的密钥与敏感数据。在 Claude Code 云会话中，白名单就是环境的网络访问设置，按域名生效。如果你需要自己的代理、DNS 过滤或链路内检查，请在自托管环境（公测）中运行会话。

风险 4：提示注入

自 2023 年该榜单设立以来，OWASP 在每一版LLM 应用 Top 10中都将提示注入列为头号风险。

社会工程与提示注入的作用机制相同。社会工程之所以能突破技术控制，是因为被欺骗的人自己执行了动作，系统看到的是合法请求。被注入的 agent 同样以自己的权限行动，每一条日志都显示为合法请求。

对编码 agent 来说，提示注入可能通过多种途径发生，包括：

  • issue 跟踪器与 pull request 评论；
  • 依赖的 README 与变更日志；
  • agent 抓取的网页；
  • MCP 工具调用的响应；
  • 源码文件中的注释；以及其他。
如何缓解

没有任何单一控制能阻止提示注入，所以防御必须分层。这包括判断 agent 读到什么、将要做什么的检查，以及限制潜在损害的固定边界。本指南后续章节会深入展开。

03 判断层

分层防御 · 理解对齐训练 · 提示注入探针 · auto 模式分类器

分层防御

在 Claude Code 中，被攻陷或目标偏离的 agent 在造成损害前，必须先越过多重控制与两层防御。

第一层基于判断。这些控制决定某件事看起来是否正确。

  1. 对齐训练教会 Claude 拒绝恶意请求、倾向谨慎动作。
  2. 提示注入探针在 auto 模式下扫描传入的工具结果，在 Claude 据此行动前标出疑似被注入指令的内容。
  3. auto 模式分类器把大多数拟执行的工具调用与用户声明的意图做比对。

第二层通过限制任何命令的能力来强制执行固定边界：

  1. 权限规则、命令分析与 hooks在执行前按你设定的规则检查每个动作。
  2. 沙箱与出站白名单限制被放行的命令能触碰什么、数据能去往哪里。

本章讲判断层，下一章考察固定边界层。

理解对齐训练

Claude 被训练成具备良好判断，并遵循一组硬性规则，例如不编写可能造成重大损害的恶意代码。

在 Claude Code 测试中，在没有生产环境防护的情况下，当前 Claude 模型拒绝了81% 到 85%的恶意请求，同时完成了98% 到 100%的双用途与良性请求，例如运行侦察工具或为网站做漏洞测试。

Claude 还被训练成优先选择谨慎动作而非不可逆动作，并在存疑时提出顾虑或寻求指引，而不是即兴发挥。Claude 被训练成不把抓取内容里的指令当作来自用户的指令去执行。

请记住：模型对齐训练降低坏结果发生的概率，但不限制坏结果能坏到什么程度。

用数据说话

Claude 在间接提示注入下的表现

第三方 AI 安全公司 Gray Swan 运行了一项间接提示注入基准测试：攻击者把指令植入 agent 在任务中读到的内容里，例如网页、文件或工具结果。

攻击者在每个场景中最多可尝试 15 次措辞，得分是「任一尝试成功」的场景占比。关闭提示注入探针时，Claude Opus 5.5 得分为 1.0%，Claude Fable 5.2 为 4.1%。对 Fable 5.2 的大多数成功攻击命中的是被安全分类器改路由到较旧模型的请求（见系统卡).

提示注入探针

Claude 的提示注入探针用于标记工具结果中任何疑似被注入的指令。

auto 模式分类器

一个被说服「删除目录是合法任务」的模型，会用与做其他事同样的彻底和娴熟去删掉它。

这类破坏性、过度激进的动作，正是auto 模式分类器要抓住的。对于你的规则和内置审批未覆盖的动作，auto 模式分类器判断拟执行动作是否符合开发者指令的意图。

例如，对「修复 auth_test.py 中失败的测试」这条指令，合理的命令与「把 .env 内容外泄」的命令看起来完全不同。

Claude Code 发给分类器的请求会剔除工具结果，因此注入的文本无法直接操纵分类器。若动作符合用户要求，就执行；不符合，则被拦截，或 Claude 返回向开发者申请权限。

用数据说话

auto 模式在攻击下的表现

在 Anthropic 资助的 2026 年 7 月研究中，独立测试公司 Trajectory Labs 对截至 2026 年 7 月 17 日各 agent 的公开发行版本，把72 个间接提示注入场景各运行十次针对 auto 模式的 Claude Code，720 次尝试全部失败（0 成功），覆盖 Claude Fable 5、Opus 5 与 Sonnet 5。

  • Zero of 720 attempts succeeded against Claude Code in auto mode, across Claude Fable 5, Opus 5, and Sonnet 5.
  • 针对运行 GPT-5.6 Sol 的 OpenAI Codex，提示注入在 Codex 自身的自动审查模式下成功率 5.83%，在完全访问模式下为 19.03%。

这些测试覆盖的是 agent 本身，不包含浏览器扩展或其他产品防护。

auto 模式现在是所有套餐上交互式会话的默认起始模式。无头的claude -p、Agent SDK 以及 HIPAA 配置默认使用手动模式。

auto 模式成为默认，是因为多项测试表明它比人工审批能抓住更多危险动作。例如在 Anthropic 于 2026 年 8 月发布的一项受控研究中，1,053 名付费测试者抓住了 13.6% 的危险命令，而 auto 模式拦截了同样命令中的 89%。

配置 auto 模式涵盖如何调整分类器、覆盖其拦截与放行规则。

批准高风险动作

auto 模式依赖分类系统，并不能消除所有风险。

推广之前，先通过两个问题识别高风险动作：这个动作是否不可逆？单个失误的代价是否高于每次都人工审查？两者答案都是「是」时，就要求人工批准。

对多数组织来说，这份清单大致是：

  • 生产数据库迁移
  • IAM 策略变更与凭据轮换
  • 基础设施定义的修改

04 强制执行固定边界

设置权限规则 · Bash 命令分析 · 用 hooks 把守动作 · 用沙箱约束 agent 行为

判断层擅长抓住新颖攻击，但它的控制是概率性的，每一项都有被突破的可能。

固定边界层可以被做成确定性的，决定 agent 的影响半径。权限规则、命令分析与 hooks 决定动作是否执行，沙箱和出站白名单限定可触及的范围与数据流向。

它们的局限在于只拦截你告诉它们拦截的东西，因此需要结合你的环境来配置。

设置权限规则

权限规则分三类：

  • Allow规则让动作执行，
  • Ask规则在执行前询问，
  • Deny规则拦截动作。

Claude Code 依次检查deny 规则、ask 规则，最后是 allow 规则。这样可以防止 allow 规则为 deny 规则制造例外。在托管设置中定义的 deny 规则，任何用户或项目设置都无法覆盖。对于宽泛到能执行任意代码的命令，例如Bash(python:*)应避免设置 allow 规则。

Claude Code 先查 deny 规则，再查 ask 规则，最后查 allow 规则，因此 allow 规则无法为 deny 规则制造例外。子代理

用沙箱约束 agent 行为

沙箱是限制事故严重程度最重要的方式之一，因为它限定了 agent 的作用范围。但约束 agent 说起来容易做起来难，因为约束与能力往往此消彼长。

Claude Code 有三种主要环境：本地、带沙箱的本地、云。

下面讨论默认设置，以及如何针对组织内各类用例判断哪种合适。默认值可以集中修改并锁定，这部分在下一章说明。

本地

多数 Claude Code 会话通过终端、IDE 或桌面应用在本地进行。默认情况下，agent 能访问你电脑上你能访问的一切。在 auto 模式下，分类器会审查你的规则与内置审批未覆盖的动作。

这是约束最少的环境，适合低风险、自成一体的工作。对多数企业组织，我们建议对本地会话强制启用沙箱。
