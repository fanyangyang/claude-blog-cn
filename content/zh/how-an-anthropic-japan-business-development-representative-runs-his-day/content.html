作为 Anthropic 日本团队的商务拓展代表，我的工作是向日本企业展示 Claude 如何简化和自动化他们的工作流程，但在今年早些时候之前，我自己的大部分工作仍然是手动的。我每天早晨要花几个小时来分派和筛选销售线索，然后用日语或英语写邮件。在剩下的时间里，我还要更新我们的 CRM，通常滞后一天或更久。现在，我的智能体在我的工作日开始之前就准备好了大部分工作，我只需审核即可。

我构建的第一个由 Claude 驱动的工作流程相当简陋，但它完成了任务。我会一次把一项工作交给 Claude，纠正它出错的地方，并保存这些纠正。随着时间的推移，这逐渐发展成一小群智能体，每个智能体负责一项不同的日常工作。

消息很快传开了，同事们开始向我要我的提示词和技能，以便他们也能构建自己的智能体。我能给他们的只是一个包含我的技能和知识库中几个 Markdown 文件的 zip 压缩包，他们必须把它上传到 Claude，然后回答一轮设置问题，一切才能开始工作。我自己的一整套配置也变得越来越难以跟踪。每个智能体都是一项技能、一个定时任务和一个共享文件夹，而我通过在任意打开的聊天中向 Claude 提要求来修改它们，所以同一个技能经常在许多不同的对话中被编辑。

我想把每个智能体只定义一次，放在一个地方，并且能够看到我对它所做的每一次更改。所以我决定尝试 Claude Managed Agents (opens in new tab)（测试版），这是我们在 Claude Platform 上的托管智能体基础设施。

一开始我有些犹豫。文档里讲的是调度、工具和凭证库，而我是一名销售代表，所以我以为 Managed Agents 是为那些能够构建和维护必要基础设施的开发者准备的。我还是试了，因为我的智能体已经存在，我只需要把它们迁移过去。

事实证明，我不需要成为开发者。我用平实的语言描述每个智能体的工作，Claude 编写了几个简短的设置脚本，我在笔记本电脑的终端上运行了它们。（如果你想从零开始，Console 中还有一个带有现成智能体模板的 quickstart。）从那以后，就没有什么基础设施需要我维护了。

在这篇文章中，我将介绍我是如何设计和原型化这支智能体舰队的，为什么把它迁移到 Managed Agents，Claude Tag 如何接住任何超出日常流程的工作，这一切如何改变了我的一周，以及我会给那些想构建自己的智能体来自动化手动、重复性工作的销售同行们什么建议。

设计我的智能体舰队

我把工作流程划分到几个智能体上，并给每个智能体分配一个明确的任务。单一职责让每个智能体都易于理解和跟踪，尤其是在出现异常的时候。我还给每个智能体起了个日文名字，因为它们大多用日语工作。它们合称为 Nakama，意为“船员”，或者更字面地说，是与你一起工作的伙伴：

  • Furiwake（"分配"）最先启动：它读取每日的入站队列，将每条线索路由给团队中合适的代表，平衡线索数量和每条线索的优先级，并检查当天谁在岗，这样在我们任何人开始一天的工作之前，每条线索都有归属人。每次运行结束时，它都会向专门的 Slack 频道发布一份报告（每条线索都已进入、每条线索都已分配），这样我就能跟踪交接情况。
  • Sabaki （"处理"）负责分诊分配给 我的线索：它筛选每条线索，按照预设标准进行分类，针对该类别采取定义好的下一步行动（起草回复，引导对方自助处理；撰写定制的首封邮件），更新 Salesforce 中的线索记录，并起草首次接触邮件。它起草内容的素材来自 Nakama 的共享知识库，也就是每个智能体都会读写的一个 记忆存储 (opens in new tab)（下文会详细介绍）。
  • Henji （"回复"）每小时扫描一次我的收件箱，查找需要回复的客户邮件，并根据邮件线程以日语或英语起草回复，使用与 Sabaki 相同的知识库。我可以审核、编辑并发送草稿。
  • Shoudan（"商机"）读取近期的客户互动，并将更新推送到 Salesforce，这样商机记录无需手动录入数据就能保持最新。
  • Nokori （"剩余事项"）在一天结束时运行：它扫描我的日历，读取附带的会议记录，总结每次会议，并起草后续跟进，同样是基于同一个知识库。

每个智能体都按照一个调度运行。第六个智能体，也就是 Nakama 的协调者，是这支舰队的运营经理。它在各次运行之间更新智能体的指令和共享知识库。当我想改变某个智能体的工作方式时，我会用平实的语言在 Nakama 的 Slack 频道里写下我的需求。只有我才能在频道里发布修改智能体指令和系统提示词的请求。协调者大约每 15 分钟检查一次该频道，接收请求并完成更新。

在 Claude 中原型化这支舰队

你不一定需要 Managed Agents 才能开始。我首先在 Claude 中完成了整支舰队的原型，使用了以下组件：

  • 每个智能体对应一项技能：即一项工作的指令。
  • 为每项技能配置一个定时任务，这样我就不需要手动运行它。
  • 笔记本电脑上的一个共享文件夹作为知识库，每项技能都把学到的内容写回其中：它起草的内容与我最终发送的内容之间的差异，以及它在过程中挖掘到的任何新信息。

在 Managed Agents 上，技能变成了智能体的系统提示词，定时任务变成了 智能体部署上的调度 (opens in new tab)，共享文件夹则变成了记忆存储。我仍然用平实的语言提出修改要求，但现在我都在同一个 Slack 频道里完成，而且对智能体指令的每次修改都会保存为一个新版本，因此每个智能体都保留着一份带编号的指令历史。我建议先在 Claude 中开始，当你的智能体数量多到难以轻松跟踪时，再把它们迁移到 Managed Agents。

在 Claude Managed Agents 上运行这支舰队

在 Managed Agents 上，有三件事对我的工作流程最重要：

智能体可以在后台运行

无论我的笔记本电脑是否打开，智能体都会按照各自的调度运行，即使电脑离线也是如此。调度是每个智能体部署的一部分。我在 Claude 里也可以安排技能，但每一个这样的调度都是在我自己的应用中设置的任务。而在 Managed Agents 上，我可以在 Console 中、在已部署智能体的指令和工具旁边设置节奏和时区，而且我不需要在旁边维护任何 cron 任务。如果某次运行出了问题，我可以在 Console 中打开它，查看智能体采取的每一步。而且当我在尝试修改某个智能体时，定时运行会继续使用已部署的版本，所以未完成的编辑不会进入第二天的运行。

Nakama 共享同一个记忆，并从我的编辑中学习

每个智能体都读写同一个记忆存储 (opens in new tab)，因此任何智能体都可以使用其他智能体学到的东西。智能体会把它们起草的草稿与我发送的邮件进行比较，并把每处差异保存为关于我如何措辞的笔记。它们还会保留在研究答案过程中挖掘到的新信息，包括来自我们内部文档和官方网站的内容。我在 Henji 的草稿中修正一次措辞，Sabaki 和 Nokori 就不会再犯同样的错误。

凭证存放在具有范围限定权限的托管保险库中

我的智能体可以访问我的邮箱和我们的 Salesforce 记录，但由于这些是客户对话和公司记录，我希望这种访问受到控制。凭证存放在 托管保险库 (opens in new tab) 中，它保护智能体登录外部服务时使用的凭证，例如 OAuth 访问令牌和刷新令牌、API 密钥以及个人访问令牌。每个智能体的部署只使用其工作所需的保险库，它永远不会看到凭证本身，而且我可以一键撤销访问权限。

把后续步骤交给 Claude Tag

对于 Nakama 产出的大部分内容，我只需要在收件箱里读一遍草稿然后发送，或者瞥一眼更新后的 Salesforce 记录。但有些事项需要后续步骤，比如弄清楚升级路径或采购路线，或者把问题升级给另一个团队。

对于这些事项，智能体不会停下来等我。它们会把事项交给 Claude Tag (opens in new tab)（测试版）。Claude Tag 是将 Claude 设置为我们的 Slack 工作区的一名成员：任何在其加入的频道中的人——无论是真人还是我的某个智能体——都可以用 @Claude 标记一个请求，它会接收请求并在该线程中处理。一旦在你的工作区配置好，就没有什么新东西需要学了。你可以像 @ 一位同事一样 @ Claude。

在我的设置中，它的工作方式是这样的。一个智能体把行动项发布到 Nakama 的 Slack 频道并标记 Claude。Claude 阅读整个线程，检查我们的规则和适用的条款，列出选项，并起草所需的内容。当某个步骤需要我审核或批准时，它会标记我。当客户或另一个团队需要先回复时，Claude 会给自己设置一个提醒，在约定的日期回来检查。在下面的线程中，它设置了一个周二提醒，用于检查客户是否已回复，以及交易台是否已答复工单。提醒到期时，Claude 会检查两者，并在同一个线程中发布进展。如果某人需要催促，它会起草消息并标记我发送。

Claude 还会发布一份关于产品和定价更新的晨间简报。Nakama 协调者会接收这份简报，并把必要的修改写入共享知识库。

我的一周发生了什么变化

既然 Claude 会准备入站回复，并在（大多数情况下）无需我手动输入的情况下保持 CRM 记录最新，我的角色就是审核任何需要人类判断的事项。一本成文的规则手册定义了每个智能体的职责范围，而像定价问题、敏感账户或模棱两可的请求这类事项会路由到我这里。来自 Henji、Sabaki 或 Nokori 的每封邮件草稿顶部都附有一段简短摘要，说明来龙去脉，这样我就不必追溯整个线程来理解上下文：我阅读摘要、确认、修改，然后发送。

看看 Nakama 每周完成事项的日志，并把每项任务按我手动完成所需的时间来估算，这支舰队大约为我节省了 60 小时的工作。我把省下来的时间花在智能体（目前）还无法有效完成的工作上：与客户交谈、对外拓展策略、跨职能项目，以及帮助同事构建他们自己的舰队。

设计更高效的智能体

定时智能体每天都在运行，无论我是否在关注，因此浪费会不断累积，体现在成本和可靠性上。一些最常见的错误包括：在现有指令上追加而不是更新它们、给智能体提供超出其任务所需的上下文，以及让每个任务都在最大的模型上以最高的努力级别运行。

让智能体保持高效的大部分因素来自我设计舰队的方式：每个智能体只有一个任务，所以它的指令始终聚焦于该任务；每个工作的智能体都按调度运行，所以它会醒来、完成一轮工作、然后停止；智能体共享记忆，所以一次修正可以在各处复用。

另一个重要因素是每个智能体运行在哪个模型上。一旦智能体的任务被定义清楚，它可能就不需要我们最强大的模型。Furiwake 和 Shoudan 遵循成文的规则手册，所以它们运行在我们较小的模型 Sonnet 上。Sabaki、Nokori 和协调者运行在我们较大的模型 Opus 上，因为它们的任务需要更多的判断力。协调者最需要它，因为它要编辑其他智能体的指令，一次糟糕的编辑会波及每个智能体。Henji 需要和 Sabaki 一样多的判断力，因为每封客户邮件都不一样，但它也比其他任何智能体运行得更频繁，贯穿整个工作日。每次都让它跑在 Opus 上会是最昂贵的选择，所以我在 Managed Agents 中使用了 顾问策略 (opens in new tab)：Henji 运行在 Sonnet 上，当它遇到自己无法做出的决定时，会向 Opus 征求建议。顾问读取 Henji 到目前为止所做的工作，发回一个计划、一个修正或一个停止信号，然后 Henji 完成草稿供我审核。我还把每个智能体的努力级别（模型在回答之前思考的时间）与其模型分开设置，并且只在推理确实困难的地方提高它，比如 Henji 的回复。

我学到了什么

有三件事我想转告给任何正在构建自己舰队的人。

  1. 你不必每次都写一份详细的提示词。描述一次任务，让 Claude 起草，修正草稿，并让它保留修正。
  2. 知识库比提示词更重要。每一次修正和过去的互动都被保存下来，供所有智能体读写，所以 Claude 从那里获取上下文，而不是依赖更长的提示词。经过几百轮便宜的起草、修正和保存，草稿才听起来像我。
  3. 尽早给 Claude 更多空间。起初我一直在做那些我自认为需要我的任务：更新知识库，或者手动编辑每个智能体的指令。当我放手之后，两者都运行得很好。现在智能体们自己把学到的东西写进知识库，而协调者会在我用平实的英语提出要求时更新其他智能体的指令。我过去对那些本可以放心交给智能体去做的工作过于谨慎了。
