在上一篇文章中，我们描述了如何让 Claude 以约 95% 的准确率回答数据分析问题，主要依靠三样产物： 

  • 一层经过治理的语义层； 
  • 一组把我们的分析惯例编码进去的 skill 文件；以及 
  • 一套用来衡量表现的评估套件。 

那篇文章聚焦于 Claude Code（我们的数据科学家和数据工程师的主要开发界面），以及提高智能体准确率的最佳实践。

这篇文章讲的是 Anthropic 的数据团队如何把那套基础用到公司其他人工作的地方：通过 Claude Tag （公开测试版），它是我们 Slack 数据分析智能体的基础。任何人都可以向它提出与数据相关的问题，并得到与分析师使用的同一套治理定义所支撑的答案。 

在 Slack 部署数据分析智能体的最佳实践

让智能体准确，和把它部署到非分析师也能用的地方，后来证明是两件很不一样的事。上一篇关于准确率的建议这里仍然适用，我们不再重复。 

我们会讲过去一年里最重要的五条经验：如何在 Slack 部署数据分析智能体，以及你该如何看待分发、权限、新鲜度和可观测性。

skill 的刷新频率，要和数据模型一样高

你可以用 skill 教 Claude 按你的风格和要求完成一项任务。skill 是一份带自然语言指令的 markdown 文件，以及 Claude 需要时可以查阅的文件。

我们做过的最重要的架构决定，是把 skill 文件当成持续刷新的已发布内容，而不是做一次就忘掉的东西。 

数据模型一天可以变好几次。例如某列被改名、某个指标定义被纠正，或某张表被废弃。这些变化每一样都需要在较短时间内落到 skill 文件里。如果 Claude 读的是上周二那份 skill，它就会带着十足把握给出上周二那个错误答案。

这种倾向尤其伤人，因为数据消费者现在已经完全脱离了判断答案准不准所需的上下文。他们不是对着一张带趋势线和关联指标的仪表盘做“嗅觉检查”。他们在 Slack 里可能只收到一两个数据点；如果这不是他们常看的数据，他们很可能会接受那个自信但错误的答案。

为了控制这种不断变化的环境，Claude Tag 的运行时会挂载我们数据仓库的 skills/ 目录，并在每次对话中重新读取。skill 文件不过是磁盘上的 markdown；智能体读它们的方式和读任何项目文件一样。 

给智能体的 skill，不能只停在知道该查什么 

最初用 Claude Tag 部署数据分析智能体时，我们的本能是做一个“知识 skill”，教 Claude 该用哪些表、我们的语义层如何组织，然后就收工。很快我们就发现，那种做法能给出正确的 数字，却止步于有用的 洞察。

大多数数据消费者往往会问开放、含糊的问题，比如“是什么在推动这次下滑？”或“你能预测这个到月底会落到哪里吗？”或“把这些数据做成漏斗给我看。”回答这些问题，智能体不仅要知道数据在哪，还要知道分析师会怎么处理它。

所以除了这个知识 skill，我们还给 Claude Tag 挂上了额外的分析或 runbook skill，包括：

  • 预测：何时以及如何拟合简单趋势、季节性假设，以及何时因为序列太短或噪声太大而拒绝。
  • 队列与留存分析：标准队列定义、向领导层汇报的留存曲线模板，以及任何会绊倒朴素实现的坑（左删失、幸存者偏差）。
  • 漏斗分析：关键产品漏斗的规范阶段定义，这样“用户在 onboarding 里从哪一环掉下去？”在各次回答中是一致的。
  • 图表：可视化惯例，比如哪类问题用哪种图、调色板，以及何时表格比图更清楚。
  • 分析写作：如何组织一项发现（先给 TL;DR，再给数字、机制、限定），以及按置信程度该用多强的措辞保留。

每个数据团队大概都已经有这些惯例；它们通常只活在某个人脑子里，偶尔才被写下来。把它们写成 skill，能确保 Claude 应用它们时，和分析师一样稳定。

接上业务上下文，而不只是仓库

即使知识和 runbook skill 加在一起，也并不总能回答一个问题。有人问“为什么周二注册量掉了？”，答案往往不在数据模型里，而是散落在 Slack 线程、事故跟踪、发布说明和文档中。

为了补上这些缺口，我们把 Claude Tag 接到内部知识索引上，它编目了公司范围内的文档、讨论和事件。当智能体看到某个指标变动时，它可以在那个索引里搜索同期上下文：当天早上开的事故、翻转的功能开关、有人在频道里分享的竞品公告。 

答案现在会像这样：“周二注册量下降 12%：那天早上 9 点到 11 点有一起支付服务事故，下滑集中在受影响地区。”

如果你的组织有知识图谱、内部搜索，哪怕只是整理得当的事故和 changelog 源，把 Claude Tag 接到它们上面，是仓库本身之后杠杆最高的信息补充。你也可以把 Claude Tag 接上，让它能阅读并从 Slack 各关键频道获取上下文。 

有意识地给服务账号授权

Claude Tag 用服务账号查询你的仓库，而不是用提问者本人的身份。这是正确的设计（你不会希望每个 Slack 用户都要直接持有仓库凭证），但每个能 @ 这个机器人的人，都拥有机器人的数据访问权限。 没有按用户的行级安全：服务账号能读到的，频道里任何人都可以问。

我们从五个方面处理这件事（我们建议认真对待，因为它很容易做错，也很难收回）：

1. 把服务账号的范围限定在治理数据上。在 Anthropic，Claude Tag 的服务账号可以读取语义层的输出表，以及喂给它们的精选 mart。它不能读取原始事件流、staging schema，或个人 sandbox 里的任何东西。如果问题需要边界之外的数据，智能体会直说，而不是猜测。这也是正确的用户体验，因为治理层之外的数据尚未经过验证。

2. 在列级别对 PII 分类，并拒绝给服务账号 clearance。 治理数据并不自动等于对 PII 安全的数据（例如，一张精选表仍可能带着邮箱地址）。我们维护一份带列级血缘的数据目录，因此每列的来源和下游流向都是已知的。新列落地时，Claude 会扫描它们，标出可能的 PII 候选供人工复核。然后由人在该列的元数据里打上分类，血缘再把这个标签传播到派生表。因为 Claude Tag 的服务账号没有 PII clearance，仓库的列级访问控制会让任何 PII 列对智能体不可见。它可以查询这张表，但敏感列根本读不到。

3. 在 skill 本身里写清连接路径。我们的仓库 skill 有专门一节讲智能体如何连接（是通过 CLI、直接 API，还是 MCP server），以及每条路径的认证具体怎么工作。这个看起来很平凡的功能，让我们能区分智能体干净地失败（“我从当前界面连不上仓库，原因是这样”），和令人困惑地失败（查询悄悄跑到了错误的项目上，或认证提示被转到了不该去的地方）。连接机制写在 skill 里时，智能体就能解释自己的约束。

4. 把 Claude 加入频道视为一次访问授权。把 Claude Tag 加进某个 Slack 频道，实际上就是把智能体能查询的一切，读权限授给了该频道的成员。我们把这一点说清楚：Claude 由数据团队成员加入频道，频道名单也由数据团队负责。

5. 给每条查询打标签。对每条仓库查询，Claude Tag 都会带上标识界面、对话和请求用户（在 Slack 提供时）的标签。这在查询时并不强制执行任何事，但提供了成本归属和审计轨迹（事后你可以确定是谁问了那个扫了 4 TB 的问题）。

我们的总体姿态是：Slack 里的数据分析智能体是你治理仓库的一份共享只读副本，我们也按这个范围去限定它。

给每一个答案做埋点

智能体给的答案够不够好，不是用眼睛扫一眼就能判断的。

我们对 Claude Tag 处理的每个问题都记录一条结构化事件。这包括：

  • 加载了哪些 skill 文件、什么版本； 
  • 用户是否用 👍/ 👎 反应，或回复了更正；以及 
  • 它所触及的表上是否有未关闭的数据质量警告。我们也会把任何数据质量警告展示在答案页脚，这样过期数据告警会出现在数字旁边，而不是隐身。

这些遥测喂给两个视图。一个跟踪采用率，即按界面和领域看，有多大比例的智能体查询走治理层而不是临时 SQL。另一个跟踪正确性，用各领域 👎 反应和更正的比率衡量。这是评估运行之间准确率的在线代理指标。

采用率后来成了我们跟踪过最可行动的一个数字。某个领域掉下去时，几乎总是意味着要么 skill 文件已经漂移，要么出现了语义层覆盖不到的新一类问题。 

这如何加速自助分析的采用

Claude Tag 线程变成了新的会议 

我们最喜欢、也最有效的 Claude Tag 线程，通常里面有好几个人。这种情况下，人们贡献想法和上下文，Claude 负责跑腿。 

例如，一位数据团队成员问 Claude，为什么某个收入仪表盘比平时多加载了几分钟。Claude 发现查询结果没有被缓存，还有一个 bug 拖慢了结果到达页面的速度。 

Claude 通知了仪表盘负责人，对方决定立刻修缓存，bug 另开一条线处理。 

负责人接着问还有哪些仪表盘变慢了，结果发现同一缓存错误影响了几十个。Claude 写了缓存修复，数据团队成员做了审查，所有受影响的仪表盘在不到一小时内恢复满负荷运转。

这些线程是开放的，这在多方面都有帮助。顺着读的人能捡到上下文（什么坏了、为什么、怎么修好的），而不需要有人为他们写摘要。更重要的是，他们不必一直当被动读者。任何知道有用信息的人都可以跳进来贡献，就像上面例子里的团队成员那样。

所以把智能体放在共享频道里，把工作放在线程而不是 DM 里，因为线程可以充当可审查的历史记录。

Claude Tag 处理重复任务

很多数据工作是周期性的：流水线健康检查、KPI 监控等等。你可以让 Claude 创建循环，按计划或在出现异常变化时处理周期性任务。我们落地过的一些数据向例子包括：

  • 主动汇报：Claude 在每周站会前给出摘要：上周动了什么、和再上一周比怎样，以及哪些值得注意。 
  • 测试监控：当我们监控一次发布或实验时，Claude 一天会给多次汇报。在最近一次实验中，它注意到设置中途变了，帮我们及早发现并修好。
  • 可观测性：其它循环监控我们的流水线和仪表盘。如果流水线失败，Claude 开始调查、起草修复，并 ping 值班的人。如果某个 KPI 意外变动，Claude 会给出可能的解释：节日效应？上游数据变更？并在任何人打开仪表盘之前先核对它们。
  • 分诊：另一个循环跟踪我们的数据问题频道。对每个新问题，它会做判断：直接回答、开始更深入的调查，还是拉人进来。等数据团队有人来看时，大部分工作已经做完了。

Claude 也可以帮忙设计这个循环。问 @Claude 它在你的频道里见过哪些重复工作，以及它能怎么帮忙。

需要时再介入

你可以让 Claude 在你选择的任何频道里更主动一些，跟着读，并在需要时介入帮忙。上个月在我们的一个数据频道里，Claude Tag 回答了人们贴出的超过 75% 的问题，通常一两分钟内就有答复，甚至没有被点名。 

例如，一位 Anthropic 团队成员在公开频道问某个仪表盘是否包含一个新的用量类别。90 秒内 Claude 回答了数据如何定义、确认新分段缺失、提出了修复方案，并起草了 PR。一位数据科学家审查并批准。Claude 随后合并了 PR 并刷新了仪表盘。 

如何开始

如果你已经做完了第一篇文章里的工作，Slack 部署大多是接水管，不过顺序很重要：

  1. 先做权限。在写一行智能体代码之前，先决定服务账号能读什么。以后放宽访问，比事后收回容易得多。
  2. 其次做分发。选择挂载仓库还是通过 MCP 提供 skills，并端到端验证新鲜度：改一个 skill 文件，确认 Claude Tag 在你的 SLA 内拾取到它。
  3. 从第一天起做遥测。你无法回头给一个月前的对话补埋点。在第一个问题上就记录结构化事件。
  4. 能接知识索引就接。仓库回答是什么；你的内部文档和事故源回答为什么。数据通路稳定后尽快接上它们。
  5. 分析 skill 放最后。先做数据访问 skill，然后让真实问题告诉你，同事实际需要哪些分析师 skill（预测、队列、漏斗）。
