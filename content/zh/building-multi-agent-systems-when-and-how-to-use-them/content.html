什么是多智能体系统？

多智能体系统是一种由多个 LLM 实例运行、各自拥有独立对话上下文并通过代码进行协调的架构。每个智能体负责任务的一个特定切片——例如，一个子智能体负责调研，而协调者负责规划——这样可以保护上下文、实现并行工作，并提供单个智能体无法维持的专业化能力。

存在多种协调模式（智能体集群、基于能力的系统、消息总线架构等），但本文聚焦于“协调者-子智能体”模式：一种由主智能体派生并管理专门子智能体来处理特定子任务的分层模型。这种模式提供了直观的协调模型，是刚接触多智能体系统的团队的良好起点。我们将在下一篇文章中详细探讨其他模式。

如今，多智能体系统常常被用在单智能体其实表现更好的场景，不过随着模型能力的提升，这种权衡也在不断变化。在 Anthropic，我们见过团队花数月构建精巧的多智能体架构，最后却发现对单个智能体改进提示词就能取得相同的结果。

在构建多智能体系统并与在生产环境中部署它们的团队合作之后，我们总结出多智能体稳定优于单智能体的三种情形：上下文污染导致性能下降时、任务可以并行运行时、以及专业化能改善工具选择或任务聚焦时。在这些情形之外，协调成本通常大于收益。

在这篇文章中，我们分享如何识别单智能体的极限、找出多智能体系统大放异彩的三种场景，并避开常见的实施错误。 

为什么应该从单智能体开始

一个设计良好、配备合适工具的单智能体，能完成的事情远超许多开发者的预期。

多智能体系统会引入额外开销。每增加一个智能体，就意味着多一个潜在故障点、多一套需要维护的提示词、多一个意外行为的来源。 

我们观察到有团队构建了精巧的多智能体系统，分别设置规划、执行、审查和迭代的智能体，结果却发现每次交接都在丢失上下文，协调消耗的 token 比执行还多。在我们的测试中，完成同等任务，多智能体实现的 token 消耗通常是单智能体方案的 3-10 倍。这种开销来自跨智能体复制上下文、智能体之间的协调消息，以及为交接而做的结果汇总。

多智能体系统的决策框架

多智能体架构的价值，体现在它们能解决单智能体无法突破的特定约束。这意味着多智能体架构应当留给那些收益明确、足以抵偿额外成本的场合。 托管基础设施也可以替你处理这些工作（参见 Claude Managed Agents 中的多智能体编排）。

以下模式是我们持续观察到正回报的情形。

上下文保护

大语言模型的上下文窗口是有限的，且随着上下文增长，回答质量可能下降。当一个智能体的上下文中积累了与后续子任务无关的先前子任务信息时，就会发生上下文污染。子智能体提供了隔离：每个子智能体都在自己干净的、专注于特定任务的上下文中运行。

设想一个客服智能体，它需要在诊断技术问题的同时检索订单历史。如果每次订单查询都会往上下文里塞几千个 token，它推理技术问题的能力就会退化。

# Single agent accumulates everything in context
conversation_history = [
    {"role": "user", "content": "My order #12345 isn't working"},
    {"role": "assistant", "content": "Let me check your order..."},

    {"role": "user", "content": "... (order details, past purchases, shipping info) ..."},

]

这个智能体必须一边推理技术问题，一边在上下文里维护 2000 多个 token 的无关订单历史，注意力被稀释，回答质量随之下降。

多智能体方案：

from anthropic import Anthropic

client = Anthropic()

class OrderLookupAgent:
    def lookup_order(self, order_id: str) -> dict:
        # Separate agent with its own context
        messages = [
            {"role": "user", "content": f"Get essential details for order {order_id}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            messages=messages,
            tools=[get_order_details_tool]
        )
        # Returns only essential information
        return extract_summary(response)

class SupportAgent:
    def handle_issue(self, user_message: str):
        if needs_order_info(user_message):
            order_id = extract_order_id(user_message)
            # Get only what's needed, not full history
            order_summary = OrderLookupAgent().lookup_order(order_id)
            # Inject compact summary, not full context
            context = f"Order {order_id}: {order_summary['status']}, purchased {order_summary['date']}"
        
        # Main agent context stays clean
        messages = [
            {"role": "user", "content": f"{context}\n\nUser issue: {user_message}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            messages=messages
        )
        return response

订单查询智能体处理完整的订单历史并提取摘要。主智能体只接收它真正需要的 50-100 个 token，上下文保持聚焦。

当子任务产生大量上下文（超过 1000 个 token）但其中大部分信息与主任务无关、子任务定义清晰且对要提取哪些信息有明确标准、以及查找或检索类操作需要先过滤再使用时，上下文隔离的效果最好。

并行化

并行运行多个智能体，可以让你探索比单个智能体所能覆盖的更大的搜索空间。这一模式在搜索和研究类任务中尤其有价值。

Anthropic 的研究团队在我们如何构建多智能体研究系统一文中记录了这一点。主智能体分析查询，然后派生多个子智能体并行调查不同的侧面。每个子智能体独立搜索，然后返回提炼后的发现。多智能体搜索通过在更大的信息空间中探索，相比单智能体方案展现出显著的准确性提升。

其核心实现是把问题分解为相互独立的侧面，并发运行子智能体，然后汇总结果。

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def research_topic(query: str) -> dict:
    # Lead agent breaks query into research facets
    facets = await lead_agent.decompose_query(query)
    
    # Spawn subagents to research each facet in parallel
    tasks = [
        research_subagent(facet) 
        for facet in facets
    ]
    results = await asyncio.gather(*tasks)
    
    # Lead agent synthesizes findings
    return await lead_agent.synthesize(results)

async def research_subagent(facet: str) -> dict:
    """Each subagent has its own context window"""
    messages = [
        {"role": "user", "content": f"Research: {facet}"}
    ]
    response = await client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=4096,
        messages=messages,
        tools=[web_search, read_document]
    )
    return extract_findings(response)

覆盖面的提升是有代价的。完成同等任务，多智能体系统通常消耗单智能体方案 3 到 10 倍的 token。原因在于：每个智能体都需要自己的上下文，智能体之间必须交换消息来协调，结果在智能体之间传递时必须做汇总。虽然并行可以相比顺序执行减少总执行时间，但由于总计算量的激增，多智能体系统的整体耗时往往比单智能体系统更长。

并行化的主要收益是彻底性，而非速度。当你需要在庞大的信息空间中搜索，或调查一个复杂问题的诸多角度时，并行智能体可以覆盖比在上下文限制内工作的单个智能体更大的范围。代价是更高的 token 消耗和常常更长的总执行时间，换来的是更全面的结果。

专业化

不同的任务有时需要不同的工具集、系统提示词或领域专长。与其让单个智能体访问几十个工具，不如让多个专门化的智能体各自配备与其职责匹配的聚焦工具集，这样反而能提升可靠性。

工具集专业化

当一个智能体可用的工具太多时，性能会受损。以下三个信号说明工具专业化会有帮助：

  1. 数量。工具太多（通常 20 个以上）的智能体难以选出合适的那一个。
  2. 领域混淆。当工具横跨多个不相关的领域（数据库操作、API 调用、文件系统操作）时，智能体会搞不清某个任务适用哪个领域。
  3. 性能退化。新增工具反而降低了既有任务的表现，说明智能体管理工具的能力已达上限。

系统提示词专业化

不同的任务有时需要不同的人设、约束或指令，而这些组合在一起会互相冲突。客服智能体需要共情和耐心；代码审查智能体需要精确和挑剔。合规检查智能体需要严格照章办事；头脑风暴智能体需要创造性上的灵活。当单个智能体必须在相互冲突的行为模式之间切换时，拆分为各自配备定制系统提示词的专门化智能体，会产出更稳定一致的结果。

每个专门化智能体的表现取决于它的指令——能改善单个智能体输出的那些提示词工程最佳实践，同样适用于每个子智能体的系统提示词。

领域专长专业化

有些任务需要深度领域上下文，而把这些全部塞给一个通用智能体会使其不堪重负。法律分析智能体可能需要关于判例法和监管框架的大量背景；医学研究智能体可能需要临床试验方法论的专业知识。与其把所有领域上下文装进单个智能体，不如让专门化的智能体各自携带与其具体职责相关的聚焦专长。

示例：多平台集成。设想一个集成系统，智能体需要横跨 CRM、营销自动化和消息平台工作。每个平台有 10-15 个相关 API 端点。拥有 40 多个工具的单个智能体常常选不对工具，把各平台的相似操作混为一谈。拆分为配备聚焦工具集和定制提示词的专门化智能体，就能解决选择错误的问题。

from anthropic import Anthropic

client = Anthropic()

# Specialized agents with focused toolsets and tailored prompts
class CRMAgent:
    """Handles customer relationship management operations"""
    system_prompt = """You are a CRM specialist. You manage contacts, 
    opportunities, and account records. Always verify record ownership 
    before updates and maintain data integrity across related records."""
    tools = [
        crm_get_contacts,
        crm_create_opportunity,
        # 8-10 CRM-specific tools
    ]

class MarketingAgent:
    """Handles marketing automation operations"""
    system_prompt = """You are a marketing automation specialist. You 
    manage campaigns, lead scoring, and email sequences. Prioritize 
    data hygiene and respect contact preferences."""
    tools = [
        marketing_get_campaigns,
        marketing_create_lead,
        # 8-10 marketing-specific tools
    ]

class OrchestratorAgent:
    """Routes requests to specialized agents"""
    def execute(self, user_request: str):
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            system="""You coordinate platform integrations. Route requests to the appropriate specialist:
- CRM: Contact records, opportunities, accounts, sales pipeline
- Marketing: Campaigns, lead nurturing, email sequences, scoring
- Messaging: Notifications, alerts, team communication""",
            messages=[
                {"role": "user", "content": user_request}
            ],
            tools=[delegate_to_crm, delegate_to_marketing, delegate_to_messaging]
        )
        return response

这一模式映射了高效的专业协作：工具与角色匹配的专家之间的协作，比试图在所有领域维持专长的通才更有效。但专业化也引入了路由复杂度。协调者必须正确分类请求并委派给正确的智能体，路由错误会导致糟糕的结果。维护多个专门化智能体也增加了提示词维护的开销。当领域可以清晰切分且路由决策毫不含糊时，专业化效果最好。

何时该走出单智能体架构

除了上述通用框架，还有一些具体信号表明单智能体模式已经不够用了：

逼近上下文限制。如果一个智能体经常使用大量上下文且性能在退化，上下文压力可能就是瓶颈。值得注意的是，上下文管理方面的最新进展（如上下文压缩）正在削弱这一限制，让单个智能体能在长得多的时间跨度上维持有效记忆。

管理大量工具。当一个智能体拥有 15-20 个以上的工具时，模型要耗费大量上下文和注意力来理解自己的选项。在采用多智能体架构之前，不妨先考虑使用 Tool Search Tool，它让 Claude 按需动态发现工具，而不是预先加载全部定义。这可以在提升工具选择准确率的同时将 token 消耗降低多达 85%。

可并行的子任务。当任务自然分解为相互独立的部分（跨多个来源的调研、针对多个组件的测试）时，并行的子智能体能带来可观的加速。

随着模型进步，这些阈值会发生变化。当前的界限是实践参考，而非根本性约束。

以上下文为中心的任务分解

采用多智能体架构时，最重要的设计决策是如何在智能体之间划分工作。我们观察到团队经常在这个选择上犯错，导致协调开销抵消了多智能体设计的收益。

关键在于分解工作时采用以上下文为中心的视角，而不是以问题为中心的视角。

以问题为中心的分解（常常适得其反）。按工作类型划分（一个智能体写功能、另一个写测试、第三个审查代码）会带来持续的协调开销。每次交接都在丢失上下文。写测试的智能体不了解某些实现决策背后的原因，审查代码的智能体则缺乏探索和迭代的过程背景。

以上下文为中心的分解（通常有效）。按上下文边界划分意味着，负责某个功能的智能体也应负责它的测试，因为它已经具备了必要的上下文。只有当上下文能被真正隔离时，才应该拆分工作。

这一原则来自对多智能体系统失败模式的观察。当智能体按问题类型拆分时，它们会陷入“传话游戏”，信息来回传递，每次交接都在降低保真度。在一个按软件开发角色（规划者、实现者、测试者、审查者）专门化智能体的实验中，子智能体花在协调上的 token 比实际工作还多。

有效的分解边界包括：

  • 相互独立的研究路径。调查“亚洲市场趋势”与“欧洲市场趋势”可以并行推进，无需共享上下文。
  • 接口清晰的独立组件。有了定义明确的 API 契约，前端和后端的工作可以并行。
  • 黑盒验证。只需要运行测试并报告结果的验证者，不需要实现上下文。

有问题的分解边界包括：

  • 同一工作的顺序阶段。同一功能的规划、实现和测试共享太多上下文。
  • 紧耦合的组件。需要频繁来回沟通的组件应放在同一个智能体里。
  • 需要共享状态的工作。需要频繁同步认知的智能体应当待在一起。

验证子智能体模式

一个在各领域都稳定有效的多智能体模式是验证子智能体。这是一个专职智能体，它唯一的职责就是测试或验证主智能体的工作。

值得指出的是，能力更强的协调者模型（如 Claude Opus 4.5）越来越能直接评估子智能体的工作，而无需单独的验证步骤。不过，在使用能力较弱的协调者、验证需要专门工具、或者你希望在工作流中强制设置显式验证检查点时，验证子智能体依然很有价值。

验证子智能体之所以有效，是因为它绕开了传话游戏问题。验证本质上需要的上下文转移极少，因此验证者可以对系统做黑盒测试，而不需要了解它是如何被构建出来的全部历史。

实现一个多智能体系统

主智能体完成一个工作单元。在继续之前，它派生一个验证子智能体，把待验证的产物、清晰的成功标准和执行验证所需的工具交给它。

验证者不需要理解产物为什么被建成这样。它只需要判定产物是否满足指定的标准。

from anthropic import Anthropic

client = Anthropic()

class CodingAgent:
    def implement_feature(self, requirements: str) -> dict:
        """Main agent implements the feature"""
        messages = [
            {"role": "user", "content": f"Implement: {requirements}"}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[read_file, write_file, list_directory]
        )
        return {
            "code": response.content,
            "files_changed": extract_files(response)
        }

class VerificationAgent:
    def verify_implementation(self, requirements: str, files_changed: list) -> dict:
        """Separate agent verifies the work"""
        messages = [
            {"role": "user", "content": f"""
Requirements: {requirements}
Files changed: {files_changed}

Run the test suite and verify:
1. All existing tests pass
2. New functionality works as specified
3. No obvious errors or security issues

You MUST run the complete test suite before marking as passed.
Do not mark as passing after only running a few tests.
Run: pytest --verbose
Only mark as PASSED if ALL tests pass with no failures.
"""}
        ]
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=4096,
            messages=messages,
            tools=[run_tests, execute_code, read_file]
        )
        return {
            "passed": extract_pass_fail(response),
            "issues": extract_issues(response)
        }

def implement_with_verification(requirements: str, max_attempts: int = 3):
    for attempt in range(max_attempts):
        result = CodingAgent().implement_feature(requirements)
        verification = VerificationAgent().verify_implementation(
            requirements,
            result['files_changed']
        )
        
        if verification['passed']:
            return result
        
        requirements += f"\n\nPrevious attempt failed: {verification['issues']}"
    
    raise Exception(f"Failed verification after {max_attempts} attempts")

多智能体系统的应用

验证子智能体适用于：

  • 质量保障。运行测试套件、对代码做 lint、按 schema 校验输出。
  • 合规检查。核验文档是否满足政策要求、按规则检查输出。
  • 输出校验。在交付前确认生成的内容符合规格。
  • 事实核查。由单独的智能体验证生成内容中的论断或引用。

“过早胜利”问题

验证子智能体最显著的失败模式，是没有经过彻底测试就把输出标记为通过。验证者跑一两个测试，看到通过了，就宣布大功告成。

缓解策略包括：

  • 具体的标准。明确要求“运行完整测试套件并报告所有失败”，而不是“确保它能用”。
  • 全面的检查。要求验证者测试多个场景和边界情况。
  • 反向测试。指示验证者尝试应当失败的输入，并确认它们确实失败。
  • 明确的指令。“在标记为通过之前，你必须运行完整测试套件”这样的指令必不可少。如果没有对全面验证的显式要求，验证智能体会走捷径。

在单智能体与多智能体系统之间做选择

多智能体系统很强大，但并非放之四海而皆准。在引入多个协调智能体的复杂度之前，请先确认：

  1. 确实存在多智能体才能解决的约束，例如上下文限制、并行化机会或专业化需求。
  2. 分解遵循上下文，而非问题类型。按工作需要什么上下文来分组，而不是按工作的种类。
  3. 存在清晰的验证点，让子智能体无需完整上下文即可验证工作成果。

我们的建议？从可行的最简单方案开始，只有在有证据支持时才增加复杂度。
