Workload Identity Federation（WIF）现已在 Claude Platform 上正式全面可用。WIF 兼容任何符合 OIDC 的身份提供方，覆盖所有 Claude API 端点，包括通过我们的第一方 SDK 和 Claude Code 访问这些端点的场景。

借助面向 workload 的 WIF，以及面向交互式会话的 ant auth login，开发者在 Claude Platform 上构建时再也不必经手静态 API key。

Workload Identity Federation 的工作原理

WIF 用请求时签发的短时、带范围凭证，取代静态 API key。无论你是在 GitHub Actions 上跑任务的两人创业公司，还是有详尽凭证策略的企业，现在都可以用与技术栈其余部分相同的方式向 Claude Platform 做身份验证。

使用 WIF，就没有需要创建、轮换或泄露的静态 Anthropic 凭证。Workload 用它们已有的身份进行认证：AWS IAM role、GCP 或 Kubernetes service account、Azure managed identity、GitHub Actions token、Okta，或其他符合 OIDC 的提供方。

我们还在 Claude Platform 上引入了 service account，让每个 workload 都可以拥有自己的身份、角色和审计轨迹，而不再共用一把 API key。首先，一条 federation rule 把外部身份绑定到一个 service account。然后，当某个 workload 请求访问时，Claude Platform 验证该 workload 签名的 OIDC token，将其 claims 与你的 federation rule 匹配，并签发一个受该 service account 角色约束的短时 access token。每一次交换和请求都会记到该 service account 的审计日志中。

几分钟内配置你的第一个 workload

Claude Console 提供了配置 workload identity 的引导流程。设置会校验每一步，并以一条测试命令收尾，确认你的 workload 能够完成认证。

让整个组织在没有静态密钥的情况下运行

WIF 可与用于组织管理的 Admin API 配合使用。Federation rule 可以通过细粒度 scope 配置为最小权限访问。 

对于大规模运营的组织，federation 配置也完全可编程。新的 Admin API 端点让你可以创建和更新 issuer、service account 以及 federation rule。

开始使用

API key 可以与 WIF 并行使用，因此你可以一次迁移一个 workload。阅读各身份提供方的设置 指南，或打开 Claude Console 连接你的第一个 workload。
