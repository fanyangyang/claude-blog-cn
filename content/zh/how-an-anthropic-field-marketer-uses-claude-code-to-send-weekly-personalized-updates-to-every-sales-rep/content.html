作为营销人员，我面临的最大挑战之一就是让销售团队及时了解前线的一切动态。大多数营销人员都熟悉这样一个场景：走廊里偶遇销售代表，对方说"哦，我从没听说过那个活动"（或那份新白皮书、那个网络研讨会），这时你意识到又错过了一次向销售代表分享最新成果的机会，进而也错过了传递给客户的机会。

我最初的解决方案是许多营销人员都会熟悉的做法：周一早上与销售团队进行 15 分钟的站会。我每周日晚上整理来自全公司的更新信息，制作成演示幻灯片，然后在会议上现场汇报，最后将文档分享到 Slack。任务完成，对吧？不尽然：有了 Claude 之后，这一切显得过于手动。随着团队扩大，我开始支持多个销售团队，我的幻灯片制作流程跟不上了。更新内容也变得不那么有用，因为我再也没有时间挑选出适合每个团队的机会。

我希望 Claude 来完成这项工作，为每位销售代表创造更好的"产品"：一份针对他们的客户量身定制、并与我们营销部门所有活动相匹配的每周摘要。

幸运的是，我们组织了一次营销黑客马拉松：专门抽出时间，用 Claude Code 重建可重复的流程和工作流。我和团队聚在一起，花了一个小时来解决这个问题，这带来了巨大的改变。像黑客马拉松这样非正式的、通常是同伴引导的学习机会，让你能够进行日常工作中不会特意安排时间进行的实验和探索，我们的团队也不例外。

你不需要会编程，你需要会解释

我经常被同行营销人员问到的一个问题是："我该如何开始使用 AI？"我的方法，特别是使用 Claude Code 时，是先向 Claude 说明：虽然我不懂技术，但我有一个具体的挑战，Claude 应该把我当作一个深刻理解业务问题的产品经理，与我一步步协作。我会边想边说，所以经常把自己解释问题的过程录下来，把转录文本交给 Claude；这样 Claude 就有了所有的业务上下文。

在我们团队的每周 AE 摘要项目中，我首先向 Claude 概述目标：每周向每位销售代表发送一条 Slack 消息，告诉他们营销部门在做什么，以及如何帮助他们服务客户。然后我写了一份假想的每周更新，给 Claude 一个模板作为参考。我知道销售代表是行动导向的，所以我先列了一个"本周三件要事"清单，包含三个行动项，例如即将举行的活动或最新内容，他们可以和客户分享。我还为管理层汇总单独写了一个模板，因为管理者通常更关注团队的整体情况，而非单个客户。

接下来，我通过 MCP 将 Claude 连接到 BigQuery；BigQuery 是我们营销团队的数据源，提供来自 HubSpot、Clay 和 Salesforce 的精细数据。我想从简单的开始，所以先从活动和网络研讨会的单一数据源入手。为了实现个性化更新，我让 Claude 从 CRM 中拉取销售代表的负责区域，以及 Slack 中任何相关的客户更新信息。这样，Claude 可以将两者结合，创建个性化的每周更新。

随着时间的推移，我与营销部门的其他团队合作，丰富了数据来源，现在简报中还包括了博客文章、电子书、客户案例、网络研讨会，甚至来自合作伙伴生态系统的活动等新内容。

用户反馈才是真正的提示工程

为了向一线推广，我从一个同意作为测试组的销售团队开始。先发给 10 个人的团队感觉没那么有压力，即使出现错误也不怕，而且这个团队承诺提供反馈。首次发送后，我进行了一些调整。

有些问题只是错误。例如，当源表格中没有活动的 URL 时，Claude 会编造一个看起来合理的链接，但实际无法访问。我们立即将其作为硬性规则写入提示词：绝不虚构 URL。现在，只有当地址与源表格中的字符完全一致时，才会渲染链接。后来的版本完全删除了没有链接的活动，因为我们意识到，销售人员无法为任何人注册的活动只是噪音。

到第一周结束时，提示词中包含了九条内容规则，每一条都来自销售代表或管理者的反馈。一位销售代表指出，为知识工作者设计的研讨会推荐了一位工程 VP，因此现在联系人头衔会与活动的目标受众进行核对，不匹配的会静默取消。一个行业门控规则确保零售客户不会收到金融晚宴邀请，而还没有客户的新销售代表会收到一条简短的欢迎消息，而不是空白消息。

其他问题是数据问题。营销部门的任何人都知道维护单一数据源有多难。例如，现场活动表格的列在六周内重新排列了三次。为了应对这种情况，我们修改了提示词，让每次运行都先读取表格的标题行，验证列映射，然后再开始编写内容。现在指令不再是"看 C 列"，而是类似于"查找活动 URL 所在的那一列"。

将摘要推广到整个业务

经过这些初步运行后，我将摘要扩展到了我支持的所有团队，而今现场营销团队已经将其推广到整个销售部门。每周一早上，Anthropic 多个销售部门的高级客户经理打开 Slack，就会看到一条私信，列出本周的三项优先行动、针对他们客户的活动、已注册即将举行的网络研讨会的联系人、相关的营销内容以及其他跟进建议。

每条消息都是根据收件人自己的客户列表编制的，因此没有两条消息是相同的。这份摘要正在发挥作用：最近我们在一周内将一个高管晚宴的注册量翻了一番，纯粹是因为合适的销售代表在周一早上看到了合适的活动。

当 Anthropic 的业务发展代表想要自己的版本时，我们只需修改一个字段就为他们复制了提示词，因为 BDR 与客户的关系在 CRM 中与客户经理不同。提示词结构和内容规则原封不动地沿用，BDR 版在两天内就上线了。此后我又为客户成功团队和合作团队做了同样的事情，我还为销售以外的其他跨职能合作伙伴提供所有营销活动的概览。

无论业务发展多快，我和我的团队借助 Claude 的帮助，确保销售代表在周一早上就知道本周发生了什么，以及哪些客户和活动需要优先关注。每周一的发送内容都会完整存档，因此我可以随时查看到任何销售代表在任何日期收到的内容，而管理者则可以在一个汇总报告中看到整个团队的建议信息。我仍然会阅读发出的内容，但系统不再等待我的批准。几周前我去度假时，周一的发送自动完成，没有任何问题。

开始使用 Claude 的最佳实践

以下是我在使用 Claude Code 过程中积累的一些技巧和心得：

  1. 从小处着手，选择你已经在手动做的事情。当周围有太多关于人们用 AI 做什么的噪音时，很难开始。我的建议：挑选你花费最多手动时间的重复性任务，让 Claude 重新构建它。这样，你能够判断输出质量，因为你已经知道"好"的结果是什么样的。如果问题仍然太大，让 Claude 作为思维伙伴，将其分解为步骤。如果这是你与他人分享的内容，先将早期版本发送给自己，这样你可以在别人看到之前发现问题。
  2. 用通俗语言编写指令，并对每个文档进行版本管理。像向新同事介绍情况一样向 Claude 简要说明，Claude 会完成其余工作。指示 Claude 将每次更新保存为编号版本，并附上一行说明更改了什么，这样你就有了每次运行所使用提示词的记录。我们的文件是一个 Markdown 文件，我的同事为他们各自的部门运行；我们从一个共享的 Google Doc 开始，当更多人需要编辑时迁移到了 GitHub。
  3. 从小型、有承诺的团队开始试点。我们的首轮测试只与几位高级客户经理进行，我们知道他们愿意花时间提供反馈并帮助改进报告，帮助我们发现问题，或提出扩展或个性化覆盖范围的建议。
  4. 利用反馈改进提示词，将每次修正转化为明确的规则。营销简报变得有用，是从收件人开始与我们分享反馈开始的，每次修正都变成了 Claude 的一条明确规则。
