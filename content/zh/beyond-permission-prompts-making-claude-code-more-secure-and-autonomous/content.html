为了帮助解决这一问题，我们在 Claude Code 中引入了两项基于沙盒（sandboxing）的新功能，二者都旨在为开发者提供一个更安全的工作环境，同时让 Claude 能够更自主地运行，减少权限确认提示。这些功能是原生沙盒的典范：通过划定明确的边界让 Claude 在其中自由工作，既提升了安全性，也增强了自主性。

我们目前保障用户安全的方式

Claude Code 采用基于权限的模型：默认情况下它是只读的，这意味着在进行任何修改或运行任何命令之前都需要请求许可。也有一些例外情况：我们使用静态分析来自动放行 echo 或 cat 等安全命令，但大多数操作仍需明确批准。

然而，不断点击“批准”会拖慢开发节奏，还可能导致“批准疲劳”——用户可能不再仔细审视自己批准了什么。为了让 Claude Code 既更安全又更高效，我们希望找到一种更好的方法。

沙盒：更安全也更自主的方式

沙盒预先划定边界，让 Claude 可以在其中更自由地工作，而不必为每个操作单独请求许可。

通过对 Claude Code 的更新，我们正转向这种方式。我们的沙盒方案构建在操作系统级特性之上，以此实现两项新功能，它们分别基于以下两类边界：

  1. 文件系统隔离， 确保 Claude 只能访问或修改特定目录。这对于防止被提示词注入的 Claude 修改敏感系统文件尤为重要。
  2. 网络隔离， 确保 Claude 只能连接到已获批准的服务器。这可以防止被提示词注入的 Claude 泄露敏感信息或下载恶意软件。

值得注意的是，有效的沙盒需要同时具备文件系统隔离和网络隔离。没有网络隔离，被攻陷的代理可能窃取 SSH 密钥等敏感文件；没有文件系统隔离，被攻陷的代理则可能轻易逃出沙盒并获得网络访问权限。正是通过同时使用这两种技术，我们才能为 Claude Code 用户提供更安全的智能体体验。

沙盒化 bash 工具：无需权限提示的安全 bash 执行

在 Claude Code 中，我们使用这一运行时对 bash 工具进行沙盒化，使 Claude 可以在你设定的限制范围内运行命令。这些命令默认更安全，所需的用户权限提示更少，因此 Claude 可以更自主地运行。如果 Claude 尝试访问沙盒之外的资源，你会立即收到通知，并可选择是否允许。

我们基于 Linux bubblewrap 和 MacOS seatbelt 等操作系统级原语构建了这一功能，以便在 OS 层面强制执行这些限制。它们不仅覆盖 Claude Code 的直接交互，还覆盖该命令衍生的任何脚本、程序或子进程。

如前所述，此沙盒同时实现了：

  1. 文件系统隔离：允许对当前工作目录进行读写，但阻止对其之外的任何文件进行修改。
  2. 网络隔离：仅允许通过连接到沙盒外部代理服务器的 unix domain socket 进行互联网访问。这个代理服务器会对进程可连接的域名施加限制，并在出现新请求的域名时处理用户确认。如果你希望获得更高的安全性，我们还支持自定义这个代理，以便对出站流量强制执行任意规则。

这两个组件都是可配置的：你可以轻松选择允许或禁止特定的文件路径或域名。

沙盒确保即使提示词注入攻击得逞，它也会被完全隔离，无法影响用户的整体安全。这样一来，被攻陷的 Claude Code 无法窃取你的 SSH 密钥，也无法向攻击者的服务器回传数据。

Claude Code on the web：在云端安全地运行 Claude Code

今天，我们还发布了 Claude Code on the web，让用户能够在云端的一个隔离沙盒中运行 Claude Code。Claude Code on the web 将每个 Claude Code 会话放在一个隔离沙盒中执行，在其中它可以安全地完全访问其服务器。我们在设计这个沙盒时确保敏感凭证（如 git 凭证或签名密钥）绝不会进入沙盒环境。这样一来，即使沙盒中运行的代码被攻陷，用户也不会受到进一步伤害。

Claude Code on the web 使用一个自定义代理服务来透明地处理所有 git 交互。在沙盒内部，git 客户端使用一个专门构建的限定范围凭证向该服务进行身份验证。代理会校验此凭证以及 git 交互的内容（例如确保仅推送到配置的分支），然后在把请求发送到 GitHub 之前附加正确的身份验证令牌。
