如果你在 Claude Platform 中构建的智能体包含多个子智能体，可以使用我们的迁移工具包来判断哪些适合折叠进主智能体循环。它会运行一个引导式工作流来识别你的模式、评估备选方案并验证最佳方案。它包含一个演示，你可以在正式应用于你的智能体之前先在模拟系统上试用。

子智能体——拥有自己的上下文窗口、工具和指令、由协调器编排的智能体——是智能体设计的核心组成部分。它们在验证、并行工作和模块化权限管理方面非常有效。我们在许多使用 Claude Platform 构建的智能体中都使用了它们，例如我们的多智能体研究系统。

然而，最近 Applied AI 团队发现，在企业智能体部署中，将路由器、规划器和领域子智能体折叠进主智能体循环的做法让很多部署受益。在我们对多个企业部署的对比研究中，带技能的单一智能体在质量上经常同时胜过"一个提示词搞定一切"的设计和子智能体设计，而且每个任务的成本和延迟往往更低。

例如，一家公司发现，其面向客户的智能体中的十几个专家子智能体，使维持一致的品牌体验变得困难，而且增加的延迟损害了用户体验。

我们还经常看到一些常见的智能体设计方案遵循相似的演进路径：意图分类器、固定的多步推理流水线、用户分群、独立的推荐分支，以及顶层的多智能体编排器。

在这些案例中，反馈往往是：大部分这种结构在做的工作，模型已经不再需要它做了，一个清晰的系统提示词、4-5 个轻量数据工具和严格的输出护栏就能覆盖大多数用例。

需要明确的是，子智能体仍然有它们的用武之地，包括在研究前沿。在以下情况使用它们：

  • 单一智能体循环因上下文膨胀而出现可测量的性能下降，或
  • 多个任务需要用全新的上下文窗口并行处理，这些窗口在任务完成后即可丢弃，或
  • 单一智能体难以选择合适的工具，或系统提示词中存在相互冲突的指令。

但我们太经常看到企业为每个团队或问题类型都配备自己的子智能体，导致智能体架构变成组织架构图的翻版（这就是康威定律在起作用）。

这篇文章结合我们从大型组织构建智能体中学到的经验，解释了何时应考虑将子智能体折叠进主智能体循环。

大型组织构建智能体的失败模式

企业通常希望构建一个将多种产品和能力整合到单一客户界面的智能体。

通常，每项能力由不同的团队负责，所以企业先让每个团队各自构建自己的智能体，然后由中央平台团队在上面构建一个编排器。这可以采取多种结构，包括编排器-子智能体，或者以 MCP 工具形式暴露特定智能体的单一智能体。

这看起来是最简单的解决方案，但会立即引入以下复杂性：

  • 上下文管理：你需要决定智能体之间交换什么上下文，而且经常在来回传递中丢失细节。
  • 子智能体泛滥：每个团队都发布自己的子智能体，结果企业最终拥有数百个重叠的子智能体，没有强制执行的标准，也没有明确的负责人。
  • 弗兰肯提示词：每个团队都往系统提示词里加一句，导致规则相互冲突，也没有一致的表达风格。
  • 未经审查、过度局部的评估：每个人都添加自己的评估，这些评估针对各自的子任务过度优化。没有人拥有或维护整套评估，领导层基于被稀释的、过度局部的分数做决策。
  • 延迟：多智能体架构的复杂性会增加延迟。一位客户将自己的多智能体外壳与单一智能体循环做了对比评估，发现后者运行速度快约 2 倍。

使用渐进式披露的智能体循环

上述编排器-子智能体设计是协调跨团队构建的专家的合理方法，但通常更有效的方法是通过技能渐进式披露上下文和通过工具搜索渐进式披露工具。换句话说，智能体看到的是技能和工具的简短描述，只有在需要时才完整加载。

这种方法之所以有意义，有三个原因：

  • 共享上下文能产生更好的答案：对于运行时间更长的智能体，我们希望来自多个不同任务的上下文都留在主上下文窗口中。一个看到了每个早期步骤结果的智能体可以把它们连接起来，从而比子智能体返回的一组摘要产生更丰富的输出和更深入的洞察。这也意味着更少的上下文窗口和更少的有损交接。
  • 渐进式披露可防止上下文膨胀：这种技术让团队能够构建可完成各种任务的单一智能体，而无需把所有上下文立即加载到一个冗长的系统提示词中。这消除了团队以往将工作拆分到子智能体的主要原因。事实上，我们将 Claude Code 面向更先进模型的系统提示词减少了 80% 以上，其中包括与渐进式披露技能和工具相关的删减。
  • 模型能力更强了：从 Opus 4.5 开始，模型在单一循环中能管理的内容远超大多数团队的预期。你不能关闭 Opus 5.5 和 Fable 5.1 的思考功能，而且近期的模型越来越会在过程中叙述自己的进展并检查自己的工作，这使得一些外壳元素变得多余。每个新模型都让你可以把更多决策从外壳转移到模型本身。更简单的循环也更容易迁移到下一代模型；在我们帮助客户完成的迁移中，僵化的多智能体结构往往是阻碍新模型承担更多工作的原因。

单一智能体循环设计需要纪律：精心管理的系统提示词、能在正确时机触发的技能和工具描述，以及对上下文窗口、记忆和笔记记录的有意处理。本文后续章节会更深入探讨迁移和设计方面的考量。

应该由一个中央团队负责端到端质量和系统提示词，在每一个新工具和评估发布之前进行审查。保持中央团队精简有助于快速迭代，并降低大型组织中的协调成本。

如果走多智能体路线，先从可行的最简单模式开始（生成器-验证器、编排器-子智能体等）。通过按上下文划分来有效分解边界：给每个子智能体分配一份对系统其余部分依赖很少的工作，并让它返回一个紧凑的结果（好的候选包括独立的研究路径、具有干净接口的独立组件，或黑盒验证）。当智能体按问题类型拆分时，它们会陷入"传话游戏"，来回传递信息，每次交接都会降低保真度。

如何将子智能体折叠进主智能体循环

许多团队在生产环境中已经有一个编排器和一组专家智能体。以下是建议你朝着它努力的单一循环设计：

  • 一个模型和一个上下文窗口运行开放式工具循环，限制条件（轮次和成本预算、写入闸门）在外壳中设置。
  • 每一轮，模型发出一批工具调用。外壳并行运行这些调用，并将原始结果返回给同一个模型，由模型决定下一步：再发一批、向用户提问，还是给出答案。
  • 当模型给出答案或达到预算时循环停止。答案之后可以可选地运行目标或验证器检查。
  • 模型在第一轮把计划写进上下文，并在结果到达时修订它。这是与编排器和专家智能体设置的主要区别：写计划的模型也正是执行计划的模型，所以它可以在轮次中途改变计划。
  • 上下文仍然会被加载，并由智能体自己管理：
    • 不再需要根据规则目录重写计划的代码步骤，因为模型自己决定每一步。
    • 排序和领域流程移入技能。
    • 硬性限制（验证、审批闸门）以及对话过程中出现的任何其他内容（例如记忆查找）移入工具。
    • 代码仍可用于加载任何成本低廉且几乎总是相关的内容（例如实体解析步骤），并处理循环所调用工具中的机械性部分（载荷构建、流解析、恢复澄清）。

这种单一循环设计也有助于许多团队正在追求的终态（一个理解用户高层目标并代表用户行动的智能体），因为它把智能体学到的一切都保存在一个上下文中。

下面的建议说明了团队如何分阶段从多智能体系统过渡到单一智能体循环，以及多个团队如何在此过程中持续为该智能体做贡献。

任务完成度评估

第一步是创建一套评估集，帮助你判断是否应该把某个子智能体折叠进主智能体循环。我们看到的行之有效的评估结构是：由中央团队拥有的一套共享端到端评估集，加上各技能所属团队随每个技能发布的小型评估集。哪怕只有 10 个黄金示例也足够开始了。

按照评分标准对智能体的最终消息进行评分，是跟踪回答质量的一个很好的起点。当你仍有编排器时，还应跟踪路由准确性（它是否选对了子智能体？）。一旦子智能体被折叠进来，改为检查智能体是否加载了正确的技能或调用了正确的工具。随着时间推移逐步构建任务完成度评估是很有帮助的，因为在比较架构时这一点最为重要。

在内部系统难以回放、用户交互难以模拟的环境中，这可能很复杂。我们在内部行之有效的一种方法是记录重要事件的时间戳，以便日后回放并作为针对性评估运行。

逐步减少子智能体

向单一智能体循环演进涉及把子智能体折叠进工具和技能。这可以通过合并领域子智能体、把它们作为工具调用，或用技能和工具取代它们来实现。

合并领域智能体

在第一次合并之前，先构建一个小型端到端评估。然后按共享上下文折叠，从使用最多的子智能体开始。

合并那些相互衔接输出、处理相同数据或经常被一起调用的专家。例如，如果生产流量中有相当大的一部分是一个专家紧接着另一个专家，那就是一对紧密耦合的组合，适合合并成一个领域智能体。

将子智能体作为工具调用

当上述三个条件之一适用并且你保留了某个子智能体时，让主智能体把子智能体作为工具来调用会很有效，这样它就能继续与用户保持对话。

我们只建议在子智能体需要直接与用户交谈时，才进行完全交接（由子智能体接管对话）。其他一切都可以是主循环中的技能加工具。

这将允许你为子智能体定义共享的响应模式，由主智能体对照真实数据验证结论，并精简任何最终综合步骤的输入。这是一个很好的第一步，因为你不需要重写子智能体。它还能让你在决定把任何子智能体折叠进主智能体之前，先在任务完成度评估上获得一个基线。

不过，一些失败模式仍然存在：

  • 每个专家都有自己的提示词、上下文、所属团队和评估
  • 每次调用仍然会返回有损的摘要
  • 每次调用都是一个嵌套的模型循环，会增加延迟

通过技能和工具将子智能体折叠进主智能体

一次折叠一个子智能体：把每个子智能体的提示词变成技能，把 API 调用变成 MCP 工具。比较有和没有该子智能体时的评估表现，然后决定保留哪些。

比较时，不要只看最终得分，还要看看哪些任务发生了翻转。当我们在一个示例支持智能体上测试时，把一个子智能体折叠进另一个子智能体降低了延迟，但也破坏了一个原本一直正常的流程。主智能体自己拿着订单查询工具自行回答，而没有向发货专家询问交货日期。

在每次更改之前，确保你的评估为生产环境中一起运行的每一条智能体链、以及智能体绝不能违反的每一条规则都设有任务，并且每个任务运行不止一次，因为像这样的破坏只在两次运行中的一次出现。

多个团队如何为单一智能体做贡献

领域推理可以从知识库、技能和 MCP 工具中获取。各个团队可以把所有权从智能体转移到技能和工具上，由一个小型中央团队保持对系统提示词和端到端质量的所有权。这包括在新技能、工具和评估发布之前进行审查。

MCP 工具

当智能体需要执行操作、从系统读取实时数据或以固定格式返回结果时，工具是合适的方案。你也可以在迁移期间用工具继续调用子智能体。我们建议按用户意图对工具分组（而不是每个 API 一个工具），因为一旦系统提示词中的工具定义超过 30-50 个，工具选择往往会变差。

使用带延迟加载的工具搜索，限制硬性前置条件，并把任何必要的前置条件移入工具中。例如，如果 Y 需要 X 的输出，Y 的工具会检查它是否存在，并返回一条模型可以执行的指令。按用户权限也是同样的方式。每个工具检查调用它的用户可以看到什么或能做什么，并返回模型可读的明确拒绝信息，因此一个循环就能服务于拥有不同访问权限的用户，而无需为每个权限级别设置单独的智能体。

技能

当智能体需要知道一个团队如何做工作——比如专家子智能体的提示词曾经承载的步骤、规则和判断——时，技能是合适的方案。

我们扩充技能库的方法是让维护工作回到编写技能的人手中。Claude 可以通过能够构建、测试和精简其他技能的技能来完成繁重的工作。

为了防止技能泛滥，你可以让每个团队的 DRI 拥有自己的技能，并确保它们制作精良、彼此区分明显，且随附适当的评估一同发布。

  • /skill-creator 允许你编写结构良好的新技能，并审计现有技能以精简、去重和重构它们。
  • /skill-doctor 允许你查看库中每个技能的消耗成本以及实际使用频率，并删除冗余。

知识库

对于智能体只是偶尔需要的参考资料，知识库是合适的方案。事实和参考资料（政策、指标定义、产品规格）可以放在模型调用的搜索或查找工具之后，或作为技能内的参考文件随技能发布。避免让代码检索并把这段上下文粘贴进提示词。

加速这项工作的工具

我们最近发布了一组 Claude API 技能，可以帮助完成上面提到的大部分工作。我们的迁移工具包把这些技能串联成一个引导式工作流，用于评估并把多智能体系统迁移到单一智能体循环。它包含一个演示，你可以在真实系统上运行之前先试一试：

  • /claude-api build-eval：可以帮助创建由中央团队拥有的第一套端到端评估集，或每个团队随技能发布的小型评估集
  • /claude-api prompt-audit：可以标记你的提示词、技能和工具描述中为旧模型编写的指令，并以 diff 形式提出修复建议。你可以对系统提示词运行它，找出那些为早期模型添加、现在让智能体变慢或更僵化的规则。每个团队的 DRI 也可以对自己的技能和工具描述运行它。
  • /claude-api hillclimb：可以针对现有评估迭代改进应用。它可以用于"折叠 vs 保留"的对比（在把一个子智能体折叠成技能加工具之后，让它对技能和工具描述进行迭代，看看折叠版本是否达到或超过子智能体的表现），也可以用于你的系统提示词。
  • /claude-api cost-optimize：分析你的调用去向，并从提示词缓存、精简不必要的输入和输出 token、努力程度和模型选择等选项中提出节省建议，一次只改一项。这有助于降低特定设计的成本和延迟。

随着模型的演进，我们对如何最好地使用它们的理解以及最佳实践指南也在演进。这使得任何单一架构都不如它背后的原则重要：测量、一次只改变一件事，并保留经得起考验的东西。

这就是这样的案例之一。随着模型能力越来越强、智能体运行时间越来越长，你的更多子智能体可以变成技能和工具。不过你不必一步到位。构建一个小型端到端评估，折叠一个子智能体，只有当折叠后的版本得分更差时才把它保留为子智能体，然后反复进行。
