过去几个月，我们观察到「常驻型 agent」重新兴起。

常驻型 agent 是有状态且主动的：它们跨会话管理上下文，并在没有直接监督的情况下采取行动。底层上，它们运行在与其他 agent 相同的核心循环之上。区别在于外围架构，它由若干原语构成，用来控制 agent 何时唤醒、每次运行之间保留什么、以及工作成果如何抵达用户。核心循环与其他 agent 相同。区别在于外围架构，它由若干原语构成，用来控制 agent 何时唤醒、每次运行之间保留什么、以及工作成果如何抵达用户。

这轮复兴主要源于近期的模型进步，让常驻型 agent 变得更实用。首先，最新模型的判断力更好：它们更可靠地理解用户意图，也更清楚何时该主动确认。其次，智能正在变得更便宜——在一个长周期编程基准上，Opus 5.5 每个已解决任务的成本比 Opus 5 低 78%，而在典型工作负载上只低 40%。一个长周期编程基准上，Opus 5.5 每个已解决任务的成本比 Opus 5 低 78%，而典型工作负载上只低 40%。

客户开始询问我们如何把这类体验集成进自己的产品。有些公司已经在运行这些模式，另一些则刚开始探索。

本文拆解常驻型 agent 背后的原语，并说明它们如何组合在一起。

常驻型 agent 背后的循环

常驻型 agent 其实并不是字面意义上的「一直在线」。这只是对用户体验的描述。

实际上，agent 大部分时间在休眠，周期性唤醒去干活。每一段工作称为一次运行（run）：agent 接收到一个事件，完成任务，然后保存发生了什么。一次运行工作在会话（session）之上，会话是消息与工具调用的记录。运行结束后，agent 回到休眠状态，等待下一个事件。

核心原语

常驻型 agent 的外围架构有五个核心原语：事件收件箱、定时器、记忆、权限和发件箱。

事件收件箱

大多数 AI agent 只在用户发消息时运行。相比之下，常驻型 agent 可以被许多来源触发。

一种诱人的做法是让每个事件源直接调用 agent，但这在故障场景下有几个问题。

这正是事件收件箱的用武之地。每个来源不直接调用 agent，而是把事件发到收件箱，由收件箱负责唤醒。

最简单的版本包含三个组件：

  • 一个持久化的事件列表，通常是一张数据库表；
  • 一个处理器，通常是一个 HTTP 端点，把事件写入列表；以及
  • 一个 worker，通常是一个后台服务，从列表中读取事件。

收件箱应跟踪每个事件的状态，并且可以根据来源的唯一标识对事件去重。

新事件到来时，处理器把事件写入收件箱并唤醒 worker。worker 读取待处理事件，并一次性取走。

接下来，worker 把事件交给 agent 循环，等待运行结束，然后标记对应事件为已处理。

  • 处理器应快速确认事件。某些来源（例如 webhook 提供方）会把慢响应视为失败。处理器仍可以轻量地做校验和写入。
  • 收件箱应是事实来源。worker 被唤醒时，应先从收件箱拉取最新事件。这样即使 worker 中途崩溃，也不会丢失事件。
  • 一个收件箱同时只应有一个活跃 worker。这能防止两次运行重复工作或互相覆盖。若运行中途出现新事件，可以让它排队等待本轮结束。
  • worker 应把待处理事件批量合并。例如用户连续发了几条消息，worker 可以把它们合并成一次运行，避免重复处理同一段上下文。

定时器

与事件收件箱配合，定时器让常驻型 agent 能够主动行动。定时器通常分为两类。

定时器有自己的持久化存储，通常是另一张数据库表，与收件箱分开。收件箱不应存放定时器。

定时器本身不会发起运行。而是由一个调度器（通常是后台服务）轮询存储，做三件事：

  1. 扫描存储，找出到期的定时器。
  2. 按类别更新每个定时器。
    1. 一次性跟进应被标记为完成。
    2. 周期性计划应把到期时间更新为下一次出现的时间。
  3. 向收件箱写入一个事件并唤醒 worker。

调度器可以自己实现，也可以使用持久化执行引擎。

记忆

常驻型 agent 跨许多不连续的运行工作，依赖记忆保持连续性。

与事件收件箱和定时器类似，记忆应有自己的存储。在我们的产品中（例如 Claude Code 的自动记忆和 Messages API 的记忆工具），它实现为一个文件目录。对常驻型 agent 而言，这些目录应映射到持久化存储。

经验法则是：记忆只应保存 agent 无法重新查到的内容。如果某些信息已经存在于别处，就不必复制进记忆。

  • 用户指令：用户对 agent 行为的任何指令都应保存在独立文件中，并在每次运行时加载。
  • 用户笔记：agent 应保存它了解到的关于用户的信息，例如角色、偏好或任何纠正反馈。
  • 过往消息：agent 应跟踪已经告诉过用户什么，避免重复。可以存摘要，也可以存原始消息。
  • 任务进度：对于每个进行中的任务，agent 应维护一个进度文件，记录已完成与待完成的部分。任何需要跨运行延续的内容都应写入其中。

上下文窗口内部

开始任何工作之前，agent 会加载系统提示、工具定义和记忆文件。这份初始上下文「开销」会包含在每次运行中，因此我们建议保持精简，并使用提示缓存来降低成本。

新会话只带着这份上下文开销和触发运行的事件启动。而既有会话则会带回此前各轮的消息与工具调用。

如果会话变得过长，你可以选择压缩较早的消息或开始一个新会话。两种方式都会损失细节，因此任何需要持久保留的内容都应在过程中写入记忆。

权限

权限是常驻型 agent 风险最高的地方。一次运行持有用户的访问权限，且按设计在无人值守下操作。对每次工具调用，agent 都需要判断是自己继续、拦截，还是等待批准。

权限所需的组件与其他 agent 相同：

  • 凭据存储：常驻型 agent 往往需要敏感的用户凭据（如密码或访问令牌）才有用。推荐模式是在 agent 环境之外设置一个代理，由它给外发请求附加凭据。agent 发送不带凭据的请求，代理在转发前注入真实凭据。
  • 自动模式：常驻型 agent 应能在没有持续用户输入的情况下工作。我们在 Claude Code 的自动模式中已经处理过这类问题的一个版本。自动模式使用分类器审查高风险操作，拦截被判定为危险的操作，从而让 Claude 寻找更安全的路径。不过，最重要的决策仍需要用户审查。
  • 延迟工具调用：在 Claude Code 中，一个钩子可以延迟工具调用并等待用户追加输入。同样的模式适用于常驻型 agent——它们在某些操作前可能需要澄清或批准。当一次调用被延迟，运行结束，会话在调用中途被保存。请求会展示给用户（例如通过用MCP Apps构建的交互卡片），用户的回答作为事件回到收件箱。该事件启动新的运行，带着用户输入恢复已保存的会话。在延迟调用等待响应期间，worker 可以处理其他事件，因此 agent 不会被阻塞。

发件箱

对大多数 AI agent 而言，回复是边生成边流式推给用户的，用户可以看到 Claude 如何推理、调用工具并写出答案。

而常驻型 agent 大部分工作在后台完成。用户拿到的是结果和少量细节，而不是完整的逐步拆解。

一次运行可以以三种方式结束：

  • agent 向发件箱发送一条消息，
  • agent 判断无需发送任何内容，或
  • agent 使用延迟工具调用请求权限或额外输入。

大多数常驻型 agent 用一个「发送」工具直接把消息投递给用户就够了。只有当你需要控制消息节奏，或让 agent 能从错误中恢复时，才需要正式的发件箱。

发件箱是一张独立的外发消息表，与事件收件箱类似。同时还有一个分发器（通常是后台服务），类似 worker。分发器读取待发消息，决定投递哪些，然后发给用户。延迟工具调用的请求既可以走发件箱，也可以直接在界面中展示。

除投递之外，调校 agent 的发消息频率也很重要。发太多的 agent 会变得嘈杂，发太少的则会漏掉用户需要知道的事。我们建议通过评测找到合适的平衡点。实践中，让 agent 一开始保持安静，再逐步赢得用户的注意力，效果更好。

各部分如何组合

五个原语是这样组合在一起的：

每次运行都始于收件箱中的一个事件——无论是用户消息、webhook 还是定时器。worker 取到事件后启动一次运行，在新的或既有的会话中唤醒 agent。agent 读取记忆作为基线，在权限范围内采取行动，然后把学到的东西更新回记忆。运行结束后，agent 向发件箱写入一行记录，分发器把消息投递给用户。

这些部分共同构成一个循环。一次运行可以设置定时器，稍后再次唤醒 agent；当用户回复消息时，回答作为事件回到收件箱。每次运行都很短暂，但循环会无限持续下去——这正是 agent 让人感觉「一直在线」的原因。
