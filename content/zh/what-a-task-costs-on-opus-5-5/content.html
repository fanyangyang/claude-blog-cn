任务的花费，以及重试的花费

你开始时并不是要购买数百万个 token。你是要构建一个功能、完成一次迁移，或者运行一个任务。token 数量是模型完成任务所需的量。

两个每 token 成本相同的模型，在同一任务上的花费可能差异巨大。一个只读一遍代码。另一个读了代码、尝试修复、再读一遍。每一步都是一个 turn，而每个 turn 都会重发当前对话。所以需要更多 turn 的模型花费更高，即使价格相同。

读完本文，你应该能回答关于自己工作的三个问题：

  • 在 Opus 5.5 上，我典型任务的花费是多少？
  • 哪些设置会改变花费，改变多少？
  • 如何查看自己的会话用量？

我想先说明的权衡是：每种省 token 的方法都可能让你失去一个完成的任务。更低的 effort、更小的模型或更少的上下文确实都能省 token。但一次重试的花费高于所有这些节省。本文试图为每个权衡标上价格。

这里有些数字是目录价，有些是基于目录价构建的示意。图表是交互式的，阅读时可以调整输入。这些是尽力而为的示意，请务必查看我们的文档并自己核算。

一个任务花费多少？

Claude Code 中的任务是一个循环。模型读取对话、调用工具、读取结果，然后继续循环直到完成。每循环一圈就是一次请求。有四个因素决定循环的成本。

轮次（Turns）。每个 turn 都会重发当前对话。turn 越少，处理的输入越少。

缓存读取（Cache reads）。一个 turn 重发的大部分内容，都是模型在上一 turn 见过的文本。这部分按缓存读取计费，价格仅为输入价格的很小一部分。

输出 token 类型。最贵的 token，价格为输入价格的五倍。思考（Thinking）按输出计费，所以在得出答案过程中推理更少的模型花费更低。

模型。每个模型都有自己的价格（见定价页），所以你选择的模型决定了每个 token 的价格。

我们的示例使用 Opus 5.5 API 目录价：输入每百万 token $4，输出每百万 $20，缓存读取每百万 $0.20。与下方的计算器一样，示例按读取价计费缓存输入，其余按输入价计费，不计缓存写入。token 数量为示意。

轮次（Turns）

假设一个任务从 20K token 的上下文开始，随着模型读取文件和工具结果增长到 120K。在 40 个 turn 时，平均每个 turn 发送约 70K token。整个任务约 2.8M 输入 token，尽管对话从未超过 120K。若 90% 来自缓存读取，输入成本约 $1.62。同样的任务用 25 个 turn 处理约 1.75M token，输入成本约 $1.02。

一个 turn 的成本高于它新增的 token，因为它会重发之前的所有内容。所以最便宜的 turn 是你不需要的那个。

一个可以减少 turn 的习惯是给模型一种检查自己工作的方法。例如，一个要运行的测试、一次构建，或一个调用端点的脚本。能检查自己工作的模型会更早发现自己的错误。

一次性收集所需信息并批量调用工具的模型，重发的次数也更少。

缓存读取

同样的 2.8M 输入 token，如果全部不来自缓存，成本为 $11.20。命中率 90% 时为 $1.62，96% 时约为 $0.99。没有其他设置能如此大幅度地改变输入成本。稳定的会话会自动保持高命中率。我在本文后面介绍了一些避免破坏缓存的注意事项。

输出 token

在 Opus 5.5 上，一个输出 token 的价格是一个缓存读取的 100 倍。典型任务 60K 输出 token 花费 $1.20，相当于从缓存读取 6M token。输出包含思考。即使 Claude Code 只向你显示摘要，你也要为全部思考付费。这就是为什么 effort（主要改变模型思考多少）对账单影响如此之大。

模型

缓存读取更便宜的模型主要有利于长会话。输出更便宜的模型主要有利于需要大量推理的任务。

Opus 5.5 有什么变化

变化有两点：价格，以及模型完成的工作量。

每一档价格都更低。输入和输出 token 比 Opus 5 便宜 20%。缓存读取便宜 60%。输入价格下降，读取费率也随之下降，从输入价格的十分之一降到二十分之一。图 A 对比了两个模型每百万 token 的价格。这些是 API 目录价。在 Pro、Max 或 Team 套餐下，更低的 Opus 5.5 价格会传导到你的额度（包括缓存上下文），所以同样额度比 Opus 5 多用约 25%。缓存读取的额外降价是 API 价格调整。

最大化会话价值的技巧

Opus 5.5 更低的价格让每个 token 成本下降。如何运行会话决定了你用多少 token，下面这些步骤有帮助。

换模型前先提高 effort

Effort 设定模型在每个 turn 上花费多少 token 的整体倾向：它的思考、它写的文本、它的工具调用。较低 effort 时，它调用更少的工具且调用更短。Opus 5.5 有四个级别（low、medium、high 和 xhigh），外加单会话使用的 max。选择下面的级别可查看何时使用及对应命令。

Levels run from least to most thinking per turn.

Claude Code 为每个模型设置默认 effort 级别，/effort status 显示你的当前级别。范围明确、日复一日的工作请尝试 medium；当 medium 卡住时，尝试 high。它每 turn 的花费高于 medium，但低于换到更大的模型。机械性工作（如重命名或在多个文件中套用已知模式）使用 low。

粗略估算 effort 定价：假设 high 在整个任务中多花 20K 思考 token。在 Opus 5.5 上约 $0.40。一个十 turn 的重试循环，100K 缓存上下文、共 10K 输出 token，成本大致相同。所以在能省下一次重试的任务上，high 就值回票价。而在 medium 一次就能完成的任务上，它就白花了。

当 medium 只修好一层时

最明显需要更高 effort 的信号，是修复停在某一层。

假设 API 处理器中重命名了一个字段。在 medium 下，模型更新了处理器，处理器测试通过，但客户端仍在发送旧字段。它完成了被要求的任务，只是没读得足够远，没找到第二个调用方。在 high 下，它会在写代码前花更多 turn 阅读调用点，并一次改完两层。

一个检查也能抓住同样的 bug。如果模型能运行一个走客户端的测试，旧字段在写出的那个 turn 就会让测试失败（即使在 medium 下）。所以提高 effort 之前，先检查模型是否有办法检查自己的工作。一次测试运行花费一个 turn 及其输出。更高 effort 则给每个 turn 都增加思考。

如果升级 effort 级别并添加检查仍不起作用，那就换到更大的模型。

会话中途更改 effort

在 Claude Code 中，用 /effort 加级别运行，例如 /effort high。/effort status 打印当前级别。你可以在任务中途更改，新级别从下一个请求开始生效。

更改 effort 或思考设置会清除缓存的对话，因为这些设置是缓存匹配的 prompt 的一部分。下一个请求要为整个对话支付缓存写入价。

为你的工作选择正确的模型

模型选择决定会话中每个 token 的价格，所以它对账单的影响比 effort 更大，影响面也更广。每个继承主模型的子代理也继承其价格。大多数日子需要三个模型：一个小的用于查询，Opus 5.5 用于你密切监督的工作，一个更大的用于最难的任务。 work you supervise closely, and a bigger one for the hardest tasks.

把 Opus 5.5 作为日常主力

用 Opus 5.5 做你监督的工作：跨几个文件的特性开发、调试、带后续修改的代码审查。你阅读它的产出并在偏离时介入，所以循环保持简短。升级到 Fable 5.1——

当结果比 token 价格更重要时，就升级到 Fable 5.1。例如：你不会监督的长运行、代码库中无既有模式的问题、以及协调多个子代理的大型改动。不要等到第三次失败。如果 high 下的 Opus 5.5 两次撞上同一个问题，就切换，解决后再切回来。交互式工作更适合 Opus 5.5，因为它的延迟更低、成本更少。

Fable 5.1 目录价为输入每百万 $10、输出每百万 $50，是 Opus 5.5 价格的 2.5 倍。其缓存读取每百万 $0.25，仅为 Opus 5.5 费率的 1.25 倍，因为按输入价格的 0.025 倍计费。所以差距在长而缓存密集的运行上最小，在输出多的任务上最大。

在自然的节点切换。缓存属于之前的模型，所以新模型的第一个 turn 要为整个对话支付写入价。先运行 /compact，或用简短书面计划开新会话，让那个 turn 更小。运行 /model 加别名或模型名来切换。/model 也会把你的选择保存为新会话的默认，所以难的部分完成后切回来。

向下迁移做查询

查询用 Sonnet 或 Haiku，写代码不用：搜索和总结、读日志和测试输出的子代理，以及『这个定义在哪』类问题。跨多文件的机械编辑，保留 Opus 5.5 并把 effort 设为 low。编辑仍在写你其余代码的模型上，每 turn 成本更低。

要把 子代理 放到更小的模型上，在其定义中设置 model: haiku 或 model: sonnet。要把所有子代理放到一个模型上，设置 CLAUDE_CODE_SUBAGENT_MODEL 环境变量。子代理定义中指定的模型优先于该变量。未设置模型的子代理运行在你的主模型上，除非设置了该变量。

每个子代理在自己的上下文窗口中运行并交回摘要，所以它的文件读取不会进入你的主对话。它仍然为自己消耗的 token 付费，所以模型设置决定这笔花费是多少。

权衡是：小模型误读搜索结果会把主模型引向错误的文件，主模型为这个绕路付费。让小模型做错误容易被发现的工作，比如找文件、跑测试、读日志。

把需要判断的决策留在主模型上。opusplan 别名用另一种方式分工：Opus 在计划模式规划，Sonnet 执行计划。这把代码编辑放在 Sonnet 上，与上述建议相反。在设为默认之前，请在自己任务上实测。

迁移时检查你的 prompt

为旧模型编写的指令可能让 Opus 5.5 写更多、重复调用工具。在 Claude Code 中运行 /claude-api prompt-audit 检查你的 Claude Code 配置（如 skills 和 CLAUDE.md 文件），排查这些 prompt 反模式。它也会检查你在 Claude Platform 上构建的应用代码。

我们在从 Opus 4.8 迁移到 Opus 5.5 时测试了这一点，使用了一个包含 44 张工单的内部客服基准，其 prompt 存在若干这类模式。切到低 effort 的 Opus 5.5 将基准成本降低了约 18%。运行 prompt-audit 又降低了 9%，最终比 Opus 4.8 起点低约 25%。审计移除了让模型写更多并重复调用工具的仪式性指令：强制六步流程、草稿本规则、二次验证规则，以及互相矛盾的指令。

这个结果来自一个基准，所以把它当作示例，而不是预期数字。运行审计，然后在真实任务上对比前后 /usage（见『自己实测』）。

缓存与压缩

Claude Code 帮你处理缓存和压缩。你如何运行会话决定它们能省多少。

缓存如何工作

Claude Code 缓存请求中重复的部分，例如系统 prompt、工具定义和现有对话。

在 Opus 5.5 上，缓存读取的成本是一个全新输入 token 的 5%。写入缓存比全新读取更贵：按当前定价，五分钟缓存为输入价格的 1.25 倍，一小时缓存为 2 倍。每次命中免费重置生命周期。

在 Claude Code 中，生命周期取决于你的付费方式。Claude 订阅为一小时。API key 或云服务商默认五分钟；订阅一旦开始消耗用量额度也会降到五分钟。

在 120K token 上下文下，Opus 5.5 上五分钟写入约 $0.60，一次读取约 $0.02。一次写入相当于 25 次读取。在 API key 下，六分钟的咖啡休息会把下一次 $0.02 的读取变成 $0.60 的写入。同尺寸的一小时写入约 $0.96；在 API 上你可以支付这笔溢价来覆盖一天中的间隙。

会话形态与命中率

缓存存储前缀，所以只能复用从开头与上一次请求匹配的部分。

稳定的会话在每 turn 都往对话末尾追加，保持高命中率。任何改变请求前部内容的操作都会降低命中率。更改工具定义会清空整个缓存；更改系统 prompt 会从该点之后清空，这几乎是全部内容。

实践中，以下情况会出现缓存写入：

  • 你暂停的时间超过缓存生命周期；
  • 你更改 effort 或思考设置（见 effort 一节），可能清除缓存的对话；
  • 你连接或断开 MCP 服务器，可能改变每个请求开头加载的内容；
  • 你切换模型，因为新模型从空缓存开始；以及
  • 对话被压缩，重写了缓存匹配的历史。

所以这些设置在会话开始时配好，运行期间不要动它们。

为什么长会话每 turn 花费更高

每个 turn 重发整个上下文，所以随着上下文增长，即使缓存是热的，每 turn 花费也更高。在 Opus 5.5 上，20K token 上下文时每个 turn 的缓存读取约 $0.004。150K 时约 $0.03，30 个该尺寸的 turn 仅读取就花 $0.90。同样的 30 个 turn 在 20K 时约 $0.12。在 Claude 4.6 及以后的模型上，更大的上下文窗口不改变每 token 价格，所以成本完全来自重发对话。

这些上下文中有很大一部分来自更早的工作：一小时前的堆栈跟踪、一个你已处理完的文件、一次你已修复的测试运行的输出。它们仍然在每一个 turn 中被发送。

压缩、/compact 与 /clear

当会话接近上下文上限时，Claude Code 会总结更早的历史，让后续 turn 发送更少。运行 /autocompact 加一个 token 数，可调整触发压缩的上下文占用阈值。

有两个命令可以手动做这件事。/clear 清空对话且不花钱，所以在转到不相关工作使用。/compact 保持连续性，花费一次请求。它读取它总结的对话，你可以指定保留什么，例如 /compact keep the failing test names and the schema change。

150K token 压缩的大致价格约为 $0.25：包含一次读取、几千输出 token 的摘要，以及在更短上下文上的一次新缓存写入。之后每个 turn 在读取上节省约 $0.025，所以压缩大约在十 turn 内回本。收尾前的压缩花得比省得多。

摘要也会丢失细节。调试会话中途的压缩可能丢掉最关键的那行日志。在自然节点压缩；当下一步依赖某个具体内容时，在 /compact 指令中说明。

输入之前加载了什么

你的 CLAUDE.md 文件 在每个会话开始时加载到上下文，所以其中的每一行都是每个 turn 重发内容的一部分。成本文档 建议保持 200 行以内。MCP 工具定义是延迟加载的。开始时只加载工具名和服务器指令，工具被使用时才加载完整定义。运行 /mcp 查看哪些服务器已连接，关掉你不需要的。

自己实测

本文中的数字都是示意。你的代码库、prompt 和习惯不同，所以请在自己任务上实测成本。方法如下。

  1. 在会话中运行 /usage/cost 做同样的事。Session 区块显示 token 用量和按目录价估算的美元成本。prompt-cache 行显示你的输入中有多少来自缓存。在 Pro、Max、Team 或 Enterprise 套餐下，同一屏幕显示你的套餐用量条。美元数字是在你机器上按目录价计算的，所以在订阅下它是你做多少工作的参考，而非账单。 /cost does the same thing. The Session block shows token use and an estimated dollar cost at list price. A prompt-cache line shows how much of your input came from cache. On a Pro, Max, Team or Enterprise plan, the same screen shows your plan usage bars. The dollar figure is computed on your machine at list price, so on a subscription it is a guide to how much work you did, not a bill.
  2. 同一任务跑两次。从你的积压工作中选一个，不要用玩具示例。用 /model 在 Opus 5 和 Opus 5.5 之间切换。记录每次运行的 turn 数、输出 token 和成本。做三到四个任务再下结论。
  3. 团队使用用量与成本报表。根据 Claude Code Analytics API 估算每位用户的成本。Usage and Cost API 则按模型以及缓存与非缓存 token 细分花费。
  4. 尝试 effort 阶梯。用 medium 和 high 各跑一个困难任务。用 low 跑一个机械任务。

解读会话

在任务结束时检查 /usage 中的三项。

  • 缓存占比。长会话应较高。如果偏低，查找长时间暂停、effort 或模型更改，或中途连接的 MCP 服务器。
  • 输出与输入之比。小改动上大量输出通常意味着 effort 级别对该任务太高，或模型在重试。
  • 总输入与会话大小的比值。如果总量是会话大小的很多倍，说明会话经历了大量 turn，值得读一遍对话找出循环重复的位置。

作为基线，Claude Code 成本文档给出企业部署平均值：每个开发者每个活跃日约 $13，90% 的用户低于每活跃日 $30。明显高于你自己正常水平的会话值得复盘。

记住

  • 范围明确的日常工作使用 medium effort。
  • 给模型一个检查自己工作的方式，跨文件改动从 plan 模式开始。
  • medium 卡住时提升到 high。在节点处更改，因为更改可能产生一次缓存写入。
  • high 两次撞上同一问题时切换到 Fable 5.1。解决后切回来。
  • 搜索和读日志的子代理放在 Sonnet 或 Haiku 上。代码编辑留在 Opus 5.5。
  • 保持长会话持续进行，让缓存保持热度。
  • 不相关任务之间用 /clear，节点处用 /compact 并注明保留什么。
  • 最重要的一条：在每个模型上各跑一个真实任务，对比 /usage 的报告。你自己的数字才值得信任。
