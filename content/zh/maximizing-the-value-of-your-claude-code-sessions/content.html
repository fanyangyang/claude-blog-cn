TL;DR

  • 在任务之间执行 /clear 。这可以避免之前无关的上下文被再次发送给模型，从而降低 token 用量。
  • 开始之前先设定好模型和努力级别（effort level）。在对话中途更改其中任何一个都会破坏你的提示词缓存，可能导致 token 成本上升。
  • 用 @ 提及文件，而不是口头描述文件名。文件会直接附加到你的消息中，省去一次 Read 调用，也省去 Claude 自己去搜索文件的过程。 
  • 给输出冗长的命令加上静默标志，或在子智能体（subagent）中运行。命令输出会像文件一样被加入对话，并在会话余下的时间里一直留在那里。
  • 在新会话中运行一次 /context。它会显示当前加载了什么（CLAUDE.md、MCP 工具定义等），你可以借此砍掉不需要的内容。
  • 离开键盘前执行 /compact。提示词缓存一小时后就会过期，趁缓存还在时压缩对话要便宜得多。

把价值最大化

直到不久之前，你用来写代码的工具都是一口价（或免费）的。无论那天下午你修复了一个测试还是五十个，编辑器的价格都一样，所以单个任务本身其实并没有自己的价格。 

而像 Claude Code 这样的智能体编码工具改变了这一点。同一个完成的任务，因使用方式不同，成本也可能不同。 

在一种会话里，Claude 读取测试及其覆盖的文件，完成修改，几个回合就结束了。在另一种会话里，它先在代码仓库里到处 grep，在到达同样那两个文件之前顺带读了十几个文件，而且这些回合中的每一个，都会把自早上以来对话里已读过的所有其他内容一并拖上。

修复的是同一个问题，但你花掉的 token 数量不同，而且整个过程中模型还不得不惦记着十个它根本不需要的文件。

高效使用 token 并不意味着总体上用得更少，而是确保你用掉的每一个 token 都花在你真正要求的事情上。

那么，我们先来看是什么决定了一个 token 的价格，再看是什么决定了一个会话发送多少 token，以及这一切对你如何运营一个会话意味着什么。

什么决定一个 token 的价格

你按 token 计费，但你真正支付的是推理：GPU（或 TPU，或模型恰好运行其上的任何硬件）在你的 token 上运行模型所花费的时间。 

有三件事决定一个 token 占用多少这种时间：你运行的是哪个模型、它是输入 token（进入）还是输出 token（产出），以及它是否被缓存。

模型

更大的模型在输入和输出 token 上都要做更多工作。哪类模型值得用于哪类工作，这本身就是一个独立的话题，我们在在 Claude Code 中选择 Claude 模型与努力级别一文中已有讨论。 

对于本文，你只需知道：我们接下来讲到的所有内容都要乘上模型的价格——当问题确实困难或模糊时用大模型，当工作只是常规操作时用小模型。
