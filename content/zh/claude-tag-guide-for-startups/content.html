01 Claude 值班

示例配置：

频道

#on-call #alerts-ci #deploy-watch #support-escalations

连接器

GitHub、GitLab、Sentry、dbt、PagerDuty、Linear、Datadog、Jira、Grafana、incident.io

讨论串与例行任务

故障响应、早晨故障摘要、周一值班交接、每日健康摘要、每小时故障复盘

起始指令

@Claude 请记住本频道的规则：监控告警，并在各自的讨论串里立即分诊。先查是否已有工单。先查数据再推理，并区分哪些是你验证过的、哪些是你推断的。如果问题属实，指出可能的根因并附上链接，@对应负责人；只有修复范围可控时才开草稿 PR。若无需处理，明确说明。每次故障后，把学到的内容追加到 [lessons 文件]。

分诊频道以噪音大著称。Sentry 报错、Datadog 告警、客户 bug 报告与支持请求不断打断，让人很难从噪音里分辨信号。这通常是团队交给 Claude 的第一项任务。

把 Claude 放在频道里充当第一响应者后，第一轮排查常常在值班工程师打开笔记本之前就已完成。Claude 会逐条读取进来的内容，调查代码库和它能访问的工具，并汇报发现。如果修复范围可控，它开草稿 PR；否则把问题连同调查结果转给合适的人。在这种配置下，每个人工审核后再合并，只有真正全新的问题才需要有人亲自启动调查。

在 Campfire——一家为财务团队打造 AI 原生 ERP 的公司——一位工程师 @Claude 反馈某个报告问题：其 AI agent 的部分已完成答案没能送达用户。21 分钟后 Claude 就开好了 PR，当天下午即合并。

Kikoff：每个分诊频道的第一响应者

Kikoff 是一家金融科技创业公司，帮助消费者建立信用、解决流动性需求、实现财务安全。Claude Tag 是公司各分诊频道的第一响应者，包括：

  • #deploys：Claude 判断每次发布后该盯什么，并标出它弄坏的地方。
  • #alerts-ci：构建失败时，Claude 查明原因并以草稿 PR 提出修复。
  • #alerts-sentry-backend：Claude 先做一轮 Sentry 异常与崩溃的排查。
  • #dog-fooding：Claude 调查员工内部试用时反馈的问题，并 @对应的负责人。
  • #support：Claude 先做一轮支持工单的排查。

Kikoff 最初只让 Claude 在被提及时才参与对话，而最大的收益出现在团队允许它主动介入之后。注册功能出故障时，Claude 追查到是一次后端改动，评估了影响范围，指明负责修复的团队，并开了草稿 PR，让应用在此期间优雅降级。

NavigateAI：用碎片化上下文修 bug

NavigateAI 为建筑现场团队打造 AI 副驾驶。他们在约 90 个频道里使用 Claude Tag，用于告警分诊、集中修 bug、快速做功能和升级支持。自六月以来，Claude 直接从 Slack 讨论串开出了约 223 个 PR，其中 134 个已合并，开启到合并的中位时间为两小时。

分诊对 NavigateAI 尤其有价值。因为 Claude 拥有大量上下文，它能找到那些一眼看去容易被忽略的非直觉根因。

有了 Claude，平均问题解决时间明显改善。有一个案例中，Sentry 告警触发 8 分钟后 Claude 就定位了根因，告警后 93 分钟修复即合并。

「高速发展的创业公司通常必须在速度与结构之间二选一。Claude Tag 让我们两者兼得。它像一个大脑，把各个工具里的点连起来，我们因此获得了结构，而不必自己去搭建结构。」Mike 说。

提示

「投入维护一个 skills 仓库，并让 Claude 能访问它，帮助很大。」Mike 说。在 Anthropic，我们的值班配置把 Claude 的指令放在仓库里的一个oncall.md文件中，Claude 会在每次故障后把学到的内容追加到lessons.md文件。

02 从讨论串到 PR

示例配置：

频道

#quick-wins #bug-bash #product-feedback #feature-requests #ux-papercuts #tech-debt #design-polish

连接器

GitHub、GitLab、Linear、Jira、Confluence、Notion、Figma、Sentry

讨论串与例行任务

每个讨论串一个需求、每周积压清理、每日 PR 汇总、每周已发布回顾

起始指令

@Claude 请记住本频道的规则：当有人描述一个 bug 或小功能时，在它自己的讨论串里推进。先查是否已有工单，并先读相关代码。信息不足时，索要细节或真实示例，不要猜。改动小且范围可控时，开草稿 PR，简要说明改了什么、怎么测的。永远不要合并；由人审核批准。若改动过大或有风险，说明原因并建议开工单。

速度是创业公司最大的优势之一，但那些能让用户惊喜的小需求，往往在流转中被淹没。这些信息常由面向客户的团队收集、在 Slack 里提交，如果没有被忽略，最终会进到 Linear 或 Jira，和几百个工单一起排队定优先级。

有了 Claude Tag，任何人都能起草 PR，懂不懂技术都行。在讨论串里提出想法，产品、工程和 GTM 在同一处实时反馈，Claude 把讨论串变成一个体现了所有人意见的草稿 PR。

我们交流的许多创业公司都用 Claude Tag 做「轻巧又讨喜」的小功能，或清理那些审核很快、但平时排不上优先级的小痛点。

Orderful：从 Slack 对话到两天上线

Orderful 是一个 EDI 平台，帮助企业通过 API 或浏览器直接与交易伙伴对接。其客户通过该平台与伙伴交换标准单据。

有一种单据类型 753，Orderful 的 Web 应用此前并不支持。这个需求一直躺在积压清单里，导致某大型零售商的货运被延误。

当客户经理在 Slack 里跟进时，PM @了 Claude：「@Claude，你来做吧。」Claude 索要该单据的真实样例，以便按实际格式构建，随后开了一个添加 753 支持的草稿 PR。

第二天早上，Claude 又为配套的 754（零售商的回执）建了工单，并开出第二个 PR。两个 PR 在 Slack 对话后约两天内都已上线。

「过去要花几周甚至几个月的事，现在一次 Slack 对话就够了。」Orderful 的 CTO Piers MacDonald 说。「价值难以证明的轻量功能以前会卡在积压里，现在它们有了出路。」

提示

给 Claude 一个真实的依据来构建。

在讨论串里放一个样例文件、一段客户消息或一张截图，它就按你真正需要的东西来做，而不是猜。

Valence：从功能需求到上线

Valence 与全球最大的雇主合作，通过 AI 教练 Nadia 把企业人才与绩效连接起来。当一位 Valence 工程师在 Slack 里说明如何处理某重要客户提出的紧急产品变更时，Claude 不只是照做，它还发现同一份配置存在于两处，因此需要一并修改。如果没有 Claude，最初这次改动会是不完整的。

另一个案例中，某客户紧急要求一项定制。Claude 查了代码，并与一位工程师协作确认无需改代码即可交付。不到一小时，同事就把方案交给了客户。

03 公司大脑

示例配置：

频道

#ask-anything #company-wiki #product-questions

连接器

GitHub、Notion、Google Drive、Linear、Jira、Confluence、Granola、Metabase

讨论串与例行任务

每个讨论串一个问题、决策日志更新、每周过期文档检查、重复问题汇总

起始指令

@Claude 请记住本频道的规则：从我们的代码、文档和过往讨论串中回答问题，并附上来源链接。若来源互相冲突，以代码为准，给出当前答案并标出过期的文档。若不确定，明确说明并 @对应负责人。当讨论串达成决策时，记录到 [docs 位置]。任何要发给客户的内容，必须先经人工确认。

在创业公司，机构知识常常只存在于人的脑中——从产品计费码的细节，到上手指南托管在哪里。

对我们交流的许多创业公司来说，Claude Tag 已成为公司大脑。Claude 回答时会附上来源，不确定时会 @负责人。它也维护这些知识的时效：当讨论串达成决策，Claude 当天就能写进文档，并标出已经过时的文档。

Moritz：从接单到排班的事实来源

Moritz 是一家 AI 原生律所，承诺合同当天交付，而据其说法行业标准至少要三周。除法律工作外的一切——接单、报价、排班、跟进——都在 Slack 里进行，每个案件一个讨论串，每个客户一个频道。

现在从 CEO 到律师助理都先问 Claude。过去在 Slack 里要搜 30 分钟的问题，现在两分钟内就有答案。基于当天讨论串起草的交接班日报，从过去约一小时拼凑变成五分钟润色。

省下的时间回到了法律工作上。Claude Tag 处理案件周边的行政事务，例如追问、提醒和状态更新。它无法访问客户文件，也无法接触 Moritz 律师的特权对话。

Campfire：随叫随到的客户体验

有一个 Slack 频道「人气爆棚」：他们的 CX（客户体验）频道。销售会用它「在与潜在客户沟通时验证某些功能」，而不必「挨个去问 10 个人」。

这类频道之所以特别有效，是因为销售能在客户正关注的当下即时给出答案，从而在早期客户沟通中更独立、更有底气。

04 自助数据

示例配置：

频道

#data-requests #ask-revops #metric-definitions

连接器

dbt、GitHub、Metabase、BigQuery、Snowflake、Databricks、Notion

讨论串与例行任务

每个讨论串一个问题、每周站会前读数、发布与实验读数、数据管道故障分诊、新问题分诊

起始指令

@Claude 请记住本频道的规则：从我们的受治理模型和 [data skills 仓库] 中的定义来回答。若数据不在其中，说明这是未经验证的，而不是猜测。先给答案，再给数字、驱动因素和注意事项。解释变化前，先查最近的故障、发布和 Slack 讨论。指标定义不明确时，先问清楚指的是哪个。对重要查询，先给出你的方案或 SQL 再执行。区分你验证过的和假设的，并在回答末尾列出未解决的数据质量警告。若有人发现错误，起草修复供数据团队成员审核。同一个问题出现第二次时，建议设为定期任务。

在高速增长的创业公司，每个部门都想要数据，数据团队必须决定先做谁的请求。把 Claude Tag 接入数据后，任何人都能用自然语言提问，不必排在数据团队队列里。

这也是我们自己采用的场景。在我们某个数据频道里，一个月内 Claude Tag 回答了人们提出的 75% 以上的问题，通常在一两分钟内。它基于受治理的数据和分析师使用的同一套定义工作，那些定义存放于版本化仓库，Claude 在每次对话中都会重新读取。

Descript：应对临时数据请求

Descript 是一个 AI 驱动的视频剪辑平台。Claude Tag 现在是数据请求和初步分析的第一道支持。产品、增长、RevOps 和财务在 Slack 里提问，得到的答案基于 Descript 的 dbt 模型。

Daisy 的例行报表准备时间从数天缩短到数小时。

例如增长团队会问：生命周期订阅为什么下降、付费搜索的末次归因是否被其他渠道抢走、一个自助账户需要多久才能变成企业商机。数据团队会追踪 Claude 生成的产物，看哪些数据资产最被各团队需要，同时把时间用在战略问题和构建让自助分析可行的上下文上。

提示

先在上下文上投入。

让你的数据团队把核心模型和指标定义文档化，因为自助分析的上限取决于 Claude 掌握的上下文。参见回答数据问题.

Orderful：从提问到看板

在 Orderful，自助分析既包括对话式分析，也包括完整的数据构建：任何人都能从 Slack 里的一个问题走到合并上线的看板。关键在于一个语义层，它编码了各方认可的定义与指标，让每个答案、每个构建都使用同一套定义。

05 报告与交接

示例配置：

频道

#sales-pipeline #customer-handoffs #standup-summary #qbr-prep

连接器

Notion、Google Drive、Gong、Salesforce、Gainsight

讨论串与例行任务

日终状态草稿、QBR 前简报、成交交接

起始指令

@Claude 请记住本频道的规则：基于我们的讨论串、文档和数据起草每份例行报告，并附来源链接。开头写清变化了什么、需要什么决策。区分你验证过的和假设的，缺信息时标出来，不要填空。把草稿发在独立讨论串里供 [负责人] 修改。未经人工批准不得发出。若某份报告反复被改成同样几处，建议更新这些指令。

我们前面讲的多数例子都是反应式的：某件事发生了，Claude 响应。而例行报告是 Claude 按计划负责的工作，就像同事负责一项周期性交付。

你只需描述一次结果，Claude 每次都执行，并把结果发在团队原本就在工作的地方。

Valence：交易复盘与交接

Valence 正在配置 Claude，让它在每次季度业务复盘前为团队做简报，涵盖客户健康度、进行中的交易、阻碍与下一步。他们也在打通交易成交后从销售到客户成功的交接。Claude 通过汇总各处的细节为团队省时间，还常常找出人们可能遗漏的关键项。

「交易成交时，Tag 会基于交易历史、通话和合同生成交接材料：谁是谁、承诺了什么、哪些是定制的、哪些还没完成。然后客户成功团队在启动会前审阅。」Sameer 说。

提示

如果你问过两次，就把它设成例行任务。

「@Claude 每周一美东时间上午 9 点，为每个本月要做 QBR 的客户发一份简报：健康度、进行中的交易、阻碍、下一步。」参见设置例行任务.
