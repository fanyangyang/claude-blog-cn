Block 构建帮助企业和个人参与经济活动的工具，包括面向卖家的 Square 和面向消费者的 Cash App。Bradley Axen 在 Block 领导 AI 能力建设，他的团队构建端到端的 AI 产品，包括 Buzz——一个面向人机协作团队 （在新标签页中打开）的开源工作空间，并与 Square 和 Cash App 团队合作构建面向客户的 AI 功能。Brad 与 Anthropic 探讨了 Claude Opus 5 和 Claude Fable 5 等前沿模型如何改变了工程师的工作方式、Block 如何将代理编排模式应用于 Fable，以及当每位员工都能使用前沿模型时保障措施的作用。

前沿模型在 2026 年取得了重大进展。这项技术对你的工作方式产生了什么影响？

AI 对我们在 Block 的工作最大的影响在于我们如何构建产品，而且这种影响怎么说都不为过。我们在 2025 年借助 Claude Code 等工具看到了它的开端，当时这些工具还需要大量人工干预。随着模型变得越来越智能，设计和工程工作已经转向设计迁移本身、审查代理行为以及构建更多面向客户的功能——这一直是我们的目标。

下一阶段是通过 Block 的产品把这些变革性技术带给客户。AI 同样能帮助小企业处理那些不想花时间打理的运营后台事务，或帮助 Cash App 客户管理财务。借助 Claude，我们在技术上有了一个全新的杠杆，可以改变人们对软件能为他们做什么的期待。想象一下，如果 AI 能响应客户需求并即时构建新的界面？我越来越觉得，我们的产品将由 AI 按需构建，以解决特定的问题。

随着前沿智能的演进，你的团队现在能做什么几个月前做不到的事？

Claude 新一代前沿模型带来最大的变化是我们构建软件的规模。编写代码仍然是核心环节，但现在我们会用 AI 进行全公司范围的迁移。这个梦想我们做了很久，而在 2025 年它很少能实现。在 Claude Fable 5 之前，你需要把问题特别规整，前沿模型才能真正发挥威力。

到 2026 年，AI 已成为我们开展所有大规模代码迁移的主要方式。对我们来说，一次迁移可能意味着跨多个仓库的成百上千个独立 pull request，涉及数百万行代码。过去，这些工作需要人类协调，模型一次只能处理一个或几个 PR。有了 Fable，我们看到它可以跨多个会话编排这些工作。人类工程师负责掌舵，Fable 专注于更高层的设计工作：数据模型、API 规范、算法。然后它指挥多达数十个更小、更经济的模型（如 Opus 或 Sonnet）去执行具体任务，比如实际的文件编辑和运行测试。

经济账算得过来。早期结果显示，编排器会先用前沿 token 做复杂的预先规划，然后把更高比例的 token 分配给更小的 worker 模型，质量没有下降。整个体系运行在 Buzz 上——我们的开源协作工作空间，人类和 AI 代理在共享频道和线程中并肩工作，让我们对团队的进展有很好的可见性。

在任何一次迁移中，我们可能合并由 Fable 编排的一千个 pull request。这让工程师可以把精力放在艰难的设计决策上，而不是机械性的工作。

你什么时候选择 Claude Fable 模型而不是其他方案？

很多模型后来都在缩小差距，Opus 也非常出色，但 Fable 刚推出时，在单次可处理的问题规模上是一个巨大的阶跃式变化。Block 的团队被这一点吸引，开始摸索在抽象层级和规模上再上一步意味着什么。

如今，我们很多讨论都围绕模型效率展开。这正是模型编排发挥作用的地方：Fable 的前沿智能在用它攻克大问题时价值最大，然后我们让更小的模型去填充代码变更中的大量细节。这是我记忆中自从我们开始用 LLM 写代码以来，第一次答案不是“100% 的时间都用最前沿的模型”。

模型编排是我们今天构建产品的重要部分，这也意味着我们需要新工具。有些工具非常聚焦单会话，界面跟不上你同时与 45 个代理协作的节奏。这正是 Buzz 的另一个用武之地。我们在 Buzz 中有多代理工作流，我们真的认为未来是多人同时与众多代理对话，组织为常规任务选择高效的模型，为更大的问题选择前沿模型。

你交给 Fable 最棘手的问题是什么？

第一个是大型迁移：数千个 PR 的迁移，Fable 编排了整个执行系统。

第二个是处理大型代码库——大约一百万行代码的规模，并确保它不会每天积累新的技术债。我们交付的 PR 比以往任何时候都多。人们发布的功能和改动越来越多，所以我们的系统积累技术债的速度比以往更快，而我们也一直缺少对应的、能加快我们维护能力的东西。现在这终于实现了。我们有代理对整个代码库进行每日或每周巡检，询问：“这里情况如何？我们需要清理和整合什么？”

在广泛开放访问的情况下，你如何推动前沿模型的高效使用？

我们让任何技术岗位的人都能完全访问最前沿的模型，因为我们战略的很大一部分就是始终工作在可能性的边缘。

用 Fable 去修 README 里的一个错字是对资源的极大浪费。所以我们需要更好的系统来为特定任务建议该用哪个模型。为此，我们一直在构建一个自动选择器，帮助员工决定何时使用哪个模型。由更大和更小的前沿模型混合驱动的多代理系统也有帮助。

我们公司目标的一个重要部分是默认高效运作，这正是我们现在正在培养的能力。我们有大量优秀的模型可供选择。如果每个人都能擅长为正确的任务选择正确的模型，我们的成本效益会大大提升，而且不会拖慢速度。

你会建议具体的优化策略吗，比如 effort 级别？

即使是一个整天和 LLM 打交道的人，我也几乎觉得 xhigh effort 下的模型和 medium 下的同一个模型像是两个不同的模型。我不把 effort 级别看作一条可以沿路行走的频谱。低 effort 的 Fable 可能就比另一个模型在高 effort 下更好。所以我把它看作一个需要优化的更大的网格。我们基准测试的每一个用例，不仅要检查每一个模型，还要检查每一个模型的每一个 effort 级别。

作为中央负责我们 AI 工作方式的人，我想要非常清晰的建议，比如：“这类任务默认用这个模型的高级别。”我们必须尽可能让工具自动完成这些事，然后让专家在想探索的时候去探索。

你如何考虑为当今的前沿模型加入保障措施？

有些事情太关键了，你需要有保证，我们还没准备好让 LLM 在我们的代码库上自由行动。合并到主分支和部署到生产环境，以及功能开关等相关变更，我们始终留给人类来做。代理可以修改代码，但这些变更必须通过我们的安全检查，然后需要两个人类批准部署。这层双重批准机制让 LLM 不可能独自推动这类变更。

在更低的层面上，一个人在不留意的情况下能在自己的笔记本电脑上做多少事，这很令人惊讶——那些你以为人类不会做、因为他们知道不该做的事。这把我们推向一些有趣的方向。我认为未来工作中很大一部分是远程工作站，因为它们更容易加固（而且还能帮助解决 LLM 带来的其他问题，比如占满磁盘空间）。我们安全体系的重要一环是构建默认安全的系统：用网络允许名单而不是拒绝名单，诸如此类，以阻止最严重的那类问题。

我们还尽量让模型少介入循环。我们的很多安全护栏都是非常便宜、高效的检查，运行时不需模型参与。我们把这些检查构建在人们工作所用的界面里。有时甚至只是一个正则表达式。越来越常见的是，较小的分类器也参与其中。

在日常工作中，还有一整类事情是你希望放开的，好让人们高效工作，而封锁并不值得。我们有意让模型可以开 PR、审查代码、查询我们的日志系统和分析数据库，这些都是为了帮助人们更快前进。

这正是模型内置保障措施真正关键的地方。我指的是 Fable 和其他前沿模型经过调校不会参与危险活动，再加上Anthropic 自己的安全分类器 （在新标签页中打开）。在我们的测试中，即使有人让 Claude “绕过”我们的双重批准系统，它也会拒绝尝试绕过。这也是我们会基准测试的内容。

对其他与前沿模型打交道的工程团队有什么建议？

我们有数千人在使用 AI 工作，他们正在推动 AI 能力的边界。他们作为个人在学习什么有效，也在改进身边的系统。比如，我的笔记本电脑上有一堆本地技能，让我即使不是专业前端开发者，也能在我们的 Square 前端工作。当所有这些背景和组织知识被记在系统层面而非个人层面时，组织的成熟度就来了。

我们的目标是把我们从做事的人身上学到的一切记录下来，放进一个让所有人都受益的系统中，这样每次运行代理时，它都带着可用的最佳上下文为你的工作做出贡献。
