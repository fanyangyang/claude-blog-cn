许多数据科学和数据工程团队都可以作证：实现自助式数据分析，向来是一件苦差事。

为了方便技术背景较弱的同事使用数据，常见做法是建立宽表和反规范化表，但随着业务扩张，这往往会导致定义不一致、相互重叠的视图大量涌现（而且对那些压根不想学 SQL 的员工帮助有限）。另一种做法是为用户开辟更多隔离环境，却常常覆盖不到业务问题的长尾需求，还会因团队各自为政而造成指标和仪表盘的泛滥。

大语言模型的兴起为自助式分析提供了另一条路径，可以绕开上述难题。然而，把 Claude 直接对准数据仓库、任由智能体自由执行，也可能制造出一种虚假的精确感。

起初从临时取数需求中解放出来的欣喜，很快会转变为恐慌——因为这种设置让业务方脱离了底层数据设施、文档和专业知识的支撑，而正是这些因素过去一直在引导他们使用精心治理的数据集。 

在 Anthropic，95% 的业务分析查询由 Claude 自动完成，总体准确率约为 95%。把这些繁琐、重复的工作交给 Claude 之后，我们的数据科学团队得以专注于因果建模、预测和机器学习等更具战略价值的工作。 

在走访了数十位 Anthropic 内部顶尖的 Claude Code 用户、并见过大量分析智能体的设计模式之后，我们总结出了一些面向数据团队使用大语言模型的最佳实践。在这篇文章中，我们将分享这些技巧和方法，帮助其他团队最大化发挥 Claude 驱动自助式业务洞察的能力，内容包括：

  • 为什么分析的准确性是上下文与验证的问题，而不是代码生成的问题；
  • 导致大多数错误的三种失败模式； 
  • 我们为解决这些错误而构建的智能体分析技术栈；
  • 我们如何衡量效果；以及
  • 我们创建绝大多数 skills 所用的基础模板（见附录）

数据不是软件

大语言模型的生成能力是一把双刃剑：让模型能为复杂问题创造出精妙解法的机制，同样也会导致幻觉式的错误输出。要充分理解分析智能体面临的挑战，不妨将它们与编码智能体做个对比。

编码是一个开放式的解空间，恰恰能发挥模型的创造力，而且文档和测试为遏制幻觉提供了天然的护栏。相比之下，分析场景往往只有唯一正确的答案，且只能来自唯一正确的数据源，同时又没有确定性的方法来证明结果的正确性。 

对于自助式智能体业务分析而言，复杂性主要源于数据的模糊性。核心问题归结为我们能否把用户的提问映射到数据模型中具体且最新的实体，并知道与它们打交道的正确方式。只要能做到这一点，后续的执行和 SQL 就变得轻而易举。

我们识别出了这一问题的三个特征，它们是绝大多数不准确回答的根源：

  1. 概念与实体的歧义：数据模型中往往有数百个可用选项（潜在字段可能多达数百万个），智能体无法选出最能回答用户问题的字段。例如，在统计活跃用户数时：哪些行为算“活跃”？要不要把欺诈用户算进去？回看窗口取多长？
  1. 数据过期：数据源、业务定义和 schema 始终在变化；数据资产和智能体的知识会逐渐过时，开始返回微妙错误的答案。
  1. 检索失败：正确的信息可能确实存在于数据模型中且标注得当，但由于搜索空间过于庞大，智能体就是找不到它。

我们的智能体自助分析技术栈

在 Anthropic，我们主要靠智能体数据技术栈来压低这三类错误。每一层的存在，主要就是为了打掉其中一个或多个问题： 

  1. 实体歧义：数据基础和事实来源把合理实体的空间不断收窄，直到只剩一个受治理的答案。 
  1. 过期：维护与验证流程防止业务变化时整套东西腐烂。
  1. 检索失败：skills 确保智能体稳定找到那个答案，并且用对。 

这一节我们会讲每一层是怎么建的。 

对于直接在 Slack 里提出的临时问题，可以看看我们的数据团队如何用 Claude Tag 部署数据分析智能体。

数据基础

确保分析智能体准确，最重要的一面是扎实的数据基础，包括数据模型、转换、测试、数据仓库里的表，以及描述它们的元数据。维度建模、dimensional modeling、对关键管道的左移测试、新鲜度和完整性检查，这些标准数据工程和数据质量实践全部仍然适用（我们不会在这里重审一遍）。

真正变了的是：数据模型的终端用户不再是数据专家（比如数据科学家），而是代表数据能力或对底层设施理解程度各不相同的用户去行动的智能体。这一转变带来的挑战是，结果不能再要求用户去核验底层是否正确，因为终端用户并不知道。

数据基础层主要对准歧义：比如 revenue 如果落到一份受治理的数据集，而不是四十个说得通的候选，问题在智能体开始搜索之前就基本消失了。第一道过期防线也在这里，因为定义规范模型的同一个仓库，天然就是强制它们保持最新的地方。

我们看到几条实践特别管用：

  • 建立规范数据集：最常见的失败，是智能体没法把一个概念（「产品 X 的收入」）映射到唯一正确的表、列和指标定义，通常是因为存在多个实现略有不同的说得通的候选。修法是更少、治理更重的逻辑模型：精选出一小套规范的、单一事实来源的数据集，所有权清晰、可直接消费、可被发现，然后积极废弃那些近似重复。物理汇总和缓存对成本和性能仍然重要，但它们应当从规范模型机械派生，而不是作为替代品和它们并排活着。目标是：智能体搜索一个概念时，找到的是一个受治理的答案。
  • 把标准执行下去：我们发现，基础只有在规范模型和指标定义被工具（智能体在结构上被先路由到它们；下文会再讲）、被 CI（绕过它们的变更过不了审查）以及被强制要求（下游团队建在受治理层上，否则要解释为什么不）执行时，才能站得住。没有执行的治理，很快就会退回多个候选的问题。
  • 把产物放在一起：我们对不断变化的数据模型和业务逻辑的主要防线是共置。几乎所有数据代码（建模、语义层、参考文档、规范仪表盘定义）都住在同一个仓库里，并用 CI 检查保护跨层完整性。如果一次建模变更会弄坏下游仪表盘，或让已文档化的指标失效，CI 会标出来，修复和变更在同一个 PR 里发出。（我们会在下面的 Skills 一节回到具体机制。）
  • 把元数据当作一等产品：编码智能体表现好，部分是因为代码库是可读的：README、类型签名、docstring 等。你的仓库也可以同样可读，前提是列和表的描述、规范指标定义、粒度文档、合法取值范围、血缘、所有权和模型分层，都按和转换本身同样的严谨程度来维护。这不是新见解，但良好治理提供了帮助智能体选对数据集的关键上下文。

事实来源

如果说数据基础是数据仓库本身，事实来源就是智能体用来导航它的参考界面。这一层减少概念与实体的歧义，把相关方问题里的「周活跃用户」变成数据模型里一个具体、受治理的实体。大致按信任度从高到低：

  • 语义层：编译好的指标和维度定义。如果一个问题能干净地映射到已定义的指标，智能体调用一个函数，得到一个数字，和公司其他所有界面产出的是同一个数字。我们的智能体在结构上（靠 skill 指令）被要求先用语义层（见附录）。我们试过一个不管用的想法：让 LLM 从原始表和查询日志自动生成指标定义，来引导语义层。它产出了看起来说得通、却把我们正想消掉的歧义写进去的定义，在评测上相对更小、由人策展的一层是净负的。因此我们建议用 Claude 生成文档，但让人拥有定义。
  • 血缘与转换图：当语义层覆盖不了一个问题时，血缘和按引用次数做的表排序，让智能体能推理哪些上游模型喂养一个概念、哪些已废弃、哪些共享粒度。这把「我不知道这个指标」变成「我知道该从哪个受治理模型做聚合」。它也是我们在下面在线验证里呈现的新鲜度和出处信号的骨干。
  • 查询语料：来自仪表盘、notebook 和以往分析的历史 SQL。直觉上这应当很有价值：它是每一道已经被正确回答过的问题的记录。实际上，我们发现给智能体对几千条过往查询的原始检索权限，准确率变动不到一个百分点 （我们会在后面一节走一遍那次消融）。非结构化检索没法把新问题映射到正确先例。真正管用的，是把那份语料蒸馏成按领域组织的结构化参考文档，以及 skills 里描述的可复用分析模式。把查询历史当作策展的原材料，而不是智能体直接读的事实来源。
  • 业务上下文：大多数团队跳过的一层，也是我们低估最久的一层。不理解你业务的智能体会回答用户问出口的话，而不是他们想问的意思。它不会知道「Q2 launch」指的是某个具体产品，不会知道两个团队对同一个词定义不同，也不会知道这个问题是因为周四有董事会才被问出来。我们接入由索引文档、路线图、决策日志和组织架构组成的公司知识图谱，让智能体能解开这些环境指称，并提出更好的澄清问题。 

这四层共同的失败模式，和数据基础层是同一类：文档差或过期。Claude 在补上缺口时极其有用（起草列描述、从查询模式提出指标文档、在 CI 里标出未文档化的模型），但策展和所有权由人来管。 

接下来两节，我们讨论如何让这份所有权便宜到真的会发生。

Skills

如果说事实来源是智能体的陈述性知识（一个指标是什么意思），那 skill 就是它的程序性知识：按什么顺序咨询哪些来源、如何在含糊数据里导航、以及一份完成的分析长什么样。 

在 Claude Code 里，一个 skill 是智能体按需阅读的一文件夹 markdown。在 Anthropic，我们开发的 skills 带来了巨大增量。没有 skills，Claude 在我们的评测上回答分析问题的准确率超不过 21%。加上 skills 之后，总体稳定在 95% 以上，某些领域经常在 99% 左右。附录里有我们用来创建绝大多数 skills 的骨架。

一些最佳实践：

做成成对的 skills： 一份知识 skill 充当薄的顶层路由器，让额外的领域细节按需加载。它会说「先试语义层，但如果没有覆盖，这里有大约 30 份这个领域的参考文件，描述相关表、列、join 和陷阱。」这个路由器，实际上就是我们对检索失败的回答：与其让智能体在百万字段的仓库里搜索，它先把空间收窄到几十份策展过的文件，然后才写查询。runbook skill 编码资深分析师会走的流程：澄清问题、找来源（通过知识 skill）、跑查询，再把结果送进对抗性审查子智能体循环。它还打包了十几种可复用分析模式（留存曲线、比率分解、漏斗分析），这样常见请求不会每次都重做一遍。

写对参考文档：为 LLM 检索而写。我们的参考文档描述表（粒度、范围和排除项）、陷阱的机制（例如「排除已知的免费邮箱域名，但保留 anthropic.com 这类自定义域名」），以及显式的路由触发（例如「IF 问题关于实验提升……DO NOT 用来做原始事件计数」），而不写会过期的规定性菜谱。下面是我们用来写参考文档的骨架。

# [Domain] Tables

## Quick Reference
### Business Context — [what this domain means in plain words]
### Entity Grain — [what one row represents]
### Standard Hygiene Filter — [the filter every query in this domain applies]

## Dimensions
- [How the key dimensions are encoded, and how the same concept is named
  differently across tables]

## Key Tables
### [table_name]
- **Grain**: [...] · **Scope/exclusions**: [...]
- **Usage**: [when to use it, when NOT to, join keys, required filters]
[... one short section per governed table ...]

## Gotchas
- [The wrong-answer modes a senior analyst would warn you about]

## Best Practices / Common Query Patterns
- [Default choices, standard cuts, worked patterns where the exact query
  form is the hard part]

## Cross-References
- [Neighboring domain docs that own adjacent questions]

把 skill 维护当成一等公民：Skill 文档描述的是每天都在变的数据模型，没有主动维护，几周内就会错。我们看着离线准确率从上线时的约 95% 在一个月里漂到约 65%，然后才把它当成工程问题。这意味着把 skill 的 markdown 文件和转换模型放在同一个仓库，改模型的 PR 就是更新描述它的文档的同一个 PR。一个代码审查 hook 会标出任何没碰到 skill 文件的报表模型变更。现在大约 90% 的数据模型 PR 会在同一次 diff 里带上 skill 变更。我们也会随着模型变强、以往失败模式不再适用，定期修剪 skill 脚手架。

在所有界面上做成一致、无缝的体验：同一个 skill 必须在 Slack、IDE、仪表盘工具和独立智能体会话里，对问题给出同一个答案。我们的做法是确保只有一个规范来源（数据仓库），并且 skill 变更自动同步。合并时，skill 会同步到 plugin marketplace（给 IDE 用户）、同步到云存储 blob（给读单个文件的托管应用），并作为资源直接通过 MCP 提供。我们从一开始就按可移植来设计，避免硬编码仓库路径和界面专属命名空间。

验证

最后，验证是你用来发现三类失败模式里还有哪一类在往外漏的办法。 

离线评测

我们常见的一种模式是：数据团队搭了精致的分析环境，却没有任何流程去理解分析智能体的准确率。

补上这个缺口的一种办法是离线评测，也就是简单的问答对。你可以把它想成类似机器学习模型的离线测试：它不会告诉你在线智能体的表现，但能很好地告诉你会不会有关键缺口。

在 Anthropic，我们部署两类离线评测。基于仪表盘的评测由 Claude 自动生成（再由人核验），覆盖最常见的相关方问题。长尾评测是我们把业务上下文（路线图、表文档）喂给 Claude，让它在该领域其余部分生成说得通的问题。我们还持续收割相关方在线程里纠正智能体的每一次，那次纠正就是一条候选评测。

其他最佳实践包括：

  • 把 ground truth 钉住，让它漂不走：对着实时数据写的评测，底层数字一动就会过期。把每条评测钉在一个快照日期，对着稳定的事实表写，或者让评分器评判智能体的查询而不是它的数字。把套件接到 CI，这样碰到依赖的 PR 会重跑受影响的评测。
  • 像遥测一样存结果，而不是像测试日志：每一次运行都落入仓库表，带上 skill 版本、git SHA、模型 ID、每条断言的通过/失败、token 数和墙上时钟。「那次变更有没有帮助？」变成一条查询，你也有时间序列去抓住单次 CI 跑不出来的缓慢回退。
  • 按领域给上线设门槛：领域所有者不能向相关方宣布智能体，直到他们那一片评测集跨过某个阈值（我们最初用约 90%）。这迫使参考文档的修复发生在用户看见失败之前。
  • 做出数量合适的评测：你该有多少评测，取决于业务领域的复杂度和底层数据模型的复杂度。用离线准确率对在线准确率的预测有多好来校准：我们发现每个主题（例如「增长」）过了几十条之后收益递减，而且这个天花板会随每一代新模型下降。
  • 离线评测准确率应当接近 100%；每一个正确答案也应当打到你的语义层（如果你有的话）。再强调一次，这种准确率并不能告诉你系统不会给出错误答案，只是说明在评测覆盖得当的前提下，没有明显缺口。

消融方法

关于 skill 的每一个结构性决定（例如暴露哪些来源、一个子智能体值不值得它的延迟、要不要把两个 skills 合成一个）都是在离线评测集固定的前提下做出的。 

我们每次只改一个组件，比较通过率。每次运行只要一小时，却能替掉很多争论。方法论比任何单次结果都更重要：

  • 为零结果而设计。我们最有用的一次消融是负向的。我们给智能体直接 grep 全部仪表盘、转换和分析师 notebook SQL 的权限（几千个文件）。然后在记录里核验它每次回答前真的读了它们。准确率往哪个方向都没动过一个百分点。我们接着检查了显而易见的混淆因素：它答错的那些问题，答案是否其实就在语料里？大约 80% 的时候，是的。「答案在」能不能预测「现在答对了」？不能，翻转率是平的。信息在那儿，智能体看见了，仍然没用上。那一次实验告诉我们，瓶颈不是对以往工作的访问，而是结构（也就是把问题映射到正确实体）。这个洞察改写了几个月的路线图。
  • 按 PR 粒度做消融。每一次有意义的 skill 编辑，都在相关评测切片上跑一次前后对比，并把差值写进 PR 描述。这让「我改进了文档」保持诚实，也能抓住那种好心添加反而把事情弄糟的意外常见情况。
  • 留一份短清单，记下什么不管用。我们有两条：过了某个点还叠更多轮文档精炼（我们连续三次净负迭代：文档在变长，没有变更好）；以及为了降延迟，把对抗性审查者换成更便宜的模型（它丢掉了大部分准确率收益，速度也没有真正加快）。负向结果记下来很便宜，也能阻止下一个人重跑同一实验。

在线验证

最后一步是尽可能保证真实在线系统的表现准确。我们采取的一些步骤包括：

  • 对抗性审查：我们发现，用一个 Claude skill 去激烈挑战潜在最终答案上的所有底层假设，能在评测集里把准确率提高 6%，代价是多 32% 的 token 和高 72% 的延迟。
  • 出处页脚：每条回复都带一个页脚，写明它来自哪一层来源（语义层 › 策展参考 › 原始表）、底层数据有多新、以及谁拥有这个模型。它不会让答案更正确，但能帮消费者判断自己能信多少。「原始表，新鲜度未知」的页脚是转给上游之前先核验的信号，也是我们对沉默失败为数不多的缓解之一。
  • 数据质量检查：有可能智能体用对了字段、用对了方式，但数据本身是错的。加上基本的数据质量检查，确保被引用的字段是最新的、完整的、没有异常，通常是好的卫生习惯。
  • 被动监控：我们持续跟踪的两个生产信号是：经语义层解决的智能体查询占比，以及回复里使用纠正语言的占比（「那是错的表」「你漏了欺诈过滤」）。两者都喂进一块仪表盘，每周和离线通过率一起审。
  • 主动收割纠正：把环闭合的那一部分。一个定时智能体每隔几小时扫描相关方频道，寻找类似的纠正语言，起草对相关参考文档的一行修复，并开一个打给领域所有者的 PR。修复路径故意很无聊——改一个 markdown 文件、合并、到处自动同步——这样领域所有者不会在这件事上花太多时间。同样的纠正也会回灌进离线评测集。

这些都抓不全的失败模式，是沉默的那一种。答案是错的，但看起来说得通，并且被不加反对地用掉了。我们的缓解是出处页脚、任何给领导层的东西都要显式的人工签字，以及每个领域顶级 KPI 的常设评测，每天对照受祝福的仪表盘做健全性检查，尽管我们还没有稳健的解决方案。

开始做自助式分析

如果你从零开始，一小撮规范数据集、几十条离线评测，再加一个薄的知识 skill，就能吃下大部分收益；本文其余部分，是我们在这些建好之后才加上的。

我们也分享了许多最佳实践，并非每一条都适合每个数据团队。先和你的组织对齐几条会影响路径的原则，可以问：

  • 今天答对有多重要，相对未来答对？ AI 模型进步很快。我们常看到公司为当前模型的短板建大量基础设施，而这些短板一旦模型变好就不再成立。知道模型短在哪里，并等模型改进来补上缺口，开销显著更小，但可能不符合你公司的风险承受度。
  • 你预期业务复杂度会如何随时间变化？ 如果我们讨论的某些流程对你来说过重，例如你产出的数据不多、输出的消费者很少，或数据模型很可能保持简单，那就不必照搬。
  • 输出的目标受众有多技术？ 换个说法，如果你是在为能认出答案不对的数据科学家建这套分析系统，你对错误的容忍度，可能高于受众对底层数据模型毫无熟悉的情况。 
  • 为提高准确率，你愿意花多少？ 我们发现对抗性验证这类流程能显著提高准确率，但常常伴随更高的成本和延迟。
  • 你对访问控制和内部数据隐私的舒适度如何？ 智能体通常上下文越多越好用；但宽的数据访问会和大多数公司的治理姿态相冲突。这决定了你是在建一个智能体，还是许多范围收窄的智能体。

无论你走哪条路，我们最大的收益都来自分别对付三类失败模式：把歧义收成一个受治理的答案，让这个答案容易被发现，并在其中任一过期时标出来。
